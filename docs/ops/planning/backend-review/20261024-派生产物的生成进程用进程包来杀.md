# 派生产物的生成进程用进程包来杀

服务端工程审查 L8 的一部分（见[服务端工程审查](./20261024-服务端工程审查.md)）。

## 以前

文件包生成对照 PDF、Word、页预览、封面时，超时了自己 `libc::kill(-pid, SIGKILL)`（`side_by_side.rs` 的 `kill_process_tree`），
没用 `retainpdf-proc`（这个包就是为了把进程树管理收在一处）。非 unix 上退回 `child.kill()`，只杀直接子进程：
Windows 桌面版上 Word 导出起的 node、typst 这些孙进程会活下来。

（审查还提到 `preview.rs:352-359`，那两处在测试里，是测试自己检查、清理进程，不算。）

## 现在

- `retainpdf-proc` 加 `kill_std_child_process_tree`：给握着同步 `std::process::Child` 的调用方，马上杀，不给宽限。
  unix 按进程组 SIGKILL（要求 spawn 时自成一组，生成命令本来就 `process_group(0)`）；Windows 用和任务 worker 一样的
  `taskkill /T /F` 连孙进程一起杀；都不成再退回 `child.kill()`。
- 文件包的 `kill_process_tree` 改成调它。unix 上行为不变。

## 没做的

- Windows 上没有 Job Object：rust_api 自己被强杀时，它起的子进程不会跟着走（unix 上靠进程组和监督进程的退出检测）。
  要用 Windows API，另说。

## 测试

文件包 42 条照旧过，其中超时以后连孙进程一起杀掉的那几条（`side_by_side_tests`、`preview` 的卡死渲染）走的就是新函数；
进程包 14 条照旧过。本机没有 Windows，Windows 分支没跑过，只按现有的 `terminate_job_process_tree_windows` 照搬。
