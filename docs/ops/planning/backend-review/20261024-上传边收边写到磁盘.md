# 上传边收边写到磁盘

服务端工程审查 M5（见[服务端工程审查](./20261024-服务端工程审查.md)）。

## 以前

`POST /api/v1/uploads` 的 `read_multipart_field_limited` 把整个文件读成 `Vec`（按倍数扩容，峰值接近两倍文件大小），
处理函数再 `to_vec()` 复制一份交给上传服务；内存预算（`RUST_API_UPLOAD_BUFFER_MIB`，默认 512）在字节全收完以后才查。
三个 200 MiB 的上传同时来，瞬时内存能到 1 GB 以上，预算形同虚设。

## 现在

- 请求体边收边写到 `uploads/.incoming/<随机>.part`（1 MiB 写缓冲），同时算 sha256、数字节
  （`retainpdf-ingest` 的 `uploads/incoming.rs`）。收的时候只占一个缓冲区。
- 收完由 `UploadService::store_incoming_for` 把临时文件换名进 `uploads/<编号>/<文件名>`（同一块盘，不复制），
  指纹用收的时候算好的，和以前整份算的一样。
- 不是 `.pdf` 的文件名、磁盘已经到下限，开始收之前就拒，不用等几百 MB 收完。
- 大小上限在写的时候查（处理函数的上限和服务的上限取小的），超了 413，已经收的部分删掉。
- 每收 16 MiB 看一次磁盘剩余空间，到了下限 503 `insufficient_storage`，已经收的部分删掉。收完再查一次时只算还要写的
  那一份（修复或规范化后的副本），原样那一份已经在盘上了。
- 请求中途断开、校验没过，临时文件在析构时删；进程被杀留下的，`UploadService::new`（起服务时）删掉一小时以前的。
- 对外接口不变：返回、错误、状态码都和以前一样。

## 没变的

- 内存预算照旧按文件大小占：页数是 `lopdf::Document::load` 读出来的，它会把整份 PDF 读进内存再解析。要真正
  不随文件大小涨内存，得换成只读交叉引用表的页数统计，另说。
- `UploadService::store`/`store_for`（测试和内部调用传内存里的字节）照旧能用，和新路径共用后面的校验和落库。
- 别的 multipart 接口（字体、术语表导入、备份恢复……）没改，它们的上限小或者不是热路径。

## 测试

- `retainpdf-ingest` `uploads::incoming`：分块写进去的和整份算的 sha256 一样、文件内容一样，没换名走的析构时删；
  超过上限 413、半截文件删掉；收到 16 MiB 以内就查磁盘，查不过 503、半截文件删掉；起来时只删一小时以前的临时文件。
- rust_api `api_tests::uploads`：成功上传落盘的就是收到的字节、指纹和整份算的一样、`.incoming/` 里一个不剩；
  超限、修复工具不在、超内存预算这几条照旧，"上传目录里不留东西"现在也看 `.incoming/` 里面。
