# 边翻边看的流不占读请求的槽

2026-10-24。处理 [服务端工程审查](./20261024-服务端工程审查.md) 的 M8 里实际要紧的那一条。分支 `fix/live-stream-own-slots`，
叠在 `fix/shutdown-drain-timeout` 上。

## 问题

边翻边看的进度流（`GET /jobs/:id/progress/stream`）每个客户端每 750ms 查一次新提交的页，走的是 `run_job_query`：
`query_execution` 的有界执行器只有 2 个槽，任务列表、详情、事件这些普通读请求共用。开着几个边翻边看的页签，
普通读请求就排在轮询后面。

## 决定

- 进度流的轮询（开流时的第一次查询和之后每次）改走 `run_state_blocking`（阻塞线程池），不再占那 2 个槽。代价是
  同一个任务、同一个游标的多个页签不再合并成一次查询，单机下每 750ms 一条小查询，不成问题。
- **不做全局请求超时**（`TimeoutLayer`）：重翻一条要等模型、服务商校验最多 20 秒、书的元数据建议要读整份规范化文档，
  一刀切的超时会掐断正常请求；单机自用场景下处理函数挂住的情况也少。真遇到再按接口加。
- **任务到终态时不主动关流**：浏览器的 EventSource 被关会自动重连，服务器一关它就重连，变成每几秒一次的重连循环；
  要关得先和前端约定结束事件。停机时有 [停机等连接的上限](./20261024-停机等连接的上限和退出时停worker.md) 兜底。
- 没做：改成 runner 写完提交事件以后进程内通知、不再轮询（远端模式 runner 在 jobsd 里，还是要轮询兜底）。

## 测试

- `api_tests::live_translation::live_events_do_not_wait_for_the_shared_read_slots`：用两个一直不返回的查询占满 2 个槽，
  再开流，3 秒内拿到响应并收到已提交的页。改回走 `run_job_query` 时红（实测）。
