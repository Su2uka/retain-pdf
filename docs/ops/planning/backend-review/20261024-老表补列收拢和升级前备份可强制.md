# 老表补列收拢，升级前备份可以强制

M6 剩下的两件（前一件见[启动时的旧数据修正改成迁移](./20261024-启动时的旧数据修正改成迁移.md)）。审查原文见
[服务端工程审查](./20261024-服务端工程审查.md) M6。

## 老表补列

以前任务系统的四张老表（`jobs`、`events`、`glossaries`、`uploads`）后来加的列分两处补：`apply_schema` 在迁移阶梯之前补一部分，
`Db::init` 又把其中一部分再补一遍、外加 `runtime_json`、`failure_json`、术语表的四列、`uploads.content_hash`。
每一列都是"`PRAGMA table_info` 看一眼，没有就 `ALTER`"，不在事务里、不拿写锁。

问题：

- rust_api 和 jobsd 同时起来升级同一个老库，两边都看到缺列、都去 `ALTER`，后到的报 `duplicate column` 起不来。
  测试里四个进程（线程）同时升级，十次里次次都有一个起不来（实测）。
- 只在 `init` 里补的列，不调 `init`、只 `connect` 的进程（命令行的部分子命令）用不上。

现在：

- 收成一张表 `schema/mod.rs` 的 `LEGACY_COLUMNS`（只许往后加），`ensure_legacy_columns` 在 `apply_schema` 里、迁移阶梯之前补，
  `init` 不再补。
- 先不加锁看一遍，都在就直接回去（平常每次起来都是这样，几条 `PRAGMA table_info`）；缺了才拿 IMMEDIATE 写锁，
  锁里再看一遍再加，和编号迁移一样。

为什么不收进编号迁移（审查的建议）：早的几个迁移（v01 起）就要用其中的列（`jobs.document_id` 等），而编号迁移从库现在的
版本往后跑，比 v01 还老的库得先有这些列才跑得了 v01。新加的列照旧走编号迁移。

## 升级前备份可以强制

升级前的备份存不成，默认照旧记 `error`、照常升级（备份目录写不进去不该让程序起不来）。新配置
`RUST_API_DB_REQUIRE_UPGRADE_BACKUP`（`DbConfig.require_upgrade_backup`，默认关）打开以后，存不成就报错、不升级，
`Db` 连不上，服务起不来，错误里写明是这个配置挡的。取值写错照 M12 不启动。

## 没做的

- 迁移没有 down、没有校验和：靠升级前备份兜底，现在可以强制要有。
- 状态列存 JSON 字符串、CAS 比较两种写法（审查 M6 最后一条）：要动所有读写状态的 SQL，另说。

## 测试

- `retainpdf-db`：编号迁移以前的老库（四张表都缺后来加的列）`init` 以后每一列都在、迁移跑到最新，再起一次不用补
  （期望的列名写死在测试里，不照抄 `LEGACY_COLUMNS`，少补一列就红——拿掉 `runtime_json` 实测红）；
  四个进程同时升级同一个老库全都起得来，跑十轮（去掉写锁实测三次三次红）；升级前备份存不成时默认放行、要求备份时报错且
  错误里有配置名，存得成时要求备份也放行并真的存了一份。
