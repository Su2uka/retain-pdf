# 读进度输出出错与逐行落库

2026-10-24。处理 [服务端工程审查](./20261024-服务端工程审查.md) 的 M2、M1，两件都在 runner 读 worker stdout 的
`process_runner/io_support.rs` 和等待进程的 `execution.rs`。分支 `fix/runner-stdout-reader`，叠在
`fix/docker-placeholder-api-key` 上（本目录是那个分支建的）。

## M2：读取任务出错，worker 没人管

以前 `read_stdout` 循环里任何一个 `?`（起步拿 attempt、阶段观测或检查点和 worker 对不上、一次 `database is locked`、
一行不是 UTF-8）都让读取任务带着 `Err` 退出，而等待方 `wait_with_limits` 不知道：worker 继续跑（吞掉 BrokenPipe 的
Python 会把翻译做完、照花模型的钱），拖到它自己退出或总超时，收尾时 `drain_stdout` 才把错误抛出来，任务落失败——
worker 其实 exit 0、产物齐全也一样。之前的审计记在 `api-reorg/20261019-正确性与状态一致性审计明细/6-流水线约定.md` 问题 1。

决定：

- **出错就停 worker**：读取任务退出时带 `Err` 就置 `reader_failed`，`wait_with_limits` 返回新的 `ReaderFailed`，
  和强制删除（`RowGone`）一样终止进程树、回收，再由 `drain_stdout` 把那个错误带出去，任务落失败（检查点还在，可以续跑）。
- **哪些错误不该让读取任务退出**：
  - 不是 UTF-8 的字节：改成按字节读一行、替换字符解码（stderr 同样处理），不再报错。
  - 逐行的任务行落库（`cas_persist_job_with_resources`）：只是进度镜像，失败记日志、下一行再试，**连续 3 次**才当作出错。
  - 阶段观测、检查点、渲染产物这三类持久化行照旧出错即退出：它们是续跑和成功校验的依据，写丢了不能当没事。

## M1：每行 stdout 整行重写一次任务

以前每读一行就走一次 `cas_persist_job_with_resources`：读出旧行做 diff、重写全部列（含请求、命令、日志尾巴）、
逐个产物 `stat` 再删了重插 `job_artifact_entries`、一次 IMMEDIATE 事务加 fsync。一本书几千行日志时数据库和磁盘全耗在这上面。

决定：**节流，但不丢事件**。

- 每行算一个落库键：状态、阶段、阶段说明、进度、错误、失败、结果、产物。派生事件（`derive_events`）只看这些里的前几项，
  键变了就马上写，所以派生出来的事件和以前一条不少、顺序不变。
- 键没变的行（只多了一行日志、`updated_at`、`runtime` 跟着变）最快 500ms 写一次。进度页的轮询是 750ms 一次，日志尾巴最多晚半秒。
- **最后几行不能丢**（前端提的：书和任务的失败页拿 `log_tail` 兜底显示，最后几行往往就是报错原因）：
  - worker 自己非 0 退出：收尾用读取任务交回的内存里那份任务落终态，日志本来就是全的。
  - 读取任务出错、排空 stdout 超时被放弃：收尾从库里重读任务。所以读取任务退出前（读到结尾或出错）先补写没写的行；
    有没写的行时等下一行最多等到窗口结束，到点就写，worker 不出声（卡住、孙进程占着管道）也照样半秒内进库。
    等下一行可以被这个超时打断：读了一半的字节留在缓冲里，下次接着读。
- 强制删除、别人落了终态靠 CAS 写失败来发现，合并以后最多晚 500ms 发现，worker 照样会被停掉（原有测试照过）。
- 没做的：审查建议的"只更新几列的窄写"和"产物登记只在发布产物时重算"。节流以后纯日志行最多每秒两次整行写，
  先看效果；要再省再改数据库层。

## 测试

- `a_failing_stdout_reader_stops_the_worker_right_away`：worker 报一条 job_id 对不上的阶段观测，再假装干 12 秒；
  driver 5 秒内收尾、任务落失败且原因是 `job mismatch`、worker 被杀。去掉 `ReaderFailed` 分支时这个测试红（实测）。
- 同一个测试还钉住：出错前读到的 `boom: the real reason` 在失败任务的 `log_tail` 里（去掉退出前补写时红，实测）。
- `last_lines_before_a_failing_exit_reach_log_tail`：worker 打完最后一行马上 `exit 3`，任务落失败后 `log_tail` 有这一行。
- `a_quiet_worker_still_gets_its_last_line_persisted`：worker 打一行就睡 3 秒，1.5 秒内这一行进库（去掉到点就写时红，实测）。
- `non_utf8_stdout_does_not_fail_the_job`：一行坏字节，任务照样成功，日志里是替换字符。
- `lossy_lines_strip_line_endings_and_replace_bad_bytes`、`persist_gate_merges_log_only_lines_but_not_visible_changes`：
  行解码和节流判断。
- 原有的强制删除、取消、并发槽位等 runner 测试不变、照过。

前端不用改：接口和事件没变，日志尾巴最多晚半秒。
