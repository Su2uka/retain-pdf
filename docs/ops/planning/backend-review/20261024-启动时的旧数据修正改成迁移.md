# 启动时的旧数据修正改成迁移

> 2026-10-24，处理[服务端工程审查](./20261024-服务端工程审查.md)的 M6（一部分）和 M11 里数据库包绕过日志那一条。
> 分支 `fix/db-startup-cleanup`（接在 `fix/auth-key-baseline` 后面）。

## 做了什么

- **`cleanup_legacy_workflows` 改成迁移 v29**（`database/retainpdf-db/src/db/schema/migrations/v29_legacy_mineru_workflow.sql`）：
  2026 年早期 workflow 叫 `mineru`，后来改名 `book`。这段修正原来在 rust_api 每次启动时跑（`app/state.rs` 的 `build_state`），
  对 `events.payload_json` 做 `LIKE '%"workflow":"mineru"%'`，事件表大了以后是一次全表扫描。现在的代码写不出 `mineru`
  （`WorkflowKind` 没有这个值），所以改成升级时跑一次：三条 UPDATE 原样搬进迁移，`Db::cleanup_legacy_workflows` 和启动时的调用删掉。
  手动修旧库的脚本 `backend/api/scripts/cleanup_legacy_workflows.py` 没动。
- **数据库包的 `eprintln!` 换成 `tracing`**（桌面版和 Docker 里 stderr 不一定有人收）：
  - 升级前备份失败：`tracing::error!`，写明"没有回退副本就升级了"。升级照常往下走：备份目录写不进去不该让程序起不来。
  - 恢复备份后补设 WAL 失败：`warn`。
  - 书库启动回填（清掉没有上传的孤儿书 `info`；全文索引回填失败、上传路径坏了或读不了 `warn`）。

## 没做的

- `ensure_*_column` 收进编号迁移、`apply_schema` 里的 `CREATE TABLE IF NOT EXISTS` 收拢：动的是所有库的建表路径，
  要逐列核对每个历史版本的库升上来结果一样，单独做。
- 备份失败时（可配置地）拒绝升级：先让失败看得见；要不要拦，等有了真实的失败再定。
- 状态列存带引号的 JSON 字符串（`"queued"`）、比较时两种写法都认：改存储格式牵涉同步、备份和所有读写，不在这次。

## 测试

- `retainpdf-api` 的 `app::state::tests::upgrading_to_v29_rewrites_legacy_workflow_rows_once`（原来的 `build_state_cleans_legacy_workflow_rows`）：
  装成 v28 的库里放一行 `mineru` 任务和事件，启动后 `workflow`、`request_json`、事件都换成 `book`；已经是 v29 的库再启动，
  之后写进来的旧名原样留着（证明不再每次扫）。反向核对：v29 换成空语句，这条红。
- `retainpdf-db` 的迁移测试（版本连续、名字不重复、幂等）照常过。
