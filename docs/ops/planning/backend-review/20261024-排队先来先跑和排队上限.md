# 排队先来先跑和排队上限

服务端工程审查 M7（见[服务端工程审查](./20261024-服务端工程审查.md)）。

## 以前

`execution_queue.rs` 的 `wait_for_execution_slot`：每个排队的任务一个 driver，每 250ms（`RUST_API_QUEUE_POLL_INTERVAL_MS`）
读一次整行任务（`db.get_job`，含请求 JSON 的反序列化）、`try_acquire` 一次名额。

- 名额空出来时谁那一轮先醒谁拿到，先排的不一定先跑。测试里五个任务排队，开跑顺序次次被打乱（实测三次三次乱）。
- 交几百本书时，每秒几次整行读乘以排队数。
- 交多少都收，没有上限。

## 现在

- 一直挂在 `Semaphore::acquire_owned` 上（tokio 的信号量按等待先后放行），用 `select!` 每个轮询间隔醒一次看取消标记和状态；
  取消、删除、改成终态就丢掉这个等待（它从等待队列里出来，不占位置），等到名额的那一刻再看一次，刚被取消就交回名额。
- 看状态只读状态那一列（`Db::job_status`），不解码整行。任务行没了照旧报「job not found」。
- 新配置 `RUST_API_MAX_QUEUED_JOBS`（`JobRunnerConfig.max_queued_jobs`，默认 1000，`0` 不限），取值写错照 M12 不启动。
  排队（queued）的已经有这么多时，`submit_job`、`relaunch_in_place` 在磁盘检查之后、落库之前返回 429，
  `error.details.reason = "queue_full"`（新的 `AppError::too_many_requests_because`，信封和普通 429 一致、只多 `reason`）。
  在跑的不算。数的是库里的行，进程内和 jobsd 两种模式一样。
- 默认 1000：审查建议的 `max_running_jobs * 50`（默认 200）离"批量交 200 本书"太近；1000 正常用碰不到，只挡跑飞的脚本。
  两个请求同时数到差一个满会一起进去，多一两个不要紧。

## 没做的

- 排队的 driver 仍然每个轮询间隔读一次库（只读状态列）：取消有进程内标记，删除、改终态（另一进程、同步）要靠读库才知道。
  要彻底不轮询得把这几种都改成通知，另说。
- 审查说的取消、删除用 `select!` 打断：取消标记仍然是轮询间隔内生效（和以前一样）。

## 测试

- `retainpdf-runner` `lifecycle_tests::queued_jobs_start_in_the_order_they_were_queued`：占住唯一名额，五个任务错开 70ms 排队，
  放开以后开跑顺序和排队顺序一样（连跑五次都过）；退回旧的 `try_acquire` 轮询三次三次红。原有的排队期间取消、重复发射、
  取消后重跑等用例照旧过。
- rust_api `api_tests::queue_limit`：上限 2、排着 2 个、跑着 2 个时建任务 429 `queue_full`、没有新行；上限 3 时同样的库
  照样建得出来（在跑的不算）；去掉 `submit_job` 里的检查红（实测）。
- `retainpdf-api-base`：带原因的 429 和普通 429 逐字段一致、只多 `reason`。
