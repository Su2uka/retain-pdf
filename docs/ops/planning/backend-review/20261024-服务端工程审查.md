## 1. 总体评价

这是一个纪律性很强、但"为单机自用产品背了一套偏重的工程设施"的服务端。

**最大的优点**：正确性意识少见地好。任务状态用 CAS 加运行代次（`run_generation`）防旧 driver 覆盖新状态；子进程自成进程组、杀进程前核对 `<pid>@<启动指纹>`；超时分"总时长"和"无输出"两条；读 stdout 的收尾有上限，防孙进程占着管道；凭据库 0600、原子写、拒绝符号链接；500 的原因只进日志、对外只给 `error_id`；备份用 `VACUUM INTO`、去掉 WebDAV 密码、先 `integrity_check` 再换库；非测试代码里几乎没有 `unwrap`（我统计到的 214 处里，剔除夹在文件中间的测试模块后，生产路径上只剩正则常量 `expect`、互斥锁中毒 `expect` 这类）。前几轮审计提出的高优先级问题大多已经有对应修复和回归测试。

**最大的隐患有三类**：
1. **默认配置的安全边界**：Docker 模板提交了一个公开的占位 API key，后端只拒绝 `dev-local-key` 这一个字面量；而这把 key 在单机模式下能打开"在服务器上执行命令"的助手终端。一旦用户把 `HOST_BIND_ADDRESS` 改成 `0.0.0.0` 又没换 key，就是远程命令执行。
2. **异步运行时上的同步阻塞是常态**：全后端 `spawn_blocking` 只有 39 处，而 `async fn` 处理函数有 200 多个，runner 的热路径（每行 stdout 一次整行 SQLite 事务加磁盘 stat）也直接跑在 tokio 工作线程上；数据库每次操作新开连接。在单用户负载下大概率感觉不到，一旦有备份、同步、多任务排队叠在一起，会出现整个 API 一起变慢。
3. **资源生命周期没有闭环**：没有磁盘空间检查，也没有任务目录和派生缓存的回收；上传先全量读进内存再做准入；优雅停机会被 SSE 长连接卡住。

代码健康方面：最大的非测试文件也只有 ~1000 行，没有 `TODO` 堆积，死代码标注只有 10 处，文档基本跟得上。主要的坏味道是迁移留下的痕迹（链式 re-export、"data" 包杂物箱）和治理成本（1931 行的 Python 架构检查脚本、冻结的多用户代码仍占 ~5% 的代码量）。

## 2. 发现清单

### 高

**H1. 公开的占位 API key 加上"能执行命令"的助手终端，默认配置校验太窄**
- 角度：安全基线 / 默认配置
- 证据：
  - `backend/packages/retainpdf-core/src/config/auth.rs:43-48`：非回环地址监听时只拒绝 `api_keys` 里含 `"dev-local-key"`；调用点 `backend/packages/retainpdf-core/src/config.rs:279`。没有最小长度、没有占位词识别。
  - `ops/deployment/docker/delivery/docker/auth.local.json` 是提交进仓库的文件，里面的 key 是 29 字符的"请替换"类占位串（只确认了形态，没抄内容）；`docker/app.env:18` 容器内 `RUST_API_BIND_HOST=0.0.0.0`，所以走的是"非回环"分支，占位串能通过校验。
  - `backend/api/src/routes/ai_terminal.rs`：`/api/v1/ai/terminal` 单机模式下代理到助手终端，README 和路由注释都写明"在服务器上执行命令"；握手另外接受查询参数里的 key（`terminal_key_is_valid`）。
  - 缓解项：`docker-compose.yml` 默认 `HOST_BIND_ADDRESS=127.0.0.1`，README 183-184 行也有提醒。
- 场景：用户想让局域网别的机器访问，把 `HOST_BIND_ADDRESS` 改成 `0.0.0.0`，没读到"先换 key"那一步。仓库里公开的占位 key 就是万能钥匙，进来可以直接开 shell、读全部凭据（`GET /credentials/:ref`）、下载备份。web 容器的 nginx 还会对没带 key 的请求自动注入后端 key（`nginx.conf.template` 的 `$retainpdf_backend_api_key`），所以只要 40001 端口可达，连 key 都不用知道。
- 建议：非回环监听时校验 key 最小长度（如 24）并拒绝已知占位词和 `dev-local-key`；或首次启动时由 entrypoint 生成随机 key 写进卷里。顺带考虑单机模式下终端默认关闭、用环境变量显式打开。
- 之前审计：`20261022-设置与平台接口审计.md` 第三节 6 提过"CORS 加公开 key 的放大"，已用来源和主机校验处理（`config/origin_policy.rs`），但没有覆盖"占位 key 本身"和"Docker 暴露面"。

**H2. 同步 SQLite 和文件 IO 大面积跑在 tokio 工作线程上，数据库每次操作新开连接**
- 角度：异步与并发 / 数据库
- 证据：
  - `spawn_blocking` 全后端只有 39 处（`rg -n spawn_blocking`），其中 `backend/api/src/routes/` 下集中在 `library_data.rs`、`accounts.rs`、`glossaries.rs`、`collections.rs`、`credentials.rs`；没有任何包装的处理函数文件：`routes/jobs/actions.rs`（8 个 async fn）、`jobs/translations.rs`（7）、`public_document_operations.rs`（8）、`document_operations.rs`（5）、`library_extras.rs`（7）、`agent_calculations.rs`（6）、`providers.rs`（5）、`health.rs`。
  - 具体例子：`routes/jobs/lifecycle.rs:23` 的 `create_job` 同步调用 `create_submission`（读上传、写库、算路径、必要时 fsync）；`routes/jobs/translations.rs:20` 的 `list_translation_items` 在处理函数里直接 `read_to_string` 解析译文清单；`routes/health.rs` 的 `/ready` 每次 `db.ping()`（新开连接）。
  - runner 里更重：`retainpdf-runner/.../process_runner/io_support.rs:103` 读 stdout 的循环里直接调同步 `cas_persist_job_with_resources`；`execution_queue.rs:14-42` 每个排队任务每 250ms 调一次 `db.get_job`。
  - `database/retainpdf-db/src/db.rs:182`：`Db::connect()` 每次 `Connection::open`，还要先拿一把 `schema_ready` 互斥锁；没有连接池，也没设置 `PRAGMA synchronous`（WAL 下默认 FULL，每次提交一次 fsync）。
  - 已有的好做法：`retainpdf-jobs/src/query_execution.rs` 的有界阻塞执行器（2 个槽、128 个键、同键合并），说明团队清楚这个问题，只是只铺了一部分。
- 场景：磁盘写入慢的时候（机械盘、杀毒软件扫描、网络盘、同步或备份正在写），4 个并发任务的 stdout 回写加几个排队任务的轮询，就能占满 tokio 工作线程（默认等于核数）；这时 `/health`、下载、SSE 一起变慢。`busy_timeout` 默认 5 秒，被阻塞的线程最长一次占 5 秒。
- 建议：先用一个统一的 `run_blocking(state, |db, root| …)` 辅助函数包住 `routes/` 里所有直接碰库和文件的处理函数（`routes/common/credentials.rs` 已经有现成写法）；runner 里把逐行落库改成"独立的写线程加通道"。`Db` 内部考虑每线程缓存一条连接，或者至少设 `synchronous=NORMAL`。
- 之前审计：`20261022-设置与平台接口审计.md` 第一节 11（A6/B9/C6）、`20261019-书库读错和阻塞线程.md`。书库、凭据、术语表、字体已改；任务、译文、文档操作、服务商、健康检查这几块按当前代码仍未改。

### 中

**M1. 每行 stdout 触发一次"整行重写加产物重登记"，写放大明显**
- 角度：数据库 / 资源（待确认实际 stdout 行数）
- 证据：`io_support.rs:103-110` 每读一行 stdout 就调 `cas_persist_job_with_resources` → `backend/packages/retainpdf-data/src/job_events.rs:125-139`（先 `db.get_job` 读整行做 diff）→ `database/retainpdf-db/src/db/job_writes.rs:229-333`：序列化并重写 `request_json`、`command_json`、`log_tail_json`、`result_json` 等全部列，对每个产物 `stat`（`collect_job_artifact_entries`，`job_writes.rs:239`），`DELETE FROM job_artifact_entries` 后逐条重新 INSERT（`job_writes.rs:357`），再派生事件写 `events`。`request_json` 里带术语表（最多 200 条）和全部翻译参数。
- 场景：Python 管线每打印一行进度，就是一次读整行、一次 IMMEDIATE 写事务、N 次 stat、若干次 INSERT 加一次 fsync。一次整本翻译几千行日志时，数据库和磁盘被这条路径主导；它和 H2 叠加最糟。
- 建议：进度类行只更新 `stage / progress / updated_at / log_tail` 几列（加合并窗口，比如 ≥200ms 才落一次）；产物登记只在 `artifact_published` 行或阶段切换时重算。
- 之前审计：未记录。

**M2. stdout 读取任务出错，worker 没人管，成功的任务可能被判失败**
- 角度：异步与并发 / 子进程管理
- 证据：`io_support.rs:61-66`（起步 `acquire_pipeline_attempt?`）、`:79-110`（循环里的 `next_line()?`、`apply_durable_*?`、`cas_persist…?`）；`execution.rs:160-162, 180-182`（`drain_stdout` 把 `Err` 原样抛出）。
- 场景：一次 `database is locked`（5 秒超时）或一行非 UTF-8，读取任务带着 `Err` 退出；等待方还在等子进程，`last_output_at` 不再更新，如果任务开了无输出超时就被杀，没开就拖到总超时；就算 worker 其实 exit 0、产物齐全，`execute_process_job` 也返回 `Err`，任务落成失败。付费翻译白跑一次（有 checkpoint 所以能续，但要用户手动续）。
- 建议：读取任务内部只对"致命"错误退出；一般错误记日志继续读；退出时通知等待方立即终止进程树并标成可续跑的失败。
- 已记录于 `20261019-正确性与状态一致性审计明细/6-流水线约定.md` 问题 1，按当前代码仍存在。

**M3. 优雅停机会被 SSE 卡住，进程内模式和 jobsd 都不收 worker**
- 角度：可观测性与运维 / 子进程管理（待实测）
- 证据：
  - `backend/api/src/app/server.rs:125-132`：`axum::serve(...).with_graceful_shutdown(...)`，随后 `tokio::try_join!(full_server, simple_server)`，没有停机超时。
  - `routes/jobs/progress.rs:102` 的 `next_live_event` 是 `loop { … sleep(750ms) }`，只在后端查询失败时才结束，任务到终态也不关（SSE 不随终态结束，已记录于正确性审计 4#5）。
  - `backend/api/src/main.rs:35-41` 的注释说"收到信号后监督的子进程会被终止、不孤儿"，但进程内模式（Docker 默认，`Dockerfile.app` 没设 `RUST_API_JOBS_MODE`）下 runner 没有任何 shutdown 钩子（`rg shutdown` 在 `retainpdf-runner` 里无命中），worker 没有 `kill_on_drop`（`execution.rs:144` 注释）；`backend/jobs/src/main.rs:262-299` 的 jobsd 也不处理 SIGTERM，只靠 `wait_for_supervisor_exit` 和下次启动对账。
- 场景：页面开着"边翻边看"时 `docker stop`，axum 一直等那条 SSE，10 秒后被 SIGKILL，监督的 AI 服务和 jobsd 没机会走正常回收路径；worker 要靠下次启动的 `reconcile_stale_running_jobs` 才被杀，重启之前它们还在继续花钱写磁盘。
- 建议：停机信号后给 axum 一个有限等待（如 10 秒）再 `abort`；SSE 流监听同一个关闭信号；进程内模式在停机时对登记的 worker 发 SIGTERM（有 checkpoint，可续）。

**M4. 没有磁盘空间保护，也没有任务目录和派生缓存的回收**
- 角度：资源与限制
- 证据：
  - 全后端只有 CLI 的 `backend/cli/src/cmd/doctor.rs:29` 检查磁盘剩余；上传、建任务、`/ready`（`retainpdf-platform/src/health_api.rs:98`）都不看。
  - 回收只有两样：事件按 30 天、孤儿上传按 48 小时（`backend/api/src/app/cleanup.rs:101-130`）。任务目录（`data/jobs/*`）、字体缓存、Typst 包缓存、派生产物（Word、并排、页预览）只在用户删任务时才清；失败任务的中间产物也没有期限。
  - 每个上传多存一份、同一 PDF 重复上传多存一份（`20261019-书库接口审计.md` 已知项）。
  - `run_cleanup_once` 自己在 async 循环里同步跑（`cleanup.rs` 的 `spawn_periodic_cleanup_with_interval`），删上传目录是同步 `remove_dir_all`。
- 场景：磁盘写满以后 SQLite 提交失败，runner 读 stdout 报错（M2），任务批量失败，且没有任何预警。
- 建议：`/ready` 加"数据目录可写、剩余空间 > 阈值"；上传和建任务在剩余空间不足时直接 507/503；加一项可配置的"终态任务目录保留天数"（默认关闭，只提示占用）。

**M5. 上传先整份读进内存，再做内存准入；还多拷一份**
- 角度：资源与限制
- 证据：`backend/api/src/routes/uploads.rs:37-39`：`read_multipart_field_limited` 把整个文件读成 `Vec`，再 `data.to_vec()` 复制一份；准入控制 `reserve_buffer` 在 `retainpdf-ingest/src/uploads/service.rs:87`，已经在字节读完之后。默认上限 512 MiB（Docker 示例配置 200 MiB）；`unlimited_body` 关掉了 axum 的体积限制，只靠字段读取时自己计数。
- 场景：3 个并发的 200 MiB 上传：每个 `Vec` 增长时容量翻倍（峰值接近 2×）再加一次 `to_vec()`，瞬时内存可达 ~1.2 GB × 3，`buffer_mib=512` 的预算形同虚设。
- 建议：边读边写到临时文件，PDF 的 `lopdf` 解析读文件；至少去掉 `to_vec()`（`Bytes` 直接传）。
- 已记录于 `20261022-设置与平台接口审计明细/C-备份同步上传与内部.md` C10，按当前代码仍存在。

**M6. 数据库迁移双轨，启动时有每次都跑的全表扫描**
- 角度：数据库
- 证据：
  - 三套机制并存：`db.rs` 的 `apply_schema` 里一大段 `CREATE TABLE IF NOT EXISTS`；`schema/mod.rs:69` 的 `ensure_table_column`（先 `PRAGMA table_info` 再 `ALTER TABLE ADD COLUMN`，不在事务里、没有写锁）；以及 28 个编号迁移（`schema/migrations/v01…v28`，有 IMMEDIATE 事务防跨进程竞争）。`Db::init`（`db.rs` 里）把 `apply_schema` 已经加过的列再 `ensure_*` 一遍。
  - `db.rs:366` 的 `cleanup_legacy_workflows` 在每次启动（`app/state.rs:45`，jobsd 也会走 `init`）都对 `events.payload_json` 做 `UPDATE … WHERE payload_json LIKE '%"workflow":"mineru"%'`，是全表扫描；这是 2026 年早期一次性数据修正，却一直留在启动路径。
  - 迁移没有 down、没有校验和；保护靠 `backup_before_upgrade`，而它失败只 `eprintln!`（`database/retainpdf-db/src/db/backup.rs:210`），迁移照常往下走。
  - 状态列存的是 JSON 字符串（`"queued"` 带引号），比较处写成 `current == quoted || current == *s`（`job_writes.rs` 的 CAS），易错。
- 场景：事件表按 30 天保留，量大时每次启动多扫几十万行；升级时备份失败没有任何人知道（stderr 在桌面版里看不到），之后迁移出错就没有回退点。
- 建议：把 `cleanup_legacy_workflows` 做成一个编号迁移后删掉启动调用；`ensure_*_column` 全部收进编号迁移；`backup_before_upgrade` 失败时用 `tracing::error!` 并（可配置）拒绝继续升级。

**M7. 排队任务无上限、轮询、不保证先进先出**
- 角度：异步与并发 / 背压
- 证据：`execution_queue.rs:14-42`：每个排队任务一个 tokio 任务，每 250ms（`config/job_runner.rs:48`）`db.get_job` + `try_acquire_owned`；`max_running_jobs` 默认 4；提交处没有"排队任务数上限"（`submit.rs` 的 `submit_job` 不看队列长度）。`try_acquire` 轮询不是公平锁，先排队的不一定先跑。
- 场景：批量提交 200 本书：200 个 driver 各自每秒 4 次整行读（含 `request_json` 反序列化）；先排的任务可能被后排的抢到名额。
- 建议：用 `tokio::sync::Semaphore::acquire_owned().await`（公平 FIFO），取消和删除用 `select!` 打断；队列长度设上限（如 `max_running_jobs * 50`），超出返回 429。

**M8. 没有全局请求超时、并发限制，SSE 和普通读共用同一个 2 槽执行器**
- 角度：资源与限制 / 背压
- 证据：全局没有 `TimeoutLayer`、`ConcurrencyLimitLayer`（`rg` 只在测试里命中 `DefaultBodyLimit`）；`app/router.rs` 的 `build_app` 层只有路由统计、主机校验、CORS、Trace。`next_live_event`（`progress.rs:102`）每个 SSE 客户端每 750ms 通过 `run_job_query` 占用 `query_execution` 的 2 个槽之一（`query_execution.rs` 的 `Default` 是 `with_limits(2, 128)`）。
- 场景：开了几个"边翻边看"页签，再点开任务列表，普通读请求排在 SSE 轮询后面等槽；慢客户端上传或读取体不设期限，占住 socket 和已分配缓冲。
- 建议：SSE 轮询改成订阅进程内通知（runner 写完事件后 `tokio::sync::watch`/`broadcast` 唤醒），不再打库；普通读和 SSE 分开槽；至少给 JSON 路由套 `TimeoutLayer`（上传、下载、SSE 除外）。

**M9. 本地回环 HTTP 客户端没有超时，也不绕过系统代理**
- 角度：异步与并发 / 超时（待确认）
- 证据：`retainpdf-jobs/src/runtime_gateway.rs:51` 的 `JobsClient::new` 用 `reqwest::Client::new()`（没有连接和请求超时）；`retainpdf-ai/src/gateway.rs:30` 的 `AiGateway` 只设了 `connect_timeout`，也没有 `.no_proxy()`。对照：`paddle/client.rs:378`、`provider_probe/ocr.rs:87`、`model_executor/mod.rs:262`、`paddle_markdown.rs:422` 都显式 `.no_proxy()`。
- 场景：用户机器设置了 `HTTP_PROXY/ALL_PROXY`（国内常见）而 `NO_PROXY` 没包含 `127.0.0.1` 时，reqwest 默认会把对回环 jobsd 和 AI 服务的请求也发给代理；jobsd 卡住时，取消、强删、发射请求会无限等待，处理函数也跟着挂住。
- 建议：回环客户端统一用一个带 `.no_proxy()` 和 5～10 秒超时的构造函数。

**M10. 同步（WebDAV）收进来的行没有逐列校验（待确认）**
- 角度：安全基线（信任边界）
- 证据：
  - `database/retainpdf-db/src/db/sync.rs:86-107`：`job` 实体同步整张 `jobs` 行（含 `command_json`、`request_json`）、`artifacts`、`job_artifact_entries`、`uploads.stored_path`；`retainpdf-data/src/sync/engine.rs:269-285` 只把 `pid` 置空、数据目录前缀做 token 替换，`is_valid_key`（`engine.rs:158-165`）只校验实体键。
  - `retainpdf-core/src/storage_paths/path_ops.rs:81`：`resolve_data_path` 遇到绝对路径原样返回，不做"必须在数据目录下"的检查（写入方向的 `to_relative_data_path` 会拒绝，读取方向不会）。
- 场景：WebDAV 是第三方或共享账号时，对端写进来的一条终态任务，其产物路径列可以指向任意绝对路径，下载接口就会把本机文件发出去。runner 重建阶段命令（`build_worker_stage_command`、`process_contract.rs` 的 `WorkerContract::from_command`）降低了 `command_json` 被直接执行的风险，我没找到直接路径，所以只标待确认。
- 建议：同步应用实体时对路径列做白名单（必须是 `DATA_ROOT` token 或相对路径，不含 `..`）；`resolve_data_path` 读取方向也要求结果在数据目录下。

**M11. 观测性偏弱：没有请求编号、访问日志、指标；数据库包绕过日志**
- 角度：可观测性与运维
- 证据：
  - `rg request_id` 只在模型执行器的上游请求编号里命中，HTTP 层没有请求编号；`TraceLayer::new_for_http()`（`router.rs`）默认在 DEBUG 才出请求日志，而默认过滤是 `info`（`main.rs:19-25`）→ 默认没有访问日志；没有 metrics（`Cargo.toml` 无 prometheus 一类依赖）。
  - 全 Rust 代码 ~100k 行（不含测试）只有约 180 处 `tracing::` 调用；日志是纯文本，没有按任务编号的统一 span。
  - 数据库包明明依赖了 `tracing`，却在关键处用 `eprintln!`：升级前备份失败（`backup.rs:210`）、恢复后的警告（`backup.rs:415`）、库启动回填（`documents/backfill.rs:56,78`）。桌面版和 Docker 里这些不一定被收集。
  - `/ready` 只看 DB 和被监督的子服务（`health_api.rs:98-150`），不看磁盘、数据目录可写、Python 管线可用。
- 场景：用户反馈"某个请求慢/失败"，没有办法把客户端、nginx 日志和后端日志对起来；备份失败静默。
- 建议：加 `tower_http::request_id` 并在 `TraceLayer` 的 span 里带上；把 `eprintln!` 全换成 `tracing`；给 runner 的日志统一带 `job_id` 字段；`/ready` 加磁盘和管线自检。

**M12. 环境变量解析遇到非法值静默回退默认值**
- 角度：配置管理
- 证据：`retainpdf-core/src/config/env_vars.rs:30`（`env_u16`）、`:46`（`env_bool`）等：`RUST_API_PORT=abc` 回到 41000，`RUST_API_UPLOAD_MAX_BYTES=200MB` 回到 0（再取 512 MiB 默认），`env_bool` 里任何不认识的值都是 `false`；`app/cleanup.rs` 的 `env_u64_allow_zero` 也一样。另外有 124 个不同的 `RUST_API_*`/`RETAIN_*` 变量名，部分绕过配置结构直接读（`jobs/lifecycle/creation/submit.rs` 读 `RETAIN_MODEL_EXECUTOR_ENABLED`，`app/state.rs`、`runner/.../startup.rs` 读 `RETAIN_MODEL_EXECUTOR_URL`，`dev_defaults.rs` 读 `RETAIN_TEST_*`）。
- 场景：用户把上限写成带单位的值，服务正常启动但限制悄悄变成别的值；拼错的布尔开关被当作关闭。
- 建议：启动时对"设置了但解析失败"的变量直接报错（`from_env` 已经返回 `Result`），再把散落的 `std::env::var` 收进 `AppConfig`。

**M13. 认证基线：单把静态 key，没有失败节流**
- 角度：安全基线
- 证据：`backend/api/src/auth.rs:15-23` 用 `HashSet::contains` 比较 key（非常量时间）；没有失败次数限制；jobsd 的 `authorized`（`backend/jobs/src/main.rs:73-81`）在 key 集合为空时返回 `true`（配置加载保证非空，所以现在不可达，但是 fail-open 写法）；终端握手接受查询参数里的 key（`ai_terminal.rs`），开 `RUST_LOG=debug` 时 `TraceLayer` 的 span 会把 URI（含 key）写进日志。
- 场景：和 H1 同一个暴露面：局域网内可以无限次试 key。
- 建议：对 key 校验失败做简单的按来源 IP 节流；jobsd 空集合改为拒绝；终端 key 改成"先用 key 换一次性短期票据"。

### 低

**L1. 输入校验没有上界**
`retainpdf-jobs/src/lifecycle/validation.rs:248-300`：`translation.workers`、`render.compile_workers`、`runtime.timeout_seconds` 只检查"非负/为正"，没有上限；请求能写 `workers=100000` 传给 Python 线程池和上游模型。单机自用影响小，对外开放时是放大器。

**L2. 依赖卫生**
- `backend/api/Cargo.toml` 里有 8 个在 `src/` 和 `tests/` 里找不到引用的依赖：`thiserror`、`once_cell`、`mime_guess`、`walkdir`、`hmac`、`getrandom`、`argon2`、`serde_urlencoded`（拆包后留下的；待用 `cargo machete`/`udeps` 确认）。
- 重复版本：`tower-http` 0.5（`api/Cargo.toml:33`）与 0.6（经 `reqwest`），`tokio-tungstenite` 0.21（`api/Cargo.toml:57`，终端代理手工转换帧类型）与 0.24（经 `axum` 的 `ws`）。
- 各包各自写版本，没有 `[workspace.dependencies]`；`tokio` 到处 `features=["full"]`；根 `Cargo.toml` 只有 `[profile.dev.package."*"]`，没有 `[profile.release]`（LTO/codegen-units/strip），Docker arm64 构建在 QEMU 下要近一小时（`build-docker-images.yml` 注释）。`target/` 现在 28 GB。
- 传递依赖共 314 个，规模不算大，`cargo tree -d` 的重复项主要是 digest/rand/windows-sys 这类生态重复，不必处理。

**L3. CI 缺少 Rust 静态检查和依赖审计**
`.github/workflows/tests.yml` 的 Rust 部分只有 `cargo test --locked --workspace` 和架构脚本；没有 `clippy`、`cargo audit`/`cargo deny`；工具链用浮动的 `dtolnay/rust-toolchain@stable`（`tests.yml:51` 等多处），新版 stable 发布当天可能让主干变红；第三方 action 多数按 tag 引用，只有 `setup-uv` 按 SHA 固定。不跑 `rustfmt` 是仓库既定约定，我不当问题。

**L4. 测试易碎的迹象**
1675 个测试，其中测试里 `sleep(` 57 处、`#[ignore]` 5 处、`set_var/remove_var` 20 处（`config/env_vars.rs` 的全局互斥锁，以及 `config/auth.rs` 的"子进程隔离"绕法）；最近一周就有三次修时序类测试的提交（`fix/preview-hung-render-test-timing`、`fix/proc-identity-test-tick`、`model_executor` 并行超时放宽，见 `CLAUDE.md` 的"本地环境的坑"）；pipeline 测试会污染仓库 `data/`。薄弱处：没有对"H2/M1 描述的热路径"的负载或并发测试；`backend/api/tests/` 下只有一个集成测试文件。

**L5. 模块边界的迁移痕迹**
- `retainpdf-runner/src/lib.rs`、`retainpdf-data/src/lib.rs` 用链式 `pub use retainpdf_core::{config, models, …}`，注释写明目的是"搬入文件中的 `crate::models` 路径原样解析"；调用方分不清一个类型到底属于哪个包。
- `retainpdf-data` 同时装着数据库再导出、WebDAV 同步引擎、OCR 厂商客户端（MinerU/Paddle）、worker 命令、凭据文件读取，是个"杂物箱"；`retainpdf-jobs` 的目录结构刻意和 `routes/jobs/` 的 HTTP 九类同名（`CLAUDE.md` 要求三处同名），业务层的组织被传输层的分类牵着走。
- `database/retainpdf-db/src/db/job_writes.rs` 里整段 `INSERT … ON CONFLICT` 在 `persist_prepared_job` 和 `cas_save_job` 各写了一份（约 60 行重复）。
- 其他：`retainpdf-runner/.../paddle_markdown.rs:197-274`、`retainpdf-jobs/src/reader/markdown.rs:108-110` 每次调用都 `Regex::new`；`retainpdf-data/src/sync/webdav.rs:196-444` 用 `lock().expect("… poisoned")`，一次 panic 会让整个同步循环永久不可用；`AppError` 文件 893 行，有 `unreachable!("handled above")` 的分支。

**L6. 开发期代码和统计代码留在生产路径上**
- `retainpdf-jobs/src/lifecycle/creation/dev_defaults.rs:64`：生产二进制也会读 `RETAIN_TEST_TRANSLATION_API_KEY` 等变量，在请求没带凭据时补进去；桌面和部署环境没有这些变量时是空操作，但属于"测试开关在生产里"。
- `backend/api/src/app/route_usage.rs` 的 `record` 中间件对每个请求拿一把全局互斥锁计数（用来"删端点之前先量"）；接口清理收尾后应该下线。

**L7. 治理和维护成本**
`backend/api/scripts/check_architecture.py` 1931 行加测试 1049 行，用正则和冻结名单约束 Rust 代码；10 月以来 1129 次提交（日均约 47）；冻结的多用户代码（`retainpdf-accounts`、账号/邀请/页额度/管理员路由和表）约 5.3k 行仍参与编译和测试；接口文档分在 `docs/api/`、`docs/core/api/`、`backend/api/docs/api-spec/`、`backend/api/*.md` 四处（`backend/api` 根目录就有 ~4000 行 md），漂移风险高。

**L8. 进程管理的重复实现；Windows 缺进程组**
`retainpdf-files/src/derived_artifacts/side_by_side.rs:217`、`preview.rs:352-359` 各自直接 `libc::kill`，没有复用 `retainpdf-proc`（该包的存在理由就是集中进程树管理）；`retainpdf-proc/src/lib.rs` 的 `configure_child_process` 在 Windows 下是空函数，靠 `taskkill`，桌面版 Windows 上没有 Job Object，API 被强杀时孙进程可能残留。

**L9. 密钥落盘和备份范围**
凭据库是明文 JSON（0600 + 拒绝符号链接，`retainpdf-data/src/credentials.rs`），Windows 上 `#[cfg(unix)]` 的权限检查不生效；DB 备份只含 SQLite，不含 `secrets/credentials.json`、上传、任务产物和 `documents/` 目录，恢复数据库后文件和库可能对不上（需要在设置页和文档里说清楚"备份 ≠ 全量备份"）。

## 3. 做得好的地方

1. **子进程生命周期管理完整**：`retainpdf-proc/src/lib.rs` 的 `terminate_child_process_tree`（自成进程组、SIGTERM→宽限→SIGKILL、握着 `Child` 时 `wait()` 回收僵尸、`refuse_non_worker_pid` 拒绝 `pid<=1`）；`retainpdf-runner/.../process_runner/execution.rs` 里"总时长/无输出"两条超时、stdout 收尾 30 秒上限、行被删时主动终止 worker（`RowGone`）；`startup.rs` 先记进程身份再写 pid；`worker_identity.rs`、`jobs/src/main.rs:127-157` 杀进程前核对身份。
2. **状态一致性设计**：`cas_save_job`（`job_writes.rs:229`）用 `BEGIN IMMEDIATE`、"行不存在绝不 INSERT"、运行代次比较；`run_generation` 贯穿 `submit.rs`；`RuntimeOwnerLock` 防止两个运行时同时对账；`driverless_sweep.rs` 运行期自愈；这些都有针对性的回归测试。
3. **错误信息对外收敛**：`retainpdf-api-base/src/error.rs:589-613` 的 500 只回 `error_id`，原因链进日志；上传修复子进程的 stderr 不外泄（`uploads/pdf.rs`）。
4. **有界阻塞执行器**：`retainpdf-jobs/src/query_execution.rs`——固定槽位、同键请求合并、不留历史结果缓存、调用方断开后槽位不泄漏；是 H2 的正确样板。
5. **备份与凭据的安全细节**：`backup.rs`（`VACUUM INTO` 一致快照、0600 临时文件、去掉 WebDAV 密码并 `secure_delete`、`integrity_check`、拒绝来自更新版本的备份）；`credentials.rs` 的 0600/符号链接/大小三重检查；`write_private` 写运行时记录。
6. **安全默认值**：默认监听 `127.0.0.1`（`config/server.rs`）；单机来源和主机校验防 DNS rebinding（`config/origin_policy.rs`、`auth.rs:reject_foreign_host`）；非回环不允许 `dev-local-key`；终端握手查 Origin；模型执行器只接受回环 HTTP 加一次性 capability（`worker_process.rs:prepare_model_worker_binding`）；Docker 应用容器以非 root 用户运行（`Dockerfile.app:331`）。

## 4. 建议的优先顺序（只做 5 件事）

1. **H1：非回环监听时强校验 API key（长度加占位词），并让 Docker 首次启动自动生成随机 key**。改动最小、收益最大：直接关掉"改一个端口绑定就变成远程执行"的路径，且不影响现有用户。
2. **M2 加 M1：修好 stdout 读取任务的错误处理，同时把逐行整行落库改成"进度只更新少数列、带合并窗口"**。这是长任务（付费翻译）最核心的热路径，既影响正确性（M2）也影响整机响应（M1），二者改的是同一块代码。
3. **H2：给 `routes/` 里剩下的直接碰库和文件的处理函数统一套 `run_blocking`，runner 里的写库搬到独立线程**。先从任务创建、译文、文档操作、健康检查四处下手，样板已经有了。
4. **M4：加磁盘空间自检（`/ready`、上传和建任务前）和终态任务目录的可配置保留期**。磁盘写满是单机产品最常见的"莫名其妙全挂"，且现在没有任何预警。
5. **M3 加 M8：给停机加超时、SSE 改成订阅通知而不是打库轮询、JSON 路由套请求超时**。让升级重启和 `docker stop` 可预期，同时去掉 SSE 对 2 槽执行器的占用。
