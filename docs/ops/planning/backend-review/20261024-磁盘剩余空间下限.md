# 磁盘剩余空间下限

2026-10-24。处理 [服务端工程审查](./20261024-服务端工程审查.md) 的 M4 的一半。分支 `fix/disk-space-guard`。

## 问题

全后端只有 CLI 的 `doctor` 看磁盘剩余空间。磁盘写满以后 SQLite 提交失败、worker 写不出产物，任务成批失败，
事先没有任何预警；任务目录、派生缓存也只在用户删任务时才清。

## 决定

- **下限**：`RUST_API_MIN_FREE_DISK_MB`（默认 `1024`，`0` 关掉检查），进 `AppConfig.min_free_disk_bytes`。
  剩余空间用 `statvfs` 的 `f_bavail × f_frsize`（普通用户能用的那部分）；路径还不存在就看最近的已存在的上级目录；
  拿不到（Windows、调用失败）一律放行——查不出来不该挡住正常使用。代码在底座包 `retainpdf-api-base` 的 `disk_space`。
- **拒绝新活，不碰在跑的**：低于下限时 503 + `error.details.reason = "insufficient_storage"`（新加
  `AppError::service_unavailable_because`，信封和普通 503 一样，只多 `reason`），同时记一条警告日志：
  - 上传：处理函数读请求体之前先按下限查一次（免得收完几百 MB 才说放不下），上传服务收完以后按「下限 + 两倍文件大小」
    再查一次（原文落两份）。
  - 建任务：`submit_job` 在建任务目录、落库之前查，所有新建任务的入口都经过它。
  - 原地重跑：`relaunch_in_place` 在挪旧 PDF、落库之前查（被拒时什么都不动，这条规矩不变）。
  - 已经在跑的任务不查：中途停掉比写满更糟，且它们已经占了位置。
- **`/health` 报出来**：`data.disk = { free_bytes, min_free_bytes, low }`。`/ready` 不跟着变：web 容器等后端就绪才启动，
  磁盘满了更要能打开页面删任务腾空间。
- 没用定期清理任务来报警：它 6 小时才跑一次，太粗；每次拒绝时记日志更直接。

## 没做的（M4 另一半）

- 终态任务目录、派生产物（Word、并排、页预览）的自动回收。删用户的东西风险大，要先定保留策略（默认关、按天数、
  只删可重建的派生产物……），单独做。
- 同一份 PDF 重复上传多存一份（书库审计的已知项）。

## 测试

- 底座包：路径不存在时看上级目录；下限 0 不查、1 字节总够、`u64::MAX` 一定不够，503 带 `insufficient_storage`；
  503 带原因的信封和普通 503 逐字段一致、只多 `reason`。
- rust_api `api_tests::disk_space`：下限设成 `u64::MAX` 时上传 503 且上传目录是空的；先传好 PDF 再把下限调高，
  建任务 503 且没有任务行；`/health` 的 `disk` 报 `low: true`、`/ready` 照旧 200；下限 0 时 `low: false`。
  去掉建任务和上传里的检查时前两条红（实测）。
- 测试用的配置下限是 0（测试机的磁盘空间不归测试管），要测的测试自己设。
