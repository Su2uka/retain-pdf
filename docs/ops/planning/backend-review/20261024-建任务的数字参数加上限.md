# 建任务的数字参数加上限

服务端工程审查 L1（见[服务端工程审查](./20261024-服务端工程审查.md)）。

## 以前

`retainpdf-jobs/src/lifecycle/validation.rs` 只查下限（非负、为正），请求能写 `translation.workers=100000`，一路传给 Python 的线程池和上游模型；
`timeout_seconds` 写成几十年也收。单机自用影响小，对外开放时是放大器。

## 现在

超过上限 400，`message` 是 `<字段> must be at most <上限>`；下限不变。

| 字段 | 上限 | 依据 |
|---|---|---|
| `translation.workers` | 256 | 内置服务商的并发最多 100（`retainpdf-config` 的 `providers.rs`），前端按服务商的上限（没写是 100）拦 |
| `translation.batch_size`、`translation.classify_batch_size` | 1000 | 一批几十条是常态 |
| `render.compile_workers` | 64 | `0` 是自动 |
| `render.pdf_compress_dpi` | 1200 | `0` 是不压 |
| `runtime.timeout_seconds`、`runtime.no_output_timeout_seconds` | 604800（一周） | 默认 1800 秒，整本书几小时 |

翻译的几项在 `validate_translation_modes`，渲染的在 `validate_render_options`，超时在所有建任务路径共用的 `validate_runtime_limits`。
多用户模式的平台并发上限（`translation_max_workers`）照旧在校验之前把并发压下来。

## 没做的

- 契约（`contracts/`）的 JSON Schema 里没加 `maximum`：前端不会发这么大的值，后端校验是兜底。
- 其他数字参数（页码范围、术语表条目数……）各有自己的语义检查，这次没动。

## 测试

`retainpdf-jobs` `lifecycle::validation`：默认值三个校验都过；七个字段刚好到上限放行、多一就 400 且报出字段名和上限。
