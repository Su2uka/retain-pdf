# 请求编号和访问日志

M11 剩下的（前面做过的：数据库包的 `eprintln!` 换成 `tracing`，见[启动时的旧数据修正改成迁移](./20261024-启动时的旧数据修正改成迁移.md)；
请求日志不记查询串，见 [key 比较和请求日志](./20261024-key比较和请求日志.md)）。审查原文见[服务端工程审查](./20261024-服务端工程审查.md) M11。

## 以前

- HTTP 层没有请求编号，客户端、nginx 和后端的日志对不起来。
- `TraceLayer` 的请求 span 是 debug 级，默认过滤是 info，请求里打的日志不带是哪个请求；默认没有访问日志。
- runner 的日志靠消息里拼 `job {id}`，没有统一的字段。

## 现在（`backend/api/src/app/request_log.rs`）

- 每个回应都带 `X-Request-ID`。请求带了像样的（1～64 个字母、数字或 `-_.:`）就沿用，否则生成 16 位十六进制。
  编号中间件在 `TraceLayer` 外面，span 建出来时编号已经写进请求头。两个端口的应用都有。单机模式的 CORS 本来就
  暴露全部回应头，跨域的页面也读得到。
- 请求 span 改成 info 级：`request{method, path, request_id}`，路径不带查询串（和以前一样）。请求里打的日志都带着它。
- 访问日志目标 `retainpdf_api::access`：拿到回应头超过 1 秒记 info `slow request`（`status`、`latency_ms`），其余记 debug，
  默认看不到，`RUST_LOG` 里加 `retainpdf_api::access=debug` 才有。每个请求都记 info 的话，桌面版前端的轮询会把日志刷满。
  5xx 照旧由 `tower_http` 记 error。
- runner 的 driver 在 `job{job_id}` span 里跑（`parent: None`，不挂在发射它的请求下面）。

## 没做的

- 指标（Prometheus 一类）：单机桌面版没有收集方；`/health` 已经有运行时、磁盘、子服务的状态。真要上服务器部署再说。
- `/ready` 加磁盘和管线自检：磁盘在 M4 定了不进 `/ready`（磁盘满了更要能打开页面删任务）；管线自检要起 Python，
  不适合放在频繁调用的就绪检查里。
- 错误回应的信封里带请求编号：回应头已经有了，信封不改。

## 测试

- `app::request_log`：客户端编号只在 1～64 个允许的字符时沿用，空的、带空格换行、非 ASCII、太长、带 `/` `=` 的都换掉；
  生成的是 16 位且自己也合格。
- rust_api `api_tests::request_log`：不带编号时生成、每次不同；带像样的原样回来；太长的换掉；未登记地址的 404、
  第二个端口的 `/ready` 也带。原有的"请求日志不记查询串"照旧过。
