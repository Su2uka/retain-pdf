# 翻译拆成独立包 retainpdf-translation

2026-10-17 用户提出：翻译部分做成一个独立的包，以后翻译相关的维护只动这一个包。包名定为 `retainpdf-translation`
（`import retainpdf_translation`，目录 `backend/translation`），和已有的 Python 包 `retainpdf-math`、
`retainpdf-pipeline`、`retainpdf-ai-service` 同一种写法。

## 拆之前的样子

翻译在 `backend/pipeline/retainpdf_pipeline/translate/`，约 300 个文件、4.5 万行，是流水线包的一个子目录。
边界其实已经比较清楚：

- 流水线其他部分用翻译，21 个文件走 `translate.public` 门面，另有两处直接调入口
  （`entrypoints/console.py`、`runtime/pipeline/book_pipeline.py`）。render 里写着「Duplicated from translate…」的
  都是注释，代码早就复制过去了，不是依赖。
- 翻译往外依赖的很少。去掉入口以后，翻译库本体只用到流水线的 7 样东西：阶段事件（`emit_stage_progress`、
  `emit_stage_transition`）、JSON 落盘、`direct_typst_math` 的三个函数、缓存目录（`paths`）、`artifacts` 目录名
  （`output_layout`）、读本地密钥（`local_env.get_secret`）、解析 `credential_ref`。

## 怎么切

**Rust 启动翻译的命令不变。** Rust 用 `python -m retainpdf_pipeline.translate --spec …` 启动翻译 worker，
这个模块名写在 `retainpdf-runner` 的进程约定里（`job_runner/process_contract.rs`、`worker_process.rs`、
`retainpdf-data` 的 `worker_command/entrypoints.rs`）。所以 `retainpdf_pipeline/translate/` 留下来当 worker 外壳：

| 留在流水线（worker 外壳） | 搬进 retainpdf-translation（翻译库本体） |
| --- | --- |
| `__main__.py`、`entrypoints/`（translate-only worker 读 `translate.spec.json`、建任务目录；`from_ocr_pipeline` 是整本 OCR→翻译→渲染）、`translation_stage.py` | `core/`、`services/`、`llm/`、`workflow/`、`artifacts/`、`public/`、`prompts/`、`prompt_loader.py`，以及翻译的测试 |

外壳可以依赖流水线的任何部分；翻译库本体只依赖自己、底座包和公式包。

**两边都要用的往下放，不在翻译包里复制一份。** OCR 和渲染也在用那 7 样东西（`events` 34 个文件、`io` 15 个、
`paths` 11 个），复制会出现两份规则。按「两边都要用的东西往下放」：

- `direct_typst_math.py` 是公式的事 → 公式包 `retainpdf_math.direct_typst`。
- 其余的 → 新的底座包 `retainpdf-base`（`backend/base`，`import retainpdf_base`）：`contracts`、`events`、`io`
  （原 `services/pipeline_shared/`）、`paths`、`output_layout`（原 `foundation/config/`）、`local_env`
  （原 `foundation/shared/`）、`credentials`（原 `stage_specs.resolve_credential_ref`）。只依赖标准库。

拆完以后的依赖：

```text
retainpdf-pipeline ──> retainpdf-translation ──> retainpdf-base
        │                       └──────────────> retainpdf-math
        ├──> retainpdf-base
        └──> retainpdf-math
```

## 分两步

1. **原地断开依赖**（分支 `refactor/translation-pkg-prep`）：建底座包，共享模块搬进底座包和公式包，所有引用改过去。
   文件位置不变，再加一条门禁 `check_translation_library_self_contained`：翻译库本体不许 import 流水线的其他部分，
   也不许 import 外壳。这一步之后，第 2 步就是纯搬家。
2. **整体搬家**（分支 `refactor/translation-pkg`）：`git mv` 到 `backend/translation/retainpdf_translation/`，
   `retainpdf_pipeline.translate.<库本体>` 机械替换成 `retainpdf_translation.<…>`（约 500 个文件，含测试和
   `tests/performance`）。不留旧路径的兼容层，仓库以前删 shim 时也是这么定的。要跟着改的还有：
   - Rust：`retainpdf-core` 的 `models/input/translation.rs` 用 `include_str!` 读 `control_context.py`、`model_wire.py`
     核对取值；`api_tests/model_executor.rs` 里内嵌的 Python 片段 import 翻译的 `llm`
   - 架构检查：`translation_rules.py` 等规则里的模块前缀和 `TRANSLATION_ROOT`
   - 打包：照 `retainpdf-math` 那次（b9c2cdd0）的清单，uv workspace、Docker、三个平台的桌面包、源码归档、
     独立运行检查、`dev.sh`、CI 的 import 检查和测试步骤；`run_translation_tests.py` 的路径；提示词的 package-data
   - CLAUDE.md 里「改了 `translate/` 要跑什么」的路径

留意：Rust 的底座包叫 `retainpdf-api-base`（`AppError`、`job_loading`），和这里的 Python 底座包 `retainpdf-base` 不是一回事。

## 不变的

- Rust 启动 worker 的命令、stage spec、stdout 协议、事件协议、翻译产物协议都不变。
- 前端不受影响：`frontend/` 下没有读这些源码路径的地方（搬家前会再全仓库 `git grep` 一次）。

## 说清楚的代价

- 「只维护翻译包」不完全成立：OCR、渲染、Rust 的任务编排还在，翻译包的输入 `document.v1` 和输出 manifest
  协议仍要和它们对齐。拆完得到的是：边界由包来强制，翻译测试可以单独跑，改翻译只动一个目录。
- 第 2 步会和所有进行中的翻译分支冲突。2026-10-17 只有 `fix/translation-label-and-musing` 改了 `translate/` 下
  2 个文件，最好在它合掉或放弃之后再做第 2 步。
