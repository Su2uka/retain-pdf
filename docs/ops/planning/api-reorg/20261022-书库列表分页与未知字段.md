# 书库列表分页与不认识的字段

> 日期：2026-10-22
> 分支：`fix/library-paging-and-unknown-fields`
> 起因：[书库接口审计](./20261019-书库接口审计.md)第二节，明细 A4、A7、A10、C7、C8、B14
> 规矩：[任务接口的规矩和删留](./20261019-任务接口规矩和删留.md)第 3、4 条，[分页约定](../../../api/00-约定/03-分页.md)

## 改了什么

### 分页（只增不改，旧字段照旧）

| 接口 | 改前 | 改后 |
|---|---|---|
| `GET /documents` | 返回 `documents`、`total`；`limit` 静默夹到 1..=500；只按 `added_at DESC` 排 | 加 `limit`、`offset`、`has_more`；`limit` 越界 400（`limit must be 1..=500`）；排序 `added_at DESC, document_id DESC` |
| `GET /documents?job_id=` | 返回 `documents`（0 或 1 条）、`total`；其余参数悄悄不起作用 | 同样回显 `limit`、`offset`（照请求），`has_more` 恒为 `false`；`limit` 照样校验；文档写明"带 `job_id` 时其余参数无效" |
| `GET /search` | 返回 `query`、`hits`；`limit` 静默夹到 1..=100 | 加 `limit`、`has_more`（多取一条）；`limit` 越界 400 |
| `GET /documents/:id/metadata-suggestions` | 返回 `suggestions`；`limit` 静默夹到 1..=100 | 加 `limit`、`has_more`（多取一条）；`limit` 越界 400 |
| `GET /documents/:id/jobs` | `has_more = offset + 条数 < total` | 多取一条判断（和 `GET /jobs` 一样），`total` 照旧 |

- `/documents` 的 `has_more` 直接用 `offset + 条数 < total`：页和 `total` 本来就在同一个 SQLite 事务里读，列表不跳过行，两者对得上，
  不用多取一条。
- `/documents/:id/jobs` 不能这么算：`total` 是 `COUNT(*)`，列表会跳过读不出来的任务行，最后一页会误报还有下一页（B14 (b)）。
  多取一条以后，坏行落在"多取的那一条"上时，`has_more` 会是 `false` 而其实后面还有好行；和 `GET /jobs` 是同一个取舍，坏行本来就要修。
- `limit` 的校验 `checked_limit` 从任务包挪到底座包 `retainpdf_api_base::paging`，任务、书库共用，提示文案只有一种。
- 搜索和元数据建议本来就没有 `offset`，这次也不加：前端、AI 都只取第一页，要更多就加大 `limit`。
- 不动的：书架 `GET /library/books`（冻结）、`GET /documents/:id/agent-versions`（留到 AI 那块）、`GET /ai/conversations`、`GET /collections`（不分页）。
- `limits.rs` 里"暂时还是静默夹"的注释跟着改，只剩 `/conversations`、`agent-versions`。

### 不认识的字段 400

加 `#[serde(deny_unknown_fields)]`：

| 类型 | 接口 | 认的字段 |
|---|---|---|
| `ListDocumentsQuery` | `GET /documents` | `limit`、`offset`、`reading_status`、`collection_id`、`job_id`、`q` |
| `PatchDocumentInput` | `PATCH /documents/:id` | `title`、`reading_status` |
| `SearchQuery` | `GET /search` | `q`、`limit`、`document_id` |
| `CreateCollectionInput` | `POST /collections` | `name`、`parent_id` |
| `PatchCollectionInput` | `PATCH /collections/:id` | `name`、`sort_order` |
| `AddCollectionDocumentsInput` | `POST /collections/:id/documents` | `document_ids` |
| `DeleteDocumentQuery`（新） | `DELETE /documents/:id` | `force` |
| `ListDocumentMetadataSuggestionsQuery` | `GET /documents/:id/metadata-suggestions` | `limit` |
| `ListDocumentJobsQuery` | `GET /documents/:id/jobs` | `limit`、`offset` |

- 合集 PATCH 传 `parent_id` 以前 200 但不生效，现在 400；登记表说明从"改合集（名字、上级）"改成"改合集（名字、排序）"。要不要支持改上级另议（要防环）。
- 查询参数被拒时走的是我们自己的 `ApiQuery`，本来就是统一的 400 信封（`code` 40000、`error.code` BAD_REQUEST），axum 默认的纯文本 400 漏不出去。
  以前 message 一律是 `invalid query parameters`，看不出哪个参数错了；现在不认识的参数和请求体一样写出名字：
  ``unknown field `tag`, expected one of `limit`, ... in the query string``（只有参数名，不带值）。类型不对、整数越界、缺参数照旧是
  `invalid query parameters`。这条对已经收紧的译文列表、事件、数据、质量条目也生效，只改了 message，状态码不变。

### 冻结的书架删除

`LibraryDeleteQuery` 原来被 `DELETE /documents/:id` 和冻结的 `DELETE /library/books/:job_id` 共用。直接给它加 `deny_unknown_fields`，
冻结接口的行为也会变（拼错的参数从"忽略"变成 400）。书架 2026-10-19 起冻结、"行为不变"，所以拆开：

- 新加 `DeleteDocumentQuery`（收紧），`DELETE /documents/:id` 改用它；
- `LibraryDeleteQuery` 留给书架，不动，注释写明不收紧；
- 新地址 `DELETE /jobs/:job_id` 用的是任务包自己的 `DeleteJobQuery`，这次不在范围里，也没动。

测试 `library_request_bodies_and_delete_query_reject_unknown_fields` 里钉了书架删除带拼错的参数照旧不报 400。

## 对前端

不用改代码。前端的 `DocumentListView` 类型早就声明了 `limit`、`offset`，现在后端真的给了。可选：

- 书库主网格（`document-library-source.ts`）可以改读 `has_more`，和现在的 `offset + 条数 < total` 结果一样。
- 书籍详情的任务列表（`job-actions.ts:81`）固定 `limit=50, offset=0`、不看 `has_more`，一本书超过 50 个任务时只显示前 50 个（审计 B14 (c)）。
  要看全就按 `has_more` 翻页。

详见 [给前端的交接](../../../core/frontend/backend-changes-handoff.md) 最后一节。

## 测试

`backend/api/src/api_tests/library_paging.rs`（先写、在没改的代码上 7 条全红）：

- `documents_list_echoes_limit_offset_and_has_more_with_a_stable_order`：5 本同一秒入库的书按 2 条一页翻三页，不重不漏、按 `document_id DESC`；默认 `limit` 50；offset 超出是空页；`limit=500` 可以。
- `documents_list_rejects_out_of_range_limit_and_unknown_params`：`limit=0`、`501` 400；`tag` 400，message 带字段名、以 `in the query string` 结尾。
- `documents_list_by_job_id_echoes_paging_fields`：带 `job_id` 回显、`has_more` false，其余参数不起作用，`limit=0` 照样 400。
- `search_echoes_limit_and_has_more`、`metadata_suggestions_list_echoes_limit_and_has_more`：`has_more`、默认值、越界 400、`offset` 400。
- `document_jobs_has_more_comes_from_the_extra_row_not_the_count`：最旧一条任务行读不出来时，`total` 仍是 3、`has_more` 是 false；`status` 参数 400。
- `library_request_bodies_and_delete_query_reject_unknown_fields`：四个请求体各一个未知字段 400（含合集 PATCH 的 `parent_id`）；前端实际发的照旧 200；删书拼错 `force` 400 且书还在；书架删除拼错照旧不 400。

另有底座包 `paging::tests::limit_must_be_within_one_and_max`，AI 的 `test_list_documents_tool_keeps_limit_within_its_declared_range`。
