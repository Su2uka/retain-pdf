# Rust API 模块化单体拆包规划

> 日期：2026-10-15
> 状态：**方案已定**（第 7 节的待定项 2026-10-15 全部按建议确定）。代码还没开始拆包。
> 相关：[任务与文件接口整理](./20261015-任务与文件接口整理.md)

## 1. 问题

- `rust_api` 有 187 个接口，`services/` 有 4.5 万行。改一处，经常要连带改很多处（"牵一发动全身"）。
- 只有一个人维护，接口太多、太分散，管不过来。

## 2. 结论：不上微服务，做模块化单体

**一个程序、一个数据库、一次部署不变，代码按领域拆成几个独立的 Rust 包（crate）。**
包和包之间的边界由编译器保证：一个包没声明依赖，就用不了另一个包的内部代码。

### 为什么不上微服务

微服务解决的是"多个团队各自独立发布、各自扩容"，这个项目没有这个需求，只会承受它的代价：

| 代价 | 在这个项目里的具体表现 |
|---|---|
| 数据库要拆 | 所有业务共用一个 SQLite 库，靠事务和触发器（约 87 个）保证一致。比如任务失败退还页数，是同一个事务里跨任务和额度两张表完成的。拆库以后只能自己写补偿逻辑，最容易出错、最难排查 |
| 改坏了发现得更晚 | 现在改一个接口，编译器会指出所有受影响的地方。拆成服务后变成网络调用，改坏了要到运行时才发现 |
| 运维翻倍 | 每个服务要单独部署、监控、查日志、传递登录状态、保持版本兼容。一个人做不过来 |
| 该独立的已经独立 | 任务调度（jobsd）、AI 服务、每份文档的 Python 流水线，本来就是独立进程。剩下的 Rust API 拆开没有收益 |

### 两种做法对比

| | 微服务 | 模块化单体 |
|---|---|---|
| 边界谁来保证 | 网络 | 编译器 |
| 改坏了什么时候发现 | 运行时 | 编译时 |
| 部署 | 每个服务各一份 | 1 个程序，不变 |
| 数据库一致性 | 自己写补偿 | 照旧用事务和触发器 |
| 一个人管理 | 更难 | 每次只打开一个包 |

## 3. 拆成哪几个包

`rust_api` 本身只负责组装：读配置、建 `AppState`、把各包的接口表注册成路由，几百行。

| 包 | 管什么 | 现在的代码（`services/` 下） | 对外接口 |
|---|---|---|---|
| `retain-pdf-accounts` | 账号、登录会话、页额度（含扣减退还台账）、邀请码、管理后台、平台设置 | `accounts`（含 `page_quota`）、`platform_settings` | `/auth`、`/account`、`/admin` |
| `retain-pdf-providers` | 模型和 OCR 服务商、凭据库、模型调用、连通性测试 | `credentials`、`provider_probe`、`model_executor`、`model_provider_headers`、`provider_api`、`model_requests_api` | `/providers`、`/credentials` |
| `retain-pdf-ingest`（入口） | 上传、校验、扣额度、建任务、启动 | `uploads`、`jobs/creation`、`jobs/validation`、`jobs/launcher`、`jobs/snapshot_factory`、`jobs/runtime_gateway`、`jobs/ocr_artifact_reuse` | `POST /uploads`、`POST /jobs`、`POST /documents/:id/translate`、`POST /documents/:id/ocr` |
| `retain-pdf-files`（出口） | 所有文件：成品、预览图、中间产物、书的原文和封面 | `artifacts`、`derived_artifacts`、`download_generation`、`download_names`、`jobs/downloads` | `/jobs/:id/files/…`、`/documents/:id/files/…` |
| `retain-pdf-jobs` | 任务的其余部分：查询、操作、进度、报告、阅读、译文、数据、模型 token 用量 | `jobs` 的其余部分、`job_data`、`quality`、`query_execution`、`document_pages`、`usage` | `/jobs` 下除 `files` 外的 8 类 |
| `retain-pdf-library` | 书、书架、合集、全文检索 | `library`（含 `book_projection`、`collection_workspace`）、`merge`（待定，见第 5 节） | `/documents`、`/library`、`/collections`、`/search` |
| `retain-pdf-glossaries` | 术语表 | `glossaries` | `/glossaries` |
| `retain-pdf-ai` | AI 问答、Agent、计算、文档操作（多用户下整块关闭） | `ai`、`agent_*`、`document_operations`、`public_document_operations*` | `/ai`、`/internal`、`/assets` |
| `retain-pdf-platform` | 同步、备份、字体、全部用量汇总、健康检查 | `sync`、`backup`、`fonts`、`health_api` | `/sync`、`/backups`、`/fonts`、`/usage`、`/health`、`/ready` |

几点说明：

- **术语表单独成包**：建任务时要读术语表（`resolve_task_glossary_request`），入口依赖术语表；书库的
  "翻译这本书"又要调入口。术语表要是放进书库，就成了 书库 → 入口 → 书库 的环。
- **用量是两件事**：`usage` 统计的是模型 token 用量，数据来自每个任务目录下的台账，跟着任务包走；
  三个地址各归各类（任务的进"报告"、书的进书库、全部汇总的进平台，都调任务包的门面）。
  商业版"管理员看用量"看的是页数额度的扣减和退还，在账号包的页额度台账里，不是一回事。
- **入口单独成包**：它是要先固定住的一头，单独成包，入口合同由编译器守住。

### 命名：统一叫 `retain-pdf-<领域>`

新拆出来的包一律用 `retain-pdf-` 开头（2026-10-15 定）。现有的包名不统一，有 `retain-core`、
`rust_api`、`retain-jobsd`、`retainpdf-cli` 几种写法，建议一起改成同一个前缀：

| 现在 | 改成 | 说明 |
|---|---|---|
| `rust_api` | `retain-pdf-api` | 只负责组装 |
| `retain-core` | `retain-pdf-core` | 共享类型、路径规则 |
| `retain-data` | `retain-pdf-data` | 事件、凭据库格式、同步 |
| `retain-db` | `retain-pdf-db` | 数据库 |
| `retain-config` | `retain-pdf-config` | 配置 |
| `retain-proc` | `retain-pdf-proc` | 子进程工具 |
| `retain-jobs` | `retain-pdf-runner` | **改名不只是加前缀**：它是任务运行器（`job_runner`）。不改的话会和新的 `retain-pdf-jobs`（任务接口）撞名 |
| `retain-jobsd` | `retain-pdf-runnerd` | 任务调度进程 |
| `retainpdf-cli` | `retain-pdf-cli` | 命令行 |

- **只改包名，不改可执行文件名**：`rust_api`、`retain-jobsd`、`retainpdf` 这几个可执行文件被启动脚本、
  Docker、桌面版引用，用 `[[bin]] name` 保持原名，部署不受影响。
- 旧包改名是纯机械替换（`retain_core::` → `retain_pdf_core::` 约 40 个文件，`retain_data::` 约 50 个），
  还要改 CI 里 `cargo test -p` 的包名。单独做一次提交，不和别的改动混在一起。

### 依赖方向（只能往下，不准反过来）

```
                     rust_api（组装）
                           │
          ┌────────────────┼──────────────────┐
         ai            platform             （其余各包）
          │
       library ──────────┐
          │              │
         jobs ───────▶ files
          │              │
       ingest            │
          │              │
      glossaries         │
          │              │
      providers          │
          │              │
       accounts ◀────────┘
          │
  retain-pdf-core / -data / -db / -runner（已有的底层包，改名后；"按编号读出任务"下沉到这一层）
```

- 上层可以用下层，下层不能用上层，同层之间不互相用。
- 跨包只能通过对方的门面（每个包的 `lib.rs` 只导出门面），拿不到内部函数。
- 编译器保证这些规则：违反了就编译不过，不用靠检查脚本。

## 4. 一个人怎么管得过来

### 先缩小真正要操心的范围

| 访问策略（多用户模式） | 个数 | 说明 |
|---|---|---|
| 网站账号可用 | 93 | **日常要维护的就是这一块** |
| 只给管理员 | 37 | 管理后台、凭据、备份，改动少 |
| 关闭 | 52 | AI、Agent、内部接口、旧别名 |
| 不需要登录 | 5 | 登录注册、健康检查 |

### 规则交给机器守，不靠人记

1. **接口登记表**：每个包有自己的 `endpoints.rs`，一个接口一条，写明方法、路径、处理函数、访问策略和一句话说明。路由注册和访问控制都从这张表生成。
2. **自动生成的接口目录**：从所有登记表汇总成一份文档，打开就能看到全部接口、谁能用、在哪个包。
3. **契约快照测试**：对外接口清单和返回格式都锁住。改坏了测试会报错，不用人记。
4. **冻结领域**：暂时不动的包（比如 `retain-pdf-ai`，多用户下本来就关着）用快照锁住，可以先放着不管。
5. **改一个领域只打开一个包**：别的包只要门面没变，就不需要看。

## 5. 拆包前必须先解决的问题

1. **任务 / 合并书 / 派生产物之间的依赖环**：`jobs ↔ merge ↔ derived_artifacts`。这个环不拆，三者就分不进不同的包。对应 services 分批整理的批次 3。
2. **文件包需要"加载任务"**：现在下载代码调用的是 `jobs::query::load_supported_job`，按上图会形成 `files → jobs` 的反向依赖。
   **已定：把"按编号读出任务并确认格式受支持"下沉到底层**。它在任务、文件、书库三处都被大量调用，
   本质是读数据库，不是任务的业务逻辑；下沉后三个包都往下依赖它，没有环。
3. **`merge`（合并阅读）放哪个包**：它既生成合并目录（像文件），又服务书的阅读（像书库）。拆环时决定。
4. **任务结构被到处直接翻**：42 个文件、343 处一路点进 `job.request_payload.*.*`。拆包前要先收成方法，比如 `job.translation_credential()`，否则每个包都会依赖任务结构的内部细节。
5. **共享的返回类型**：`models::api` 被 117 个文件引用，拆包前要按领域分开。
