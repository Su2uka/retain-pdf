# 建任务归任务包的决定

> 日期：2026-10-16
> 改的是：[模块化单体拆包规划](./20261015-模块化单体拆包规划.md)第 3 节的包表
> 起因：[入口拆包实现记录](./20261016-入口拆包实现记录.md)的"建任务这次没挪进来"

## 决定

1. **建任务留在任务包 `retain-pdf-jobs` 里，入口包 `retain-pdf-ingest` 只管上传。**
   - 规划第 3 节原来把这几块排进入口包：
     - `jobs/creation`；
     - `jobs/validation`；
     - `jobs/launcher`；
     - `jobs/snapshot_factory`；
     - `jobs/runtime_gateway`；
     - `jobs/ocr_artifact_reuse`。
   - 现在不挪。这几块都在 `services/jobs/lifecycle/` 下，拆任务时跟着任务包走。
2. **任务的文件出口 `services/jobs/files/downloads` 也留在任务包里。**
   - 规划第 3 节把 `jobs/downloads` 排进文件包，拆文件时实际没挪：
     - 它用任务领域的依赖（`jobs/deps`）；
     - 它用任务的查询能力。
   - 文件包在任务包下面，拆出去的是产物清单、派生产物、下载文件名这些两边都用的东西。
3. **两条规矩不变：**
   - 建新任务只走 `submit_job`，原地重跑只走 `relaunch_in_place`，`check_job_entry_ownership` 照旧管着；
   - 任务的文件只经 `open` 出去，`check_artifact_path_ownership` 照旧管着。

用户 2026-10-16 确认："建任务留在任务包"。

## 为什么

建任务的代码用了任务领域的另外几块：
- 依赖 `jobs::deps`（6 处）；
- 调度入口 `jobs::runtime_gateway`（2 处）；
- `jobs::query`、`jobs::presentation`、`jobs::facade` 各 1 处。

硬挪进入口包有两种做法，都不划算：
- **入口依赖任务**：任务已经依赖入口（建任务要用上传），成环。
- **把那几块先往下放**：`deps`、`runtime_gateway`、查询、返回视图都得从任务包里拆出来，放到入口和任务都能依赖的一层。
  这等于把任务拆成两个包，改动面和拆任务本身差不多大。换来的只是"建任务的代码在另一个目录"，对边界没有多少好处。

"只有一个建任务入口"本来就由 `submit_job` 和检查守着，不靠它在哪个包里。

## 对规划的影响

规划第 3 节的包表照这里理解：

| 包 | 管什么 |
|---|---|
| `retain-pdf-ingest`（入口） | 上传：校验、页数、修复、落盘 |
| `retain-pdf-jobs` | 任务的全部，包括建任务、启动、任务的文件出口 |

依赖方向不变：任务 → 入口、账号、服务商、文件、术语表；书库 → 任务、文件。
