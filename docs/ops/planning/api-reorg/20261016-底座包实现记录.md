# 底座包实现记录

> 日期：2026-10-16
> 分支：`refactor/api-base`
> 方案：[模块化单体拆包规划](./20261015-模块化单体拆包规划.md) 第 5 节第 2 条（"加载任务"下沉到底层）、第 6 节第 7 步之前的准备

## 为什么

要把领域拆成独立的包，每个领域包都要用两样东西：
- 错误类型 `AppError`：几乎每个 service 函数都返回它；
- 按编号读出任务 `job_loading`：任务、文件、书库、合并阅读都在用。

这两样原来都在 `retain-pdf-api` 里。不先放到下面一层，拆出去的包就得反过来依赖 `retain-pdf-api`，形成环。
2026-10-16 用户同意新建一个包来放它们。

## 做了什么

**新包 `retain-pdf-api-base`**，放在 `backend/packages/retain-pdf-api-base`：
- `error`：`AppError` 和它对外的 HTTP 错误契约，原来是 `backend/api/src/error.rs`；
- `job_loading`：原来是 `backend/api/src/job_loading/`。
  - 里面的 `pub(crate)` 改成 `pub`；
  - `crate::db`、`crate::models` 这类路径，改成直接写 `retain_pdf_data`、`retain_pdf_core`。
- 它只依赖 `retain-pdf-core` 和 `retain-pdf-data`。

**`retain-pdf-api` 里留转出口**：`lib.rs` 里写了 `pub use retain_pdf_api_base::error;` 和
`pub(crate) use retain_pdf_api_base::job_loading;`。原来约 211 处 `crate::error::AppError`、
`crate::job_loading::…` 的写法一行都不用改。

**上传错误怎么转成 HTTP 错误**：`impl From<UploadError> for AppError` 原来写在 `error.rs` 里。
它引用了入口领域的 `UploadError`，底座包不能反过来依赖入口领域，所以挪了地方：
- 没放进 `uploads/`：原有的检查（`check_upload_boundaries`）规定上传模块只返回自己的错误，不碰 HTTP；
- 现在放在入口领域的门面 `services/ingest/mod.rs`；
- Rust 允许在 `UploadError` 所在的包里写这个转换。

**日志过滤**：`AppError` 遇到内部错误时打的日志（带 `error_id`），日志目标变成了 `retain_pdf_api_base::error`。
默认过滤加上 `retain_pdf_api_base=info`，写成
`retain_pdf_api=info,retain_pdf_api_base=info,rust_api=info,tower_http=info`。
- 不加的话，按字符串前缀这条也会被 `retain_pdf_api` 匹配上。但那是碰巧，所以明确写出来。

**架构检查跟着改**：
- 删掉 `check_job_loading_is_below_services` 和它的 2 个单测。`job_loading` 现在在单独的包里，
  `services`、`routes`、`AppState` 它根本引用不到，编译器就会拒绝。单测剩 60 个。
- 检查脚本按逻辑路径找文件，`src/error.rs`、`src/job_loading/` 现在对应到新包的目录。
- 读任务请求的检查（`check_request_payload_access`）也扫新包，`job_loading/merged.rs` 照旧在冻结名单里。

**交付**：
- `Dockerfile.app` 逐个目录 `COPY` 工作区成员，两个阶段都加上了新包。
- CI 和开发栈都是整个工作区一起编译，不用改。
- 合并前的 `cargo test`（CLAUDE.md）加上 `-p retain-pdf-api-base`：`AppError` 的测试跟着挪过去了，
  不加的话本地跑不到。CI 跑整个工作区，不受影响。

## 怎么保证行为没变

- 只挪文件、改路径和可见范围，函数体不动。
- 三份快照都没变。
