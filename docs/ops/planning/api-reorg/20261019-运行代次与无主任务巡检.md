# 运行代次与无主任务巡检

分支 `fix/runner-run-generation`。对应状态一致性审计的 1-任务状态机 #2、#3、#7、#8 和 4-事件与进度 #1。
只动后端；对前端没有任何改动，接口的状态码、字段、错误原因都没变。

## 问题

1. runner 的 CAS 只比较 `status`，认不出"哪一次运行"。取消后立刻原地重跑：行被无条件覆盖成新的
   queued，旧 driver 还在收尾，它最后那次 CAS（期望 queued/running）通过，把旧运行的 Canceled 盖到新一次运行上；
   同时旧 driver 的登记还在，新的发射被 `claim` 失败静默丢掉，任务停在 queued。
2. 取消标记只在内存里按任务编号登记，对没有 driver 的任务点取消没人消费，下一次原地重跑的 driver 一启动就被取消。
3. API 取消先赢终态 CAS 时，runner 的 `!updated` 分支、`persist_failed_job` 都不收尾 pipeline attempt，
   attempt 一直是 `running`，之后译文修订登记永远 pending。
4. 发射可能丢（claim 失败、壳转发给 jobsd 失败只打日志、driver 出错后落失败的写也失败被 `let _` 吞掉），
   运行期没有任何自愈，只有下次启动才修。

## 决定

- **运行代次**：`jobs.run_generation`（幂等加列，`ensure_jobs_column`，不占迁移号）。建任务和原地重跑走
  `Db::save_job_as_new_run`（整行落库 + 同一事务里代次加一），别的写都不动它。`cas_save_job` 除了状态，
  还要求快照的代次等于库里当前代次，不等一律落空。`JobRecord.run_generation` 只由 `get_job` 填；列表查询的外层按固定列号
  读列，没往 `JOB_SELECT_SQL` 里加列，列表出来的快照代次是 0，不拿去 CAS。
- **driver 钉住代次**：`spawn_job` 发射时读行上的代次，driver 整个 future（和 `tokio::spawn` 出去读 stdout 的任务）
  在 `with_driver_run` 里跑，`cas_persist_*` 对这个任务的写一律用钉住的代次。深处阶段代码里随手 `get_job`
  重读到的是新一次运行的代次，也不会让旧 driver 的写通过。OCR 子任务是另一个任务编号，不受影响。
- **新一次运行不丢发射**：`JobDriverRegistry` 登记 `任务编号 → 代次`。登记着的是更老代次的 driver
  （还在收尾）时，新的发射不丢，等它释放再接手（轮询 50ms，最多 120 秒，超时交给巡检）；同代次重复发射照旧去重。
  被取代的旧 driver 在 `run_job` 入口、排队等槽位之后都会检查，发现自己被取代就直接退出，不清取消标记、不收尾 attempt。
- **取消标记按运行清**：新增 `launch_job`，新建 / 原地重跑的发射（进程内闭包、jobsd 的 launch 接口）先清掉这个任务的取消标记再起 driver。
  启动恢复和巡检用的 `spawn_job` 不清（那里的标记可能是真的取消）。
- **终态不是 driver 写的也收尾 attempt**：API 取消 CAS 赢了时 `cancel_job` 自己收尾（driver 不在也成立）；
  runner 侧 `!updated` 分支、`persist_failed_job` / `persist_canceled_job` 落空、driver 出错退出看到终态已是别人写的，都调
  `close_attempt_after_foreign_terminal`（按行上的终态收尾，幂等，被取代的运行不碰）。
- **不再静默丢**：driver 出错后落失败的读写最多试 3 次并打日志；壳到 jobsd 的 launch 转发重试 3 次（300ms/1s/3s）
  仍失败，就把任务落成失败，原因写"任务没能交给任务运行时"（`fail_unlaunched_job`，只对仍是 queued 且没有 driver 的任务）。
- **运行期巡检** `driverless_sweep`：拥有 driver 登记表的进程（进程内模式是 rust_api，远端模式是 jobsd）每 30 秒
  （`DRIVERLESS_SWEEP_INTERVAL_SECS`）扫一次，行的 `updated_at` 距现在超过 120 秒（`DRIVERLESS_GRACE_SECS`）且登记表里没有 driver
  （`{父}-ocr` 子任务看父任务）的：running 走启动恢复同一份逻辑（孤儿 worker 终止，有可续 attempt 回 queued，否则失败，
  `reconcile_running_jobs_matching`，写改成 CAS 只认 running），queued 重新发射。启动恢复的两个函数加了"只处理谁"的过滤参数，没有第二份拷贝。
  壳在远端模式下不巡检，避免和 jobsd 重复。

## 没做 / 已知边界

- 并发两个原地重跑（审计 1-#3 场景 C）：两个请求都读到终态再各自落库，现在第二个会把代次再加一并取代第一个，
  第一个 driver 随即变成旧 driver、写落空，不再互相覆盖；但 `rerun.rs` 里在落库前删 `rendered/` 的问题不在这个分支。
- 巡检把 running 回到 queued 之后，下一轮才会重新发射（刚改过 `updated_at`，要再过一个宽限期）。
- 巡检读行只用 `updated_at` 和登记表，不核对 worker 进程是不是我们的（审计 #9 另说）。

## 前端

无。`run_generation` 不进任何接口返回；取消后任务的 attempt 收尾、发射失败变成 `failed`（`error` 里有原因）都是已有字段的取值。
