# 数据库恢复后对账与自动续跑上限

分支 `fix/recover-after-restore-and-crash-loop`。对应状态一致性审计明细
[3-磁盘产物与缓存 #6](./20261019-正确性与状态一致性审计明细/3-磁盘产物与缓存.md) 和
[1-任务状态机 #10](./20261019-正确性与状态一致性审计明细/1-任务状态机.md)。

## 问题

1. 数据库恢复（`retainpdf-platform` 的 `BackupService::restore` → `retainpdf-db` 的 `restore_unpacked`）把备份里
   queued/running 的任务原样带回来。`restore_blockers` 只看恢复「之前」有没有在跑的任务，所以恢复出来的这些行没有任何 driver；
   对账只在进程启动时做，期间任务一直转圈、rerun 409。下次重启时，又会拿备份里的旧 pid 去当孤儿 worker 杀（pid 可能已被别的进程复用）。
2. 可续跑的任务没有次数上限：一份能把运行时整个弄崩的输入（栈溢出、abort、OOM），每次重启被判「有 durable attempt → Queued」，
   续跑再崩，jobsd 还被壳自动拉起，无限循环。

## 决定

- **恢复时清 pid**：`restore_unpacked` 换完库、补完结构后，把 queued/running 行的 `pid` 置空（终态行不动）。
  这些 pid 一律不属于当前进程，不杀，只清。放在数据库层，CLI 的 `retainpdf backup restore` 也一样受益。
- **恢复后立即对账，不另写一份**：用已有的运行期巡检 `driverless_sweep`（和启动恢复同一套规则：
  有可续 attempt 的放回 queued 并发射，没有的落失败并维护书卡/全文索引，queued 的重新发射），只是宽限期为 0
  （`recover_jobs_after_database_restore`）。恢复前已确认没有排队/运行中的任务，恢复后刚提交的新任务有 driver，巡检本来就不碰。
  - 进程内模式：`BackupService` 新增装配时设一次的 `AfterRestoreHook`，rust_api 的 `install_restore_recovery` 把它接到
    `recover_jobs_after_database_restore`；恢复接口在返回前做完。钩子出错只记日志（恢复已经完成，巡检还会兜底）。
  - jobsd 模式：driver 登记表在 jobsd 里，壳不碰；pid 已清，jobsd 自己的巡检（30 秒一轮、宽限 120 秒）接手，
    running 一轮内回 queued/failed，回 queued 的再过一个宽限期发射，最多约 2 分半。没有为此加 jobsd 内部接口（要改契约，收益小）。
  - 对账的文字沿用启动恢复的（「任务运行时启动时发现遗留 running 任务……」），没为恢复单写一套，免得和同时在改
    `startup_recovery` 的 `fix/worker-process-identity` 冲突。
- **自动续跑次数上限**：`pipeline_attempts` 加 `auto_resume_count`、`auto_resume_progress`（迁移 v27，编号迁移而不是
  `ensure_*_column`：表本身由 v08 建，编号迁移在 jobsd 和 API 同时启动时只跑一次）。
  - 只在「running 却没有 driver、判为可续跑」这一处计数（`reconcile_running_jobs_matching`），启动恢复、运行期巡检、恢复后对账都走它。
  - 计的是**连续没有新进度**的自动续跑次数：进度 = 这个 attempt 已提交的单元数 + 已完成的阶段数，比上一次续跑时多就从 1 重新数。
    只数次数的话，桌面端反复关开几次就会把正常的长任务判死；崩溃循环卡在同一处，不会有新进度。
  - 上限 `MAX_AUTO_RESUMES_WITHOUT_PROGRESS = 3`：第 4 次发现它中断时落 `failed`，收尾 attempt，
    `failure_code = auto_resume_limit_exceeded`（`failure_category=internal`、`retryable=true`、`resume_from=null`），
    原因写「自动续跑次数超过上限，疑似导致运行时崩溃」，恢复目录 `job_failure_catalogue` 登记了提示语。
  - 手动重试/续跑走新 attempt（失败时 attempt 已收尾），计数自然从 0 开始，不用在各个重试入口清零。
  - 只有翻译请求日志干净、确实要续跑时才计数；结果不明的翻译照旧落 `translation_request_ambiguous`。

## 没做 / 已知边界

- 审计 #6 第 5 步：恢复只换库不碰文件，备份之后新建的任务目录、上传、文档目录成为孤儿，备份之后完成的任务库里还是旧状态而磁盘上有成品。这次不做，留待办。
  相关风险：恢复出来的可续任务会按备份时的断点续跑，备份之后磁盘上已经做完的部分会被重做（翻译阶段若请求日志干净，可能重复请求上游）。
- 进程在「库已换、pid 还没清」之间崩溃：下次启动的对账会看到旧 pid，仍会走孤儿判定（kill 前核对进程身份在 `fix/worker-process-identity`）。
- 崩溃发生在「行已回 queued、driver 还没把它改成 running」之间的循环不计数（启动时直接按 queued 发射，不经过对账），实际的崩溃输入都在运行中触发。
- 恢复后对账落失败的任务，失败文案是启动恢复的那一套，没有区分「因为恢复」。

## 前端

不用改。恢复接口的请求/返回没变；`auto_resume_limit_exceeded` 是新的 `failure_code` 取值，失败弹窗按后端的 `summary`、`recovery_hint` 显示。
记在 [backend-changes-handoff](../../../core/frontend/backend-changes-handoff.md)。
