# 契约端点加函数名和传输方式

**日期：** 2026-10-22

**分支：** `contracts/client-names-phase0`

**方案：** 前端的[从契约生成前端请求函数](../api-client-codegen/20261022-从契约生成前端请求函数.md)（第 3.1 节、第 6 节）。
这里只记后端这边做了什么、一致性检查怎么比。

## 做了什么

1. 端点表（`contracts/*.schema.json` 的 `endpoints[]`）加两个字段：
   - `client_name`：前端生成的函数名，小驼峰。显式写，不从地址推。不复用 `op`（jobs-control.v1 里 jobsd 的内部操作名）。
   - `transport`：返回方式，`json`（不写等于它，`{code, data}` 信封）、`sse`、`binary`、`websocket`、`raw_json`（不带信封）。
     不叫 `response`：jobs-control.v1 已有 `response` 键，值是返回类型。
2. `library-documents.v1` 的 17 条全部写上前端起的名字和 `transport: "json"`（名单在方案第 6 节，方法、地址逐条核对过，
   全部对得上）。
3. `agent-calculation.v1` 计算产物那条的 `response_body: "binary"` 改成 `transport: "binary"`。删之前 `git grep` 过整个仓库
   （`contracts/scripts`、`contracts/tests`、前端、`backend/ai`、rust_api），没人读这个键。
4. 顺手把 `reader-data.v1` 的 `GET /jobs/:job_id/progress/stream` 标成 `transport: "sse"`：它本来就是 SSE，不写会被当成 json。
   其余端点没加 `transport`，按默认 json 算；以后补 `client_name` 时逐条核对。
5. lint（`contracts/scripts/lint-schemas.mjs`）：
   - 端点的键有白名单，拼错（比如 `clientName`）或者再写回 `response_body` 都红；
   - `method` 只能是五个 HTTP 方法，`path` 以 `/` 开头；
   - `transport` 只能是上面五个值；
   - `client_name` 小驼峰，**跨全部契约**不许重名（生成的函数以后可能从同一个入口导出，同名就撞）。
6. `contracts/tests/endpoint-client-names.test.mjs` 钉住第 0 期 17 条的（方法，地址，函数名，传输方式），以及 `response_body` 已并进 `transport`。

## 一致性检查

rust_api `src/api_tests/route_manifest.rs` 的 `contract_endpoints_are_registered`：读 `backend/contracts/*.schema.json`
（和根目录 `contracts/` 字节一致，`check_parity.py` 守着；后端测试照惯例读后端镜像，单独拆出后端也能跑）每份的 `endpoints`，
每条方法加地址都要在接口登记表（`crate::app::registered_endpoints()`）里，而且不是旧地址（`old`）。直接对登记表比，不读 `routes.txt`。

- `jobs-control.v1` 排除：jobsd 自己的接口，不在 rust_api 登记表里。jobsd 挂的路由已经由 `backend/jobs/src/contract_lock.rs`
  对这份契约双向比（多挂、少挂都红），rust_api 发出的请求地址由 `api_tests/jobs_control_contract.rs` 比，这里不重复。
  排除名单里的文件不存在了测试也红，免得名单烂掉。
- 有 `proxy_path` 的比 `proxy_path`：`runtime-config.v1` 的 `path` 是 Python AI 服务的地址（`/v1/runtime-config`），对外地址在
  `proxy_path`（`/api/v1/ai/runtime-config`）。按字段判断，不按文件名写死。
- 地址先归一：`{job_id}` 换成 `:job_id`；`?` 后面的查询串去掉（`reader-data.v1` 的 `progress/stream?after_seq=:seq`）。
- 反过来不要求：管理后台、内部接口、文件出口可以不进契约。

在没改的代码上把 `library-documents.v1` 的 `/api/v1/search` 改成 `/api/v1/library/search`、`runtime-config.v1` 的
`proxy_path` 改成 `/api/v1/ai/runtime-cfg`，测试红了并列出这两条；还原后绿。

现有契约带端点表的 16 份、64 条，排除 jobs-control 的 4 条以后 15 份、60 条，全部对得上，没有残留。

## 没做的

- 生成器、`request()`、生成物是否最新的检查都归前端（`frontend/packages/api`），这次不做；契约包只放类型，TS 类型生成物不受影响
  （生成器只读 `input`/`query`/`output` 指向的定义）。
- 其余契约的端点暂不补 `client_name`，等前端第 1 期的清单。
- `reader-data.v1` 的 `progress/stream?after_seq=:seq` 地址里带查询串，没改（没有代码读这个字符串，`git grep` 过）；
  它是 `sse`，第 0 期不生成，前端要生成它时再改成 `path` 不带查询串、另写 `query` 定义。
