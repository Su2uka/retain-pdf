# 原地重跑保留旧 PDF

分支 `fix/rerender-keeps-old-pdf`。对应状态一致性审计的 1-任务状态机 #4（含 B14 的结论）、
3-磁盘产物与缓存 #2、6-流水线约定 #8（也是 1-任务状态机 #3 的场景 C）。只动后端；对前端只多出两种 409，
原因值都是已有的（`job_active`、`stale_resolution`），前端已有中文提示。

## 问题

1. 续跑（`actions/resume`，旧名 `rerun`）选中原地重渲染时，先删 `<id>-ocr` 子任务的行和目录、`rm -rf rendered/`，
   然后才校验和发射。发射被拒（`503` 模型执行器没开、额度、落库失败）后任务还是 succeeded，`artifacts.output_pdf`
   指向已经删掉的文件，下载、阅读都 404；排队期间合并阅读要用的 `previous_output_pdf` 也被删了。
2. 原地重渲染 / 精修失败或被取消后，`output_pdf` 已经被清空（挪进了 `previous_output_pdf`），没人恢复，
   用户只能再成功渲染一次才拿得回 PDF。而且渲染写的是同一个文件名（`rendered/<名>.pdf`），
   `doc.save(...)` 直接改写，有的步骤先删再写——上一份就算还在，也可能已经被这一次截断。
3. 两个原地重跑同时来：都读到同一个终态、都通过检查，后一个用旧快照无条件整行覆盖成 queued（`pid` 清空，
   取消按钮杀不到 worker），续跑那条路还会删掉前一个正在写的 `rendered/`。

## 决定

- **原地重跑的落库改成 CAS**：新增 `Db::cas_save_job_as_new_run(任务, 读到的状态, 读到的代次)`，在一个
  `BEGIN IMMEDIATE` 事务里比对 `status_json` 和 `run_generation`，对得上才整行落库并把代次加一。
  `relaunch_in_place` 多一个参数 `RunFence`（调用方在把快照改成 queued 之前 `RunFence::of(&读到的任务)`）。
  只比状态不够（前一个可能已经跑完，又是同一个终态），所以带上代次；main 上已有的 `run_generation` 正好用上。
  写不进去时：库里是 queued/running → `409 job_active`（别人先开跑了）；还是终态但代次变了 → `409 stale_resolution`
  （读到的过期了，刷新再试）；行没了 → 404。前端对这两个原因已有中文提示（"任务还在跑""请刷新后再试"）。
- **清理放到落库成功之后，`rendered/` 不再删**：按 B14 的结论往 stage_retry 靠拢。完成判定只认 worker 发布的
  `output_pdf`（`reset_render_artifacts` 已清空），删 `rendered/` 防的"旧 PDF 被当成新产物"本来就走不通。
  `-ocr` 子任务在 `relaunch_in_place` 返回 Ok（已经发射）之后再删：渲染不做 OCR，父任务指向它的链接
  `prepare_in_place_render_job` 已经断开，子任务用的是父任务的目录，开跑后删不影响新的一次运行。
- **上一份 PDF 挪开，而不是改 Python 原子写**：渲染写 PDF 的路径很多（fitz `save`、pikepdf、typst 编译、
  原地压缩，还有先 `unlink` 再写的），逐个改成"临时文件 + rename"要动整条渲染、还要重跑翻译测试。改成在 Rust
  这边：落库前把快照里的 `previous_output_pdf` 换成同目录的 `<名>.previous.pdf`，落库成功（确认轮到这一次）、
  发射之前 `rename` 过去。渲染要写的名字空出来，新文件是另建的，旧文件碰不到。顺序是先 CAS 再改名：
  先改名的话，输掉 CAS 的请求可能把赢家正在写的新文件挪走。代价：落库和改名之间有一个很短的窗口，读者看到的
  `previous_output_pdf` 还不存在（合并阅读 `.filter(is_file)` 跳过，和以前排队期间被删一样）；改名失败只记日志。
  只挪本任务目录下的文件；已经是 `.previous.pdf`（上次没跑成接回来的）不再挪。每个任务多留一份旧 PDF，删任务时随目录一起删。
- **没跑成时接回上一份放在落库层**：`Db::save_job` / `save_job_as_new_run` / `cas_save_job` 整行写之前调
  `storage_paths::restore_previous_output_pdf`：状态是 failed / canceled、`output_pdf` 为空、`previous_output_pdf`
  的文件还在，就把 `output_pdf` 指回它。落 failed / canceled 的地方有二十多处（runner 各阶段、API 取消、启动恢复、
  超时……），放在任何一处都会漏；放在读取时解析（`resolve_output_pdf` 回退）又照顾不到产物登记表、产物清单、
  就绪判断这些直接读 `output_pdf` 的地方。落库层本来就在这里规范化路径、生成产物登记，接回这一步和它们同类。
  `previous_output_pdf` 本身只有原地重跑会写，别的任务不受影响。

## 没做的

- 精修的一次性覆盖（`specs/refine-override.json`）仍然在 CAS 之前写：两个精修同时来，后到的那个会先覆盖前一个的
  覆盖文件再被 409 拒绝。拒绝时不再删它（原因是 `job_active` 时那份可能正被前一次运行读），但内容已经是后到者的。
  要彻底修得把写覆盖挪到 CAS 之后、发射之前，`relaunch_in_place` 得接一个"落库后、发射前"的钩子，另开分支。
- 合并阅读只在排队期间用 `previous_output_pdf`，运行期间不用。现在上一份不会被改写了，运行期间也可以用，
  但这是阅读的产品选择，不在这次范围里。
