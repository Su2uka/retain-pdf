# 访问控制查登记表实现记录

> 日期：2026-10-17
> 分支：`refactor/access-from-registry`（接在 `refactor/endpoint-registry` 后面）
> 方案：[接口登记表](./20261017-接口登记表.md)的第二个分支

## 做了什么

多用户模式下"网站账号能不能用这个接口"，原来是账号包 `access.rs` 的 `route_policy` 按地址前缀判断：
- `SIGNED_FAMILIES` 里列出能用的前缀；
- 另有几组只给管理员、整组关闭的前缀和特例。

接口登记表里每条已经写了谁能用。上一个分支有测试核对过：223 条和前缀判断一条不差。这次改成直接查登记表：

- rust_api 的 `app/endpoints.rs` 新加 `route_policy(方法, 路由模板)`，第一次调用时把全部登记表收成查找表：
  - 方法和地址都登记过：用登记表里写的；
  - 地址登记过、方法没登记：取这个地址各方法里最严的一种；
  - 地址没登记：当关闭。
- 中间件 `enforce_access` 查好策略，传给账号包的 `authorize_route(principal, policy, template, params)`。
  账号包只管"策略怎么执行"和"路径参数归属"，不再猜地址归哪类。
- 删掉账号包里的 `route_policy`、`SIGNED_FAMILIES` 和前缀特例。

## 有没有变严或变松

- 登记表里的 223 条和原来前缀判断的结果一样，上一个分支的测试逐条核过。
- 方法写错的请求（地址对、方法不对）：
  - axum 会回 405，但访问控制的中间件挂在路由上，会先跑一遍；
  - 如果按"没登记就关闭"处理，网站账号会拿到 404 而不是 405；
  - 所以这种情况取这个地址各方法里最严的策略。原来按地址前缀判断时，同一个地址不同方法本来就是同一种策略，结果和原来一样。
- 地址也没登记的请求到不了这里：axum 没匹配到路由，就不会跑路由上的中间件，直接回 404。
- 原来账号包里那组策略单测搬到 rust_api 的 `api_tests/route_manifest.rs`，用例和期望结果一条没改，现在对着登记表跑。
  另外加了两条方法写错的：`DELETE /api/v1/jobs` 判成登录可用（回 405），`GET /api/v1/fonts/upload` 判成只给管理员。

## 测试

- `route_policies_come_from_the_registry`：搬过来的用例。
- `route_manifest_matches_snapshot`：接口清单的"谁能用"一列直接来自登记表，`docs/routes.txt` 没变。
- 多用户的隔离、管理后台、账号测试照常通过。
