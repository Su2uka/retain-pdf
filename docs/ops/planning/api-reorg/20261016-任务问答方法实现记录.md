# 任务问答方法实现记录

> 日期：2026-10-16
> 分支：`refactor/job-questions`
> 方案：[模块化单体拆包规划](./20261015-模块化单体拆包规划.md) 第 5 节第 4 条、第 6 节第 6 步"任务结构收成'问答'方法，加检查防止退回去"

## 原来的样子

任务提交时的完整请求（`job.request_payload`）字段多、层次深，到处一路点进去直接读：

- `job.request_payload.source.artifact_job_id.trim().is_empty()`：判断是不是复用了别的任务的 OCR；
- `job.request_payload.translation.execution_connection.is_some()`：判断翻译走不走 Rust 模型执行器。

rust_api 的非测试代码里一共 **29 个文件、101 处**这样写，账号、书库、文件、服务商这几个领域都有。
拆成包以后，每个包都得知道请求的内部结构，改一个字段牵动一片。

## 现在的样子

**问答方法**：`retain-core` 新加了 `models/job/questions.rs`，在 `JobRecord` 上提供"问题"方法。
`JobSnapshot` 也能直接调用，因为它会自动转成 `JobRecord`。

| 方法 | 回答 |
|---|---|
| `source_job_id()` | 用的源任务（复用 OCR，或者原地重渲染时是它自己），没有是 `None` |
| `source_upload_id()`、`source_url()` | 上传编号、原文地址（原样） |
| `has_stored_source()` | 原文是存下来的上传或网址，可以从头再跑 |
| `requested_workflow()` | 提交时请求的 workflow |
| `ocr_language()`、`ocr_page_ranges()`、`ocr_options()` | OCR 语言、请求的页码范围、整份 OCR 设置 |
| `translation_model()`、`translation_page_window()`、`translation_page_list()` | 模型名、本地页码窗口、只翻哪些页 |
| `inline_translation_api_key()`、`translation_credential_ref()`、`credential_refs()` | 直接带来的密钥、翻译凭据、全部凭据编号 |
| `model_connection()`、`uses_model_executor()`、`matches_frozen_translation()` | Rust 模型执行器的连接、是否走执行器、连接是否和冻结的设置一致 |
| `render_options()`、`typst_font_family()`、`renders_after_translation()` | 整份排版设置、字体、翻译完是否接着排版 |

- 23 个文件里的 43 处读取，都改成调用这些方法。
- 改完 rust_api 少了约 60 行，例如：
  - 删凭据时收集凭据编号的 12 行，变成一行 `job.credential_refs()`；
  - 检查连接和冻结设置是否一致的 4 个条件，变成 `job.matches_frozen_translation(&profile)`。
- 方法配了 4 个单测。

**只有 6 个模块还直接动字段**，它们都在生成或改写请求：
- 建任务时处理凭据：`lifecycle/creation/ocr_credentials.rs`；
- 重跑：`actions/rerun.rs`；
- 重试阶段：`actions/stage_retry*.rs`，共 3 个文件；
- 合并阅读的虚拟任务：`job_loading/merged.rs`。

**防止退回去**：`check_architecture.py` 新加 `check_request_payload_access`，配了 4 个单测，架构检查的单测一共 62 个。
- rust_api 的非测试代码里，除了冻结名单 `KNOWN_REQUEST_PAYLOAD_WRITERS` 里的这 6 个文件，出现
  `request_payload.<字段>` 就报错，换行写的也算。
- 名单只许减不许加；某个文件不再直接动字段了还留在名单里，也报错。
- 整份请求原样传给别的函数不算。例如脱敏用的 `sensitive_values(&job.request_payload)`、对外投影
  `public_request_payload(...)`，这些不依赖具体字段。
- 测试代码不管：测试要自己搭请求。
- 往真实代码里故意写了一处直接读字段，检查会报。

## 和原来不完全一样的地方

下面 3 处原来用的是原样的源任务编号，现在用 `source_job_id()`，也就是去掉首尾空白、空的当作没有：
- 预扣页数；
- 译文修改记录里的 `source_job_id`；
- 发射时找书。

**结果不变**：建任务时 `ResolvedJobSpec::from_input` 已经把这个编号的空白去掉了；重跑设的是任务编号，
本身不带空白。三份快照都没变。

## 没管的

- **用别名绕过去的写法**：例如 `let request = &mut job.request_payload; request.workflow`，检查认不出来。
  - 现在只有发射时换平台模型这一处（`lifecycle/launcher.rs` 的 `apply_platform_models`），它本来就是在改写请求。
  - 有别名、但只是在读的写法，这次都改成了方法：页数预扣、模型连接核对、合并阅读的页码。
- **rust_api 以外的包**：
  - 任务运行器（`retain-jobs`）按请求拼流水线命令，本来就要读全部字段；
  - 数据库（`retain-db`）的检索和写入、`retain-core` 自己的对外投影，和请求的定义在同一层或更下层。
  - 这些不在拆包的范围里，这次没动。
- **生成和改写请求的模块**：例如清掉密钥、换凭据，这些写法还散在上面 6 个文件里。
  要收成"改写"方法（比如 `strip_inline_secrets()`），可以以后再做。名单已经冻结，不会再变多。
