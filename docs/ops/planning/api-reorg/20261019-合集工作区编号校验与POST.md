# 合集工作区：编号校验、404、POST 新地址、删合集清目录

分支 `fix/collection-workspace-path`。对应[书库接口审计](./20261019-书库接口审计.md)第一节第 1 条、第二节第 5 条（明细 A6），
以及删留里"合集 agent 工作区"那一行；顺带把[正确性与状态一致性审计](./20261019-正确性与状态一致性审计.md)明细 2 #7
（合集工作区链到在跑的半成品）剩下的一半修掉。只动后端；前端要改一处请求方法，见
[交接](../../../core/frontend/backend-changes-handoff.md)。

## 问题

1. `collection_workspace_dir` 把路径参数 `collection_id` 原样 `join` 进 `<data_root>/collections/`。axum 会把路径参数百分号解码，
   `GET /api/v1/collections/%2E%2E/agent-workspace` 得到 `..`，拼成 `<data_root>/collections/../ai`，对数据目录下的 `ai/books`
   做 `remove_dir_all` 再重建、写一份 `collection.v1.json`。实测：在未改的代码上，测试里预先放在 `<data_root>/ai/books/keep.txt`
   的诱饵文件被删掉了。AI 服务读工作区那一侧（`backend/ai/retainpdf_ai/fx_workspace.py`）早就挡了，Rust 写的这一侧没挡。
2. 合集不存在也返回 200，并建出 `collections/<id>/ai/`。
3. 物化工作区（删目录、建链接、写清单）挂在 GET 上。
4. 删合集不清 `data/collections/<id>/`，目录永远留着。
5. 成员书只读前 200 本（`MAX_BOOKS`），多出来的悄悄少掉；"还没有可读译文"的书退回书卡的 `active_job_id`，
   那个任务可能还在跑，链过去是半成品目录。

## 决定

- **编号只认生成器的形状**：`new_collection_id` 生成的是 `col-` + `build_job_id()`，即 `col-` + 14 位数字时间 + `-` + 6 位小写十六进制
  （`col-20260917055937-8f4844`），从 2026-07 加合集起就是这个格式（`build_job_id` 没改过）。工作区的编号不是这个形状就 400
  `invalid collection_id: …`，不拼路径、不碰磁盘。审计建议的是宽一点的 `^col-[A-Za-z0-9_-]+$`，这里取更严的：
  编号只从生成器来，同步、备份恢复带过来的也是别的设备上同一个生成器生成的，没有别的形状要兼容；
  宽的那条已经挡住了 `.` 和 `/`，严的再挡掉"看着像编号的任意字符串"。
  校验放在书库包 `collection_workspace.rs` 的 `collection_dir`，拼目录只有这一个入口；
  `ensure_collection_workspace` 和删合集清目录都走它。别的接口（改名、加书、删书）只查数据库，不拼路径，不加校验，状态码不变。
- **顺序是 400 → 404 → 碰磁盘**：编号不合格 400；合格但数据库里没有这个合集 404 `collection not found: …`，不建目录。
- **POST 新地址，GET 标旧地址**：`POST /api/v1/collections/:collection_id/agent-workspace` 和 GET 同一个处理函数，多用户下照旧 `closed`。
  登记表原来只支持"换地址"（旧地址和新地址方法相同），这次是同一地址换方法：GET 那行行尾写
  `old "/api/v1/collections/:collection_id/agent-workspace"`（指向自己的地址）。登记表测试 `endpoint_registry_is_complete`
  和接口目录生成放宽成"方法相同，或者地址相同、只换方法"，目录里旧地址那栏带上方法（`GET /collections/…`）。
  写法记在 `backend/api/src/app/endpoints.rs` 的 `endpoints!` 文档里。前端改用 POST 以后删掉 GET。
- **删合集清目录**：`delete_collection` 删掉数据库行之后 `remove_dir_all(data/collections/<id>/)`，整个目录都清（包括 agent 在 `ai/`
  下留的东西——目录是这个合集专属的，合集没了就没人能再打开它）。目录不存在不算错；别的错误只 `eprintln!` 记日志，删除照样返回 200。
  编号形状不对的不去拼路径（这种编号本来也删不到数据库行，先 404 了）。子合集（`parent_id` 是 `ON DELETE SET NULL`）不跟着删，目录也不动。
- **超过上限进 `skipped`**：成员书分页读完，按原来的顺序（`added_at` 倒序）前 200 本进工作区，之后的每本写进 `skipped`，
  `reason` 是 `超过一次最多纳入 200 本的上限`。上限按成员书的顺序算，不是按"有译文的书"算：要按有译文的算就得对每本都解析阅读入口
  （可能现场生成合并目录），合集大的时候太慢。
- **没有可读译文直接进 `skipped`**：`reason` 是 `还没有可读的译文`，不再退回书卡的 `active_job_id`。
  原来退回那条路上的两个原因（`active_job 指向一个已经不存在的任务`、`任务没有产物目录`）随之没了。`CollectionWorkspaceSkip.reason`
  从 `&'static str` 改成 `String`，JSON 形状不变。

## 没做的

- 删合集清目录如果失败（权限之类），目录会留下；之后同一编号不会再被生成（时间戳 + 随机数），留下的只是垃圾，不影响功能。没做后台清扫。
- Python 侧 `_SAFE_COLLECTION_ID` 的正则比 Rust 宽，没改（它还要 `resolve()` 后仍在 `collections/` 下、清单文件存在，挡得住）。
