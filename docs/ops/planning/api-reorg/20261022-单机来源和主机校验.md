# 单机来源和主机校验

2026-10-22。分支 `fix/single-mode-origin-checks`。来自 [设置与平台接口审计](./20261022-设置与平台接口审计.md) 第三节 6，
用户在 [删留](./20261022-设置与平台接口删留.md) 里定"收紧"。

## 问题

- 单机模式 `cors_layer` 是 `CorsLayer::permissive()`，开发栈默认 key `dev-local-key` 是公开的：任意网页都能带着它跨源调本机 API、
  读返回（凭据、本地 OCR 命令这些审计第一节的问题因此从"本机程序能做"放大成"任意网页能做"）。
- 更严重的是助手终端 WebSocket（`/api/v1/ai/terminal?api_key=…`）：浏览器不对 WebSocket 做 CORS，处理函数只看 key，
  `dev.sh` 又开着 `RETAIN_AI_FX_SHELL_MODE=1`——任意网页都能连上去执行命令。AI 服务自己的 `/v1/fx/terminal`（41100，回环）
  同样只看 key，网页也能直连。
- CORS 防不住 DNS rebinding：攻击者的域名解析到 `127.0.0.1` 后，页面和 API 同源，带 key 的请求不需要 CORS。

## 定下来的做法

### 一份来源名单，CORS 和终端共用

`OriginPolicyConfig::allows_origin`（`backend/packages/retainpdf-core/src/config/origin_policy.rs`）只认 `http(s)://host[:port]`，三类放行：

1. 回环：`localhost`、`127.0.0.0/8`、`[::1]`，端口、http/https 不限。
2. 主机和这次请求的 `Host` 或 `X-Forwarded-Host` 相同、只是端口不同。`X-Forwarded-Host` 可以信：跨源页面设它就要先发预检，
   预检里只有头的名字没有值，过不了；WebSocket 和简单请求设不了自定义头。
3. `RUST_API_ALLOWED_ORIGINS` 列出的来源（逗号分隔，转小写、去末尾 `/` 后精确比较，不支持通配；`null` 丢掉）。

`null`、`file://`、扩展页、带路径或用户名的一律不认。

- **CORS**：`AllowOrigin::predicate` 调它。不在名单里**只是不回 CORS 头，不拒**：`serve_same_origin.py` 转发时 `Host` 变成
  `127.0.0.1:41000`、页面的 `Origin`（例如 `http://192.168.x.x:40001`）原样转发，浏览器看来是同源，拒了反而打不开。方法、
  请求头回显（来源已经收紧），响应头 `ExposeHeaders::any()`（和以前一样，下载要读 `Content-Disposition`、`Content-Range`、`ETag`），
  不带 credentials（单机前端不带）。
- **终端**：`/api/v1/ai/terminal` 握手时带 `Origin` 且不在名单里就 403（统一信封，`request origin is not allowed`），在看 key 之前；
  日志记来源不记 key。不带 `Origin` 的是命令行客户端，照旧只看 key。
- **AI 服务终端**：`/v1/fx/terminal` 带 `Origin` 一律拒（握手前关，uvicorn 回 403）。浏览器从不直连它，合法调用方只有 rust_api 的
  代理（tungstenite 不发 `Origin`）和命令行，不用在 Python 那边再维护一份名单。

### `Host` 校验（防 DNS rebinding）

`auth::reject_foreign_host` 挂在完整 API 和第二个端口所有路由外面，只在单机模式：

- 后端监听回环地址（`RUST_API_BIND_HOST` 是 `127.0.0.0/8` 或 `::1`，桌面版固定 `127.0.0.1`）时，`Host` 必须是 `localhost`、
  IP 字面量或 `RUST_API_ALLOWED_HOSTS` 里的主机名（去端口、转小写比较），否则 403 `request host is not allowed`。
  rebinding 的 `Host` 一定是攻击者的域名，不会是 IP 字面量，所以 IP 字面量放行（局域网、容器 IP 探测都不受影响）。
- 监听非回环地址（Docker 的 `0.0.0.0`、换了 key 的开发栈；`dev_stack` 已经不许这时用默认 key）时，只有配了
  `RUST_API_ALLOWED_HOSTS` 才查。没配不查：已有的域名部署升级后不能打不开。
- 只看 `Host`（HTTP/2 没有时看 `:authority`），不看 `X-Forwarded-Host`：rebinding 的页面和 API 同源，能随便设它。
- 没有 `Host` 的请求放行：rebinding 一定经过浏览器，浏览器一定带 `Host`。
- 用 403 不用 421：沿用统一信封里已有的 `FORBIDDEN`（多用户的 Cookie 来源检查也是 403），而且 421 的本义是"这条连接不该处理这个主机"，有的浏览器收到会换一条连接重发。

**`/health` 不豁免。** 查过所有探测：桌面壳 `backend-http.js`、`port-occupant.js` 打 `http://127.0.0.1:<端口>/health`，`dev.sh`
打 `http://127.0.0.1:$API_PORT/health`，`dev_stack.py` 打 `http://127.0.0.1:<端口>/ready`（`0.0.0.0` 换成 `127.0.0.1`），
Docker 健康检查打 `http://127.0.0.1:41000/ready` 和 web 容器的 `http://127.0.0.1/health`（NGINX 转发 `Host: 127.0.0.1`）。
`Host` 都是 IP 字面量，用不着豁免；不豁免也少一个 rebinding 能读的口子。

### 配置

| 变量 | 默认 | 作用 |
|---|---|---|
| `RUST_API_ALLOWED_ORIGINS` | 空 | 额外放行的网页来源。页面和 API 不同主机时才要配 |
| `RUST_API_ALLOWED_HOSTS` | 空 | 额外放行的 `Host` 主机名。回环监听 + 反向代理把域名放进 `Host` 时必须配；非回环监听时配了才查 |

起名跟 `RUST_API_BIND_HOST` 一族：是单机服务器的监听面配置。多用户模式的跨域名单 `RETAIN_ALLOWED_ORIGINS` 语义不同
（带凭据、管 Cookie 写请求），不合并，互不影响。

## 前端要配合的

桌面壳网关起不来时退回 `file://`。实测（Electron 44.4.3）`fetch` 不带 `Origin` 不受影响，终端 WebSocket 握手带 `Origin: file://`，
不放行（双击打开的本地 HTML 也是这个来源）。前端已在 `fix/desktop-gateway-origin` 做完：网关端口用尽时退到端口 0，退回 `file://` 时
用 `webRequest.onBeforeSendHeaders` 把发往本机 `apiBase` 的 `Origin` 改成 `http://127.0.0.1`。详见
[交接文档](../../../core/frontend/backend-changes-handoff.md) 末尾一节。

## 没做的

- AI 服务（41100）的 HTTP 接口没有 `Host` 校验。它没开 CORS，跨源网页读不到返回；但 DNS rebinding 到 41100 时页面同源，
  能带公开的默认 key 调它的 HTTP 接口（问答、会话）。终端那条已经靠"带 Origin 就拒"堵上，HTTP 的要另开一项。
- 多用户模式不动。
