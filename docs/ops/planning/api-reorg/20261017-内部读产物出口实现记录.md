# 内部读产物出口实现记录

> 日期：2026-10-17
> 分支：`refactor/stored-artifact-exit`（接在 `main` 63502203 后面）
> 起因：[文件出口实现记录](./20261015-文件出口实现记录.md)的"还没做"第 2 条：冻结名单里的 12 个文件逐个改成调出口

## 做了什么

`check_artifact_path_ownership` 规定产物路径只许出口模块拼。2026-10-15 有 12 个文件还直接调 `storage_paths::resolve_*`，
冻结在 `KNOWN_ARTIFACT_PATH_READERS` 里，只许减不许加。这次全部改完，名单清空。

**为什么不直接改成调 `open`**：对外下载的出口 `JobDownloads::open` 会做三件事：
- 按需生成派生产物（对照版、Word、预览图）；
- 把 PDF 线性化；
- 带上下载文件名。

内部读产物一件都用不上。比如阅读区块要读翻译清单，合并阅读要把译文 PDF 的路径交给 Python。所以加了一个只回答"这份产物放在哪"的窄出口：

```rust
// 任务包 files/downloads/stored.rs，门面导出
pub enum StoredFile {
    SourcePdf, TranslatedPdf, OcrMarkdown, OcrImagesDir,
    NormalizedDocument, NormalizationReport,
    TranslationManifest, TranslationDebugIndex, TranslationRequestJournal,
}
pub fn stored_path(job: &JobSnapshot, data_root: &Path, file: StoredFile) -> Option<PathBuf>
```

- 它放在下载模块 `files/downloads/` 下，本来就是出口模块，规则不用另开口子。
- 产物名到存放位置的对应只在这里写一次。别处只说要哪个产物，不用知道 `resolve_*` 和存放规则。
  以后流水线改输出布局，改 `storage_paths` 和这一个文件就够了。
- **语义不变**：返回的就是原来那个 `resolve_*` 的结果。"文件在不在、是不是文件"照旧由调用方判断，原来怎么过滤还怎么过滤。
  有的地方原来只看路径能不能解析出来、不看文件在不在（比如封面地址只要原文登记过就给），改成判断存在会改变行为，所以这次一律不动。

改了的 12 个文件，每处都是 `resolve_X(job, data_root)` → `stored_path(job, data_root, StoredFile::X)`：

## 架构检查

- `KNOWN_ARTIFACT_PATH_READERS` 改成空集合。照"服务之间的环"那条的先例：
  - 名单留着，"只许减不许加"的逻辑也留着；
  - 加单测断言它是空的，并且 `stored.rs` 可以拼路径。
- 报错提示改成先指向 `stored_path`，再说下载的 `open` 和文件包的产物清单。
- 往真实代码里故意写违规：任务包的 `readiness.rs`、书库包的 `collections.rs` 直接调 `resolve_*`，两处都报了。
- 测试代码里照旧可以直接用 `resolve_*`，规则本来就不查测试。

## 怎么保证行为没变

- 函数体只换了调用的入口，参数、过滤条件、错误处理一字没改；
- 三份快照都没变，测试总数不变（见开发记录）。
