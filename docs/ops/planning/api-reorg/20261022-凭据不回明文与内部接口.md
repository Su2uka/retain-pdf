## 改了什么

| 问题 | 改法 | 对外 |
|---|---|---|
| `GET /credentials?include_values=true` 回凭据库里全部密钥原文（含建任务导入的 OCR、翻译 Key），没有调用方 | 删掉这个分支和视图里的 `secret` 字段；`ListCredentialQuery` 变成空结构加 `deny_unknown_fields` | 带 `include_values`（或任何查询参数）200 → 400 `unknown field` |
| 凭据 5 个处理函数在异步线程上做文件 IO、进程内锁 + `flock`、`fsync`，删除时数 SQLite 引用 | `routes/common/credentials.rs` 的 `run_credentials_blocking`：只带走 `Arc<Db>` 和数据目录，`spawn_blocking` 里跑 | 不变 |
| 凭据的三种 409 没有 `error.details.reason` | `CredentialReference` 的响应按 `error.code` 加小写 `reason`：`credential_in_use`、`credential_revision_conflict`、`credential_vault_revision_conflict` | 只增；其余凭据错误仍是 `details: {}` |
| `PUT` 能改凭据的 `kind`：被任务引用的凭据换了种类，重试时 `CREDENTIAL_KIND_MISMATCH` | 规范化后和现在的种类不同就 400；带同样的种类照常（前端更新时整份载荷带着 `kind`） | 换种类 200 → 400 |
| 文档没写"建任务导入的副本什么时候清" | `api-spec/credentials.md` 补一节 | — |
| 模型执行器内部接口用 axum 原生 `Path`/`Json`：写错时回纯文本 400/415/422，且先解析请求体再验令牌 | 换 `ApiPath`；`submit` 先收 `Bytes`（读取失败也先不报），验令牌（格式 + 会话）之后再 `parse_json_body` | 报错都走统一信封；没有有效令牌一律 401，不再告诉调用方哪个字段写错了；不认识的字段 422 → 400（和全站规矩一致） |
| `POST /internal/model/jobs/:job_id/capability` 没有生产调用方 | 删路由、`ModelRequestsApi::issue`、只给它用的 `JobSnapshot::matches_frozen_translation`；登记表去掉 `launcher` 那张表 | 404 |
| 架构检查漏掉嵌套写法的原生提取器（`use axum::{extract::{Path, ..}}`，上面那个文件就是这样漏的） | `check_route_input_extractors` 改成扫所有 `extract::{…}`，加单测 | — |
| `/ready` 503 时信封仍是 `code: 0`、`message: "ok"` | 不就绪时 `code: 50300`、`message: "not ready"`、带 `error`（`SERVICE_UNAVAILABLE`，`details.reasons`），`data` 照旧给整份就绪视图 | 503 的信封变了，状态码、`data` 不变 |
| `/health` 读库失败时计数当 0，看着像空闲 | `queue_depth`、`running_jobs` 改 `Option`，读不出来是 `null` | 只在读库失败时从 `0` 变 `null` |
| `/health`、`/ready` 返回字段没文档；"只有 `/health` 免密钥"的说法不全 | `runtime-and-events.md`、`docs/core/api/index.md` 补字段；五处认证说明改成列全：`/health`、`/ready`、登录注册三个、模型执行器三个（凭能力令牌） | — |

## 取舍

1. **`include_values` 直接 400，不是"留着字段但忽略"。** 审计给了两个选项。忽略的话，旧脚本以为自己拿到了值、实际是空，
   更难查；而且 `git grep` 整个仓库（`frontend/` 含 `dist`、`frontend/desktop`、`backend/ai`、`backend/cli`、`ops/`、`tests/`）
   除了 api_tests 没有调用方传它，前端 2026-09-16 起就不带了。400 的报错带字段名，一眼看得出。
2. **`PUT` 带同样的 `kind` 不算改。** 前端 `credential-vault.ts` 的更新把整份载荷（含 `kind`）发给 `PUT`，
   一律拒绝 `kind` 字段会误伤；比较前按 `validate_kind` 规范化（去空白、转小写）。顺序是没有这条 404 → 换种类 400 →
   凭据库修订号 409 → 这条的修订号 409，所以凭据库修订号的检查从 `mutate_vault` 挪进了更新的闭包（"先看请求写没写对，再看状态"）。
3. **`/ready` 改信封但留着 `data`。** 审计建议信封保持、只写文档，理由是 CLI `context.rs:157` 读 `data`。
   这里两头都顾：`code`、`message`、`error` 按错误约定给，`data` 仍是整份就绪视图，读 `data` 的写法（CLI、
   `tests/e2e/agent/agent_live/stack.py` 读 `data.status`）不用改。核对过按状态码判断的：开发栈 `dev_stack.py`
   `wait_until_ready` 等 2xx、Docker `curl -fsS`、`agent_e2e.py` 看 HTTP 状态码、桌面端只调 `/health` 看 `data.status === "up"`、
   CI 的镜像冒烟（`build-docker-images.yml`）`curl --fail` 打 `/health`、前端 `shell-smoke.test.mjs` 看 2xx；没有谁按信封的 `code` 判断就绪。
4. **`/health` 读库失败时 `status` 不跟着变。** 计数读不出来但 ping 通时仍是 `up`：桌面端靠 `status === "up"` 认端口上是不是自己的后端，
   改了会让一张坏表把桌面壳卡在"端口被占用"。计数给 `null` 已经能让看计数的人知道"读不出来"。
5. **Python 客户端没改。** `rust_executor.py` 只按状态码分支（401/403、409、其余非 2xx 当暂时不可用重试），不读报错的形状，
   信封化对它没有影响；`capability` 它本来就不调。审计第 11 条另提了"对 400 直接报错、别重试到期限"，不在这次范围，
   改它要动翻译包，单开。
6. **令牌验两次。** 处理函数先 `authorize`（只验令牌、不查任务），解析完请求体后 `submit` 里照旧再验一次再查任务：
   多一次按哈希查会话表，换来门面方法单独调用时语义不变。

## 测试

- 凭据：`credential_api_persists_only_safe_metadata_in_responses`（原来钉"能拿回明文"，改成钉列表不含 `secret`、

  修订号和删除的两条加了 reason 断言；底座包 `credential_conflicts_carry_a_lowercase_reason`（新）。
- 模型执行器：`http_worker_checks_the_capability_before_reading_the_body`、`http_worker_body_errors_use_the_api_error_envelope`、
  `capability_issuance_route_is_gone`、`http_submit_on_a_corrupt_job_is_500_without_leaking`（新）；只测 `issue` 的三条删了，
  其余测试的令牌改成直接找执行器要（和运行时一样）；`http_worker_routes_accept_only_their_own_job_capability`（原
  `http_routes_separate_launcher_and_worker_authority`）。
- 健康：`not_ready_is_a_503_with_an_error_envelope_and_the_readiness_view`、`health_reports_null_counts_when_the_jobs_table_cannot_be_read`（新，顺带钉住 `/health` 的 8 个键）。
- 架构检查：`test_route_raw_extractors_are_caught_in_nested_axum_imports`（新）。
- 新测试在没改的代码上跑过：9 条红（临时 worktree，跑完删了），改后全绿。

## 没做的

- 单机 `CorsLayer::permissive()` 加公开的默认 key 是这一类问题的放大器，用户定单独开一项收紧（删留文档最后一行）。
- 服务商校验接口的 `deny_unknown_fields`、`/providers/ocr` 的阻塞读配置归 `fix/provider-probes`、`fix/ocr-server-owned-options`。
- 前端死代码（`credentials.ts` 的 `includeValues`、`secret?`）写进了交接，由前端删。
