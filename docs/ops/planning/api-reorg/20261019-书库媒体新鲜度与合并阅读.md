# 书的图跟着原文走、合并阅读按最后使用清理、页数缓存、合并只生成一次

2026-10-19，分支 `fix/library-media-freshness`。修的是 [书库接口审计](./20261019-书库接口审计.md)
第一节的第 4、7、8 条（明细 B 组的 1、2、3、8、10）。

## 问题

- **B1**：书的原文会变。单机下 Agent 文档操作提交以后，书的原文换成新版本的文件（`version-upload-<版本>`），书的编号
  （第一次上传时的指纹）不变。封面、缩略图只看文件在不在，旧图永远不更新；原文页预览服务端会重渲染，但响应头
  `private, max-age=31536000, immutable` 让浏览器一年不来问。代码注释和文档都写着「书编号就是原文指纹，地址内容不变」。
- **B2**：`merge/build.rs` 的 `prune_stale` 按目录修改时间（= 生成时间）删超过 24 小时的旧合并目录，不看有没有人还在读。
  删掉以后旧虚拟 id 的读请求是普通 404 `job not found`，和「任务被删了」分不出来。
- **B3**：`/reading` 和 `/translation-coverage` 每次请求都把原文和每个任务的译文 PDF 用 lopdf 整份载入，只为数页数。
- **B8**：覆盖用 `documents.page_count`，阅读入口数原文 PDF；老数据没记页数（0）时覆盖说「0 页」，阅读器照常打开整本合并。
- **B10**：`/reading` 里生成合并目录不排队、不去重，同一本书同时打开两次各生成一遍。

## 决定

1. **封面、缩略图按原文判断新鲜**：和页预览用同一套 `cached_output_is_fresh`（生成前记下原文的戳：路径、大小、修改时间、inode，
   见 [派生产物超时与新鲜度](./20261019-派生产物超时与新鲜度.md)）。换了版本就是换了路径，记录对不上就重新渲染；这次改动之前
   生成的封面没有记录，按修改时间比（新版本文件比旧封面新）。任务自己的封面（`/jobs/:id/files/…`）走同一个函数，任务的原文
   不会变，不受影响。
2. **缓存头选 `private, max-age=0, must-revalidate` 加已有的 `ETag` / `Last-Modified`**（`stream_file` 本来就给，没变回 304），
   封面、缩略图、原文页三个都是这个，和任务的译文页预览一致。没选「地址里带版本号、继续 `immutable`」：要前端改用后端给的地址
   （原文页 `answer-enhance.ts` 是手拼的），而且 `cover_url` 在任务包的展示层里拼、要查当前版本，改动面大。代价：书架每次渲染
   每张封面多一次条件请求（304、不传图），服务端只做一次查库和几次 `stat`。原文 PDF 本身不设缓存头（前端读原文时自己带 `?version=`），没动。
3. **合并目录按最后一次被读清理**：每次按虚拟 id 读（`job_loading::load_virtual_job`）、每次 `/reading` 指到它，都更新目录里的
   `.last-used` 标记（最多 10 分钟写一次）；`prune_stale` 按「标记和目录修改时间取晚的」算年龄，超过 24 小时没人读才删；
   阅读入口现在指向的那个（刚生成或刚命中的）从不删。标记放在合并目录里面：跟着目录一起删，不在 `merged/` 下留孤儿文件。
   剩一个小窗口：清理判断完、删之前恰好有人读，这次读会 404 带 reason，客户端重新问一次就好。
4. **过期的虚拟 id 是 404 带 `error.details.reason = "merged_reading_expired"`**：id 格式对、合并目录（说明文件 `reading.json`）不在。
   `message` 照旧 `job not found: <id>`（只增 reason，旧客户端行为不变）。id 格式不对仍是不带 reason 的 404。生成到一半进程没了、
   说明文件没写上的目录也是这个 reason：下一次 `/reading` 会补写，客户端做的事一样。
5. **页数按文件戳缓存，一本书的页数只有一个来源**：新模块 `merge/page_count.rs`，进程内按 `(路径, 大小, 修改时间纳秒, inode)` 缓存
   PDF 页数（满 4096 条整个清掉）。一本书的页数 `book_page_count`：**原文 PDF 的实际页数为准**，读不出来才退回 `documents.page_count`。
   没选审计建议的「`documents.page_count` 优先」：阅读入口以前就数原文 PDF，合并按页拼原文，数据库里记错的页数（上传时数错）会拼错；
   有了缓存，数原文不再贵。覆盖在原文不在磁盘上时照常回（用记下的页数），阅读入口那时是 404，和以前一样。
   原文页预览的越界判断（`media.rs`，`page > documents.page_count` 直接 404）没改：那是 `/files` 清单 `pages.page_count` 同一份，
   版本提交时 `upsert_document_from_upload` 会一起更新它。
6. **同一份合并只生成一次，全进程最多同时生成 2 个**：`build.rs` 里按合并目录路径（书 + 指纹）单飞，后到的等它做完直接用；
   不同指纹超过 2 个排队。没用文件出口的 `DownloadGeneration`：它是异步的、结果类型是要回给客户端的文件，2 个名额和文件下载共用
   （一次合并两步各 120 秒，会把下载堵住）；合集工作区在阻塞线程里同步调合并，也要去重。等待在阻塞线程里（`spawn_blocking`），
   每步子进程有 120 秒时限，不会无限等。

## 对前端的影响

- 缓存头、封面重新生成：前端不用改。浏览器会自己带 `If-None-Match` 来问。
- `merged_reading_expired`：可选。阅读器现在拿到旧虚拟 id 的 404 会显示「任务不存在」；按 reason 自动重新问 `/reading` 换新 id
  能接着读。具体写在 [后端改动交接](../../../core/frontend/backend-changes-handoff.md) 最后一节。
- 页数、去重：接口形状没变；只有老数据 `documents.page_count = 0` 的书，覆盖的 `page_count`、`segments` 从 0 / 空变成实际页数。
