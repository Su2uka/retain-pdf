# 契约第 1a 期：已有端点补函数名

2026-10-22，分支 `contracts/client-names-phase1a`。接着 [契约端点加函数名和传输方式](./20261022-契约端点加函数名和传输方式.md)，
清单来自前端的「第 1 期接口清单」（`docs/ops/planning/api-client-codegen/20261022-第1期接口清单.md`，前端分支 `docs/api-client-codegen-phase1-list`，还没合）的 1a 部分：契约里已经有、前端在调、只缺 `client_name` 的 16 条。

## 做了什么

1. 16 条端点写上前端给的 `client_name`，`transport` 都是 `json`（方法、地址逐条对过，`route_manifest::contract_endpoints_are_registered` 照旧全绿）：
   - `job-status.v1`：`GET /jobs` → `listJobs`，`GET /jobs/:job_id` → `getJob`
   - `create-job.v1`：`POST /jobs` → `createJob`
   - `library-books.v1`：`DELETE /jobs/:job_id` → `deleteJob`
   - `job-data.v1`：`GET /jobs/:job_id/data` → `listJobDatasets`，`GET /jobs/:job_id/data/:dataset` → `getJobDataset`
   - `job-events.v2`：`GET /jobs/:job_id/progress/events` → `listJobEvents`
   - `reader-data.v1`：`files` → `listJobFiles`，`progress/layout` → `getLiveLayout`，`progress/pages/:page` → `getLivePage`，
     `reader/markdown` → `getReaderMarkdown`，`reader/metadata` → `getReaderMetadata`，`reader/regions` → `getReaderRegions`
   - `token-usage.v1`：`GET /usage` → `getUsageSummary`，`GET /documents/:document_id/usage` → `getDocumentUsage`，
     `GET /jobs/:job_id/reports/usage` → `getJobUsage`
2. 名单钉在 `contracts/tests/endpoint-client-names.test.mjs`。

## 前端问的三件事

1. **`GET /api/v1/jobs` 登记了两次**（`job-status.v1`、`library-books.v1`）。名字只写在 `job-status.v1`；`library-books.v1` 那条**留着**，
   写了 `note`。原因：生成的 `contracts/src/library-books.ts` 只导出端点 `input`/`query`/`output` 用得到的定义，删了这条，
   `JobListView`、`ListJobsQuery` 就不再从 `@retainpdf/contracts/library-books` 导出，前端已有的引用会断。两边的 Job 定义由
   `contracts/tests/job-definitions-parity.test.mjs` 锁成一致。以后前端都改从 `job-status` 引这两个类型了，再删这一条。
2. **`job-status.v1` 的 `ts_consumer`** 还写着已经没了的 `apps/web/src/js/job/types.ts`，改成 `@retainpdf/contracts/job-status :: JobListView` / `:: JobDetailView`。
3. **`progress/pages/:page` 的页码**：从 0 开始，和返回的 `page_idx` 同一个数（处理函数直接按 `u32` 读，不是非负整数时 400），写进这条的 `note`。

生成的 TS 类型没变（`client_name`、`note` 不进生成器）。1b 的 16 个新端点下一个分支做。
