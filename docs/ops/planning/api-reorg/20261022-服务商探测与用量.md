## 改了什么

### MinerU 校验丢了错误链（A3）

`classify_probe_error(err.to_string())` 只拿到最外层的 context「MinerU apply upload url failed」，Token 无效、过期、超时全落成
`provider_error`、还叫人稍后重试。改成和 Paddle 一样先在错误链里找：

1. `err.downcast_ref::<MineruResponseError>()`（anyhow 的 downcast 穿过 context 层）：拿它的 `info`，`Unauthorized` /
   `PermissionDenied` → `unauthorized`，`CredentialExpired` → `expired`，3xx → `redirected`，其余 `provider_error`；
2. 链里的 `reqwest::Error`：超时、连不上、中途断开 → `network_error`（超时的 summary 写"超时"）；
3. 都没有才退回原来的字符串判断，喂的是 `format!("{err:#}")`（完整的链）。

原来那几个手写字符串的测试留着（第 3 步还在用），另加走真实路径的：假 MinerU 服务器回 401（不带错误码）、200 + `A0202`、
200 + `A0211`，以及一个收下连接不回的服务器。没改之前这几个都是 `provider_error`，测试先红后绿。

### 超时不一致（A4）

前端 `frontend/packages/api/src/providers.ts` 对四个接口都只等 30 秒（`PROVIDER_PROBE_TIMEOUT_MS = 30_000`，`submitJson` 的
`AbortController`）；CLI 一直等。后端以前：MinerU 用正式任务的 `RUST_API_MINERU_REQUEST_TIMEOUT_SECS`（120 秒），Paddle 120 秒且
超时、连不上都重试 3 次（中间退避），对端挂起时最长 6 分钟多；翻译接口、余额 20 秒。

- 新的 `RUST_API_PROVIDER_PROBE_TIMEOUT_SECS`（默认 20 秒）四个接口共用，没设时认旧名 `RUST_API_DEEPSEEK_PROBE_TIMEOUT_SECS`；
  进 `ProviderRuntimeConfig.probe_timeout_secs`，`DeepSeekRuntimeConfig.probe_timeout_secs` 也读同一个值（多用户的平台设置在用）。
- 校验的 HTTP 客户端单独建（`ProbePolicy::http_client_builder`：连接超时、整体超时都是它），MinerU、Paddle 客户端加了
  `with_http_client` 构造函数接收它；`with_runtime`（正式任务）不变。
- Paddle 校验把 `request_retry_attempts` 设成 1，只试一次。
- 没有夹上限：运维要在慢网络上调大可以调，代价是网页端先显示"检测超时"，文档写明了。

### 跟随重定向（A5）

四个接口的客户端都设 `redirect::Policy::none()`（模型执行器早就这么做）。服务商回 3xx 时：

- 翻译接口、余额拿到的是 3xx 响应本身，给 `status: "redirected"`，`provider_message` 带 `Location`；
- MinerU、Paddle 的客户端把非 2xx 包成各自的错误类型，校验从里面读出 3xx，同样给 `redirected`（拿不到 `Location`）。

`redirected` 是新加的 `status` 值（`ok: false`、`retryable: false`、summary「… 返回了重定向（HTTP 302），请检查接口地址」）。
没有并进 `provider_error`：用户要做的是改地址，不是"稍后重试"。测试：一台假服务器对所有路径回 302 到第二台，第二台记下
收到的每个请求，六种探法（MinerU、Paddle、OpenAI、Anthropic、Anthropic 列模型、Responses）加余额都断言 `redirected`，
第二台一个请求都没收到；去掉 `Policy::none()` 这两个测试就红。

风险：默认的三个官方地址如果对探测的路径本身做了重定向，校验会从"能过"变成 `redirected`。没有实跑（不调用要鉴权的接口），
按各家文档这几个 API 地址不重定向。

### 不认识的字段（A8）

`MineruTokenValidationRequest`、`PaddleTokenValidationRequest`、`DeepSeekTokenValidationRequest` 加 `deny_unknown_fields`，
走 `ApiJson` 的统一 400 信封，`message` 带字段名。核对过的调用方：

| 调用方 | 接口 | 发的字段 |
|---|---|---|
| `frontend/web/src/app/home/composition/create-credentials.ts:118` | MinerU | `mineru_token` |
| 同上 `:123` | Paddle | `paddle_token`、`base_url`（写死官方地址） |
| `frontend/web/src/features/credentials/domain/validation.ts:192` | 翻译接口 | `api_key`、`base_url`、`model`、`api_protocol` |
| 同上 `:246` | 余额 | `api_key`、`base_url` |
| `backend/cli/src/cmd/setup.rs:52,56` | 翻译接口、余额 | `api_key`、`base_url`、`model`、`api_protocol`（余额也发这四个，都认） |
| `backend/cli/src/cmd/setup.rs:73-74` | MinerU、Paddle | `mineru_token` / `paddle_token` |

`frontend/desktop`、`backend/ai`、脚本里没有调用。`ListCredentialQuery` 归 `fix/credentials-no-plaintext`，这里没动。

### 返回结构（A9）

- Rust 类型 `MineruTokenValidationView` 改名 `ProviderProbeView`（三家共用），JSON 字段一个没变；
- `provider_message`、`operator_hint` 截到 500 个字符，超出加 `…`（`ProviderProbeView::bounded`，余额只截 `provider_message`）。
  核对时发现明细里说的"非 JSON 正文原样整段返回"不准：非 JSON 正文 `summarize_deepseek_error_payload` 返回 `None`；
  会整段返回的是"JSON 但没有 `error.message` / `message`"的正文，测试按这个写；
- 各家 `status` 的全集写进 [Provider 校验接口](../../../core/rust_api/08-Provider%20校验接口.md)，原来只写了 MinerU 的 5 个。
- **不加契约**：审计第四节定了契约放最后统一做。到时候写 `provider-probe.v1`，`status` 写成 `enum` 但说明"会加值"，
  前端的 `Promise<any>` 换成契约类型。

### 用量（A11）

`summarize` 里 `record.ts[..7]` 按字节切：台账的 `ts` 是原样的字符串，前 7 个字节切在多字节字符中间（例如 `2026-1月1日`）
就 panic，`spawn_blocking` 的 `JoinError` 变成 500「usage summary task failed」，整个用量页打不开，直到那行被删。

- 改成 `month_of(ts)`：`ts.get(..7)` 取不到、或不是 `\d{4}-\d{2}` 的形状（契约 `token-usage.v1` 的 `month` 本来就是这个 pattern）
  → 这一行照样计入总数、按阶段、按模型，只是不进 `by_month`；
- `first_at` / `last_at` 用同一个判断：以前非空就参与比较，`zzz` 这种怪值会成为 `last_at`，契约说的是 RFC 3339；
- 测试 `odd_timestamps_are_left_out_of_the_monthly_breakdown`：没改之前 panic 在 `mod.rs:314`。
- **全量扫盘先只记录**：每次 `GET /usage` 都遍历 `output/` 下每个任务目录、读台账和报告，没有缓存。任务数上去以后再加按目录
  修改时间的缓存（台账是追加写，目录 mtime 不一定变，要看台账文件本身的 mtime）。
- `docs/api/` 补了一页 [模型用量](../../../api/11-用量/01-模型用量.md)，链到契约。

### 本机模型服务没法校验（A13）

**拦截的代码和它保护的东西**：`provider_probe/url_policy.rs` 的 `validate_provider_base_url`，在发请求之前只看 `base_url`
的字面地址，拦 `localhost`、回环、私网、链路本地、`0.0.0.0`。四个校验接口的 `base_url` 是请求体里随便填的，探针会带着 Key
去请求它，再把服务商回复里的错误信息（`provider_message`）转回来。在多用户的网站上，填地址的是网站用户，拦截挡的是：

- SSRF：让服务器替用户去访问服务器所在内网、本机上的服务，并从 `provider_message` 读回一段内容；
- 云主机的元数据地址（`169.254.169.254`）；
- 平台设置里管理员测平台 Key 时，Key 被发到内网地址。

开关是 `RUST_API_ALLOW_PRIVATE_PROVIDER_URLS`（默认关），`ops/development/`、`frontend/desktop` 都没设，所以单机用户把翻译接到
`http://127.0.0.1:11434/v1`（Ollama）时，检测 400，前端显示网络错误；真正建任务又不检查 `translation.base_url`，能用。

**改成按部署模式**（`PrivateTargets`，在 `ProviderApiDeps::from_runtime(&ProviderRuntimeConfig, DeploymentMode)` 里定）：

| | 回环、私网 | 链路本地 |
|---|---|---|
| 单机（`AllowLocal`） | 放开 | 拦 |
| 多用户（`Block`） | 拦，和以前一样 | 拦 |
| 设了 `RUST_API_ALLOW_PRIVATE_PROVIDER_URLS=1`（`AllowAll`） | 放开 | 放开 |

- 单机为什么放开：调接口的就是这台机器的主人（单机只有一个本机用户，凭 `X-API-Key`），回环和私网就是他自己的机器和局域网；
  同样的人建任务时本来就能让翻译请求发到任意地址。
- 链路本地为什么还拦：正经的模型服务不会在 `169.254.x` / `fe80::` 上，单机版也可能装在云主机上，这一段只剩元数据地址的风险。
- 剩下的口子：单机 CORS 现在全放开、开发栈的 key 是公开的 `dev-local-key`（审计第三节 6），一个网页可以借校验接口去请求本机、
  局域网的服务。能做的有限：路径是固定的（`/chat/completions`、`/models`、`/responses`、`/messages`、MinerU
  `/api/v4/file-urls/batch`、Paddle `/api/v2/ocr/jobs/<随机>`），只回 JSON 里的错误信息且截到 500 字，不跟随重定向；
  而同一个 key 已经能做更多（建任务）。根上的修法是收紧单机 CORS（`fix/single-mode-origin-checks` 在做）。
- 多用户：校验接口行为不变（`Block`）。平台设置的"测一下"（`admin/platform/test`）只在多用户下用，写死按 `Block`，
  和以前一样；它也用上了短超时、不重试、不跟随重定向。"域名解析到内网不拦"（只看字面地址）没修：多用户已冻结，只记录；
  要修是连接前解析域名再判一次（或者给 reqwest 换一个检查解析结果的 resolver）。

## 对前端的影响

不用改代码：字段、地址都没变，界面本来就按 `ok` + `summary` 显示。

- `status` 多一个值 `redirected`（`ok: false`），界面不认识也会按 `summary` 显示；
- 单机下本机、内网的模型服务以前检测 400（前端显示网络错误），现在能正常检测；
- 拼错字段以前被忽略，现在 400（核对过前端发的字段都认，见上表）；
- 可以顺手改：`frontend/packages/api/src/providers.ts:4-6` 的注释写的是 `RUST_API_DEEPSEEK_PROBE_TIMEOUT_SECS`，
  现在是 `RUST_API_PROVIDER_PROBE_TIMEOUT_SECS`（四个接口共用，默认 20 秒）。
