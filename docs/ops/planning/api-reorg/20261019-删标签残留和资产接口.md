## 一、标签残留

标签 2026-09-26 已删（提交 `c3d44ff8`：`document_tags` 表不再建、`DocumentRecord.tags`、`ListDocumentsQuery.tag`、
`PatchDocumentInput.tags` 去掉），但下面几处还在发、读、写，全被静默忽略。

| 地方 | 改前 | 改后 |
|---|---|---|
| AI 服务 `list_documents` 工具（`backend/ai/retainpdf_ai/tools.py`） | 给模型的参数有 `tag`（"按标签过滤,可选"），描述写"标题、标签、阅读状态"；结果每条带 `"tags": null` | 去掉 `tag` 参数和结果里的 `tags`，描述改成"标题、页数、阅读状态" |
| AI 服务 `RustApiClient.list_documents`（`rust_client.py`） | 有 `tag` 形参，非空时发 `?tag=` | 去掉 |
| 登记表 `router/documents.rs` 书的 PATCH 说明 | 改书的信息（书名、标签、阅读状态……） | 改书的信息（书名、阅读状态）——`PatchDocumentInput` 现在只有这两个字段 |
| 文档 | `library-api.md` §1 写着 `tag=`、`tags[]`、`tags?`、"整体替换"语义，迁移路径写"拿到标签"；`docs/core/api/index.md`、`api-spec/jobs-document-history.md` 写 `total` 应用了 `tag` | 都删掉 |
| 测试 | `api_tests/library_data.rs` PATCH 书时还带 `"tags": [...]` | 去掉 |

Rust 里没有别的读写标签的代码（`git grep` 过：剩下的 `tag` 是 serde 的 `#[serde(tag = …)]`、WebDAV 解析 XML 标签、
合集工作区测试里一个叫 `tag` 的局部变量）。AI 服务里别的 `tags` 是 fx 模型目录里的能力标签（`fx_openai_bridge.py`），和书库无关。
AI 工具的描述和 schema 没有快照测试，不用重录；新加的测试 `test_list_documents_tool_has_no_tag_filter_or_tags_field` 钉住
schema、结果和发出的查询参数。

前端已在 `refactor/drop-document-tags` 改完（书列表只发 `limit`、`offset`、`reading_status`、`collection_id`、`q`；
PATCH 只发 `title`、`reading_status`），见[前端交接](../../../core/frontend/backend-changes-handoff.md)最新一节。

**没做的一步**：前端和 AI 都不发了以后，`ListDocumentsQuery`、`PatchDocumentInput` 加 `deny_unknown_fields`，
让书列表和 PATCH 拒绝不认识的字段（400，按[请求体不认识的字段 400](./20261019-任务接口规矩和删留.md) 的规矩）。

## 二、删 `POST /api/v1/assets`、`GET /api/v1/assets/:asset_id`

这两个接口给收藏截图用，收藏 2026-09 删掉以后没有调用方（`git grep` 前端、`backend/ai`、`backend/cli`、`scripts`、`ops`、测试：
只有一条测上传限额的 Rust 测试）。多用户下本来就是 `closed`。

  （文件留着，会话的处理函数还在里面，架构检查的白名单条目照旧有用）；
- 书库包 `retainpdf-library/src/assets.rs`（`store_asset`、`load_asset`、`AssetDownload`）、`api.rs` 的 `store_asset_view`、`load_asset_view`、

  `RUST_API_ASSET_ALLOWED_MIMES` 不再读；

### `assets` 表、同步、`data/assets/`：先留着

**决定**：这次不删表、不删目录，只是不再有代码往里写、从里读接口。理由：

1. 迁移是编号的（`database/retainpdf-db/src/db/schema/migrations/mod.rs`：已上线的条目不能改、不能删），`v02` 照旧会建
   `assets` 表、给 `favorites` 加 `asset_id` 列。删表只能新加一个 `v28 DROP TABLE`。
2. 删表要连同步一起动：`v19` 给 `assets` 挂了三个触发器写 `sync_dirty`，同步引擎把 `asset` 当一种实体
   （`db/sync.rs` 的 `SYNC_KINDS`、`SYNC_SEED_VERSIONS`、`entity_spec`，`sync/files.rs` 的 `SYNCED_ROOTS` 和按哈希找 `assets/` 下文件）。
   表没了而 `asset` 还在种类表里，开过同步的设备下一轮登记会因为表不存在出错；从种类表里拿掉，老版本设备发来的 `asset` 记录会被
   当成"新版本才有的种类"一直挂着（`engine.rs` 的 `consider`），本机 `sync_dirty`、`sync_entities` 里的 `asset` 行也要清。
3. 收藏同样是接口删了、表和同步种类留着（`favorites` 还在 `SYNC_KINDS` 里，`favorites.asset_id` 指向的就是这张表）。
   两张表一起退场更干净。
4. `data/assets/` 里是用户以前收藏的截图，启动时自动删用户文件不合适；现在没有代码会再建这个目录，同步照旧会带上已有的文件。

**以后单独做**（一个分支，收藏和资产一起）：新迁移删 `favorites`、`assets` 两张表（触发器跟着没），同步种类表、`entity_spec`、
`SYNCED_ROOTS` 去掉 `favorite`、`asset`，清本机 `sync_dirty` / `sync_entities` / 挂起记录里这两种，`consider` 对这两种已退场的种类直接丢弃
而不是挂起；`data/assets/` 要不要删、怎么提示用户，到时候问用户。

- 标签：前端在 `refactor/drop-document-tags` 已改完，后端这边只是不再在文档和说明里提；接口行为没变（`tag`、`tags` 照旧被忽略）。
