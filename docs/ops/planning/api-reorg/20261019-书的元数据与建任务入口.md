# 书的元数据建议与书上的建任务入口

> 日期：2026-10-19
> 分支：`fix/document-metadata-and-entries`
> 出处：[书库接口审计](./20261019-书库接口审计.md) 第一节 2、5、6、9（元数据部分），明细 C1、C2、C3、C4、C5、C7、C9、C10

## 改了什么

| 审计 | 问题 | 现在 |
|---|---|---|
| C1 | 生成建议在异步线程上整本解析 PDF（只为取 Info Title），把最多 256MB 的规范化 JSON 整份读进内存再建成 `Value` | 读文件的那段放进 `spawn_blocking`；PDF 只解析 trailer 指的那个 Info 对象（Info 压在对象流里、或直接写成字典时才退回整本解析，而且不留流内容；加密的 PDF 不取 Info Title）；规范化文档边读边算哈希、只留前 8 页，证据哈希和以前逐字节相同 |
| C9 | 建议生成在 `stored_path` 找不到时自己拼 `<任务目录>/ocr/normalized/document.v1.json` | 只调 `stored_path`；没登记规范化文档的任务当没有（复用 OCR、重试也是这么认的）。架构检查补一条：出口模块以外的字符串字面量里不许出现 `ocr/normalized`、`document.v1.json` |
| C2 | 同一本书换个文件名再传，自动命名永远不生效 | 「书名还是默认值」只看 `title_source == filename` 且没锁，数据库层守卫和视图层 `can_apply` 两处一起改；老数据见下 |
| C3 | apply 返回的书少 `source_pdf_url`、`cover_url`、`thumbnail_url` | 过 `with_document_media_urls`，和 GET / PATCH 一样 |
| C4、C10 | `/documents/:id/ocr` 强改 `workflow`、清 `artifact_job_id`/`source_url`；`/translate` 清 `source_url`；书的入口先查状态再查请求 | 和入口矛盾的字段 400（提示写字段名）；先查请求（`runtime.job_id`、矛盾字段）再查书、原文、要复用的 OCR；请求体和 `POST /jobs` 一样先收 JSON 再解析，提示统一成 `invalid job payload: …` |
| C5 | 元数据接口的错误 `details` 是 `{}`；`OCR_JOB_NOT_FOUND` 同码两种信封；两个 422 | 都带 `error.details.reason`；元数据的「任务不存在」顶层 `code` 照旧、`error.code` 改成 `DOCUMENT_METADATA_JOB_NOT_FOUND`；两个 422 改 409 |
| C7 | 生成、应用建议的请求体不拒绝未知字段 | 两个请求体 `deny_unknown_fields`，400 |

## 取舍

- **老数据怎么兼容（C2）**：书名来源表 `document_title_state` 是 v12 才有的，之前手改的书名没有来源记录，读出来是
  `filename`。光改成只看来源，这些书会被自动命名盖掉。所以加迁移 v28：升级时没有来源记录、书名又不等于「文件名去掉
  `.pdf`」的，一次性补一条 `user` + 锁定。只跑一次——之后没有来源记录、书名不等于文件名的就是换名重传，正该自动命名。
  升级前已经换名重传过的书和老的手改分不出来，也按手改处理：和升级前一样不自动命名，用户自己改名就行。
- **不改重传时覆盖 `source_filename`**：那是正确性审计 2-#10 的事（重传覆盖页数、字节数、文件名），这里只把判断从文件名上拿掉。
- **原文 PDF 不在盘上照旧是普通 404**：原文随上传就有，不在就是丢了，不会"过一会儿产出"，和
  [还没产出返回 404](./20261019-还没产出返回404实现记录.md) 定的书的原文一样，不带 reason。审计建议的 409 `artifacts_missing` 不采用。
- **413 不改**：`DOCUMENT_METADATA_SOURCE_TOO_LARGE` 是大小问题，留 413，只补 reason。
- **422 → 409**：规范化文档坏了、还没有可用书名，都是"换一份 OCR / 等 OCR 做完同一个请求就能成功"，按 400/409 的分工是 409。
- **`OCR_JOB_NOT_FOUND`**：顶层 `code` 前端和老调用方可能在看，不动；`error.code` 换名，让「看 `error.code`」的客户端不会把它当成建任务复用 OCR 的那个错误（那边带 `can_fallback_to_ocr`）。
- **`/ocr` 的 `workflow`**：缺省值是 book，要分清"没写"和"写了 book"，书的两个入口改成先收 JSON（`DocumentJobRequest`）。
  `POST /jobs` 本来就是这样收的，书的入口的未知字段提示因此和它一致（以前是 `unknown field … in the request body`），字段类型错从 422 变成 400。
- **`source.upload_id` 只认这本书最新的那份上传**：没放宽（审计 C4 提过放宽成任一份），旧的 upload_id 照旧 400——这不是悄悄改写，不在这次范围。
- **元数据的 DB 读写仍在异步线程**：只把重的文件活挪进阻塞线程；按编号读一行、插一行的 SQLite 操作和书库其它接口一样，统一挪由 `fix/library-lookup-errors` 做。
- **架构检查只加两个字面量**：`ocr/normalized`、`document.v1.json` 现在出口模块外一处都没有。`translation-manifest.json`
  （`merge/build.rs`）、`resolve_job_root`、`resolve_ocr_markdown_images_dir` 这些是审计 B9 的事，不在这次加，免得要往冻结名单里加文件。

## 对前端

- 无需改。前端 OCR 发 `{workflow:"ocr", ocr:{…}}`、翻译不发 `source.source_url`/`source.upload_id`/`runtime.job_id`
  （`features/library/domain/documents/submit-payloads.ts`、`book-detail/ui/use-book-detail-translate.ts`、`ingest/domain/workflow/payload-assembly.ts`）；
  自动命名发 `{job_id, fields:["title"], apply_if_default:true}`（`document-auto-naming.ts`），错误只打日志，不按 422 分支。
- 之前因换名重传而不自动命名的书，升级后照旧不自动命名（见上）；以后换名重传的会自动命名。
- apply 回包多三个链接（前端没调 apply）。
