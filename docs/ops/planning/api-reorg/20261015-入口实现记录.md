# 入口实现记录

> 日期：2026-10-15
> 分支：`refactor/api-entry`
> 方案：[模块化单体拆包规划](./20261015-模块化单体拆包规划.md) 第 6 节第 4 步"入口：只留一个提交函数"

## 原来的样子

建新任务有 5 个函数，每个都把同一串步骤抄一遍：

| 函数 | 谁在用 |
|---|---|
| `create_translation_job` | `POST /jobs`（非 OCR）、书库翻译、重试、续跑 |
| `create_ocr_job` | `POST /jobs`（`workflow=ocr`） |
| `create_ocr_job_from_upload` | `POST /ocr/jobs`、书库 OCR |
| `create_translation_bundle_job` | `POST /translate/bundle` |
| `create_ocr_ambiguity_recovery_job` | OCR 结果不确定后的两种恢复 |

另外，原地重跑（续跑出的重渲染、原地重渲染、原地精修）直接调 `start_job_execution`；
OCR 重试建完任务后还要自己再补一次归属；书库建完任务后又把任务往书上关联一遍再核对。

那串步骤是：补开发栈默认值 → 多用户换成平台模型 → 按 workflow 校验并建任务 → 明文 key 导入凭据库、
加使用锁 → 落库（预扣页额度）→ 归到书下 → 发射。各处抄得不完全一样，见下面"顺带修掉的"。

## 现在的样子

- **只有一个提交函数**：`services/jobs/creation/submit.rs` 的 `submit_job(deps, NewJob)`。
  上面那串步骤只在这里写一次。各入口不一样的地方写在 `NewJob` 上：
  - `with_upload(上传)`：文件随请求一起传（`/ocr/jobs`、`/translate/bundle`），先存成上传再交进来；
  - `derived_from(任务)`：OCR 重试只带上传，按上传归不到书时从源任务继承归属；
  - `for_document(书)`：书库发起的提交，建完确认任务确实归到了这本书下；
  - `resolving_ocr_ambiguity(…)`：OCR 歧义恢复，和"源任务那次 OCR 已处理"写在同一个事务里，不计费。
- **原地重跑**单独一个 `relaunch_in_place`，只接已经落过库的任务，没落过库的直接报错。
- `JobsFacade` 加了 `create_document_submission`，书库的翻译和 OCR 都走它。
- 删掉了 `creation/bundle.rs`、`BundleBuildDeps`、`launcher::start_job_execution`。
- **防止退回去**：`check_architecture.py` 的 `check_job_entry_ownership`。除了 `creation/submit.rs`，
  `services/`、`routes/`、`app/` 下的代码都不许直接调 `persist_job_with_resources`、
  `create_ocr_recovery_job_state`、`runtime.launch`。配了 3 个单测。

## 怎么保证行为没变

先提交了建任务各入口的结果快照 `backend/api/docs/submissions.txt`（`bf8340dd`），再改代码。
快照有 25 个场景：
- `/jobs` 的各种 workflow 和报错；
- `/ocr/jobs`、`/translate/bundle`；
- 重试、续跑、原地重渲染；
- OCR 歧义的两种恢复；
- 书库翻译和 OCR；
- 多用户下换平台模型、按页预扣、页数不够。

每个场景记下这几样：
- 返回；
- 新任务落库的请求；
- 归属和书；
- 事件；
- 凭据库多了几条；
- 页额度变化。

改完重新生成，只变了一行，是下面第 1 条有意修掉的。

## 顺带修掉的

1. **多用户模式下 `/translate/bundle` 把用户自带的 key 存进了凭据库。**
   - 其他入口都是先换成平台模型，再导入凭据。这个入口抄漏了"先换"，用户的 key 先被导进了凭据库，落库时才换成平台的。
   - 现在统一先换。快照里这一条的 `credentials: +2` 变成了 `+0`。
   - 这个接口多用户下网站账号本来就用不了，只影响管理员。
2. **`/ocr/jobs` 没写 `workflow` 时，按 `book` 判断平台配置。**
   - 多用户下，平台没配翻译模型时，只做 OCR 的提交也会被拒。
   - 现在这个入口先把 `workflow` 定成 `ocr` 再往下走，只要求平台配了 OCR。
   - 落库的任务和以前一样。这个入口多用户下网站账号也用不了，同样只影响管理员。

## 还没做

- 第 5 步：拆掉 jobs ↔ merge ↔ derived_artifacts 的依赖环。
- 上传（`POST /uploads`）本身没动。`/ocr/jobs`、`/translate/bundle` 存文件用的是 `store`（记在 local 名下），
  `POST /uploads` 用的是 `store_for(账号)`。多用户下网站账号用不了这两个带文件的入口，所以暂时没有影响。
  这两个入口以后对网站账号开放时要改成 `store_for`。
