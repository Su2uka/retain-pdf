# 契约第 1b 期：译文条目和书的任务

2026-10-22，分支 `contracts/phase1b-translations-documents`。接着 [契约第 1a 期补函数名](./20261022-契约第1a期补函数名.md)，
清单是前端「第 1 期接口清单」第 3 节（1b）里译文条目 3 条、书 3 条。任务操作、报告那 10 条另一个分支做（新建 `job-actions`、`job-reports` 契约），这里不碰。
接口行为没改，三份接口快照没变。

## 做了什么

| 方法 | 地址 | `client_name` | 契约 | 返回 |
|---|---|---|---|---|
| GET | `/api/v1/jobs/:job_id/translations` | `listTranslationItems` | translation-revisions.v1 | `TranslationDebugListView`（查询 `ListTranslationItemsQuery`） |
| GET | `/api/v1/jobs/:job_id/translations/:item_id` | `getTranslationItem` | translation-revisions.v1 | `TranslationDebugItemView` |
| POST | `/api/v1/jobs/:job_id/translations/:item_id/replay` | `replayTranslationItem` | translation-revisions.v1 | `TranslationReplayView`，不带请求体 |
| GET | `/api/v1/documents/:document_id/jobs` | `listDocumentJobs` | library-documents.v1 | `DocumentJobListView`（查询 `ListDocumentJobsQuery`） |
| POST | `/api/v1/documents/:document_id/translate` | `translateDocument` | library-documents.v1 | `JobSubmissionView`，请求体 `CreateJobInput` |
| POST | `/api/v1/documents/:document_id/ocr` | `ocrDocument` | library-documents.v1 | `JobSubmissionView`，请求体 `CreateJobInput` |

定义名照 Rust 的类型名（`TranslationDebug*` 是 Rust 里的名字，没改成「TranslationItem*」，免得两边各叫一个名）。

## 取舍

1. **译文条目放进 `translation-revisions.v1`，不另建契约。** 同一组地址 `/jobs/:job_id/translations/…`，写回（PATCH）和修订历史
   已经在这份里，前端一个 `@retainpdf/contracts/translation-revisions` 就能拿到这一组的全部类型。契约标题没改，`description` 补了一句。
   同一份契约里 PATCH 和 `revisions` 两条前端清单没给名字，不起名（测试钉住它们没有 `client_name`）。
2. **重放不写 `input`。** 处理函数没有请求体参数，前端也是空 body、不带 content-type；`note` 写明「不带请求体，带了也忽略」。
   单条和重放的 `item`、`payload` 是页文件里的原样条目、开发脚本的输出，契约写成开放对象（`additionalProperties: true`，
   TS 是 `{[k: string]: any}`），描述里说明不是稳定结构。
3. **翻译、OCR 的请求体抄 `create-job.v1` 的 `CreateJobInput`，不跨文件引用。** `$ref` 跨文件不行：`lint-schemas.mjs` 只解析本地指针，
   前端生成器（`frontend/packages/api/scripts/generate-client.mjs`）也只认同一份契约 `definitions` 里的名字，并从
   `@retainpdf/contracts/<同名契约>` 导入。所以把 `CreateJobInput` 和它引用的 `JobSourceInput`、`OcrInput`、`TranslationInput`、
   `RenderInput`、`RuntimeInput`、`GlossaryEntryInput`、`ModelConnection`、`JsonValue` 原样抄进 `library-documents.v1`，名字不变
   （TS 是结构类型，两边的 `CreateJobInput` 可以互相赋值）。书的任务列表条目 `JobListItemView` 及它用到的阶段、失败摘要，
   提交结果里的 `JobLinksView`、`JobActionsView`、`ActionLinkView` 从 `job-status.v1` 抄。
   新测试 `contracts/tests/library-documents-shared-definitions.test.mjs`：抄来的定义和源头逐字相同（连说明一起），
   抄的是闭包（引用的东西都抄了）；`library-documents.v1` 原有的 `WorkflowKind`、`JobStatusKind` 说明文字不同，只比值。
   和已有的 `job-definitions-parity.test.mjs`（job-status 与 library-books）同一个做法。要改先改源头，再照抄。
4. **`JobSubmissionView` 第一次进契约，定义放在 `library-documents.v1`。** `create-job.v1` 的 `createJob` 还没写 `output`；
   以后给它补上时照这份抄过去，并把它加进上面那条一致性测试（或者两边都加）。`sibling_job_ids` 只有拆成几个任务时才出现，
   不进 `required`。
5. **402 页数额度。** 只有多用户模式才计页（单机不会有 402）。信封和别的错误不一样：顶层 `code` 是字符串
   `PAGE_QUOTA_EXCEEDED`（不是 40200 这种数字），`error = {code: "PAGE_QUOTA_EXCEEDED", http_status: 402, details: {required_pages, balance}}`，
   被拒时不留任务。写进 `translateDocument`、`ocrDocument` 的 `note`，`error.details` 另加定义 `PageQuotaExceededErrorDetails`
   （和 translation-revisions.v1 的 `TranslationRevisionErrorDetails` 同一个做法）。复用 OCR 出错的信封（顶层字符串 `code`、`reason`、
   `can_fallback_to_ocr`）也写进了 `translateDocument` 的 `note`。
6. **端点表测试。** `endpoint-client-names.test.mjs` 第一个 test 原来 `deepEqual` 整张 `library-documents.v1` 表，改成只比前 17 条
   （第 0 期那 17 条顺序、内容没动，新 3 条接在后面）；1a 的 test 原来扫除 library-documents 以外的全部契约，改成只扫 1a 那 7 份契约
   ——不然这期、以及另一个分支新建的契约一加名字它就红。1b 这 6 条另起一个 test。
