# 书库读错和阻塞线程

> 日期：2026-10-19
> 分支：`fix/library-lookup-errors`
> 出处：[书库接口审计](./20261019-书库接口审计.md) 第一节 3、9（删除那半）、10，第二节"书不存在时用量给 200"；明细 A3、A5、A12、B4、B7、B13、C6

## 改了什么

| 问题 | 改法 | 状态码 |
|---|---|---|
| 读书、读合集时把任何错误都转成 `not_found`：库被锁、行解码失败也说成"书不存在" | 统一换成 `AppError::from_lookup`：没有这一行 404，其余 500 | 只有库读错时 404 → 500 |
| 删除时"还有任务在跑"的 409 没有 `reason` | `conflict_because("job_active", …)`，和任务操作同一个值 | 409 不变，多一个 `reason` |
| `GET /documents/:id/usage` 书不存在给 200 全零汇总 | 先读书，`from_lookup`；有书没任务照旧 200 空汇总 | 200 → 404（不带 reason） |
| 书、合集、搜索、字体的处理函数在异步线程上跑 SQLite、删目录、起子进程 | 放进 `spawn_blocking` | 不变 |

`from_lookup` 换掉的地方（书库包 11 处 + 附带的几处）：

- `documents.rs`：`require_document_upload`（`/translate`、`/ocr`、生成元数据建议都经过它）、`get_document`、`document_delete_job_ids`、`patch_document`；`?job_id=merged-…` 分支的 `.ok()`（书不在仍是空列表，读错 500）。
- `collections.rs`：`patch_collection`；`add_collection_documents` 里 `get_document(..).is_err()` → 404。
- `media.rs`：`document_source`（`/files/…`、`/reading`）、`document_files_view`（`/files`：只有"书在、原文不在磁盘上"才是 `ready: false`，其余错误照常返回）。
- `conversations.rs`：建对话、分叉对话时核对书。
- `metadata_suggestions.rs`：建议列表；指定 OCR 任务时 `get_job` 的任何错误 → 404 `OCR_JOB_NOT_FOUND`，改成只有没有这个任务才是它。
- `reading.rs`：翻译覆盖读页数（走 `get_document`）。
- AI 包 `public_document_operations.rs`：`GET /documents/:id/agent-versions`。
- 任务包 `reports/usage/api.rs`：书的用量。

数据库层两处让"没有这一行"带上 `QueryReturnedNoRows`（`from_lookup` 凭它判 404），和 `get_document` 一样：

- `update_collection` 更新后读不到合集；
- `update_document_fields` 先确认书在。以前不确认：改书名时标题状态表的外键先报错，书不在的 PATCH 在新写法下会变成 500。

## 取舍

1. **阻塞线程用普通 `spawn_blocking`，不用 `run_read_query_once`。** 审计建议读接口包一层 `run_read_query_once`（书架那样）。
   但那个池只有 2 个槽、最多 128 个排队，满了回 429；`GET /documents` 是调用最多的接口，和任务的读查询抢 2 个槽、多出一种 429，
   都改变了返回。这次照 `reading.rs`、`token_usage.rs` 的写法直接 `spawn_blocking`，返回和错误不变。
   处理函数里的公用写法是 `routes/common/library.rs` 的 `run_library_blocking`、`routes/common/fonts.rs` 的 `run_fonts_blocking`：
   只带走数据库和配置的 `Arc`，在阻塞线程里重新组 `LibraryDeps` / `FontApiDeps`，不带任务运行时。
2. **删除时遇到读不出来的任务行，改成 500，不再跳过。** 以前删书、删文档逐个 `if let Ok(job) = get_job(..)`，读不出来的任务直接跳过：
   既不检查它在不在跑（绕过了 `job_active`），也不在删除名单里。现在没有这一行才跳过，读不出来 500，带 `force=true` 也一样。
   代价是有坏任务行的书删不掉，要先查库；比悄悄删掉一本名下可能还有任务在跑的书好。删书前反查所属文档（`get_document_by_job_id`）
   读错也不再吞掉。
3. **书的用量书不存在 404。** 以前书删掉以后，助手台账里带这个 `document_id` 的行还能查到；现在查不到了，和任务用量
   （库里没有、目录也没有才 404）不完全一样：书没有自己的目录可以退回。前端 `BookUsageCard` 只对已有的书调用。

## 没做的

- 元数据建议的其余问题（不进阻塞线程、409/404 没有 reason、422）归 `fix/document-metadata-and-entries`，这里只改读错。
- 书的 `/translate`、`/ocr`、元数据建议、对话、`/assets` 的处理函数没有放进阻塞线程（不在这次范围，`/assets` 要删）。
- `media.rs` 里没有上传记录时退回 `active_job_id` 任务找原文那一步，`get_job` 读错仍当成"原文不在"（404）；
  `reading.rs` 合集工作区挑书时的 `.ok()` 留给合集工作区那个分支。
- AI 包里 `agent_capabilities.rs`、`document_operations/facade/create.rs` 还有同款 `map_err(|_| not_found)`，归 AI 那块。

## 对前端

- 删除 409 多了 `reason = "job_active"`。`error-messages.ts` 的 `friendlyDocumentDeleteError` 现在靠"409 且不是 job_has_dependents"判断，
  结果不变；方便时可以改成按 `reason === "job_active"` 判断。
- 库读错时书库接口由 404 变 500。前端对非 OK 都走"读取失败"，没有按书接口的 404 判断"书没了"的地方
  （`session-load-plan.ts` 的 404 判断针对的是任务）。
- 书刚被删时用量卡片从"0 用量"变成读取失败。
