# OCR 提供方选项分客户端和服务器

> 日期：2026-10-22
> 分支：`fix/ocr-server-owned-options`
> 出处：[设置与平台接口审计](./20261022-设置与平台接口审计.md) 第一节 1、第三节 5；
> 明细 [A 服务商、密钥和用量](./20261022-设置与平台接口审计明细/A-服务商密钥与用量.md) 第 2、12 条。

## 问题

建任务时请求里的 `ocr.options` 原样盖在 `ocr_providers.json` 的默认值上
（`retainpdf-data` `worker_command/stage_specs.rs` 的 `provider_options_for_stage`），写进 `provider.spec.json`。
流水线 `provider_pipeline._args_from_spec` 把 `options.command` 交给 `local_command_driver`，`shlex.split` 后
`subprocess.run`，环境是后端进程的全部环境变量。所以单机模式下能调 `POST /api/v1/jobs` 的，带上
`{"ocr": {"provider": "local", "options": {"command": "<任意程序>"}}}` 就能让服务器跑任意程序；`raw_provider`
（原始结果交给哪个转换器）同样能被请求改掉。`GET /providers/ocr` 还把 `command` 列成选项、给出运维配的默认值，
看起来就是让客户端填的。多用户平台模式会清空 `ocr.options`（`lifecycle/launcher.rs`），单机不会。

改之前先写了三个测试证明现状（都在没改的代码上红）：

- `retainpdf-data` `stage_specs::tests::provider_stage_options_never_take_server_owned_options_from_the_request`：
  请求的 `command`、`raw_provider` 原样出现在 stage spec 的 options 里；
- `retainpdf-api` `api_tests::jobs_creation::every_entry_rejects_server_owned_ocr_options`：`POST /jobs`
  带 `ocr.options.command` 建任务成功、进了队列；
- `backend/pipeline` `test_local_command_server_owned.py`：stage spec 里的 `options.command` 被执行了（写出了标记文件）。

## 规则

选项分两类：

- **客户端可填**：建任务请求可以在 `ocr.options` 里带，盖在配置默认值上（和以前一样）。
- **只能服务器定**：值只来自 `ocr_providers.json` 和环境变量。请求带了 400，stage spec 里只有服务器的值，
  流水线也不认 stage spec 里的。

一个选项算哪类（Rust `retainpdf-data` `ocr_provider::catalog::option_is_client_settable` /
`is_server_owned_ocr_option`，Python `ocr_provider_config.is_server_owned_ocr_option`，两边同一套）：

1. `command`、`raw_provider` 永远只能服务器定，不管哪个提供方、配置怎么写（`SERVER_OWNED_OCR_OPTION_KEYS`）；
2. 配置里写了 `"client_settable": true/false` 的照它（只能用来放开第 1 条以外的）；
3. 配置里带 `env` 的只能服务器定——写了 `env` 说明这是运维用环境变量定的东西；
4. 其余客户端可填。配置里没登记的选项（Paddle CLI 的 `cli_timeout`、`use_*` 开关等）也按这条，客户端可填。

第 2 条是给以后加的命令型提供方留的口子：带 `env` 的超时之类想让客户端填，配置里明说 `client_settable: true`。

## 每个选项的分类

`backend/config/ocr_providers.json`（和没有这份文件时 `retainpdf-core` `provider_config.rs`、Python
`ocr_provider_config.py` 写死的那份）里现在的全部选项。`retainpdf-data` `catalog::tests::every_configured_option_is_classified`
钉着这张表：往配置里加选项时它会红，想清楚归哪边再改表。

| 提供方 | 选项 | 配置里有 `env` | 分类 | 理由 |
|---|---|---|---|---|
| mineru | `model_version` | 否 | 客户端可填 | 选 MinerU 模型（`vlm` 等），前端一直发顶层同名字段 |
| mineru | `language` | 否 | 客户端可填 | 识别语言 |
| mineru | `disable_formula` | 否 | 客户端可填 | 开关 |
| mineru | `disable_table` | 否 | 客户端可填 | 开关 |
| paddle | `transport` | 否 | 客户端可填 | `official_http` / `official_cli`，建任务已校验取值；`official_cli` 执行的程序来自服务器的 `RETAIN_PADDLE_CLI_PATH` 或 PATH 上的 `paddleocr`，不来自请求 |
| paddle | `paddle_model` | 否 | 客户端可填 | 选模型，有别名表 |
| paddle | `paddle_api_url` | 否 | 客户端可填 | 前端一直发顶层同名字段（`buildOcrPayload`）；`options` 里的这个键流水线其实不读（读的是顶层 `ocr.paddle_api_url`）。密钥会发到请求指定的地址，见「没做的」 |
| local | `command` | 是 `RETAIN_LOCAL_OCR_COMMAND` | **只能服务器定** | 流水线拿它执行 |
| local | `raw_provider` | 是 `RETAIN_OCR_RAW_PROVIDER` | **只能服务器定** | 运维配的转换器名，和命令输出的格式配套 |

配置里没登记、流水线会读的 `ocr.options` 键（都客户端可填）：Paddle CLI 的 `cli_model_type`、`cli_request_timeout`、
`cli_poll_timeout`、`cli_timeout`（上限 `PADDLE_CLI_MAX_TIMEOUT_SECONDS`）、`use_doc_orientation_classify` 等十几个开关和阈值
（拼成 `paddleocr api --<名字> <值>` 的固定参数名，值是单独的 argv，不经 shell）；命令型提供方的兼容凭据
`credential`、`token`、`api_key`（建任务时导入凭据库，不进 stage spec）。

## 在哪里拦

- **建任务**：`retainpdf-jobs` `lifecycle/validation.rs` 的 `validate_client_ocr_options`，和 `validate_runtime_limits`
  一样挂在 `job_builders` 的两个构建函数（`build_translation_job_snapshot`、`build_ocr_job_snapshot`）开头，
  `submit_job` 的每个调用方都经过：`POST /jobs`、书的 `/translate`、`/ocr`、重跑、阶段重试、OCR 歧义恢复。
  报 400 `ocr.options.command is server-owned; configure it on the server (backend/config/ocr_providers.json or the
  option's environment variable), not in the request`，几个键一起带时列全（`… are server-owned`）。不带 `reason`：
  请求写错了，和状态无关。多用户平台模式在这之前已经清空了 `ocr.options`，不会走到这里。
- **重试的 overrides**：`actions/stage_retry_overrides.rs` 两个合并函数在合并 `ocr` 段之后也调它。原地重渲染、
  原地精修不经建任务校验，靠这里。
- **双保险**：`provider_options_for_stage` 跳过请求里只能服务器定的键，stage spec 里只有配置的默认值。
- **Python 兜底**：`provider_pipeline._args_from_spec` 用 `client_ocr_options` 去掉 stage spec 里只能服务器定的键，不再从
  spec 填 `local_ocr_command` / `local_ocr_raw_provider`；内置的 `local` 和配置型命令提供方一样，命令从
  `ocr_providers.json` 的默认值（每次现读）和环境变量来；`local_command_driver` 不再认 `args.command` / `args.raw_provider`
  这两个属性名。就算 Rust 哪天漏了，请求带的命令也到不了 `subprocess.run`。

## 老任务请求里存着的怎么办

2026-10-22 之前建任务不拦，老任务的 `request_payload.ocr.options` 里可能存着 `command`、`raw_provider`。
重跑、阶段重试是复制源任务的请求再走一遍 `submit_job`，直接校验会让这些老任务再也重跑不了。

选了**复制时剔掉**，不是校验前剔掉：

- `actions/rerun.rs` 的 `build_rerun_request`、`actions/stage_retry_request.rs` 的 `build_retry_request`（OCR 歧义恢复也用它）
  复制完调 `strip_server_owned_ocr_options`；原地重渲染、精修的 `prepare_in_place_render_job` 同样剔掉；
- 剔掉以后才合并 overrides，所以 overrides 里再带就 400，不会被悄悄吃掉；
- `submit_job` 里的校验不认来源，所有入口一个规则；要是在校验前按"这是内部提交"剔掉，就得给 `NewJob` 加一个
  "跳过检查"的开关，外部入口误用它就又开了口子。

剔掉不影响老任务的运行：这两个值本来就该由服务器定，剔掉以后用配置和环境变量里的。
任务运行时派生的 `{id}-ocr` 子任务复制父任务的请求、不经 `submit_job`，老父任务的请求里要是还存着，靠双保险和 Python 兜底。
`submissions.txt` 快照新加了这几种情况（源任务存着 `command` 的 OCR 重试、翻译重试、续跑出的原地重渲染都成功且新请求里
`options` 是 `{}`；overrides 带 `command` / `raw_provider` 400）。

## `GET /providers/ocr`

两个都做：每个选项加 `client_settable`（只增），只能服务器定的选项**照样列出、`default` 给 `null`**。

- 只加 `client_settable` 不藏默认值：运维在配置里写的命令通常带本机路径，会给所有登录用户看（明细第 12 条）；
- 整个不列出：客户端就不知道这个提供方要服务器先配命令，`local` 的选项会变成空表；`env` 名也是运维排查要看的。

所以列出、标明、不给值。键集合没变，`default` 本来就可能是 `null`（配置里没写时），只是值变了；流水线要的真实默认值走
`provider_public_definitions`，接口走新加的 `provider_client_definitions`。`env` 名、`artifact_layout` 照旧给（明细第 12 条也提到，
不在这次范围里）。

契约 `contracts/ocr-providers.v1.schema.json`（`@retainpdf/contracts/ocr-providers`）把现在的返回钉住，照
`contracts/README.md` 的流程生成 TS、登记 exports / lint / generate / package-boundary 测试、`backend/contracts/` 镜像和
`check_parity.py`。Rust 侧 `api_tests::providers::list_ocr_providers_matches_published_schema` 对真实接口的返回逐项比类型和
键集合（选项里只有 `env` 可以不出现），并查 `client_settable: false` 的 `default` 是 `null`。

## 调用方核对

`git grep` 了前端（含 `frontend/desktop`、`frontend/web/scripts`）、`backend/ai`、`backend/cli`、`ops`：

- 前端界面：`features/ingest/domain/workflow/payload.ts` 的 `buildOcrPayload` 发 `provider`、`credential_ref` 或
  `<提供方>_token`、`model_version`、`language`、`page_ranges`，Paddle 加顶层 `paddle_api_url`；**不发 `ocr.options`**。
  书库的 `assembleOcrPayload` / `assembleTranslatePayload` 在它上面叠页码，也不带。重试的 `overrides` 只有 `translation`（书库 `job-actions.ts` 的重新翻译）和 `render.engine`
（`use-book-detail-stage-actions.ts`），没有 `ocr`。
  `GET /providers/ocr` 前端没调（用自己写死的 `platform/config/providers.ts`）。不受影响。
- `frontend/web/scripts/frontend-status-smoke.mjs`：`--ocr-options <json>` 原样放进 `ocr.options`，帮助里写着
  `local requires a configured command`。拿它传 `{"command": …}` 跑本地 OCR 的会 400；传 Paddle 的 `transport` 不受影响。
  写进交接文档，请前端改帮助文字（后端不改 `frontend/`）。
- `backend/ai`：`agent_command_broker.py`、`runtimes/fx_acp.py` 里的 `options` 是 agent 自己的参数，不是建任务请求。没有建任务时发 `ocr.options` 的地方。
- `backend/cli`：`cmd/setup.rs` 的 `ocr_options` 是选 OCR 提供方的菜单，不发 `ocr.options`。
- 桌面端 `frontend/desktop/src/main/backend-env.js`：只把 `RETAIN_OCR_PROVIDER_CONFIG` 指到 `backend/config/ocr_providers.json`
  （Rust 和 Python 读同一份），没有 `RETAIN_LOCAL_OCR_COMMAND`，不建任务。

## 没做的

- **`ocr.paddle_api_url`、`translation.base_url` 会把服务器配的密钥发到请求指定的地址**（明细第 2 条顺带提到）：
  建任务不过 `validate_provider_base_url`。这是另一类问题（密钥外发，不是执行命令），而且前端一直发 `paddle_api_url`，
  收紧要先和前端定，这次没动。
- `GET /providers/ocr` 仍给 `env` 名和 `artifact_layout`。
- 任务详情的 `request_payload.ocr.options` 对老任务仍会显示当时存进去的 `command`（只是请求里自己写的东西，不是密钥），
  重跑以后新任务里没有了。
