## 做了什么

平台领域拆成第二个领域包 `retain-pdf-platform`，放在 `backend/packages/retain-pdf-platform`，管这几样：
- 多设备同步 `sync`；
- 数据库备份 `backup`；
- 字体 `fonts`；
- 健康检查 `health_api`。

照样板做：
- 整个目录挪过去，`mod.rs` 改名 `lib.rs` 当门面；
- 路径改成直接写包名；
- rust_api 里写 `pub(crate) use retain_pdf_platform as platform;` 接上；
- 加进 `EXTRACTED_DOMAINS`、工作区成员、`Dockerfile.app`、合并前的 `cargo test`。

## 和术语表不一样的一处：健康检查读进程监督器

拆之前，健康检查直接去读 rust_api `runtime` 里两个监督器（AI 服务、jobsd）的状态。原有的两条规则对此有限制：
- `runtime` 不许依赖业务领域；
- 读监督器状态只限装配代码和"明确的健康检查使用方"。

现在这样分工：
- **状态码挪进底座包**：`retain_pdf_api_base::supervisor`，含状态码和对应的说明文字。
  - 监督器的 `AI_STATUS_*`、`JOBSD_STATUS_*` 取的是这里的值；
  - 健康检查也用这里的说明文字，原来是两份一样的 `match`。
  - `runtime` 和平台都往下依赖它，谁也不依赖谁。
- **当前状态由调用方传进来**：
  - `HealthApiDeps::new` 多了两个参数（AI 服务、jobsd 的当前状态）；
  - `routes/common/health.rs` 建依赖时从 `runtime` 读好传进去。它本来就在每次请求时现读，所以返回不变。
- **规则的白名单**：允许读监督器状态的文件里，`services/platform/health_api.rs` 换成了 `routes/common/health.rs`。
  它是健康检查的依赖构建函数，读状态的事挪到了这里，规则的本意不变。
- **删掉的函数**：`runtime` 里 `ai_service_status_label`、`jobsd_status_label` 没有用处了，已删掉。
  原来测试说明文字的那个测试，改成调 `supervisor_status_label`。

## 怎么保证行为没变

- 健康和就绪接口的测试（`api_tests/health.rs`）照旧通过；
- 三份快照都没变；
- 函数体除了上面说的读状态的位置，没有改动。

## 下一步：顺序要按依赖方向排

一个包只能依赖已经拆出去的包，不能依赖 rust_api。所以被依赖的领域要先拆。领域之间的依赖见
`ALLOWED_DOMAIN_DEPENDENCIES`：

| 领域 | 依赖 |
|---|---|
| 入口 | 账号 |
| 账号 | 服务商 |
| 任务 | 账号、文件、术语表、入口、服务商 |
| 书库 | 文件、任务 |

按这个排出的顺序：
1. 服务商（providers）：不依赖别的领域；
2. 账号（accounts）；
3. 入口（ingest）；
4. 文件（files）：不依赖别的领域；
5. AI：不依赖别的领域；
6. 任务（jobs）；
7. 书库（library）：它依赖任务，**必须排在任务后面**。

这和规划里"任务最后拆"不一样，以这里为准。
