# worker 进程身份与运行时独占

分支 `fix/worker-process-identity`。对应状态一致性审计的 1-任务状态机 #6、#9 和 6-流水线约定 #3（含第 5 步 jobsd 的 terminate 接口）。
只动后端；对前端没有任何改动。

## 问题

1. **第二个运行时杀第一个的 worker**：进程内模式的 rust_api 在 `build_state` 里先做启动对账（`reconcile_stale_running_jobs`），
   再 `bind` 端口。同一个 `data/` 上再起一个实例（另一个 worktree 的开发后端、换了端口的实例），它会把第一个实例正在跑的任务
   判成孤儿、组杀 worker、改成 queued/failed，之后才在 bind 上失败——换了端口的话连 bind 都不会失败。jobsd 靠「先 bind 再对账」，
   同样只挡得住同一个端口。
2. **按旧 pid 组杀，不核对身份**：启动对账、运行期巡检、取消都按库里记的 pid `kill(-pid)`，只用 `kill(pid, 0)` 判断「活着」。
   长时间宕机、重启机器之后这个号可能归了别的程序（macOS 上 launchd 起的 GUI 程序都是进程组组长），会被整组杀掉。取消路径的窗口是
   「worker 已退出、库里 pid 还没清」。
3. **jobsd 的 terminate 接口杀任意 pid**：`POST /internal/v1/processes/:pid/terminate` 带 key 就能组杀任意 pid；pid=0 变成
   `kill(0, …)`（jobsd 自己的进程组），pid=1 变成 `kill(-1, …)`（当前用户能发信号的所有进程）。

## 决定

### 运行时独占：按任务库加文件锁，不改启动顺序

- 选文件锁而不是「先 bind 再对账」：端口只代表「同一个配置」，挡不住换了端口、换了 worktree 指向同一个 `data/` 的第二个实例；
  任务库才是真正被争的东西。锁文件是任务库旁边的 `jobs.db.runtime-owner.lock`（默认 `DATA_ROOT/db/jobs.db.runtime-owner.lock`），
  `std::fs::File::try_lock`（Unix 上是 `flock(LOCK_EX|LOCK_NB)`，Windows 上是 `LockFileEx`），拿不到立即报错退出、不对账。
  锁跟着打开的文件走，进程怎么退出（包括 SIGKILL、OOM）都由内核释放，不会留下要手动删的锁文件；锁文件本身留着无害。
- 谁拿：进程内模式的 rust_api 在 `serve_with_shutdown` 里、`build_state` 之前拿（`app/jobs.rs` 的 `acquire_owned_runtime_lock`），
  一直拿到服务退出；jobsd 在 bind 之后、对账之前拿（bind 仍在前，同端口的二次启动照旧先在 bind 上失败）。两边是同一把锁，
  进程内模式的 rust_api 和 jobsd 混着指向同一个库也互相挡住。远端模式的壳不拿：它不对账，锁归它监督的 jobsd。
- 测试不受影响：锁只在真实服务的入口拿，单测直接调 `build_state`，同一个测试进程里并存多个 `AppState`（各自或共用临时目录）都不碰锁。
  `flock` 在同一进程里对同一文件的两次打开也互斥，所以「本进程里另一个持有者」同样会被拒绝，测试用这一点模拟「另一个运行时」。

### worker 进程身份：spawn 时记，杀之前核对

- **记什么**：`retainpdf_proc::process_identity(pid)` → `<pid>@<指纹>`。Linux 读 `/proc/<pid>/stat` 第 22 个字段 starttime（开机以来的滴答）
  并带上 `/proc/sys/kernel/random/boot_id`（`linux:<boot_id>:<ticks>`）；macOS 用 `proc_pidinfo(PROC_PIDTBSDINFO)` 的启动时间
  （`darwin:<秒>.<微秒>`）；别的平台读不到，记 NULL。同一个进程每次读都一样，pid 被复用后一定不同。
- **存哪**：`jobs.worker_identity TEXT`，幂等加列（`ensure_jobs_column`，和 `run_generation` 一样不占迁移号）。只由
  `Db::record_worker_identity` 写，任务行的 upsert（`save_job` 等）不碰它。`spawn_started_process` 在 spawn 之后、把新 pid
  CAS 写进任务行**之前**记：中间崩了，库里还是旧 pid（通常是 NULL），和新身份串里的 pid 对不上，不会被误认；反过来先写 pid
  再写身份，中间崩了新 worker 就没身份可核对。清 pid 的各处不清身份列——身份串自带 pid，和下一个 pid 对不上就等于没有。
- **怎么核对**（`retainpdf-runner` 的 `worker_identity.rs`，启动对账、运行期巡检、取消、jobsd 的 terminate 共用一套）：
  - pid ≤ 1 或进程不在：已不在（`Gone`），只清 pid。
  - 有身份信息且 pid 对得上：指纹相同才是我们的（`Ours`），否则（包括读不到当前进程的指纹）是号被复用（`NotOurs`）：不杀，只清 pid。
  - 没有身份信息（见下）：按启动时间粗判。
- 启动对账对 `NotOurs` 记一条新的说明（「库里记的 pid 现在属于别的进程（pid 已被复用），没有终止它」），失败分类照旧
  `worker_process_missing`（和 worker 已不在同一个恢复建议）；有可续的 attempt 照旧回 queued。
- 取消（含强制删除，走同一条路径）：`cancel_job` 改调 `runtime_gateway` 的 `terminate_job_worker`，它先核对，`Ours` 才调 `terminate_runtime_process`，否则只打一行日志、返回成功，取消照常落终态。
  远端模式下 jobsd 收到 terminate 还会再核对一次。

### 没有身份信息的老行：按启动时间粗判，不一律杀也不一律不杀

升级前写的 running 行、读不到身份的平台上写的行，没有 `worker_identity`。三个选项：

| 做法 | 号被复用时 | 真孤儿 worker 时 |
| --- | --- | --- |
| 照旧组杀 | 误杀整组（就是这次要修的问题） | 杀掉 |
| 只杀单个 pid | 照样误杀那个进程 | worker 的子进程（OCR、渲染子进程）活下来 |
| 一律不杀 | 安全 | 孤儿 worker 继续跑；任务被重新排队后新 worker 和它写同一个任务目录 |

Python worker 不受 `RETAIN_SUPERVISOR_PID` 监督，运行时崩了它会一直跑下去，所以「一律不杀」在最常见的场景（运行时崩溃后升级重启）
反而更糟；「只杀单个 pid」两头都不讨好。取的是第四种：**读得到进程启动时间时，进程启动晚于任务行最后一次写入（`updated_at`）30 秒以上
就当号被复用、不杀，否则照旧组杀**；读不到启动时间（平台不支持）照旧组杀——那些平台本来也没别的办法。

道理：真 worker 一定在 pid 落库之前就启动了（落库那次写的 `updated_at` 取的是 spawn 前一刻，只精确到秒，所以留 30 秒余量）；
被复用的 pid 属于 worker 死后、而且运行时也已经不在（不再写这一行）之后才起来的进程，正常要晚得多，重启机器之后更是如此。
这条规则只对没有身份信息的行生效，升级后第一次启动对账完，这类 running 行就没有了。

### jobsd 的 terminate：只杀登记过的 worker

- pid ≤ 1：400，`{"accepted": false, "reason": "invalid_pid"}`，不查库、不发信号。
- 库里没有 running 任务记着这个 pid，或者记着但身份核对不上：404，`{"accepted": false, "reason": "not_a_registered_worker"}`，不发信号。
  「登记过」就是「库里 running 任务的 pid + spawn 时记的身份」：worker 的 pid 和身份都是 jobsd 自己的 runner 写的，
  不另建一份内存登记表（重启后会丢，还要和库对账）。查库失败也按不受理处理，宁可这次取消晚一点生效。
- 壳（`runtime_gateway` 的 Remote 实现）把 404 当作「没有要杀的」，返回成功、打一行日志；其他非 2xx 照旧报错。
  契约 `contracts/jobs-control.v1.schema.json`（和 `backend/contracts/` 的镜像）的 terminate 语义和 `AckResult.reason` 一起改了。
- 纵深防御：`retainpdf_proc::terminate_job_process_tree(_blocking)` 自己也拒绝 pid ≤ 1 和超出 `i32` 的 pid（取负会溢出），
  所有调用方（包括 AI 的受限执行器）都不会再发 `kill(0)` / `kill(-1)`。

## 测试

- 进程内第二实例：`backend/api/tests/api_process_startup_recovery.rs` 的 `second_in_process_api_on_the_same_data_exits_without_touching_live_workers`
  （真起两个 rust_api，换端口）；jobsd 的 `backend/jobs/tests/terminate_endpoint.rs` 里 `jobsd_exits_without_reconciling_when_another_runtime_owns_the_db`。
- 身份核对：runner 的 `startup_recovery_does_not_kill_a_process_that_reused_the_recorded_pid`、
  `startup_recovery_spares_a_legacy_pid_that_started_after_the_row_was_last_written`、`startup_recovery_still_kills_its_own_orphan_worker`、
  `startup_records_worker_identity_with_the_pid`；rust_api 的 `cancel_and_force_delete_spare_a_process_that_reused_the_recorded_pid`。
- jobsd terminate：`terminate_rejects_pid_zero_instead_of_killing_its_own_process_group`、`terminate_only_kills_workers_jobsd_registered`；
  pid=1 只在纯函数单测里测（`terminate_rejects_pid_zero_and_one_before_any_lookup`）——改坏了的版本在真实接口上跑 pid=1 会杀掉当前用户的所有进程，
  测 pid=0 的集成测试也把 jobsd 放进自己的进程组里起。`retainpdf-proc` 的守卫同理只测守卫函数本身。
- `build_state_terminates_and_fails_running_jobs_with_live_pid` 的任务行 `updated_at` 是写死的过去时刻，改成像真实 spawn 一样记下身份。

## 没做 / 已知边界

- 核对和发信号之间仍有极短的窗口（核对完、发信号前 worker 恰好退出且号立刻被复用），没有 pidfd 一类的手段可以在两个平台上统一消除。
- AI 的受限页面执行器（`retainpdf-ai` 的 `document_operations/executor.rs`）按 dispatch 索引文件里的 pid 组杀，是同一类写法，
  这次只靠 `retainpdf-proc` 的 pid ≤ 1 守卫兜底，没有加身份核对。
- 远端模式的壳不拿运行时锁：两个远端模式的壳指向同一个库时，各自监督的 jobsd 里后起的那个会在锁上失败退出（和以前同端口时在 bind 上失败一样），由壳的监督循环按它的重启策略处理。

## 前端

无。`worker_identity` 不进任何接口返回；jobsd 的 terminate 接口只有壳调用。
