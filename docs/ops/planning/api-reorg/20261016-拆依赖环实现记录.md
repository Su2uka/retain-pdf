# 拆依赖环实现记录

> 日期：2026-10-16
> 分支：`refactor/api-cycles`
> 方案：[模块化单体拆包规划](./20261015-模块化单体拆包规划.md) 第 5 节第 1～3 条、第 6 节第 5 步前半

## 原来的样子

`check_architecture.py` 加"services 之间不准成环"这条规则时，已经有两个环，登记在
`KNOWN_SERVICE_CYCLE_EDGES` 里（7 条边）：

- 任务 ↔ 合并阅读 ↔ 派生产物：`jobs → merge`、`merge → jobs`、`jobs → derived_artifacts`、
  `derived_artifacts → merge`、`merge → derived_artifacts`
- 任务 ↔ 下载调度：`jobs → download_generation`、`download_generation → jobs`

逐条看下来，造成环的引用一共 6 处：

| 边 | 在哪 | 为什么 |
|---|---|---|
| `jobs → merge` | `jobs/query.rs` 的 `load_supported_job`，`jobs/translations/edits.rs` | 认出、读出合并阅读的虚拟任务（`merged-<文档>-<指纹>`） |
| `derived_artifacts → merge` | `derived_artifacts/merged.rs`；`derived_artifacts.rs` 的缓存目录 | 生成合并目录要用合并计划；虚拟任务的缓存放在合并目录里 |
| `merge → derived_artifacts` | `merge/reading.rs` | 调生成合并目录 |
| `merge → jobs` | `merge/coverage.rs` | 取任务结束时的说明文字（`terminal_completion_note`） |
| `download_generation → jobs` | `download_generation.rs` | 用文件句柄类型 `FileDownload` |
| `jobs → download_generation` | `jobs/files/downloads` | 下载交给调度 |

## 现在的样子

1. **按编号读出任务下沉到 `src/job_loading/`**（services 下面一层，规划第 5 节第 2 条早就定了）。
   - 从 `jobs/query.rs` 挪来：`load_job_or_404`、`load_supported_job`、`load_ocr_job_or_404`、
     `load_ocr_job_with_supported_layout`、`ensure_supported_job_layout`。
   - 从 `merge/reading.rs` 挪来虚拟任务的读取：`is_virtual_job_id`、`load_virtual_job`、
     `contributing_jobs`、说明文件 `ReadingSidecar` 和文件名 `SIDECAR`。
   - 从 `derived_artifacts/merged.rs` 挪来合并目录的布局 `MergedTranslation`（只是几个路径）。
   - 任务、派生产物原来为了认出虚拟任务才依赖合并阅读，现在都往下依赖 `job_loading`。
2. **生成合并目录挪进合并阅读**：`derived_artifacts/merged.rs` → `merge/build.rs`（测试一起挪）。
   它用的是合并阅读自己的计划和来源；对派生产物只用通用的子进程监管和缓存目录，单向依赖。
3. **`FileDownload` 挪进下载调度**：调度的就是这个类型。`services::jobs` 照旧转出它，别处不用改。

拆完以后：

- `KNOWN_SERVICE_CYCLE_EDGES` 清空，出现任何环都直接报错。
- 新加 `check_job_loading_is_below_services`：`job_loading` 里不许出现 `crate::services`、`crate::routes`、
  `crate::app`、`AppState`。
- 往文件里故意写环、往 `job_loading` 里故意写对 services 的依赖都试过，两条规则都会报错；另加了 3 个检查脚本单测。

只挪代码、改引用路径和可见范围，函数体不动。接口清单、文件下载、建任务入口三份快照都没变。

## 定下来的

- **合并阅读放书库那一侧**（规划第 5 节第 3 条）。它在文件之上，往下依赖派生产物（生成）、
  `job_loading`（读取）和任务（`coverage` 取结束说明），没有东西反过来依赖它，只有书库和路由调它。

## 和方案不一样的地方

- 原来打算把 `terminal_completion_note` 下沉到任务的数据结构上。拆完前两处，`merge → jobs`
  已经不在环里（只剩单向），这处就不动了。
