## 怎么做的

- 用户要求让 Sonnet 来看。分 6 块，每块一个 Sonnet 子代理，只读代码，不跑测试。
- 要找的是"状态会错、会对不上"的地方，不看代码风格：
  - 同一件事存在好几处，彼此对不上；
  - 多步更新做到一半失败，或者中途崩溃；
  - 两件事同时发生时互相抢；
  - 状态机跳步，或者终态被覆盖；
  - 重复调用上游；
  - 缓存过期了还在用；
  - 错误被吞掉，留下半截状态。

## 整体判断

**底层的纪律做得扎实**：
- 文件都是写临时文件再改名；Python 那边的断点、译文页、修订日志、请求日志都先 fsync 再改名。
- 任务的终态走 CAS，晚到的写入不会覆盖已经落定的终态。
- 事件流不丢、不重复，游标不会指错。
- 判断成功不只看退出码，还要产物齐全，并且逐页校验哈希。
- 断点的指纹覆盖了模型、页范围、术语表等配置，换了配置不会混着续跑。
- 凭据原子写，内联的 key 不落库。

**问题集中在"缝"上**，也就是记录写得对，但读记录、按记录做判断的那一方对不上：
1. 防重复调用上游的记录挂错了任务，或者从来没被标成"结果拿不准"，防护形同虚设。会重复计费。
2. 有好几种外部动作不通知 runner：
   - 强制删除；
   - 原地重跑；
   - API 抢先落终态；
   - 第二个 API 实例；
   - 恢复数据库。

   结果是任务卡住、被复活成幽灵行，或者运行记录停在"运行中"。
3. 两套修复规则互相矛盾：运行时维护书卡用一套规则，启动时用另一套规则把书卡全部重算。
4. 删除只管被删的那一个对象：不检查别的任务是否依赖它的产物，不清全文索引，不清文档目录。

## 一、先修：会花钱、会卡死，而且不会自己恢复

| # | 问题 | 出处 | 核对 |
|---|---|---|---|
| 1 | **OCR 防重复提交在默认流程上失效**。整本翻译任务把 OCR 放在子任务 `<id>-ocr` 里跑，"已经提交给上游"的记录挂在子任务名下。重试前的检查、失败诊断、"绑定已有回执"恢复，查的都是父任务。结果：崩溃或传输出错以后重试，会再向付费的 OCR 提交一次；绑定的回执永远读不到。现有测试都把记录直接放在任务自己名下，没有覆盖父子结构。 | 1#1、5#1 | 已核对：记录用子任务编号，查询用父任务编号 |
| 2 | **OCR 提交在请求过程中出错（超时、断连），记录不会被标成"结果拿不准"**，一直停在"已发出"。重试前只认"拿不准"这一种状态，所以会直接重发。生产代码里没有任何地方调用 `mark_pipeline_dispatch_ambiguous`。 | 5#2、1#1 | |
| 3 | **翻译、精修重启后自动续跑，不看请求日志**，会把重启前已经发出的请求再发一遍。手动重试反而要用户确认，OCR 这种情况也会拦下来，三处做法不一致。 | 5#3、6#6 | |
| 4 | **强制删除正在跑的任务或书，不通知 runner**。runner 继续跑、继续花钱；它下一次 CAS 写入时任务行已经不在了，会重新插入，任务被复活成一条没有书的"运行中"幽灵行。 | 1#5、2#1、3#5 | |
| 5 | **运行期没有"排队或运行中、却没有人在跑"的自愈**，只有启动时会修。任务会丢发射的几处：<br>• 认领失败被静默丢掉；<br>• 远端发射失败只打日志；<br>• 出错分支里 `let _ = persist_failed_job`。<br>另外 CAS 只看状态、不认是哪一次运行。取消以后马上原地重跑，旧 runner 的收尾会把新一轮的排队状态改掉；取消标志也会留在内存里，下一次原地重跑一开始就被取消。 | 1#2、1#3、1#7 | |
| 6 | **每次启动都把所有书卡重算成"最近一次成功的任务"**，没有成功任务就清空。运行时的规则是保留失败卡、优先显示在跑的任务，两套规则正好相反。重启以后，失败卡和进度卡都会消失。启动恢复把任务改成终态时，也不维护书卡和全文索引。 | 2#3、2#8 | 已核对 `backfill_active_jobs` |
| 7 | **取消抢在 runner 之前落了终态时，这一次运行的记录永远停在"运行中"**。之后改译文，登记会一直停在"等待"，读的时候也修不好。 | 4#1、1#8 | |
| 8 | **改译文时，Python 子进程如果被强行结束（客户端断开、API 关闭），页文件会领先于断点记录**。回滚写在异常处理里，强行结束时执行不到。之后每次改译文都返回 409 `publication_inconsistent`，渲染也会因为哈希对不上而失败，只有重跑翻译阶段才能恢复。 | 3#1 | |

## 二、其次：会错，但较难触发或影响面小

- **原地重渲染的旧 PDF**（1#4、3#2、6#8）：
  - `rerun.rs` 在校验之前就删掉旧的渲染结果和 OCR 子任务，请求失败的话旧 PDF 就没了；
  - 原地重渲染失败以后，任务丢掉了原本可用的译文 PDF，`previous_output_pdf` 没人再用；
  - 先删文件、再落库，中间没有并发保护。

  这一条也纠正了任务接口审计 B14："旧 PDF 被当成新结果"实际走不通，真正有害的是 `rerun.rs` 提前清理。
- **删除不完整**（2#2、2#4、2#5、3#10）：
  - 删任务不检查别的任务是否依赖它的译文目录，换字体重排的任务指向它的话，整本书的阅读入口会 500；
  - 删任务不清全文索引，搜索会命中已经删掉的任务；
  - 删书不清 `data/documents/<id>/`；
  - 老库里有收藏记录的书，删除时返回 500，不是文档里写的 409。
- **改了译文但没重渲染时，产物之间对不上**（3#3、3#4）：没有任何"PDF 已过期"的标记；Word 的缓存只比较 PDF 的修改时间；QA 和诊断报告不更新；合并阅读的指纹只算 manifest，不算页文件。
- **恢复数据库**（3#6）：备份里"排队/运行中"的任务原样带回来，要到下次启动才会对账，在那之前一直转圈。
- **杀进程不核对身份**（1#6、1#9、6#3）：
  - 同一个数据目录起第二个 API 实例时，它会在绑定端口之前对账，把第一个实例的 worker 杀掉；
  - 启动对账按库里记的旧 pid 杀整个进程组，不核对这个 pid 还是不是我们的 worker；
  - jobsd 的 `terminate` 收到 `pid=0` 时会杀掉自己的进程组。
- **读 stdout 出错**（6#1）：读取任务一出错就退出，worker 没人管；最后即使退出码是 0、产物也齐全，任务还是被判失败。我核对的情况是：读端退出后，"没有输出就超时"的看门狗还在，Python 往关掉的管道写会出错，所以"worker 跑完整本付费翻译"的可能性比报告说的小，存疑。
- **解压 MinerU 返回的包时不防 `../`**（6#10）：包来自外部服务，属于安全边界，建议跟第一节一起修。
- 其余几条：
  - 下载用的派生产物子进程没有超时，会把只有 2 个名额的生成通道占满（3#8）；
  - 提交接口没有幂等键（5#4）；
  - Python 模型客户端遇到 `choices: []` 这类意外返回，会漏掉释放并发槽（5#5）；
  - 合集 agent 工作区直接用书卡上的任务，会链到还在跑的半成品（2#7）；
  - 原地重跑以后，阶段快照按整个任务历史选，可能显示上一次运行的 `finished`（4#2）；
  - 可续跑的任务没有次数上限，会陷入崩溃循环（1#10）；
  - 从失败任务导入断点续跑以后，实时译文看不到继承来的页（6#2，存疑）。

## 三、低

剩下约 30 条低等级，见各块明细，这里不展开。主要是：
- 时间戳精度不一致（4#4）；
- SSE 不随任务终态结束（4#5，任务接口审计 B10 也提过）；
- 后台预热没有"完成"标记（4#3）；
- 封面写入不是原子的（3#7）；
- 领域识别超时的空结果被永久缓存（6#7）；
- 多用户额度的隐患（5#9，多用户已冻结）。

## 建议的修法和顺序

1. **OCR 防重复**（第一节 1、2、3）：开一个分支一起做。
   - 派发记录统一挂在父任务名下，或者查询时同时查 `<id>-ocr`。
   - 进程内的提交错误把记录标成"拿不准"。
   - 翻译自动续跑先看请求日志，有拿不准的就停下来，等用户确认。
   - 先写一个端到端测试复现：整本任务、崩溃、重试必须被 409 拦住；绑定回执以后不再提交。
2. **runner 感知外部动作**（第一节 4、5、7）：
   - CAS 带上"第几次运行"（attempt 代次），旧 runner 的写入一律落空；
   - 任务行不存在时不再插入；
   - 强制删除先取消 runner；
   - API 落终态时，把这一次运行的记录一起收尾；
   - 运行期加一个定时巡检，处理"排队或运行中、却没人在跑"的任务。

   这是 runner 的核心改动，要写足测试。
3. **书卡规则统一**（第一节 6）：启动回填改用运行时同一套规则，只修明显错的书卡，比如指向已删除的任务或别的书的任务。
4. **改译文的进程被强行结束**（第一节 8）：不用 `kill_on_drop` 去杀写回进程，改成超时后先发 SIGTERM、等它回滚；或者下次 PATCH 时先检测"页文件领先断点"，自动回滚。
5. 第二节按块分批修，解压防 `../` 跟第 1 步一起做。
