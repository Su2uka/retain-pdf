# 事件与进度

（代码基线：wt-int，即本地 main + 9 个 batch-1 修复。只读审计，没跑 cargo。）

## 结论

事件流（event feed）这一块设计得很严：来源身份、投递位置、显示顺序分开；文件靠 inode+大小+mtime+首尾指纹判断被替换或截断；半行不推进 offset；写入走 revision 的 CAS 和事务内的 epoch 校验；并发读者、重跑追加、状态变化、保留期清理都有测试。我没有找到会丢事件或重复事件的路径，也没有找到同一个 epoch 里 `seq` 回退或游标指向不同事件的路径（换 epoch 时游标一律作废）。
真正有问题的在这块的边上：pipeline attempt 的收尾，只有 runner 在"自己赢了终态 CAS"时才做。API 取消赢了这场竞争时，attempt 会永远停在 `running`，之后译文修订登记会永远停在 pending（问题 1）。另一块是阶段快照按"整个任务历史"选阶段，没按每次运行分开，原地重跑之后再取消或失败，`stage` 可能显示上一次运行的 `finished`（问题 2）。其余是低等级隐患。

## 问题

### 1. 取消（或任何输掉终态 CAS 的出口）后，pipeline attempt 永远停在 running，译文修订永远登记不上
- 等级: 中（状态错且不会自愈，但只影响取消后的译文修订和快照清理）
- 确认程度: 已确认（两条路径都读到底了；竞争的两种先后顺序都能到达。没有实跑）
- 场景:
  1. 一个 book/translate 任务在跑。runner 的 `read_stdout` 已经 `acquire_pipeline_attempt`（io_support.rs:61），attempt 状态 `running`。
  2. 用户 `POST cancel`。`cancel_job` 先 `terminate_runtime_process` 杀进程，然后非 OCR 任务由 API 自己用 CAS 写 `canceled`（cancel.rs:80-103）。这里**不调用** `finish_latest_pipeline_attempt`。
  3. 同时 runner 看到进程退出。如果 API 的 CAS 先成功，runner 那边：
     - `run_job` 的 CAS 返回 `updated=false`，走 `if !updated { … return Ok(()) }`（lifecycle.rs:253-266），**不收尾 attempt**；
     - 或 workflow 返回 Err，`spawn_job_with_workflow` 里 `!Canceled` 才调 `persist_failed_job`（lifecycle.rs:44-49），已经是 Canceled 就跳过；
     - `persist_failed_job`/`persist_canceled_job` 也只在 `updated` 为真时才 `finish_latest_pipeline_attempt`（lifecycle.rs:149-153、199-203）。
  4. 结果：任务 `canceled`，attempt 仍是 `running`，没有 `pipeline_attempt_terminal` 事件。全库唯一调用 `finish_latest_pipeline_attempt` 的地方只有 lifecycle.rs（三处，都在 CAS 赢了之后）、启动恢复、OCR 子任务收尾；API 的取消、重跑路径都没有。
  5. 之后用户对这个取消的任务做译文修订（PATCH 允许非 queued/running 的任务，edits.rs:56）。`publish_page` 看到该页最新一行属于 `running` 的 attempt，返回 `RunningAttempt`，不登记（revisions.rs:195-201、235-241）；接口回 `live_publication.status="pending"`。
  6. 读时自愈 `heal_live_translation_revisions` 只跳过 queued/running 的**任务**，对 canceled 任务照样调用 `publish_translation_revisions`，结果同样是 `RunningAttempt`；runner 终态时的 `publish_translation_revisions_after_terminal` 也一样。所以实时译文页快照、SSE 提交事件永远是修订前的文本，而磁盘上的页文件和之后的渲染用的是修订后的。
  7. `prune_superseded_revision_snapshots` 看到 running attempt 就直接返回 0（translation_revisions.rs:148），旧 generation 快照目录不再清理。
  8. 只有这个任务之后又走了一次原地重渲染并正常跑完（`acquire_pipeline_attempt` 会"续用"这条 running attempt，runner 赢了 CAS 时才收尾），才会补登记。
  - 同类的窗口：runner 赢了任务行 CAS 之后、`finish_latest_pipeline_attempt` 之前进程崩溃，任务是 succeeded 而 attempt 仍 running（启动恢复只看 status=Running 的任务）。另外 `finish_latest_pipeline_attempt(...)?` 出错会让 `run_job` 提前返回，跳过 `update_document_after_job`（书卡和全文索引，靠启动时 backfill 才纠正）。
- 位置: backend/packages/retainpdf-jobs/src/actions/cancel.rs:80-103；backend/packages/retainpdf-runner/src/job_runner/lifecycle.rs:41-49、142-153、192-203、253-281；database/retainpdf-db/src/db/pipeline/attempts.rs:180-253；database/retainpdf-db/src/db/pipeline/revisions.rs:195-201、235-241；backend/packages/retainpdf-data/src/translation_revisions.rs:148；backend/packages/retainpdf-jobs/src/progress/live_translation.rs:heal_live_translation_revisions
- 现有防护为什么不够: 收尾被写成"谁赢了终态 CAS 谁收尾"，但 API 取消是另一个会赢的写者，且它没带收尾。启动恢复只扫 `status=running` 的任务和"父任务已终态的 OCR 子任务"（startup_recovery.rs:67-80、188-222），不扫"任务已终态、attempt 还 running"。测试只覆盖了正常路径（revision_publish.rs:228 断言的是正常结束后没有 running attempt），没有取消后的用例。
- 建议修法: 让每个把任务行写成终态的出口都收尾 attempt：`cancel_job` CAS 赢了就调 `finish_latest_pipeline_attempt(.., "canceled")`；`run_job` 的 `!updated` 分支按库里实际终态收尾。再加一个启动时/读时的兜底：任务已终态而 attempt 仍 running 的，按任务状态收尾。对前端没有影响。

### 2. 原地重跑之后，阶段快照按整个任务历史选，终态任务的 `stage`/`stage_detail` 可能是上一次运行的 finished
- 等级: 低（只影响 `stage`、`stage_detail` 和事件时间线的展示，`status` 是对的）
- 确认程度: 已确认（读代码推出，没有实跑；没找到覆盖这个场景的测试）
- 场景:
  1. 任务 A 跑完，`succeeded`。事件里有 `stage=finished`（`job_stage_rank`=3）等历史事件。
  2. 用户对 A 发起原地重渲染/精修（`create_new_job=false`，rerun.rs:61、stage_retry.rs:136）。事件表和 `pipeline_events.jsonl` 都是追加的，旧事件还在，同一个 feed 里。
  3. 在重渲染产生第一条 rank≥3 的渲染事件之前，用户取消（排队中取消很容易），或者它在最前面失败。新增事件只有 `status_changed(queued→…)`、`stage=canceled/failed`（rank 0）。
  4. `select_main_stage_event` 在非 Running/Queued 时取 rank 最大的（snapshot.rs:135-140），选中的是第 1 步里的旧 `finished` 事件。`build_job_stage_view` 优先用 live 的 `stage`/`stage_detail`（stage_view.rs:22-34）。于是详情/列表里 `status=canceled`，`stage="finished"`，`stage_detail` 是上一次运行的完成文案。`should_keep_progress_stage` 只在选中的是 `failed` 事件时才生效，这里不触发。
  - Running 中的重跑不会受影响：Running 时先排除 terminal-done 事件，取时间最新的（snapshot.rs:125-134）。
- 位置: backend/packages/retainpdf-jobs/src/progress/live_stage/snapshot.rs:117-141；backend/packages/retainpdf-jobs/src/progress/stage_view.rs:22-34；backend/packages/retainpdf-core/src/models/job/stage.rs:202-223
- 现有防护为什么不够: 选择规则假设一个 feed 只有一次运行。原地重跑是唯一会让同一个 job_id 出现第二次运行的路径，规则没有按"本次运行的起点"（例如最近一次 queued/`pipeline_attempt_started`）切开。
- 建议修法: 终态任务选阶段时，只在最近一次运行的事件里选（以最后一次 `queued` 状态变更或最新 attempt 的起始为界）。对前端没有影响，只是 `stage` 字段值变对。

### 3. 后台阶段（render_prewarm）没有"完成"标记，失败和成功都报 3/3，终态任务仍带着它
- 等级: 低
- 确认程度: 已确认（官方文档里也承认是"仍然存在的不一致"）
- 场景:
  1. 预热线程成功时发 `stage_progress 3/3`（prewarm.py:128-141），失败时也发 `3/3`（prewarm.py:146-157），只有 payload 里多一个 `error_type`。预热线程崩了/被丢弃则最后一条停在 1/3 或 2/3。
  2. `latest_background_stages` 只取每个 key 的最新一条，没有"已结束"的判断（snapshot.rs:174-198）。`build_job_stage_view` 对任务状态不做过滤，只丢掉 `display_stage=="done"` 的（stage_view.rs:36-45）。
  3. 终态任务的 `background_snapshots` 里还留着它，`stages.render.progress` 会拿到残留的 2/3 或 3/3（`stage_progress` 先看后台快照，stage_view.rs:242+）。
- 位置: backend/pipeline/retainpdf_pipeline/render/source/prewarm.py:128-157；backend/packages/retainpdf-jobs/src/progress/live_stage/snapshot.rs:174-198；backend/packages/retainpdf-jobs/src/progress/stage_view.rs:36-45
- 现有防护为什么不够: docs/core/frontend/backend-changes-handoff.md 已把它写成"仍然存在的不一致"，让前端走 `stage_history` 绕开；后端没修。
- 建议修法: 终态任务直接返回空的 `background_snapshots`，并让预热失败发带 `lane=background` 的"失败/结束"标记而不是复用 3/3。这是行为改动，对前端是新增字段/去掉残留，需要在 api-reorg 记录里写清楚。

### 4. 事件时间戳精度不一致（DB 事件是秒，Python 事件是微秒），按字符串比较时同一秒内顺序是错的
- 等级: 低
- 确认程度: 存疑（精度差异和排序规则已确认；对用户可见的影响只在"没有 attempt 的旧任务"这类 JSONL 阶段事件和 DB 派生事件混合的情况，我没有构造出具体的错误展示）
- 场景:
  1. `now_iso()` 是秒精度 `…:00Z`（common.rs:71）。Python 写 `…:00.123456Z`（events.py:80）。字符串比较里 `.`(0x2E) < `Z`(0x5A)，所以同一秒内**所有 DB 事件都排在所有 JSONL 事件之后**，与真实先后无关。
  2. feed 导入批次内按 `ts` 排序（sync.rs:359-364），首次建 feed 的发布顺序也按 `ts`（event_feed.rs:274），阶段选择的 `latest_by_time` 也按 `ts`（snapshot.rs:247-255）。
  3. 对有 attempt 的任务，阶段/进度事件都来自 DB（JSONL 的同类事件被跳过，sync.rs:338-350），所以只有诊断类 JSONL 事件会在同一秒内被排到 DB 事件前面。没有 attempt 的旧任务才会让 JSONL 阶段事件和 DB 派生的 `stage_updated` 在同一秒内错序。
- 位置: backend/packages/retainpdf-core/src/models/common.rs:71；backend/base/retainpdf_base/events.py:80；backend/packages/retainpdf-jobs/src/progress/event_feed/sync.rs:359-364；database/retainpdf-db/src/db/event_feed.rs:274-276
- 现有防护为什么不够: 没有，tie-break 之后才用 seq。
- 建议修法: `now_iso()` 改毫秒或微秒精度，或比较前统一规整到同一精度。要同时核对保留期 cutoff（秒精度）的比较不被打破。对前端没有影响。

### 5. 实时译文 SSE 不会随任务终态结束，每个连接每 750ms 占一次查询槽
- 等级: 低（隐患）
- 确认程度: 已确认
- 场景:
  1. `GET …/live-translation/events` 的流永远循环（progress.rs:102-130），除非后端查询报错或客户端断开。任务早已 succeeded，仍然每 750ms 调一次 `run_job_query`。
  2. `QueryExecution` 只有 2 个槽、128 个 key（query_execution.rs:Default）。连接多了会得到 `too_many_requests`，流被"关闭"（progress.rs:120-127），EventSource 自动重连又进来。
  3. 另外同 key 的在途查询会被合并：写入刚完成后立刻读，可能 join 到写入之前就开始的那次查询，拿到旧结果（read-your-writes 不保证）。下一轮 750ms 会补上，所以只是短暂的。
- 位置: backend/api/src/routes/jobs/progress.rs:60-130；backend/packages/retainpdf-jobs/src/query_execution.rs
- 现有防护为什么不够: 没有终态收尾，也没有连接数上限。
- 建议修法: 任务已终态且没有新提交事件时发一次终止信息并关闭流。对前端：EventSource 需要处理流正常结束（这是行为改动，需写进对应文档）。

### 6. 读 stdout 的循环里，进度落库的任何错误都会让整个任务失败
- 等级: 低
- 确认程度: 存疑（错误传播路径已确认；"瞬时 DB 错误"是否会真实发生没确认。busy_timeout 默认 5s，event feed 首次发布 `publish_initial` 会在一个 Immediate 事务里对全部 feed 行做 ROW_NUMBER 重排，数据量大时可能持锁较久）
- 场景:
  1. `read_stdout` 对 `apply_durable_stage_observation`、`apply_durable_checkpoint`、`apply_durable_artifact_commit` 以及每行的 `cas_persist_job_with_resources` 都用 `?`（io_support.rs:78-107）。
  2. 任何一次出错（`stage order regressed`、`sequence regressed`、`stale pipeline cursor`，或者 SQLite busy 超时）都会让读取任务返回 Err；`drain_stdout` 里 `joined?`（execution.rs）把它冒泡成 `execute_process_job` 的 Err，随后 `persist_failed_job` 把任务写成失败。管道被关后，Python 下一次 print 还会 BrokenPipe，worker 也跟着死。
  3. 也就是说一次进度写入失败可以让已经花了钱的长任务整体失败，而不是只丢一条进度。逻辑错误（顺序回退）需要这样硬失败，瞬时错误则可以重试几次。
- 位置: backend/packages/retainpdf-runner/src/job_runner/process_runner/io_support.rs:78-107；backend/packages/retainpdf-runner/src/job_runner/process_runner/execution.rs:drain_stdout
- 现有防护为什么不够: 没有区分"数据不一致"和"数据库暂时忙"。
- 建议修法: 对 busy/locked 做有限次重试再失败；对 stdout 观测只有顺序类错误才硬失败。对前端没有影响。

## 查过、靠得住的

- **事件流不丢不重**
  - JSONL 增量读取：半行不推进 offset（files.rs:read_batch 的 `!complete → break`）；超过 4MB 的行跳过并告警；非 UTF-8 行跳过；每批最多 1MB/1024 行。
  - 文件被替换、截断、同长度重写：inode 变、大小小于 offset、大小相同但 mtime 变、首尾 256 字节指纹不符，都判为变化并整体重建（files.rs:71-85；测试 batch_tests.rs "partial_jsonl_append_rewrite_replacement_and_removal"、feed_recovery.rs "replacing_jsonl_invalidates_cursor_even_when_replacement_has_same_length"）。
  - 发布前再 inspect 一遍文件，替换/缩小就放弃本轮重试（sync.rs:430-440）。
  - Python 写入端是追加（`open("a")`），原地重跑不会截断 `pipeline_events.jsonl`；全仓库没有别处删除或截断它（只有 rerun.rs 删 OCR 子任务目录和 rendered 目录）。
- **并发读者**：`commit_event_feed` 是 Immediate 事务，校验 feed revision 和所有来源 revision，输了返回 false 让调用方重来；提交后再读一次 revision，不是自己的就放弃（sync.rs:455-464）。最多重试 8 次，仍冲突才回 503。测试 cursor_contract.rs "concurrent_readers_get_the_same_stable_feed_without_duplicate_imports"。
- **seq 与游标**
  - 同一 epoch 里 feed 的 `seq` 严格递增：增量发布从 `high_seq+1` 开始，只有真正插入成功才加一（event_feed.rs:246-256），`UNIQUE(owner, source_key)` 和 `UNIQUE(owner, event_id)` 防重复。
  - 每一次 reset（来源 revision 变、context 变、保留期 cutoff 变、文件被替换）都生成新 epoch，旧游标统一得到 410（read_events 的 `cursor.epoch != state.epoch`，以及 `read_event_feed_rows` 在同一事务里校验 epoch）。游标里还带批次上界，游标分页期间新追加的事件属于下一页。
  - API 重启后游标和事件 id 仍然可用（feed 持久化在 DB；测试 feed_recovery.rs "cursor_and_event_identity_survive_an_api_state_restart"）。
  - 事件 id 对没变化的物理文件保留 incarnation，重建后不变（sync.rs:256-271）。
  - 状态变化（含终态）会改 context，使游标失效，这是有意设计且有测试（"terminal_context_change_expires_cursor…"）。
- **`events` 表自己的 seq**：`append_event`、阶段观测、状态事件、修订登记都在 Immediate 事务里 `MAX(seq)+1` 插入；`event_source_versions` 的触发器记住历史最高 seq，seq 在删除后复用会 bump revision，使 feed 重建（测试 "db_sequence_reuse_after_deletion_does_not_reuse_event_identity"）。保留期清理会同时清 feed 项、bump 来源 revision、换 epoch，不会让过期历史"复活"。
- **阶段/进度的写入者**：运行中的任务行只有 runner 写（逐行 stdout、阶段推进、OCR 子任务镜像都走 CAS，只在 queued/running 时写，避免把取消盖回）；API 只在取消和提交/原地重跑时写任务行。取消 vs runner 的 lost update 都有 CAS 保护和注释。阶段推进（translation_flow_stage.rs:161、207）同样是 CAS。
- **阶段观测的 fencing**：`observe_pipeline_stage`/`commit_pipeline_units` 都在 Immediate 事务里校验 attempt 的 generation、worker_id、状态，并在同一事务内写事件行，所以阶段行、提交行和对应事件要么都在要么都不在；同一进度通道里 `progress_current` 只增不减（Python 侧和 DB 侧各做一次）；producer_seq 回退、阶段序号回退会被拒绝。
- **译文提交 vs 页快照 vs 修订登记**
  - `publish_translation_revision` 在一个事务里更新 `pipeline_units`、`pipeline_stages` 并追加 `pipeline_unit_committed` 事件，所以快照读到的行和事件流一致。
  - 对账幂等、按 producer_generation 单调，两次修订交错时旧的不会覆盖新的（`Superseded`）；写回成功但登记失败时，下一次 PATCH（含重发同一请求）或打开版面会补登记；读页快照时遇到旧 generation 被清理会重读一次 DB。
  - SSE 与列表接口用同一个函数 `load_live_translation_events_after`、同一个原始 seq，没有两套口径；SSE 的游标取 `after_seq` 与 `Last-Event-ID` 的较大值。
- **同一进度来源**：之前"数字一个来源、文案另一个来源"和"批次 vs 块"来回跳的问题，checkpoint 已不再写 job.progress（checkpoint_commit.rs 的注释），翻译进度只有 pipeline 的观测一个来源。
- **事件读取的脱敏**：`redact_job_events` 与事件一一对应，没有过滤，`event_id` 的 zip 不会错位。

## 没有深查、供其他人参考

- Python `PipelineEventWriter._seq` 的自增没有加锁，渲染预热线程和主线程共用同一个 writer（events.py:184、prewarm.py:33-43）。但 Rust 侧的 `producer_seq` 回退检查是按 `(job, attempt, stage_key)` 行做的，预热线程写 `render` 行、主线程此时写 `translate` 行，两者不在同一行，实际不会触发回退拒绝。若以后让它们写同一个阶段行，需要加锁。
- 崩溃留下的半行 `pipeline_events.jsonl` 会和 worker 恢复后追加的第一条拼成一条坏行，那一条会被"malformed event line skipped"丢掉（只丢一条诊断类事件，阶段事件走 stdout 不受影响）。
- `startup`、`provider` 之类 `job_user_stage` 不认识的阶段，`stage_transition` 不会落 DB（`durable_stage_key_for_observation` 返回 None），而 JSONL 里的同类行在 authority 模式下被跳过，所以这类"worker 已启动"诊断事件不出现在 feed 里；只是缺一条提示。
