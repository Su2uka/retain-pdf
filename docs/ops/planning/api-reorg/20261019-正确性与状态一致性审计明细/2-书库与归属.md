# 书库、书、任务归属（documents / jobs.document_id / active_job_id）

读的代码：integration worktree `wt-int`（下文路径都相对它）。

## 结论

这一块的主干是靠得住的：上传落库、整本删除（`delete_document_cascade`）、书卡指针在任务终态/取消时的回退（`active_job_after_success` / `release_document_active_job`）、合并阅读的指纹目录和原子发布，都是单事务或不可变目录，而且有针对性的测试。真正的问题集中在三类缝隙上。第一，`documents.active_job_id` 有两套互相矛盾的修复规则：运行时的 release 保留失败卡、优先在跑的任务，而每次 `Db::init`（API 和 jobsd 每次启动）都会跑的 `backfill_active_jobs` 无视这些规则，把没有成功任务的书的指针清成 NULL。第二，"删除"这件事只处理被删对象自己：强制删除运行中的任务不取消 runner，也不查别的任务是否还依赖被删任务的目录或译文；删书漏掉 `data/documents/<id>/` 之类的派生目录，删任务不重建全文索引。第三，运行时之外写终态的路径（启动恢复）绕过了书卡和全文索引的维护。没有发现会丢用户原文或让两本书互相串内容的问题。

## 问题

### 1. 强制删除运行中的任务/书不取消 runner，已删的任务行会被 runner 写回来
- 等级: 中（只有 `force=true` 才触发，但触发后状态错且不会自愈；还会继续烧 OCR/模型额度）
- 确认程度: 已确认（删除侧、写回侧的代码都读过；没有做真实运行复现，runner 下一次写库的具体时刻没追）
- 场景:
  1. 任务 J 在 running，`DELETE /library/books/J?force=true`（或 `DELETE /documents/:id?force=true`）。
  2. `ensure_deletable` 因为 force 放行（`books.rs:102`），然后直接删 jobs/events 行（`books.rs:62`、`documents.rs:171`）、删磁盘目录。整个流程没有调用 cancel，也不通知 runner。
  3. runner/子进程还在跑。runner 的进度、日志落库走 `persist_job_with_resources`（`job_events.rs:69-77`），底层是 `INSERT … ON CONFLICT DO UPDATE`（`job_writes.rs:59-64`）。行不存在时就是重新插入。终态写走 `cas_save_job`，它在"行不存在"时 `current_status` 为 None，跳过期望状态检查，同样 INSERT（`job_writes.rs:151-169`）。
  4. 结果：被删的任务几秒后以 running 回来，`document_id` 为 NULL（upsert 不写 document_id）。终态时 `job_document` 按 `upload_id` 重新归属（`lifecycle.rs:347`），书卡又被指过去；若是 `delete_document`，则 documents 行已没，job 变成没有书的孤儿。输出目录被删后流水线多半失败，于是出现一个"删了又冒出来的失败任务"。子进程在目录被删后继续消耗外部额度。
- 位置: `backend/packages/retainpdf-library/src/books.rs:45,62,102-110`；`documents.rs:147,171`；`database/retainpdf-db/src/db/job_writes.rs:59-64,151-169`；`backend/packages/retainpdf-runner/src/job_runner/lifecycle.rs:347`
- 现有防护为什么不够: 只有 `ensure_deletable` 的 409 保护，force 直接绕过。runner 侧没有"我的行被删了就退出"的检查（grep `deleted`/行缺失处理无结果）。测试里没有 `force=true` 的删除用例。
- 建议修法: force 删除先走 `cancel_job`（等 CAS 落终态、worker 退出）再删行；或者 CAS 写在行不存在时返回 false（不要 INSERT）。对前端无影响（前端没有传 force）。

### 2. 删除一个任务不检查别的任务是否还依赖它的产物，之后整本书的阅读入口会 500
- 等级: 中（会错，要把依赖它的任务也删掉才恢复）
- 确认程度: 已确认（Rust 侧到 Python 合并命令的路径都读过；没有真跑 Python）
- 场景:
  1. 书 D 有翻译任务 A（succeeded）。用户对 A 做"换字体重新排版"，产生 render 任务 R。R 的 `translations_dir` 指向 A 的 `translated/`（`render_flow_artifacts.rs:42,62`；`merge/reading.rs` 里 `producer_created_at` 的注释也写明这点）。
  2. 用户删除 A（`delete_library_book`，只删 A 和 `A-ocr`，`books.rs:38-67`）。A 的目录整个被删。
  3. 之后 `GET /documents/D/reading`：`job_merge_source(R)` 只要求 R 自己的 `rendered/*.pdf` 存在且页数对得上，`translations_dir` 用 `resolve_data_path` 解析、不检查是否存在（`merge/sources.rs:121-125`）。R 被放进合并计划，`artifacts_plan_json` 把已不存在的目录交给 Python `merge-translated-artifacts`；Python 在 `translation-manifest.json` 缺失时直接 `MergeArtifactsError`（`render/tools/merge_translated_artifacts.py:191-193`）。整个阅读入口返回 500，直到 R 也被删掉。
  4. 同类：直接引用被删任务 OCR（`artifact_job_id`）的翻译任务，之后重试/续跑才报错；比 1 轻。
- 位置: `books.rs:38-67`；`merge/sources.rs:121-125`；`merge/build.rs:127-145`（`artifacts_plan_json` 的 `translations_dir` 只检查 Some）
- 现有防护为什么不够: `reading_tests.rs:49 a_render_job_whose_producer_is_gone_falls_back_to_its_own_time` 只覆盖了"排序退回自己的提交时间"，没覆盖"产出者被删后合并怎么办"。
- 建议修法: `job_merge_source` 里要求 `translations_dir/translation-manifest.json` 存在，否则不参与合并；根本上删任务前查"还有谁引用我"（`translations_dir`、`artifact_job_id`）并 409。不影响前端字段。

### 3. 每次 `Db::init` 都跑的 `backfill_active_jobs` 和运行时的书卡规则相反：会把指针改成最好的成功任务，没有成功任务时清成 NULL
- 等级: 中（API 或 jobsd 重启就触发；只影响书卡展示/“当前任务”，任务本身不丢）
- 确认程度: 已确认（SQL 语义：`x IS NOT NULL` 在 x 非空时为真，子查询无行时 `SET active_job_id = NULL`）
- 场景:
  1. 书 D 只有一个任务 J，失败了（或还在 running）。书卡指向 J。`release_document_active_job` 的设计是"没有成功任务就保留失败卡，能看到错误、能重试"（`crud.rs:553-563` 及测试 `release_active_job_falls_back_only_when_…`）。
  2. 重启 API（`state.rs:44` `db.init()`），或单独重启远端 jobsd（`backend/jobs/src/main.rs:191` 同样调 `init()`）。`init` 末尾无条件调 `backfill_library_records` → `backfill_active_jobs`（`backfill.rs:209-221`）：`UPDATE documents SET active_job_id = (BEST_SUCCEEDED) WHERE active_job_id IS NOT (BEST_SUCCEEDED)`。BEST_SUCCEEDED 只看 succeeded，没有则为 NULL，于是 D 的 `active_job_id` 变 NULL。
  3. 失败卡消失。之后 J 如果是重启时恰好在跑的，终态失败时 `release_document_active_job` 要求"书卡仍指着它"才动（`crud.rs:569`），NULL 不匹配，卡不会回来。成功时 `active_job_after_success(current=None)` 会指回（所以成功路径自愈，失败路径不自愈）。
  4. 另一面：书有旧的成功任务 S 和正在跑的新任务 N，书卡指 N（提交时设的）。重启把卡改回 S，N 的进度从书卡消失，直到 N 成功。runtime 规则（`IN_PROGRESS_JOB_SQL`）明明规定在跑的优先。
  5. 此外 `init()` 在 `reconcile_owned_runtime`（`state.rs:51`）之前跑，回填看到的是"遗留 running"的旧状态。
- 位置: `database/retainpdf-db/src/db/documents/backfill.rs:11-17,209-221`；`database/retainpdf-db/src/db/db.rs:355`；`crud.rs:12-34,553-590`；`backend/api/src/app/state.rs:44-52`
- 现有防护为什么不够: 测试 `active_job_backfill_prefers_non_ocr_success_over_newer_ocr_job` 等只验证"有成功任务时换成最好的"，没有"无成功任务/有在跑任务"的用例。
- 建议修法: 回填只修"悬空/指向不存在的任务"和"指针为空且有成功任务"，别动指向在跑/失败任务的指针（即 WHERE 加 `AND (active_job_id IS NULL OR active_job_id NOT IN (SELECT job_id FROM jobs))` 或限制为终态成功的）。对前端：书卡 `active_job_id` 字段值更稳定，无字段变化。

### 4. 删任务（`delete_library_book`）不清全文索引，搜索会命中已删任务
- 等级: 中（会错，要等该书下次任务成功才自愈）
- 确认程度: 已确认
- 场景:
  1. 书 D 有任务 A、B，`blocks_fts` 里有 A、B 的行（`blocks_fts.job_id` 记的是提供该页的任务）。
  2. 删除 A：`delete_jobs` 只删 events 和 jobs（`crud.rs:602-607`），随后只 `reconcile_document_active_job`（只修指针）。没有调用 `rebuild_document_fts`/删 `blocks_fts` 行（对比 `delete_document_cascade` 会删，`crud.rs:521`）。
  3. 全文搜索 `search_blocks` 直接查 `blocks_fts`，返回 `job_id=A` 的命中（`search.rs:86-150`，不 join jobs）；点开命中拿到一个不存在的任务，AI 问答引用的页号锚点同理。
  4. 自愈条件：D 的下一个任务成功（`maintain_document_after_terminal` 里重建），或重启回填时发现有"比索引新的成功任务"。如果 D 只剩 A 一个任务被删，D 变"干净馆藏"，索引行永远留着，除非删整本书。
- 位置: `books.rs:57-82`；`crud.rs:488-495,602-607`；`documents/backfill.rs:76-120`
- 现有防护为什么不够: `backfill_fts_indexes` 只在"没有索引行"或"有更新的成功任务"时重建，不处理"索引里有已不存在的任务"。
- 建议修法: `delete_library_book` 在删除成功后对该书 `rebuild_document_fts`（失败只记日志即可），或 `delete_jobs` 同事务里 `DELETE FROM blocks_fts WHERE job_id IN (…)`。无前端影响。

### 5. 整本删除漏掉 `data/documents/<id>/` 和相关目录，留下无人回收的孤儿
- 等级: 低（磁盘泄漏；重新上传同一个 PDF 会复用同一个 document_id 目录）
- 确认程度: 已确认
- 场景:
  1. `delete_document` 删 job 目录、zip、upload 目录（`documents.rs:171-186`），不碰 `data/documents/<document_id>/`。那里有封面/缩略图/页预览（`derived_artifacts.rs:54-61`、`media.rs:151`）、合并阅读缓存 `merged/<指纹>/`（含整本合并 PDF 和译文副本，`merge/build.rs:176`）、AI 的 `ai/`（`ai_carryover.rs:159`）。
  2. 只有 `merge::build::prune_stale` 在**为同一本书构建新指纹时**清理旧合并目录；书已删就再不会触发。
  3. `version-upload-*` 的上传行指向 `data/operations/.../outputs/candidate.pdf`，删书只删其 `outputs/` 目录，operations 工作区其余部分（source 副本、program、日志）残留。
  4. 另外：DB 删完后文件删除任一步 `?` 失败会中断，剩下的文件没有任何扫描器回收（`cleanup.rs` 只清 events 和孤儿 uploads 行）。代码注释说"孤儿文件可回收、可重删"，但没有回收者，且重删会 404。
- 位置: `documents.rs:163-195`；`books.rs:112-124`；`app/cleanup.rs:93-136`
- 建议修法: 删书成功后 `remove_dir_all(data/documents/<id>)`；再加一个按 DB 反查的孤儿目录扫描（jobs/、documents/、uploads/ 下没有对应行的目录）。无前端影响。

### 6. 老库里的 `favorites` 行会让整本删除/删任务一律失败（500），且不是文档里写的 409
- 等级: 低（新代码没有写入 favorites 的路径，只影响老库/多设备同步进来的行）
- 确认程度: 存疑（FK 语义已确认；是否还有用户库里有 favorites 行没确认——`grep` 在 backend/database 里找不到任何 `INSERT INTO favorites`，只有同步引擎能写）
- 场景: `favorites.job_id REFERENCES jobs(job_id) ON DELETE RESTRICT`（`migrations/v04_favorites_job_fk.sql:6`），连接开了 `foreign_keys=ON`（`db.rs:191`）。`delete_document_cascade` 先删 jobs 行再删 documents 行（`crud.rs:509-535`），RESTRICT 在第一步就立刻报错，整个事务回滚，书删不掉；`delete_library_book` 同样。报错被 `From<anyhow::Error>` 变成 500。路由注释 `library_data.rs:190` 写的"被收藏引用 → 409"并没有实现。cascade 到 `favorites` 本来该由删 documents 行触发，但顺序反了。
- 位置: `crud.rs:509-535`；`books.rs:62`；`library_data.rs:189-190`
- 建议修法: cascade 里先删 documents 行（触发 favorites CASCADE），再删 jobs；或 `delete_library_book` 里先检查并返回 409。

### 7. 合集 agent 工作区对"单任务整本"的书直接用 `active_job_id`，不看状态，会链到在跑/失败的任务
- 等级: 中（会错，任务结束后刷新才对）
- 确认程度: 已确认
- 场景:
  1. 书 D 已有整本翻译 J1（succeeded）。用户再提交 J2（重新翻译），提交时书卡被设成 J2（`launcher.rs:162`）。
  2. `GET /collections/:id/agent-workspace`：`resolve_reading_target` 对 D 得到 `ReadingTarget::Job(J1)`，但 `collection_agent_workspace` 的闭包只处理 `Merged`，`Job`/`None` 都返回 None，"交回按 active_job 的逻辑"（`reading.rs:91`）。
  3. `ensure_collection_workspace` 取 `document.active_job_id` = J2 后只检查任务存在（`collection_workspace.rs:193-216`），不检查是不是 succeeded。工作区的 `books/<名>` 链到 J2 的任务目录（半成品或空），manifest 里写 J2。agent 读到的是没有译文的目录；J1 的完整译文被丢掉，而 `ReadingTarget::Job(J1)` 明明已经算出来了。
  4. 只有 J2 成功后下一次物化才对。
- 位置: `backend/packages/retainpdf-library/src/reading.rs:77-93`；`collection_workspace.rs:177-216`
- 建议修法: 闭包对 `ReadingTarget::Job(id)` 也返回该任务的根目录；`None` 时进 skipped（"还没有可用的翻译"）而不是退回 active_job。该路由是 `closed`（多用户关），单机可用。无前端影响。

### 8. 启动恢复把任务改成终态时不维护书卡和全文索引
- 等级: 低（只影响展示，下次重启回填会纠正一部分）
- 确认程度: 已确认（路径读过）；影响面取决于上面第 3 条
- 场景:
  1. 任务 J 运行中进程崩溃，且 J 的渲染产物已提交。重启后 `reconcile_stale_running_jobs` 把 J 改成 Succeeded（`startup_recovery.rs:96-112,146`）或 Failed，直接 `persist_job_with_resources`，不经 `run_job` 的终态处理，所以不调用 `maintain_document_after_terminal`（不设书卡、不 `rebuild_document_fts`）。
  2. J 成功后书卡仍指向旧任务/NULL，J 的页不在搜索索引里。下一次启动 `backfill_active_jobs` 和 `backfill_fts_indexes` 才会纠正（后者只在"有 created_at 更新的成功任务"时重建，若 J 比索引里最新任务更早提交则不会补）。
  3. `settle_orphaned_ocr_children`（`:213`）同理，但子任务不参与书卡。
- 位置: `backend/packages/retainpdf-runner/src/job_runner/startup_recovery.rs:96-146,213`；对照 `lifecycle.rs:291-319`
- 建议修法: 恢复完成后对涉及的书统一调一次"书卡 + 索引"维护（就是 `maintain_document_after_terminal` 的那段），或给回填加上"已 succeeded 但不在索引里"的判据。

### 9. 提交类入口在任务已落库并启动之后才报错，调用方会以为没建成
- 等级: 低
- 确认程度: 已确认（代码路径）；触发需要数据库临时失败/并发删书，不易遇到
- 场景:
  - (a) `submit_job`：`persist_and_launch` 已落库、已 `runtime.launch`，然后 `for_document` 的归属校验 `document_id_for_job != document_id` 返回 internal 错误（`submit.rs:149-156`）。任务在跑，客户端收到 500，重试就会得到第二个任务并重复计费。触发条件：`link_new_job_to_document` 的写库失败（它只记日志，`launcher.rs:160-165`）、或此时这本书恰好被并发的 `delete_document` 删了（`require_document_upload` 到落库之间没有锁）。
  - (b) `submit_segments` 分段提交：校验全部通过后逐个 `create_document_submission(...)?`（`translate.rs:151-153`），第 k 段失败时前 k-1 个任务已经启动，调用方只看到错误，看不到已建任务的 id（`sibling_job_ids` 只在全成功时返回）。注释里说要避免"半截提交"，但只防了校验失败，没防创建失败。
- 位置: `lifecycle/creation/submit.rs:149-156`；`library/src/translate.rs:146-160`
- 建议修法: (a) 归属校验放到 `launch` 之前，或失败时返回已建任务；(b) 失败时在错误里带上已建任务 id，或回滚（取消已建的）。

### 10. 同一内容重新上传/回填会用原始 PDF 的页数、字节数、文件名覆盖文档元数据，而当前源可能已是编辑后的版本
- 等级: 低
- 确认程度: 存疑（需要"编辑版本页数与原件不同"才可见；没确认 restricted page program 能否改页数）
- 场景:
  1. 书 D 提交过文档操作，`commit_document_candidate` 之后 `project_committed_candidate_as_source` 写一条 `version-upload-<v>` 上传并 `upsert_document_from_upload`，documents 的 `page_count/bytes` 变成新版本的值（`source_projection.rs:86-107`）。
  2. 用户又上传同一个原始 PDF（哈希相同，`staging.rs:100` → `upsert_document_from_upload_on` 的 `ON CONFLICT DO UPDATE`，`crud.rs:153-185`），或 `adopt_job_source_document` 命中旧上传（`source_document.rs:31-35`，用 `upload_with_content_hash` 取**最早**的上传）。`page_count/bytes/source_filename` 被改回原件的值，而 `find_upload_for_document` 仍优先返回 version-upload（`crud.rs:364-405`）。文档记录（页数）与实际源 PDF 不一致；`media.rs:107` 的页预览按 `document.page_count` 限页。
  3. 同一条链上的非原子：`commit_document_candidate`（DB 里改 `active_version_id`）与 `project_committed_candidate_as_source`（写 upload + 更新 documents）是两步（`actions.rs:76-79`）。两步之间失败/崩溃，`active_version_id` 已指向新版本但没有 version-upload 行，`find_upload_for_document` 退回原上传。只有客户端重发 commit（Committed 状态下会重新投影，`actions.rs:56-58`）才修复，没有服务端自愈。
  4. 新任务按当前源（编辑版）翻译，旧任务的 `ocr_page_numbers` 是按旧页码，合并计划按新页数铺，可能错位（未深究）。
- 位置: `crud.rs:153-185,364-405`；`source_projection.rs:86-107`；`actions.rs:56-79`；`source_document.rs:31-35`
- 建议修法: `upsert_document_from_upload_on` 只在 INSERT 时写 page_count/bytes，ON CONFLICT 只更新 `updated_at`（或在有 `active_version_id` 时不改）；commit+投影放进同一个 DB 事务。

### 11. 删书和提交/上传并发时的窗口（TOCTOU）
- 等级: 低
- 确认程度: 存疑（逐步骤的时序是读代码推出的，没有复现）
- 场景:
  - `delete_document` 先快照 `job_ids_for_document` 和 `uploads_for_document`，之后才开事务（`documents.rs:139-171`）。快照之后新提交的任务（document_id=D）不会被删，随后 documents 行和 uploads 行被删、上传文件被删，留下一个源文件已没的运行任务和 `document_id` 指向不存在文档的 jobs 行。
  - 同时另一次同内容上传（新 upload_id）在快照之后落库：事务删了 documents 行但没删这条新 upload 行（不在 `upload_ids` 里），留下"有 upload 无 document"；孤儿上传 GC 会在 `orphan_upload_retention_hours` 后清掉（`retention.rs:93-134`），所以不会永久残留，但这期间用这个 upload_id 提交的任务 `link_job_to_document` 会把 `jobs.document_id` 指向不存在的文档。
- 位置: `documents.rs:139-171`；`crud.rs:509-535`
- 现有防护: 事务内删的是快照里的行；没有把"快照"放进同一事务。
- 建议修法: 在 IMMEDIATE 事务里重新取 job/upload 列表再删，文件路径用事务内的结果。

### 12. 全文索引重建在同一本书上并发完成时可能后写覆盖先写
- 等级: 低
- 确认程度: 存疑（需要同一本书两个任务几乎同时成功；锁/事务本身是对的，问题在"读列表"和"写"之间没有串行化）
- 场景: 书 D 的任务 A、B 同时在跑。A 终态后 `rebuild_document_fts` 读 `list_jobs_for_document`（此时 B 还没成功）→ B 终态并完成自己的重建 → A 的重建事务后提交，把索引替换成"没有 B"的版本（`search.rs:50-82`，整本 DELETE 再 INSERT）。若 B 的 `created_at` 早于 A（旧任务后完成），`fts_backfill_targets` 的判据是 `j.created_at > i.newest`（`backfill.rs:96-117`），也不会在下次启动补上。
- 位置: `lifecycle.rs:312-316`；`search.rs:50-82`；`backfill.rs:96-117`
- 建议修法: 重建时在写事务内读任务列表，或对每本书用一把互斥。

### 13. 上传的 `content_hash`（即 document_id）是修复前的原始字节的哈希
- 等级: 低（隐患）
- 确认程度: 已确认
- 场景: `prepare_upload` 对收到的字节算 sha256（`staging.rs:64`），之后若 PDF 解析失败，会用 PyMuPDF 原地修复上传文件（`service.rs:115`）。存盘的文件不再是这个哈希对应的内容。同一个坏 PDF 再传仍得到同一个 document_id（所以去重没问题），但 `backfill_upload_hashes`（`backfill.rs:151-179`）或 `adopt_job_source_document`（`source_document.rs:28`，对盘上文件重新哈希）对同一份文件算出的是另一个哈希，会生成第二本"同一本"书。
- 建议修法: 约定 document_id 的含义，要么哈希修复后的文件，要么注释清楚；至少回填别对已有 content_hash 的上传重算。

### 14. 崩溃留下的孤儿目录没有回收者
- 等级: 低
- 确认程度: 已确认
- 场景: 上传目录在 `prepare_upload` 里先写文件，DB 发布在后；崩溃落在中间会留下 `uploads/<id>/`（`PendingUpload` 的 Drop 只管正常失败）。`adopt_job_source_document` 的 `copy_into_uploads`（先写文件后写库，`source_document.rs:74-100`）同理。清理器只处理 DB 里已有的行（`cleanup_orphaned_uploads`），不扫目录。
- 建议修法: 同第 5 条的目录对账扫描。

## 查过、靠得住的

- 整本删除：`delete_document_cascade` 把 job、events、upload、blocks_fts、documents 行放在一条 IMMEDIATE 事务里（`crud.rs:509-535`），文件在事务成功后才删，失败的最坏结果是孤儿文件而不是悬空索引；有测试覆盖。
- 书卡回退：`active_job_after_success`（`active_job.rs`）把"旧任务后完成不能顶掉新任务"、"OCR 不顶掉翻译"、"失败/取消的卡被成功接管"都做成了纯函数并有 12 个用例；`release_document_active_job` 在取消（`cancel.rs:105-121`，CAS 赢了才调）和 runner 的各条终态路径（`lifecycle.rs:154,204,287,337`）都调用，CAS 输家走 `release_document_after_foreign_terminal`，没有漏掉的终态写入点（除第 8 条的启动恢复）。
- `documents.active_job_id` 指向别的书的任务：所有设置点（`launcher.rs:162`、`lifecycle.rs:311`）的 document_id 都是从该任务解析出来的；没有发现跨书指针。悬空指针由 `reconcile_document_active_job`（删任务后）和回填兜底。
- 任务归属 `jobs.document_id`：建任务入口（`link_new_job_to_document`）按 upload → `source.artifact_job_id` → `derived_from` 三级解析；OCR 子任务在建行后立即归属（`translation_flow_child.rs:119`）；provider 下载的源文件走 `adopt_provider_source_document`；`backfill_job_document_links` 补老数据，包括只带 `artifact_job_id` 的任务。重试、重跑、从产物重渲染都有覆盖。
- 上传：上传行和文档行在同一事务里发布（`save_upload_with_document_for`，测试 `upload_and_document_publish_rolls_back_and_preserves_deduplication`）；同一内容并发上传是两行 upload + 一行 document（`ON CONFLICT`），不会出现重复文档；失败路径由 `PendingUpload` 的 Drop 清目录。孤儿上传 GC 排除了有 documents 行/任务引用的上传。
- 合并阅读：产物目录名是内容指纹（含合并器版本、源 PDF、每页来源、每个任务的 PDF/manifest/OCR 文档的大小+mtime），build 在临时目录里完成两步后 `rename` 发布，并发构建同一指纹时输家丢弃自己的；sidecar 先写临时文件再 rename，崩溃后再次请求会补写；旧目录 24 小时后才清，虚拟任务 id 读的是不可变目录，打开期间新任务完成不会换掉；`load_virtual_job` 只依赖 base 任务行，被删时 404 而不是读到错数据。删除较新的任务会改变指纹（有测试 `deleting_a_newer_job_changes_the_fingerprint…`）。
- 合集/文件夹：`collection_documents` 对 documents 和 collections 都是 `ON DELETE CASCADE`，且连接开了 `foreign_keys=ON`，删书不会留悬空成员；`add_documents_to_collection` 在事务里 `INSERT OR IGNORE`；父文件夹被删时子文件夹 `SET NULL`，不会出环。
- 元数据：`update_document_fields` 和 `apply_document_metadata_suggestion` 的标题锁在事务内（后者 IMMEDIATE），用户改名后建议不会覆盖；`list_documents_with_total` 用同一快照读列表和总数；书页数在列表/详情里统一来自上传记录（`SummaryCache::book_page_count` 是请求级缓存，没有跨请求的陈旧问题）。
- 摘要缓存：`SummaryCache` 生命周期只在一次请求内；封面/缩略图/页预览走 `cached_output_is_fresh` 的 mtime 比较，源文件更新后会重新生成。（浏览器侧页预览是 `max-age=1year, immutable` 且 URL 不带版本，换了编辑版后客户端可能看到旧图——前端当前没用这个接口，未列为问题。）
