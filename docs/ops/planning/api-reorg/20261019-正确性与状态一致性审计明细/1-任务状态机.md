# 任务状态机与运行（提交到终态的整条链）

代码基线：wt-int（本地 main + 9 个 batch-1 修复）。下文路径省略前缀 `backend/packages/`，`runner/` = `retainpdf-runner/src/job_runner/`，`jobs/` = `retainpdf-jobs/src/`。

## 结论

runner 内部的"终态不被覆盖"做得相当扎实：所有阶段推进、进度、取消收尾都走 `cas_persist_job_with_resources(.., ["queued","running"])`，driver 去重、启动恢复（孤儿进程、死 pid、可续跑、父已终态的 OCR 子任务、卡在 queued 的任务）都有对应代码和测试。真正的洞集中在三类地方：
（1）**OCR 的"请求结果不确定"防重复提交机制，在最主要的 Book 路径上整个失效**——派发记录写在 `<id>-ocr` 子任务名下，而检测、恢复、回执种子都按用户看到的父任务 id 去找（高）；
（2）**CAS 只看 status，不认"哪一次运行"**，加上"原地重跑"是无条件整行覆盖、driver 认领失败时静默丢弃发射，导致任务可以停在 queued 没有任何 driver，运行期没有任何自愈（只有启动时修）；
（3）几个"外部动作不通知 runner"的口子：强制删除运行中的任务、同一数据目录起第二个 rust_api、`rerun.rs` 在校验前就把旧 PDF 删掉。
审计表 B14（retry-stage 原地渲染不清 rendered/ 和 OCR 子任务）经核实：不一致属实，但"旧 PDF 被当成新成功"走不通；反而是 `rerun.rs` 的清理才有害。

## 问题

### 1. Book 任务上的 OCR 歧义防护整个失效：派发记录在 `<id>-ocr` 名下，检测和恢复按父任务 id 找
- 等级: 高（防的是重复计费；主路径上无声失效，且"绑定已有回执"恢复会再提交一次）
- 确认程度: 已确认（静态逐步追踪；现有测试都直接拿"任务 id 自己"当派发持有者，没有任何端到端用例走 父任务→`-ocr` 子任务）
- 场景:
  1. 用户提交 Book 任务 `S`（网页主路径）。`run_job_with_ocr` 建子任务 `S-ocr`，OCR 在子任务里内联执行（`runner/translation_flow.rs:176-181`）。
  2. 传输层的 `begin_ocr_dispatch(deps, job, ..)` 里 `job` 是子任务，所以 attempt 和 `pipeline_dispatches` 的 `job_id` 都是 `S-ocr`（`runner/ocr_flow/dispatch_journal.rs:24-27`，调用点 `ocr_flow/mineru.rs:50`、`paddle.rs:57/137`）。
  3. 在"意图已落库、回执未落库"之间进程崩溃，或传输层出错：派发状态停在 `intent`。重启时父任务 `S` 没有自己的 running attempt（attempt 在子任务名下），被判 Failed（"worker_process_missing"），子任务被 `settle_orphaned_ocr_children` 收成 Failed（`runner/startup_recovery.rs:182-221`）。派发记录仍是 `intent`，没有人把它改成 `ambiguous`。
  4. 用户点"重试/重跑 S"：`ambiguous_ocr_dispatch(db, "S")` 按 `job_id = S` 查 `pipeline_dispatches`，查不到（`jobs/actions/ocr_ambiguity.rs:106-113`；`rerun.rs:77`；`stage_retry.rs:81-92`）。没有 409，直接 `submit_job` 建新 Book 任务 → 新子任务 → 再向 MinerU/Paddle 提交一次，重复计费。`reports/failure.rs:15-19` 的诊断也按 `S` 查，页面上看不到 `ocr_request_ambiguous`。
  5. 即使是"能被检测到"的独立 OCR 任务（workflow=ocr）走 `bind_existing_receipt`：`build_retry_request` 对 Ocr 阶段固定建 **Book** 工作流（`jobs/actions/stage_retry_request.rs:6-12`）；`create_ocr_recovery_job_state` 把回执种子和 attempt 种在新任务 `R` 名下（`database/retainpdf-db/src/db/ocr_recovery.rs:68-101`），但 R 的 OCR 实际在子任务 `R-ocr` 里跑，`begin_pipeline_dispatch` 按 `R-ocr` 查不到回执 → 返回 `Send`，**绑定的回执从不被读取，照样重新提交**。种下的 R 的 `ocr` attempt 还会被 `acquire_pipeline_attempt(R, .., "translate")` 当成同一个 running attempt 续用（`attempts.rs:46-80`，`effective_stage_key` 取旧的 `current_stage`），后续 translate/render 的持久化观测挂到 `ocr` 阶段上，`apply_durable_artifact_commit` 因 `stage_key != "render"` 直接跳过。
  6. 另：`mark_pipeline_dispatch_ambiguous` 在生产代码里没有任何调用（`database/.../dispatches.rs:163`），`intent → ambiguous` 只发生在"同一个 job id 的 attempt 被重新认领"时（`dispatches.rs:62-77`）。所以不重启的传输错误（响应丢失）之后，独立 OCR 任务的 `intent` 也不会被识别为 ambiguous，用户重试同样不被拦（这一条属设计缺口，存疑，取决于是否打算只靠重启触发）。
- 位置: `runner/ocr_flow/dispatch_journal.rs:24-47`；`runner/translation_flow.rs:176-181`；`jobs/actions/ocr_ambiguity.rs:35,106-113`；`jobs/actions/stage_retry_request.rs:6-12`；`database/retainpdf-db/src/db/ocr_recovery.rs:68-101`；`jobs/reports/failure.rs:15-19`；`database/.../pipeline/dispatches.rs:163`
- 现有防护为什么不够: 测试 `ambiguous_ocr_requires_explicit_resolution_and_can_bind_existing_receipt`（`api_tests/jobs_retry/retry_stage.rs`）、`service_restart_preserves_bound_ocr_receipt_recovery`（`app/state/tests.rs`）、`jobs/tests/startup_process_recovery.rs`、`retainpdf-data/tests/pipeline_*` 都是把派发直接种在任务自己名下、且只检查 DB 种子，不跑 runner；真实的父子结构没有被覆盖。
- 建议修法: 让 OCR 子任务的派发/attempt 记在父任务名下（`begin_ocr_dispatch` 用 `output_job_id_override`/父 id 做 key），或者 `ambiguous_ocr_dispatch`/诊断/恢复种子都同时按 `<id>-ocr` 查和种；补一个"Book 任务 → 崩溃 → 重试被 409 / 绑定回执后不再提交"的端到端用例。对前端无影响（只会多出本来该有的 409 和 `ocr_ambiguity` 字段）。

### 2. 运行期没有"queued/running 但没有 driver"的自愈，只有启动时修；发射丢失即永久卡住
- 等级: 中（卡死，不会自愈，但用户能取消 queued 的任务；running 的 OCR 任务连取消都无效）
- 确认程度: 已确认（各个"丢发射"的来源都追到了代码；driver panic 一项是推断，存疑）
- 场景（任选其一都会留下 DB 行 queued/running、没有 driver）:
  a. 壳/jobsd 分离模式下发射失败：`launch_remote` 用 `tokio::spawn` fire-and-forget，HTTP 失败只 `tracing::error`（`jobs/runtime_gateway.rs:100-111`、`api/src/app/jobs.rs:63-66`）。任务行已落库为 queued。jobsd 没重启就不会再有人看这一行（`requeue_stuck_queued_jobs` 只在 jobsd 启动时跑，`backend/jobs/src/main.rs:211`）。壳在远端模式下启动不做任何恢复（`api/src/app/jobs.rs:19-22, 34-36`）。壳在"落库之后、POST 之前"崩溃同理。
  b. driver 认领失败被静默丢弃：`spawn_job_with_workflow` 里 `claim` 返回 None 就直接 `return None`，`spawn_job` 还把返回值丢了（`runner/lifecycle.rs:26-41`）。launch 接口照样回 `accepted:true`（`backend/jobs/src/main.rs:76-88`）。见问题 3。
  c. driver 自己出错/panic：`run_job` 的错误分支是 `if let Ok(job)=get_job { let _ = persist_failed_job(..) }`（`runner/lifecycle.rs:44-51`），若这次读/写也因 SQLite 忙等失败，行停在 queued/running；整个 runner 没有任何 `catch_unwind`/JoinHandle 检查，tokio 任务 panic 只打一行日志，行留在原状态、worker 子进程不被杀（子进程没有 kill_on_drop）。
  d. 此时用户的操作：queued 任务 → 取消可行（API 直接 CAS Canceled，`jobs/actions/cancel.rs:78-96`）；**running 阶段的 OCR 任务** → `cancel_job` 只登记取消标志、不写库（`cancel.rs:54-77`，把终态交给 runner 检查点），没有 driver 就永远不会落终态，接口还返回 200，重复点取消无效，重跑被 409 拒绝（`rerun.rs:99-103`）。
- 位置: `runner/lifecycle.rs:26-54, 214-281`；`jobs/runtime_gateway.rs:100-111`；`api/src/app/jobs.rs:33-46, 58-74`；`backend/jobs/src/main.rs:76-88, 192-216`；`jobs/actions/cancel.rs:54-77`
- 现有防护为什么不够: 启动恢复（`reconcile_stale_running_jobs` / `requeue_stuck_queued_jobs`）覆盖崩溃，但 `list_stuck_queued_job_ids` 文档明确"只许启动时调"（`database/.../pipeline/queries.rs:88-94`），因为没有运行时的 driver 登记可比对；没有周期性巡检。
- 建议修法: 在 driver 登记的所有者进程里（进程内=壳，远端=jobsd）加一个低频巡检：库里 queued/running 超过 N 秒、`JobDriverRegistry` 里没有且无活 pid 的任务，按启动恢复同样的规则处理；`claim` 失败要返回错误或至少落日志/事件；`launch_remote` 失败要重试并最终把任务标成 failed。对前端无影响。

### 3. 原地重跑（`relaunch_in_place`）是无条件覆盖 + 旧 driver 的收尾 CAS 认不出"不是同一次运行"
- 等级: 中（窗口窄，但一旦命中任务会停在 queued 没人管，或被旧运行的 Canceled 盖回）
- 确认程度: 已确认（代码路径通；窗口长短取决于旧 driver 收尾耗时，存疑）
- 场景 A（重跑被旧 driver 的收尾覆盖）:
  1. 非 OCR 任务运行中，用户取消：`cancel_job` 杀进程、CAS 写 Canceled（`jobs/actions/cancel.rs:50-52, 86-96`）。旧 driver 此时还在收尾（`collect_process_execution` 排空 stdout 最多 30s，再 `finalize_completed_process`，`runner/process_runner/execution.rs:160-170`），它的 `JobDriverGuard` 还在登记表里。
  2. 用户立即点"重新渲染"（`retry-stage render create_new_job=false` 或 `rerun`）：状态是 Canceled → 通过检查；`prepare_in_place_render_job` 把行重置为 Queued；`persist_and_launch` 用无条件 `persist_job_with_resources` 整行覆盖（`jobs/lifecycle/creation/submit.rs:191`）。
  3. `deps.runtime.launch` → `spawn_job` → `claim` 失败（旧 guard 还在）→ 发射被静默丢弃（问题 2b）。
  4. 旧 driver 的 `run_job` 末尾 CAS 的 `expected = ["queued","running"]`，而行现在是新的 Queued → CAS 通过，把旧运行的 Canceled 快照写进来（`runner/lifecycle.rs:253-266`）。结果：用户的重跑被无声取消，一次 `finish_latest_pipeline_attempt(canceled)` 和书卡处理照常走。
- 场景 B（成功后立刻重跑）: `run_job` 先 CAS 写 Succeeded，然后才做收尾（结束 attempt、登记修订、`update_document_after_job` 里重建 FTS 等，`runner/lifecycle.rs:267-280`），guard 要等整个任务结束才放。这段窗口内发起原地精修/重渲染 → 行被重置为 Queued、发射被丢弃 → 任务永远 queued（用户可取消；不取消只有重启能修）。
- 场景 C（两个并发的原地重跑）: `rerun_submission`/`retry_stage_submission` 都是"读任务 → 判终态 → 清理/准备 → 无条件落库 → 发射"，没有锁也没有"仅当当前是终态才改成 queued"的 CAS（`rerun.rs:24-61`、`stage_retry.rs:123-136`）。两个请求都通过检查；第二个的无条件 `save_job` 把第一个已进入 Running 的行重置回 Queued（并且 `rerun.rs:48-54` 的 `remove_dir_all(rendered)` 会在第一个渲染进程运行中把输出目录删掉）；第二个的发射因 claim 失败被丢弃。
- 位置: `jobs/lifecycle/creation/submit.rs:162-200`；`runner/lifecycle.rs:26-54, 253-280`；`jobs/actions/rerun.rs:24-61, 98-152`；`jobs/actions/stage_retry.rs:123-136`；`database/retainpdf-db/src/db/job_writes.rs:123-166`
- 现有防护为什么不够: CAS 只比较 status 字符串，没有"运行代次"（run epoch）；`repeated_launch_has_one_driver_even_while_queued` 只测"同时重复发射只有一个 driver"，不测"driver 收尾中行被重新排队"。
- 建议修法: 原地重跑改成 CAS（`expected = 终态集合`，只在行仍是终态时才重置为 Queued，否则 409）；给 run 加单调的 `run_id`/`started_epoch`，driver 的所有 CAS 同时比对它；`claim` 失败时让 launch 返回 busy 并由调用方报 409/排队重试。对前端：只会多出 409（已有"任务在跑"的处理）。

### 4. `rerun.rs` 在校验和发射之前就把旧 PDF 和 OCR 子任务删了；B14 的核实结论
- 等级: 中（失败时丢掉用户已有的好 PDF；不影响成功路径）
- 确认程度: 已确认
- 场景:
  1. 任务 `J`（Succeeded，用 Rust model executor：`execution_connection` 有值，且环境没开 `RETAIN_MODEL_EXECUTOR_ENABLED`/`RETAIN_MODEL_WORKER_ENABLED`），用户点"继续/重跑"，`resume_plan` 判定可原地重渲染。
  2. `rerun_submission` 先 `delete_job("J-ocr")`、删 `jobs/J-ocr` 目录、`remove_dir_all(output_root/J/rendered)`（`jobs/actions/rerun.rs:28-54`），然后才 `prepare_in_place_render_job(...)?`、`clear_pending_refine_override(...)?`、`relaunch_in_place(...)?`。
  3. `persist_and_launch` 里 `uses_model_executor()` 且环境未开 → 返回 503（`submit.rs:182-187`）；同样的位置还有 `platform.resolve()`、`reserve_for_job`、`persist_job_with_resources` 失败。请求失败了，但 `rendered/` 已清空；`J` 仍是 Succeeded、`artifacts.output_pdf` 指向一个不存在的文件，下载/阅读都 404；`-ocr` 子任务行（连同级联删除的 attempt/事件）也没了。
  4. 即便成功路径，这也和设计相悖：`job_merge_source` 明确写着"原地重跑还在排队：上一份 PDF 还在磁盘上，就用它"，`reset_render_artifacts` 特意把旧路径存进 `previous_output_pdf`（`library/src/merge/sources.rs:78-90`、`rerun.rs:154-167`，测试 `in_place_rerun_keeps_the_previous_pdf_for_reading_until_it_runs`），而 `rerun.rs:48-54` 在这之前就把它删了，于是排队期间 `.filter(|p| p.is_file())` 为空，整本书的合并读取少了这个任务的页；渲染失败时用户也没有任何旧 PDF 可退回。
- B14 核实: `stage_retry.rs:123-136` 的原地渲染路径确实不删 `rendered/` 和 `-ocr` 子任务（与 `rerun.rs` 不一致，属实）。但"旧 translated.pdf 被完成检测当成新成功"**走不通**：`output_pdf` 只由 worker stdout 里的 `artifact_published` 事件写入（`runner/stdout_parser/artifact_rules.rs:25-34,115`），`reset_render_artifacts` 已把它清为 None（`rerun.rs:154-167`），成功契约要求 worker 退出码 0 且发布了 output_pdf 并且文件存在（`runner/process_runner/completion_pipeline.rs:44-53`、`runner/process_contract.rs validate_render_outputs`），产物路径解析只看 DB 登记、没有按目录约定回退（`core/src/storage_paths/resolvers.rs:56-59`）。所以 stage_retry 不清理反而更接近设计；该清的不一致应往 `stage_retry` 靠拢，而不是把 `stage_retry` 改成也清。遗留的小问题: `-ocr` 子任务行在 stage_retry 路径下不删，只留一个无害的孤儿行，`prepare_in_place_render_job` 已清了父任务的 `ocr_job_id` 链接。
- 位置: `jobs/actions/rerun.rs:26-68`；`jobs/lifecycle/creation/submit.rs:172-200`；`library/src/merge/sources.rs:78-90`
- 现有防护为什么不够: 没有"清理放在发射成功之后"的约束，也没有测试覆盖"重跑失败后旧产物仍在"。
- 建议修法: 删除 `rendered/` 的动作挪到 `relaunch_in_place` 成功之后（或干脆不删，让渲染覆盖写同名文件，保留 `previous_output_pdf`）；`-ocr` 子任务的清理同理后移。对前端无影响。

### 5. 强制删除运行中的任务/文档不通知 runner；CAS 在行不存在时会"插入"，把任务复活成幽灵行
- 等级: 中（需要 `force=true`，前端有这个调用；后果是幽灵任务和在已删目录里继续跑的 worker）
- 确认程度: 已确认（删除侧、CAS 侧代码都核对了；复活后的下游表现未逐个追）
- 场景:
  1. 任务 `J` 运行中，用户对书或文档调用 `DELETE ...?force=true`（`ensure_deletable` 只在 `force=false` 时拦运行中，`library/src/books.rs:102-110`；`documents.rs:143-148`）。
  2. 删除流程提交 DB 删除、删磁盘、清凭据（`books.rs:67-81`、`documents.rs:171-181`），全程没有 `request_cancel`、没有终止 worker 进程、没有等 driver 退出。
  3. driver 和 worker 仍在跑。下一次 stdout 行落库调用 `cas_save_job`：`SELECT status` 查不到行 → `current_status` 为 None → 跳过期望状态检查 → 直接 `INSERT ... ON CONFLICT DO UPDATE`（`database/retainpdf-db/src/db/job_writes.rs:151-167`）。已删除的任务被重新插入（`document_id` 为空，带着旧快照），在任务列表里重新出现；worker 继续往（被重建的）输出目录写，直到跑完，最终又落一个 Succeeded/Failed。
  4. 级联删除掉的 `pipeline_attempts`/`pipeline_units`/事件不会回来，所以幽灵行的 attempt 状态与文件状态彼此不一致。
- 位置: `database/retainpdf-db/src/db/job_writes.rs:123-167`；`library/src/books.rs:36-81, 102-110`；`library/src/documents.rs:124-181`
- 现有防护为什么不够: `should_stop_ocr_child` 只在"父任务行不存在"时让 OCR 子任务停（`runner/cancel_registry.rs:59-66`），父任务自己的 CAS 却会把它插回来；没有测试删除一个运行中的任务。
- 建议修法: `cas_save_job` 行不存在时返回 `Ok(false)`（新建行用 `save_job`/显式 insert，`create_ocr_child_job` 本来就走无条件写）；强制删除前先走和 `cancel_job` 一样的取消+终止流程并等 driver 退出。对前端无影响。

### 6. 进程内模式下，第二个 rust_api 实例在 bind 之前就会杀掉第一个实例的 worker 并把任务判失败
- 等级: 中（需要同一数据目录起两个进程，属操作失误；后果是正在跑的任务被杀）
- 确认程度: 已确认（代码顺序；未实际起两个实例）
- 场景:
  1. 实例 A（进程内模式）有任务 `J` 在跑，worker pid=P 存在 DB。
  2. 实例 B（比如开发时在另一个 worktree 起了一个，指向同一个 `data/`）：`serve_with_shutdown` 先 `build_state`（`api/src/app/server.rs:37`）→ `reconcile_owned_runtime` → `reconcile_stale_running_jobs`（`api/src/app/state.rs:51`）。对 `J`：pid 存活 → 判 `Orphaned`，`terminate_job_process_tree_blocking(P)` 先 SIGTERM 进程组、宽限期后 SIGKILL（`runner/startup_recovery.rs:37-52`），然后把任务改成 Queued（有 attempt）或 Failed。
  3. 直到之后 `TcpListener::bind` 失败（`server.rs:81`）B 才退出。A 的 `J` 已被杀；A 的 driver 看到 worker 退出，按失败收尾或与 B 写下的 Queued 互相覆盖。
- 位置: `api/src/app/server.rs:37, 81`；`api/src/app/state.rs:51`；`runner/startup_recovery.rs:27-52`；对照 jobsd 的做法 `backend/jobs/src/main.rs:178-193`（先 bind 拿"所有者租约"再 reconcile）
- 现有防护为什么不够: jobsd 注释明说"二次启动必须在 bind 上失败，而不是去回收别人的 worker"，进程内路径没有同样的顺序保证，也没有数据目录锁文件。
- 建议修法: 进程内模式也先 bind（或对数据目录加文件锁）再 `build_state` 里的 reconcile。对前端无影响。

### 7. 取消标志泄漏：对没有 driver 的任务点取消，标志留在内存里，下次原地重跑被立刻取消
- 等级: 低
- 确认程度: 已确认（代码）；需要先有"无 driver 的任务"（见问题 2）
- 场景:
  1. 任务 `J` 因问题 2 的原因 queued 但没有 driver；用户取消：`request_cancel` 往登记表插入 `J`（`cancel.rs:25`），API 直接 CAS Canceled（`cancel.rs:78-96`），没有 driver 来消费标志；`cancel_job` 只在"任务已终态"时才清标志（`cancel.rs:32-36`）。
  2. 用户再对 `J` 原地重新渲染：行变 Queued，新 driver 起来，`run_job` 开头 `should_skip_job_execution` 看到标志 → 清标志 → `persist_canceled_job` 因行是 Queued 把它写成 Canceled（`runner/lifecycle.rs:60-69, 222-225`）。重跑"瞬间被取消"，再点一次才行。远端模式下标志留在 jobsd 内存里，直到 jobsd 重启。
- 位置: `jobs/actions/cancel.rs:25-36, 78-96`；`runner/lifecycle.rs:60-69, 214-225`；`runner/cancel_registry.rs:8-19`
- 现有防护为什么不够: 清标志的唯一责任人是 driver，没有 driver 就没人清。
- 建议修法: 原地重跑的 `relaunch_in_place` 在发射前先 `clear_cancel(job_id)`；或 cancel 在自己 CAS 成功后也清标志。对前端无影响。

### 8. API 的取消 CAS 抢先落终态时，pipeline attempt 不被收尾，留成 `running`
- 等级: 低
- 确认程度: 存疑（"竞争谁先写"取决于时序；留下 running attempt 的后果没逐条追完）
- 场景:
  1. 非 OCR 任务运行中取消：API 杀进程后立刻 CAS 写 Canceled。driver 若比 API 慢（没有 worker 进程可等的阶段，如 Rust 原生阶段、排队），它的 `run_job` 末尾 CAS 失败，走 `!updated` 分支（`runner/lifecycle.rs:260-266`），这个分支做了修订登记、书卡回退、清标志，**没有** `finish_latest_pipeline_attempt`（只有 `updated` 分支和 `persist_failed_job`/`persist_canceled_job` 里有，`lifecycle.rs:149-153, 199-203, 273-275`）。
  2. attempt 一直是 `running`。此后原地重跑同一个 job id，`acquire_pipeline_attempt` 会把这个旧 attempt 当成"可续用"认领，`effective_stage_key` 取旧的 `current_stage`（`database/.../attempts.rs:46-80`），`dispatch_workflow` 也按它决定续跑路径（`runner/lifecycle.rs:95-118`）；若重跑途中崩溃，启动恢复也会按这个旧 attempt 的 committed render 单元去"恢复成功"（`startup_recovery.rs:273-296`）。
- 位置: `runner/lifecycle.rs:260-266`；`database/retainpdf-db/src/db/pipeline/attempts.rs:46-80`
- 现有防护为什么不够: 没有测试断言"API 取消后 attempt 被收尾"；`api_tests`/`lifecycle_tests` 只看 status。
- 建议修法: `!updated` 分支里读库按终态补一次 `finish_latest_pipeline_attempt`（幂等，没有 running attempt 时返回 false）。对前端无影响。

### 9. 靠库里记的 pid 直接杀进程组，没有校验这个 pid 还是我们的 worker
- 等级: 低
- 确认程度: 存疑（需要 pid 被复用且恰好是进程组组长，未复现）
- 场景: 启动恢复对每个 Running 且 `worker_process_exists(pid)` 的任务，直接 `kill(-pid, SIGTERM)`，宽限期后 `SIGKILL`（`runner/startup_recovery.rs:31-52`、`retainpdf-proc/src/lib.rs:57, 149-172`）。`worker_process_exists` 只用 `kill(pid,0)`，任何同 pid 的进程都算"存在"。长时间宕机/重启机器后，库里旧 pid 可能已属于别的进程（自己的 shell、别的服务）；只要它是组长，整个进程组被杀。取消路径同样（`cancel.rs:50-52`），窗口是"worker 已退出、库里 pid 还没清"。
- 位置: `runner/startup_recovery.rs:31-52`；`retainpdf-proc/src/lib.rs:57-72, 149-172`；`jobs/actions/cancel.rs:50-52`
- 现有防护为什么不够: 没有记录启动时间/命令行/进程组指纹来核对。
- 建议修法: 记录 worker 的进程启动时间（或在 worker 环境里带 job id，校验 `/proc/<pid>/environ`/`ps -o lstart`），不匹配就不杀、只清 pid。对前端无影响。

### 10. 可续跑的任务没有次数上限，会让"能把整个运行时弄崩的输入"陷入崩溃循环
- 等级: 低
- 确认程度: 存疑（需要一个会让 rust_api/jobsd 进程整体崩溃的输入，如栈溢出/abort/OOM，仓库里已有 `JOB_WORKER_THREAD_STACK_BYTES` 的先例）
- 场景: 某任务触发运行时进程崩溃 → 启动恢复把它判为"有 durable attempt → Queued 自动续跑" → 续跑又触发同样崩溃 → 每次启动重复（jobsd 还被壳监督器自动重启）。`acquire_pipeline_attempt` 只递增 generation，没有"已续跑 N 次"的计数。
- 位置: `runner/startup_recovery.rs:95-107`；`database/.../attempts.rs:46-80`；`api/src/app/jobs.rs:33-46`
- 现有防护为什么不够: 没有计数/熔断。
- 建议修法: 在 attempt 上记 `resume_count`，超过阈值就按失败收尾并给出"疑似使运行时崩溃"的原因。对前端无影响。

## 查过、靠得住的

- **runner 内的终态保护**: 全部阶段推进、逐行进度、OCR 子任务、父任务镜像、渲染/翻译产物接管都走 CAS（`runner/translation_flow_artifacts.rs:54`、`render_flow_artifacts.rs:46`、`translation_flow_stage.rs:161,207`、`process_runner/io_support.rs:101`、`startup.rs:44,61`、`ocr_flow/support.rs:26,104`、`translation_flow_child.rs:50,134`）；runner 内唯一的无条件任务行写是 `create_ocr_child_job` 建新行（有 ALLOW 注释和理由），其余无条件写只在测试和启动恢复里。`cas_save_job` 用 `BEGIN IMMEDIATE`，避免读锁升级死锁。对应测试 `canceled_job_is_not_revived_while_adopting_*`、`consumed_cancel_flag_still_lands_a_terminal_state`、`cancel_while_waiting_for_a_slot_still_lands_a_terminal_state` 等都在。
- **启动前双重 CAS + 启动后兜底**: `spawn_started_process` 在起进程前检查取消标志并 CAS，起进程后写 pid 的 CAS 若失败会终止刚起的 worker（`process_runner/startup.rs:42-74`）。
- **取消与完成的竞争**: `cancel_job` 登记标志后重新读库，若已终态就清标志（`cancel.rs:32-36`，有测试）；排队中的取消、标志被队列门/`run_job` 开头消费后的空洞，都有 `persist_canceled_job` 补终态（`lifecycle.rs:176-212`，有测试）。
- **driver 去重**: `JobDriverRegistry` 按任务 id 认领，`JobDriverGuard` 在 Drop 时释放；`list_resumable`/`list_stuck_queued` 都排除 `<父>-ocr` 子任务，避免对同一个 OCR 起两个 driver。
- **启动恢复**: 孤儿 worker 终止后落终态/续跑、已提交的渲染输出恢复为成功（要求输出+summary 文件都在）、父任务已终态的 OCR 子任务一次性收尾（有测试且幂等）、壳在远端模式下不碰 jobsd 的 worker；jobsd 先 bind 拿所有者租约再 reconcile（`backend/jobs/src/main.rs:181-193`）。
- **完成检测**: 成功必须同时满足退出码为 0、worker 通过 `artifact_published` 事件声明了产物、文件真实存在（`completion_pipeline.rs:44-53`、`process_contract.rs`）；产物路径只按 DB 登记解析，没有目录回退，所以磁盘上残留的旧 `rendered/*.pdf` 不会被当成新成功（见问题 4 的 B14 核实）。取消优先于成功判定（`classify_process_completion`）。
- **OCR 派发日志（独立 OCR 任务、同 id 重启）**: intent → receipt → resume / ambiguous 的状态机和重启后不重复提交的行为是对的（`retainpdf-data/tests/pipeline_process_crash.rs`、`backend/jobs/tests/startup_process_recovery.rs`）；歧义恢复的建任务+消解派发+种子 attempt 在同一个 `IMMEDIATE` 事务里，两个请求同时来只有一个会赢（`ocr_recovery.rs:32-61`）。问题只在父子 id 对不上（问题 1）。
- **OCR 子任务对父任务的取消**: 内存标志 + 库里父任务状态双重兜底，父行不存在也当作取消（`cancel_registry.rs:50-67`，有测试）。
- **建任务**: `submit_job` 拒绝客户端指定 job id、重名 409；预扣在落库之前、落库失败会释放（`submit.rs:114-128, 188-196`）；OCR 恢复任务的建立是事务的。
- **书卡指针**: `active_job_id` 的成功/失败/取消回退规则集中在 `active_job.rs` 和 `release_document_active_job`，覆盖了旧任务后完成、纯 OCR 顶替、取消后回退等场景，单元测试齐全。
