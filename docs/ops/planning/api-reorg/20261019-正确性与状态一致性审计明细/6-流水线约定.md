# Rust 和 Python 流水线之间的约定（runner 怎么驱动 Python、怎么信它的结果）

读的是 integration worktree（`.../scratchpad/wt-int`）。路径都相对它的 `backend/`，除非特别写明。

## 结论

这一块整体比较靠得住。成功不是只看退出码：Normalize / Translate / Render 三类 worker 退出 0 之后，还要必需产物存在，翻译还要 manifest 加已提交的 checkpoint 并且逐页校验 sha256，缺了一样就判 Failed。产物路径来自本次 stdout 的 `artifact_published` 事件，原地重跑前会清掉 `output_pdf` / `summary`，所以旧文件很难冒充成功。Python 侧最关键的几个文件（checkpoint、页、manifest、revision、document.v1）都是临时文件 + fsync + `os.replace`。checkpoint 的指纹覆盖了文档字节、模型、端点、页范围、术语表、提示词版本等，跨配置续跑会被拒绝并丢弃拷来的页。

主要问题集中在“Rust 读 Python stdout 的那条管道”这一个点：读取任务一旦出错就退出，但 worker 不会被杀，成功的运行也可能被判成失败。其余是低等级的隐患和策略不一致，以及一处按旧 pid 杀进程组的风险（见 1 和 3）。没有找到会丢数据且不会自愈的高等级问题。

## 问题

### 1. stdout 读取任务出错后，worker 没人管，成功的任务会被判失败

- 等级: 中
- 确认程度: 已确认（代码路径走通；没有测试覆盖，grep `read_stdout` 只在实现和 spawn 处出现）
- 场景:
  1. runner 起了 worker，随后 spawn `read_stdout`（`execution.rs:106`）。这个任务逐行解析 stdout，并且每行都做一次整行 CAS 落库。
  2. 循环里任何一个 `?` 都会让任务带着 `Err` 退出，管道读端随之被丢弃。会触发的情况有：
     - 起步的 `acquire_pipeline_attempt` 失败（`io_support.rs:61`）。
     - 某行 CAS 落库返回 `Err`，例如 SQLite 忙超时，或 `to_relative_data_path` 对 worker 报的“DATA_ROOT 之外的路径”直接 `bail`，这会让之后每一行都失败。
     - `apply_durable_checkpoint` / `apply_durable_stage_observation` / `apply_durable_artifact_commit` 里的 `bail!`：stage 不匹配、job_id 不匹配、同一页重复、PDF 不是常规文件。
     - 一行不是合法 UTF-8（`lines()` 返回 InvalidData）。Rust 不设 `PYTHONUTF8`，只靠外部环境，桌面端设了，裸 Windows 不一定。
  3. 此时 `collect_process_execution` 还在 `wait_with_limits` 里等子进程（`execution.rs:117-126`）。没有任何代码把读取任务的失败传给这个等待，也没有杀 worker。任务一直是 running，没有进度更新，`no_output_timeout` 默认关闭。
  4. worker 下一次往 stdout 写就会 BrokenPipe。但 Python 侧如果在重试或异常处理里吞掉这类异常，它会照样把翻译 / 渲染做完（含付费模型请求）。最长拖到总超时（默认 1800 秒）。
  5. 子进程退出后 `drain_stdout` 的 `joined?` 把那个 `Err` 原样抛出（`execution.rs:160-161`、`180-181`），整个 `execute_process_job` 返回 `Err`。`run_job` 走 `persist_failed_job`（`lifecycle.rs:44-49`、`127-162`）把任务写成 Failed，错误信息是“database is locked”之类。即使 worker 其实 exit 0、产物齐全、checkpoint 已 committed，也一样。
- 位置: `packages/retainpdf-runner/src/job_runner/process_runner/io_support.rs:61-66, 79-110`；`execution.rs:106-126, 160-162, 180-182`；`lifecycle.rs:44-49`
- 现有防护为什么不够: 超时能兜底，但要等满总时长。`persist_failed_job` 的结果是失败而不是“让 worker 自己跑完再核对产物”。契约校验 `validate_successful_worker_outputs` 在这条路径上根本走不到。
- 建议修法: 读取任务出错时立即 `terminate_child_process_tree`，把任务判为可续跑的失败（checkpoint 还在）。或者让读取任务对非致命错误只记日志并继续读，不退出。纯后端，对前端无影响。

### 2. 从失败任务导入 checkpoint 续跑后，实时译文接口看不到继承来的页

- 等级: 中
- 确认程度: 存疑（Python 侧“不会补报继承页”这一步读懂了；没确认译后阶段是否总会整本重存页文件，如果会，这些页在收尾时才补上，问题只是进行中看不到）
- 场景:
  1. 任务 A 翻到一半失败，A 的 DB 里有若干页的 `pipeline_units`。
  2. 用户“继续翻译”，建任务 B（`artifact_job_id=A`）。`import_translation_checkpoint_candidate` 把 A 的页快照和 checkpoint 拷进 B 的 `translated/`（`translation_checkpoint_resume.rs:15-103`）。拷来的 checkpoint 里每页带着 A 报告过的 `published_page_hash`。
  3. B 的 Python 启动，`_replay_durable_checkpoint` 只重放最后一次写入的 `committed_pages`（`session.py:325-344`）。后面的 `update()` 里，没改动的继承页 `published == page_hash`，既不属于“变了的块”也不属于 `stale_published_pages`（`session.py:176-187`），所以不会再报给 B。
  4. B 的 DB 因此没有这些页的 unit。`load_live_translation_page` 靠 `latest_pipeline_unit_for_page(B, "translate", page)` 取页，取不到就返回 `LIVE_TRANSLATION_PAGE_NOT_COMMITTED`（`retainpdf-jobs/src/progress/live_translation.rs:100-105`，SQL 在 `database/retainpdf-db/src/db/pipeline/queries.rs:271-288`）。
- 位置: `translation_checkpoint_resume.rs:15-103`；`backend/translation/retainpdf_translation/workflow/checkpoint/session.py:176-187, 325-344`；`live_translation.rs:100-105`
- 现有防护为什么不够: 同一任务内续跑没问题（查询按 attempt 倒序，旧 attempt 的 unit 还在），测试也只覆盖了拷文件，没覆盖拷完后 DB 里的 unit。导入时没人给 B 补 unit。
- 建议修法: 导入后让 Python 在第一次 `update()` 里把所有页都当作未报告（导入时清掉拷来的 `published_page_hash`），或者 Rust 导入时按 checkpoint 给 B 补 unit。前端无影响（只是以前读不到的页能读到了）。

### 3. 启动对账按 DB 里的旧 pid 杀进程组，不核对进程身份

- 等级: 中（极难触发，但一旦触发是误杀用户别的程序）
- 确认程度: 已确认（代码路径；触发概率取决于 pid 恰好被一个进程组组长复用）
- 场景:
  1. 任务 running，DB 记着 worker 的 pid。
  2. 机器重启 / 崩溃 / 服务被杀，之后 runtime 重启，`reconcile_stale_running_jobs` 读 `list_job_process_records_with_status(Running)`。
  3. 它对每个记录的 pid 用 `kill(pid, 0)` 判断“还活着”（`retainpdf-proc/src/lib.rs:54-64`），为真就当作孤儿 worker，对 `-pid` 这个进程组先 SIGTERM，宽限后 SIGKILL（`retainpdf-proc/src/lib.rs:157-181`，调用在 `startup_recovery.rs:30-45`）。
  4. 重启后 pid 空间被复用，这个 pid 现在可能是任意一个自成进程组的应用（macOS 上从 launchd 起的 GUI 程序都是组长）。它会被整组杀掉。
  5. 同类写法还有 jobsd 的 `POST /internal/v1/processes/:pid/terminate`（`backend/jobs/src/main.rs:111-135`）：带 token 就能杀任意 pid 的进程组；`pid=0` 会变成 `kill(0, …)`，杀的是 jobsd 自己的进程组。
- 位置: `startup_recovery.rs:30-45`；`packages/retainpdf-proc/src/lib.rs:54-64, 157-181`；`backend/jobs/src/main.rs:111-135`
- 现有防护为什么不够: `kill(pid, 0)` 只能证明“有这个 pid”，不能证明是我们的 worker。DB 里没有记录进程启动时间或命令行。
- 建议修法: 记录 worker 的启动时间或 pgid 并在杀之前核对（Linux 读 `/proc/<pid>/stat` 的 starttime，macOS 用 `proc_pidinfo`），对不上就当“已死”。jobsd 接口至少拒绝 `pid<=1`，并只接受自己登记过的 pid。前端无影响。

### 4. Provider / Unknown 类 worker 退出 0 时不校验任何产物

- 等级: 低
- 确认程度: 已确认
- 场景:
  1. OCR 走 `provider-ocr`（配置的命令式 provider、Paddle 官方 CLI）时，`WorkerContract::from_command` 判成 `Provider`，`validate_successful_worker_outputs` 直接 `Ok(())`（`process_contract.rs:113-123`）。
  2. `execute_ocr_job` 在这条路径上就是一次 `execute_process_job`，没有后续 normalize 阶段（`ocr_flow/mod.rs:103-105`）。
  3. worker 退出 0 但没发布 `normalized_document_json` 时，纯 OCR 任务会被标成 Succeeded。翻译任务要到 `ocr_ready_inputs_for_translation` 才报“OCR succeeded but artifacts are missing”（`stage_contract.rs:51-79`）。
- 位置: `process_contract.rs:121`；`ocr_flow/mod.rs:103-105`
- 现有防护为什么不够: Python 侧 `_finish_ocr_only_provider_job` 会在写 summary 时读 normalized 文档，缺了会抛异常，所以靠 Python 守住。Rust 没有第二道。
- 建议修法: 给 `Provider` 加和 `Normalize` 同样的必需产物检查（至少 `normalized_document_json`、`normalization_report_json`）。前端无影响。

### 5. 书籍任务渲染阶段，DB 行里 `finished_at` 和 `result` 还是翻译阶段的值

- 等级: 低
- 确认程度: 已确认
- 场景:
  1. 翻译阶段 `attach_process_result` 无条件设 `finished_at=now`、`result=ProcessResult{success:true,…}`（`process_runner/result_support.rs:16-33`）。
  2. 翻译作为中间阶段，状态保持 Succeeded，内存里随后进入 `run_render_stage_after_translation`，只把 status 改回 Running、清进度（`translation_flow_stage.rs:191-203`），不清 `finished_at` / `result`，随后 CAS 落库。
  3. 渲染的几分钟甚至更久里，库里是 `status=running` 但 `finished_at` 非空；`sync_runtime_info` 里 `total_elapsed_ms` 用 `finished_at` 当终点，于是被冻结在翻译结束那一刻（`retainpdf-core/src/models/job/lifecycle.rs:55-58, 118-121`）。`timestamps.duration_seconds` 取 `result.duration_seconds`，只含最后一阶段（`retainpdf-jobs/src/views/job_builders.rs:73-76` 的同款逻辑）。
- 位置: `translation_flow_stage.rs:170-218`；`result_support.rs:16-18`
- 现有防护为什么不够: `ProcessStageKind::Intermediate` 只管不压 `finished` 历史，没管这两个字段。
- 建议修法: 进入下一阶段时 `finished_at=None`，并保留累计时长。注意前端若以 `finished_at != null` 判完成，这是行为变化，需要在文档里写清（只增不改：可保留旧字段，新增 `stage_finished_at`）。

### 6. 重启后的自动续跑不看“请求结果不明”，手动重试却要用户确认

- 等级: 低
- 确认程度: 已确认（代码路径）
- 场景:
  1. 翻译 worker 有未收尾的上游 LLM 请求（journal 里只有 dispatch，没有 terminal）时被杀或 runtime 重启。
  2. 手动 rerun / retry-stage 会读 journal 判 `requires_confirmation`，没有 `accept_duplicate_risk` 就 409（`actions/rerun.rs:82-88`、`actions/stage_retry.rs:101-117`）。
  3. 启动对账只看 `has_running_pipeline_attempt`，把任务直接改回 Queued（`startup_recovery.rs:62-125`），`dispatch_workflow` 随后重启翻译 worker（`lifecycle.rs:95-118`）。Python 侧对 `prior_ambiguous` 只记日志（`artifacts/request_journal.py:125-139`），照发。
  4. 结果：重启后会重复发这些请求，可能重复计费，用户没机会拒绝。量不大（最多 `workers` 个在途请求），但和手动路径的策略不一致。
- 位置: `startup_recovery.rs:62-125`；`lifecycle.rs:88-125`；`actions/rerun.rs:82-88`
- 现有防护为什么不够: 只有 API 动作做了歧义检查，runner 自动恢复路径没有。
- 建议修法: 要么在自动恢复前检查 journal，有歧义就改成 failed 并提示“需确认重复风险”；要么在文档里明确这是自动恢复的取舍。前端无影响。

### 7. 领域识别超时的“空结果”会被缓存成这个任务目录里的永久结果

- 等级: 低
- 确认程度: 已确认
- 场景:
  1. 翻译开头的领域识别超时，进入 `except DomainContextTimeoutError`，把 `_empty_domain_context(preview_text)` 通过 `save_domain_context` 写进 `translated/domain-context.json`（`llm/domain_context.py:238-250`）。
  2. 之后任何一次续跑，`load_cached_domain_context` 看到 `preview_text` 一致就直接命中（`domain_context.py:205-208`），没有“空结果不算命中”的判断；共享缓存倒是要求 summary 或 guidance 非空，没被污染。
  3. 这个文件还会被 Rust 导入 checkpoint 时一起拷到新任务（`translation_checkpoint_resume.rs:91-97`），指纹不匹配丢弃页时也不删它（`checkpoint/resume.py:44-64` 只删页、manifest、checkpoint）。于是一次偶发超时导致整条续跑链都没有领域提示，翻译质量悄悄变差，界面仍是“任务完成”。
- 位置: `backend/translation/retainpdf_translation/llm/domain_context.py:195-250, 308-312`
- 现有防护为什么不够: 缓存命中是为了让指纹稳定（`domain_guidance` 在 `resolved_policy_sha256` 里，重新推断会让旧 checkpoint 作废），所以这是权衡，不是疏忽，但超时的空结果被当成了正常结果。
- 建议修法: 超时的空结果带一个标记（如 `"timed_out": true`），命中时只对没有这个标记的缓存生效；或者超时不落盘。前端无影响。

### 8. 原地重渲染入口先删文件、再落库，且没有并发保护

- 等级: 低
- 确认程度: 存疑（两个并发请求都通过 `resume_plan` 的状态检查这一步是读代码推出来的，没找到会拦住的锁；没验证真实时序）
- 场景:
  1. 用户对一个 Failed 任务快速点两次“继续/重渲染”（或两个客户端同时调）。两个请求都读到 Failed、都过了 `resume_plan` 的 Queued/Running 检查（`actions/rerun.rs:24-26`）。
  2. 请求 A 删掉 `rendered/`，`prepare_in_place_render_job`，`relaunch_in_place` 落库并 `launch`，driver 被 claim，开始渲染写 `rendered/`。
  3. 请求 B 在 A 的 driver 起来之后才执行到 `remove_dir_all(rendered_dir)`（`rerun.rs:48-54`），然后用自己手里那份旧的 Failed 快照 `relaunch_in_place`。后者是无条件 `persist_job_with_resources`（`lifecycle/creation/submit.rs:162-173` 调 `persist_and_launch`，里面是 `save_job`），把行改回 Queued、`pid=None`。`launch` 因为 driver 已被 claim 而什么都不做。
  4. 结果：A 的渲染目录被删，A 的 worker 可能写不出 PDF 或在不存在的目录上失败；行被覆盖成 Queued / 无 pid，取消按钮杀不到 worker，直到 A 的下一行 stdout 通过 CAS 把状态写回去（CAS 允许 queued → running，所以会自愈）。
- 位置: `retainpdf-jobs/src/actions/rerun.rs:24-61`；`lifecycle/creation/submit.rs:162-198`
- 现有防护为什么不够: 状态检查和写入之间没有锁或 CAS，`relaunch_in_place` 不是 CAS。
- 建议修法: `relaunch_in_place` 改成“只在库里还是终态时才写”（CAS），删文件放到 CAS 成功之后。前端无影响。（这块可能和 jobs 生命周期那一块的审计重叠，建议合并看。）

### 9. 导入 checkpoint 出错会让整个“继续”任务失败，不回退成无 checkpoint 重跑

- 等级: 低
- 确认程度: 存疑（需要源任务的 checkpoint 或快照确实损坏；正常崩溃有 `snapshot_path` 兜底，我没找到不靠磁盘损坏就能触发的路径）
- 场景:
  1. `import_translation_checkpoint_candidate` 对源 checkpoint 的每一页调 `resolve_checkpoint_page_source`，快照缺失或哈希不对就返回 `Err`（`translation_checkpoint_resume.rs:70-90`、`stage_contract.rs:191-258`）。
  2. 这个 `Err` 通过 `prepare_job_from_ocr_artifacts` 的 `?` 一路抛到 `run_job`，新任务直接 Failed（`translation_flow_artifacts.rs:31-36`）。
  3. 源任务不变，用户每次点“继续”都是同样的结果，只能放弃 checkpoint 重新翻译（走“重试 OCR”或新建任务）。`stage_plan` 里 `translation_checkpoint_available` 只检查文件是否存在，不会提前发现它坏了。
- 位置: `translation_checkpoint_resume.rs:49-101`；`translation_flow_artifacts.rs:31-36`
- 现有防护为什么不够: 导入失败是硬错误，没有“丢掉 checkpoint 但继续用 OCR 产物”的降级。
- 建议修法: 导入失败只记日志并按无 checkpoint 起跑（目标目录里已经拷的东西先清掉）。前端无影响。

### 10. 安全相关：解压 MinerU 包没有防 `../`

- 等级: 低
- 确认程度: 已确认（代码）；利用需要服务商给出恶意 zip
- 场景: `unpack_zip` 用 `dest_dir.join(entry.name())` 直接拼路径，没用 `enclosed_name()`（`retainpdf-data/src/ocr_provider/mineru/client.rs:309-327`）。zip 里有 `../../x` 时会写到 `provider_raw_dir` 之外。下载只校验 HTTP 状态，不校验内容。
- 位置: `backend/packages/retainpdf-data/src/ocr_provider/mineru/client.rs:309-327`
- 现有防护为什么不够: 信任 MinerU CDN。
- 建议修法: 改用 `entry.enclosed_name()`，为空就跳过或报错。前端无影响。

## 查过、靠得住的

- **成功判定**:
  - 取消优先；退出码非 0 且 stderr 含 “Exception ignored in” 时，只有必需产物（render 要 `output_pdf` + `summary`，translate 要 `translations_dir` + `summary`）都存在才算成功（`completion.rs:133-172`）。
  - 退出 0 之后还要过 `validate_successful_worker_outputs`（`completion_pipeline.rs:44-53, 239-249`）。翻译一类要 `ensure_translations_dir_ready`：manifest 存在，且 checkpoint 为 committed、`final_manifest` 对得上、逐页 sha256 对得上、manifest 为 complete（`stage_contract.rs:290-420`）。
  - 翻译的 manifest 先发布、checkpoint 后 `complete`，中间崩溃会留下“manifest complete + checkpoint validating”，Rust 这道门会拒绝，不会被当作可渲染。
  - 过期文件冒充成功的口子基本堵住了：路径只来自本次 stdout 事件，原地重渲染会把 `output_pdf` 挪进 `previous_output_pdf`，清 `summary`（`rerun.rs:155-165`）；`rerun.rs` 路径还会删 `rendered/` 与 `*-ocr` 目录。`stage_retry` 路径没删目录，但 artifacts 已清空，旧 PDF 不会被当成功。
- **超时和杀进程**:
  - 总时长与空闲时长两条独立超时（`execution.rs:62-87`）；超时后 `terminate_child_process_tree` 组杀并回收，读取任务有 30 秒收尾上限，防止孤儿孙进程占着管道把 runner 挂死（`execution.rs:17-28, 172-218`）；超时落 Failed 前先读库，已取消就不覆盖（`timeout_support.rs:82-128`）。
  - 空闲超时默认是关的，所以卡死的 worker 要等满总超时（默认 `timeout_seconds=1800`）。这是配置问题，不算 bug。
  - 渲染准备辅助进程是 `kill_on_drop`，失败和超时只记日志，不影响状态（`render_prepare.rs`）。
- **Python 写入的原子性**:
  - 用 tmp + fsync + `os.replace` 的：checkpoint（`checkpoint/store.py:83-104`）、页文件（`core/payload/translations.py`）、manifest、revision 链（带回滚，`workflow/revision.py`）、normalize 产出的 `document.v1.json` 与报告（`save_json_atomic`）、prewarm / prepare 缓存、fit / QA / refine 报告。Rust 侧导入拷贝和 refine override 也是 tmp + rename。
  - 非原子的 `save_json`（`base/retainpdf_base/io.py:10-33`）用在 `pipeline_summary.json`、`translation_diagnostics.json`、`translation_review.json`、`translation_debug_index.json`，以及 provider 路径下的 `normalized_json`（`mineru_provider/job_flow.py:51`、`local_command_driver.py:259`）。这些路径都在写完之后才通过 stdout 发布，Rust 读它们时用 `.ok()` 容错（`reports/failure.rs:98-110`、`summary_loaders`），所以被杀留下半个文件也不会被当成产物。最终 PDF 是直接 `doc.save` 到成品路径（`render/document/pdf_ops.py:14, 29`），同样只在存完后才发布。
  - 书籍任务里翻译和渲染共用同一个 `artifacts/pipeline_summary.json`，渲染会覆盖翻译的。读侧是 manifest 优先、summary 兜底（`summary_loaders/shared.rs:92-107`），所以不影响展示。
- **checkpoint 续跑不会混配置**:
  - 指纹覆盖 normalized 文档 sha256、起止页、mode、math_mode、批大小、model、base_url、规则档与自定义规则、解析后策略的 hash、context / glossary / memory 模式、术语表全量条目、提示词文件 hash 与协议 / 策略版本、译前准备的冻结产物 hash，以及 Rust 执行器的连接指纹（`checkpoint/identity.py`、`core/engine_identity.py`）。
  - 同一 attempt 里不匹配直接报错；跨 attempt（导入来的）不匹配就只删拷来的页、manifest、checkpoint，从头开始（`checkpoint/resume.py`、`session.py:134-140`）。
  - 不进指纹的 `workers` 和 API key 不影响译文；reviewer 的模型只用于渲染前的精修，不改翻译页。
  - 导入只接受 Failed / Canceled 源；目标已有 checkpoint 时不覆盖；checkpoint 最后一个发布，拷到一半不会被当成可续跑（`translation_checkpoint_resume.rs`，有测试）。
- **崩溃后重放与互斥**: checkpoint 里有 `committed_pages` 的 outbox，下次启动重放最后一次写入的 stdout 事件（`session.py:325-344`）。页文件比 checkpoint 超前时用快照恢复（`store.py:106-138`）。`.translation-checkpoint.lock` 用 flock，防止两个 worker 写同一个目录。
- **spec 和 stdout 协议漂移**: Python 对 stage spec 做 `schema_version` 严格校验；`batch_size` 的兜底值两边对齐并有测试（`stage_specs.py:40-60`）。`contracts/pipeline-stdout.v1.schema.json` 和 `stdout_parser/contract_lock.rs` 互相锁住。解析失败的事件行会被静默丢弃（`.ok()?`），所以对“字段类型漂移”不敏感的是容错，对“漂移了也没人知道”的是风险；目前靠契约测试守。
- **渲染产物的崩溃恢复**: `output_pdf` 事件到达后 Rust 对 PDF 做 sha256、提交 `output-pdf` 单元并结束 render 阶段；此后崩溃，重启会直接按已提交的产物判成功（`startup_recovery.rs:262-318`）。代价是事件之后才跑的“渲染后重算翻译 QA”会被跳过，QA 报告可能是旧的，影响很小。
- **取消 / 终态覆盖**: 启动子进程前后、阶段切换处、每行 stdout 的落库都是 CAS（`startup.rs:42-74`、`io_support.rs:101-110`、`translation_flow_stage.rs:161-167, 207-216`），且各有测试。
- **输出脱敏**: `attach_process_result` 对 stdout / stderr 做了脱敏再入库；密钥只通过 env 传给 worker。
