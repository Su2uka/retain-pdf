# 磁盘产物、派生缓存、译文修订

代码基线：wt-int（local main + batch-1 九个修复）。路径均相对 `backend/` 或 `database/`。

## 结论

这一块的写盘纪律整体不错：Python 侧译文页、manifest、checkpoint、修订日志都是「临时文件 + fsync + rename」，Rust 侧派生产物（对照 PDF、Word、线性化、zip、合并目录）也都是临时文件加 rename；内存里只有请求级的 `SummaryCache` 和按「路径+大小+mtime」校验的 `data/` 数据集缓存，没有按名字长期留存的内存缓存。真正的问题集中在三类：（1）修订 PATCH 的 Python 子进程会被 `kill_on_drop` 用 SIGKILL 打断，而回滚只在 `except` 里，被杀时页文件会领先 checkpoint，之后没有任何自动修复；（2）修订不重渲染时（`rerender` 默认 false），Word 缓存、QA/诊断报告、合并目录指纹都不感知译文变化，各产物互相不一致；（3）删除/恢复只管 DB 行和任务目录，运行中任务、文档级目录、备份里的「在跑」状态都有遗留。没有发现会丢用户译文数据的高等级问题，但有几处「不会自愈」的状态错误。

## 问题

### 1. 修订 PATCH 的 Python 子进程被 SIGKILL 后，页文件领先 checkpoint，且没有任何自动修复
- 等级: 中
- 确认程度: 已确认（逻辑链完整；窗口只有一次修订的几百毫秒到约 1 秒，触发概率低）
- 场景:
  1. 用户 PATCH 一个块。Rust `revise_translation_item` 用 `Command::...kill_on_drop(true)` 起 `translation-revise`，等 `wait_with_output`（`retainpdf-jobs/src/translations/revision.rs:92-127`）。
  2. Python 在 `_revise_locked` 里先 `_atomic_write_bytes` 改页文件，再 `project_progress` + `snapshot_pages`（整本每页读一遍算 sha256），然后才 `store.save(checkpoint)`，最后改写 `revisions.v1.jsonl`（`translation/retainpdf_translation/workflow/revision.py:~470-520`）。
  3. 这段时间里客户端断开（axum 在连接关闭时丢弃处理函数的 future，`routes/jobs/translations.rs:37` 是直接 await，没有 spawn 隔离），或 API 进程关闭，`Child` 被 drop，tokio 发 SIGKILL。`except BaseException: _rollback(...)` 不会执行（`revision.py` 文件头注释说「进程在两次 rename 之间被杀掉的情况，由 checkpoint 的 generation 快照兜底」，但兜底只在下次翻译阶段续跑时才发生）。
  4. 结果：页 JSON 已是新内容，checkpoint 仍记旧 `page_hash`。之后每次 PATCH 在 `_verify_publication` 处返回 409 `publication_inconsistent`（`revision.py:~205-217`）；渲染阶段 `load_translated_pages` 按 checkpoint 的 hash 校验页文件，也会抛 "Translation publication is not committed or consistent"（`pipeline/retainpdf_pipeline/render/translation_loader.py`），所以 `rerender` 和普通原地重渲染都失败。
  5. 唯一的修复路径是 `restore_committed_pages`，它只在翻译阶段的 `TranslationCheckpointSession._initialize` 里调用（`checkpoint/session.py:135`），即用户必须重跑 translate 阶段。API 没有任何检测或提示。
  6. 第二个更窄的窗口：`store.save(checkpoint)` 之后、写 `revisions.v1.jsonl` 之前被杀，checkpoint 已前进、日志里没有这一条；重发同一请求得到 `unchanged`、`revision: None`，日志永远补不上，`publish_translation_revisions` 因为在日志里找不到 `page_hash` 而不会登记这一页（`retainpdf-data/src/translation_revisions.rs:84-87`）。
- 位置: `retainpdf-jobs/src/translations/revision.rs:92-127`；`translation/.../workflow/revision.py`（`_revise_locked`、`_rollback`）；`checkpoint/store.py:106`（`restore_committed_pages`）；`render/translation_loader.py:_committed_page_hashes`
- 现有防护为什么不够: 回滚只覆盖 Python 异常，覆盖不了 SIGKILL；文件锁在进程被杀时自动释放，所以后面的请求能进来，但只会撞上 `publication_inconsistent`。Rust 侧超时 120 秒不是问题，问题是 drop 即杀。
- 建议修法: Rust 不要在 drop 时 SIGKILL 这个子进程（用 spawn 出去的任务跑完，或 drop 时先发 SIGTERM 并让 Python 捕获后回滚）；另外在 `publication_inconsistent` 分支让 Python 直接用 checkpoint 快照把页文件恢复（`restore_committed_pages` 已有现成实现）。对前端无影响。

### 2. 原地重渲染/精修失败后，任务丢掉可用的译文 PDF，`previous_output_pdf` 之后再没人用
- 等级: 中
- 确认程度: 已确认「`output_pdf` 被清空且失败时不恢复」；「旧文件被新渲染覆盖」存疑（没核实原地重渲染的输出文件名是否与上次相同）
- 场景:
  1. 一个成功的任务有 `artifacts.output_pdf`。用户触发 retry-stage render（`create_new_job=false`）或原地精修，或 PATCH 时带 `rerender=true`。
  2. `prepare_in_place_render_job` 调 `reset_render_artifacts`：`output_pdf` 取出放进 `previous_output_pdf`，`output_pdf=None`（`retainpdf-jobs/src/actions/rerun.rs:154-165`）。
  3. 渲染失败或被取消。`output_pdf` 只有渲染成功时由 stdout 解析器重新设置（`retainpdf-runner/.../stdout_parser/artifact_rules.rs:115`），失败路径没有恢复。全仓库只有 `rerun.rs` 和合并来源（`retainpdf-library/src/merge/sources.rs:~86`，且只在 `Queued` 时用）读 `previous_output_pdf`。
  4. 结果：任务状态 failed，`resolve_output_pdf` 为 None，`/files/output/translated.pdf`、预览、Word 里「有译文 PDF」的分支全部不可用（404 "not ready"），而磁盘上上一版 PDF 可能仍在（或被 Python 的 `doc.save(output_pdf_path)` 直接截断改写，`render/document/pdf_ops.py:27`，不是原子替换）。用户只能再渲染一次成功才拿回 PDF。
- 位置: `retainpdf-jobs/src/actions/rerun.rs:98-165`；`retainpdf-runner/src/job_runner/stdout_parser/artifact_rules.rs:115`；`retainpdf-library/src/merge/sources.rs:~86`；`pipeline/retainpdf_pipeline/render/document/pdf_ops.py`
- 现有防护为什么不够: `previous_output_pdf` 的设计只照顾了「排队中」的读取，终态为 failed/canceled 时没有「回滚到上一次成功状态」的逻辑，也没有「先渲染到临时文件、成功后再换名」。
- 建议修法: 失败/取消终态里，若 `output_pdf` 为空且 `previous_output_pdf` 文件仍在，就恢复它（或让 Python 渲染先写临时文件再 rename）。只涉及后端字段，对前端只增不改。

### 3. 修订（不带 `rerender`）之后，没有任何「PDF 已过期」标记，Word 缓存、QA/诊断报告、合并目录各自不一致
- 等级: 中
- 确认程度: 已确认（Word 缓存键、报告文件、合并指纹都读过）
- 场景:
  1. 任务已成功，用户先下载过 Word（缓存 `artifacts/<job>-layout-dpi180-v2.docx`）。
  2. 用户 PATCH 一个块，`rerender` 缺省为 false。Python 只改 `translated/page-*.json`、checkpoint、`revisions.v1.jsonl`；`translated.pdf` 不变，`translation_qa.v1.json`、`translation_diagnostics.json`、`fit_report.v1.json` 不变（`translations/edits.rs:54-95`；这些报告只在渲染阶段生成）。
  3. 再次下载 Word：`ensure_layout_docx` 的新鲜度只比较源 PDF 和译文 PDF 的 mtime（`retainpdf-files/src/derived_artifacts/word.rs:69-76`），译文 JSON 不是输入，所以返回旧 Word（不含修订）。而从没生成过 Word 的任务，首次生成会读 `job_root/translated/page-*.json`（`render/output/word/job_io.py:19`），带上修订。同一任务的 Word 因缓存状态不同而内容不同，且都和 `translated.pdf` 不一致。
  4. translate-only 的任务（没有译文 PDF）Word 只依赖源 PDF，修订后永远命中旧缓存。
  5. QA/诊断/fit 报告继续展示修订前的问题（`reports/translation_reports.rs` 只是读文件），响应里除了 `rerender_error` 没有任何持久的「过期」状态。
- 位置: `retainpdf-files/src/derived_artifacts/word.rs:58-98`；`retainpdf-jobs/src/translations/edits.rs`；`retainpdf-jobs/src/reports/translation_reports.rs`；`retainpdf-jobs/src/files/downloads/files.rs`（`TranslatedDocx` 分支）
- 现有防护为什么不够: `cached_output_is_fresh` 只认 mtime，且 `RENDERER_VERSION` 只管代码版本；没有把 checkpoint `generation` 放进缓存键。
- 建议修法: 把当前 checkpoint 的 `generation`（或 manifest/checkpoint 的 mtime）加进 Word 缓存文件名/新鲜度判断；任务视图或文件清单里带一个 `translation_generation` 与 `pdf_generation` 对比，让前端能提示「译文已改，PDF 未重渲染」（新增字段，不改旧字段）。

### 4. 合并阅读目录的指纹只含 manifest 的 mtime，修订后合并的译文 JSON 不会更新
- 等级: 低（`rerender=true` 时 PDF 的 mtime 变化会连带换目录；只有不重渲染时才暴露）
- 确认程度: 已确认
- 场景:
  1. 一本书有多个范围任务，合并结果目录按 `merge_fingerprint` 命名（`retainpdf-library/src/merge/build.rs:77-113`）。指纹包含每个任务的 `output_pdf`、规范化文档、`translation-manifest.json` 的大小和 mtime，不含各页 JSON 和 checkpoint。
  2. 在源任务上 PATCH 一个块（`rerender=false`）。`revision.py` 不改 manifest，只改页文件，所以指纹不变，旧目录「存在即新鲜」。
  3. 合并阅读（阅读器选区、Word 导出、AI 问答、全文搜索，见 `build.rs` 头注释）读到的还是修订前的译文，而源任务自己的阅读页已是新译文。
- 位置: `retainpdf-library/src/merge/build.rs:77-113`；`translation/.../workflow/revision.py`（不写 manifest）
- 现有防护为什么不够: 目录名不可变是为了断点续传，但指纹输入漏了译文页的真实来源。
- 建议修法: 指纹里加入 `checkpoint.generation`（或 `translation-checkpoint.v1.json` 的 stamp）。对前端无影响。

### 5. 强制删除运行中的任务不会取消 runner
- 等级: 中
- 确认程度: 已确认「删除路径不取消」；runner 在行消失后的具体行为存疑（没逐行追到底）
- 场景:
  1. `DELETE /library/books/:job_id?force=true` 或 `DELETE /documents/:id?force=true`，任务正在 running。
  2. `delete_library_book` / `delete_document` 只做：`ensure_deletable(force)` → `db.delete_jobs` 或 `delete_document_cascade` → `remove_job_files`（`retainpdf-library/src/books.rs:35-100`、`documents.rs:124-190`）。没有调用取消，也不通知 `canceled_jobs` 注册表，也不 `release_for_job` 页额度。
  3. worker 进程仍在跑：继续调 OCR/翻译服务（计费）、继续往 `data/jobs/<id>/` 写文件（目录被重新创建，成了孤儿目录）；终态 CAS 因为行不在而更新 0 行，被当成「已终态」安静退出（`runner/lifecycle.rs:~250-262`）。
- 位置: `retainpdf-library/src/books.rs:35-100`；`retainpdf-library/src/documents.rs:124-190`
- 现有防护为什么不够: `force` 只绕过 409 检查；没人把「删除」翻译成「先取消再删」。
- 建议修法: force 删除前先走取消流程并等到终态；或者删除接口对 running 任务返回 409 并要求先取消。对前端无影响。

### 6. 数据库恢复把备份里的「排队/运行中」任务原样带回来，没有重新对账；陈旧 pid 会在下次启动时被当作孤儿进程处理
- 等级: 中
- 确认程度: 已确认「运行中恢复后不对账」；「重启时按陈旧 pid 误杀进程」存疑（只确认了 `kill(-pid)` 的实现没有校验进程身份）
- 场景:
  1. 自动备份每 24 小时一次（`platform/src/backup/mod.rs`），备份时恰好有任务 queued/running，很常见。
  2. 之后用户恢复这份备份。`restore_blockers` 只检查「现在」有没有在跑的任务（`database/.../backup.rs:~255-275`），不检查备份内容。
  3. 恢复后 DB 里是 queued/running 行，没有任何 driver；`reconcile_stale_running_jobs`、`requeue_stuck_queued_jobs` 只在进程启动时调用（`api/src/app/jobs.rs:24-41`），不在恢复后调用。用户看到永久转圈；`rerun` 遇到 queued/running 直接 409。
  4. 下次重启时，对这些行里记录的旧 pid 调 `worker_process_exists`（只是 `kill(pid,0)`，`retainpdf-proc/src/lib.rs:57`）；如果该 pid 已被不相干进程复用，就会 `kill(-pid, SIGTERM/SIGKILL)`（`lib.rs:84-96`）。
  5. 同时，恢复只换 DB，不碰文件：备份之后新建的任务目录、上传、文档目录成为没有 DB 行的孤儿；备份之后完成的任务，DB 里还是旧状态，而磁盘上已有成品。文档注释承认这点，但没有任何清理/对账手段。
- 位置: `retainpdf-platform/src/backup/mod.rs`（`restore`）；`database/retainpdf-db/src/db/backup.rs:restore_unpacked`；`retainpdf-runner/src/job_runner/startup_recovery.rs:27-70`；`api/src/app/jobs.rs:24-41`
- 现有防护为什么不够: 恢复用 SQLite online backup 一次写入，一致性没问题，但「恢复后的状态是否可信」没人负责。
- 建议修法: 恢复成功后立即对恢复出的 queued/running 行做一遍 `reconcile_stale_running_jobs`（pid 置空，判定为失败/可恢复）；启动对账里 kill 之前校验进程命令行或启动时间。对前端无影响。

### 7. 封面/缩略图和背景清理缓存的写入不是原子的，且只检查「文件存在/大小>0」
- 等级: 低
- 确认程度: 已确认（代码）；触发需要写入中途进程被杀
- 场景:
  1. `render_book_image` 里 `pix.save(output)` 直接写目标文件（`retainpdf-files/src/derived_artifacts/preview.rs:~125-140`）；`ensure_book_image_at_path` 只判断 `output_path.exists()` 就复用。进程被杀或磁盘写满时留下半截 JPG，之后永久命中（封面带 `max-age=86400` 的浏览器缓存）。单页预览已经是 `.part.jpg` + `os.replace`，这里没做。
  2. 渲染的背景清理缓存：`shutil.copy2(cleaned_background_pdf, cached_background_pdf)` 直接写（`render/output/typst/book_renderer.py:~846`），命中条件是 `exists() and st_size > 0`（`~826`），缓存键不变，半截 PDF 会让之后每次渲染都命中并失败，除非手动清 `background-cache/`。
- 位置: `retainpdf-files/src/derived_artifacts/preview.rs:55-125`；`pipeline/retainpdf_pipeline/render/output/typst/book_renderer.py:~820-850`
- 现有防护为什么不够: 单飞（`download_generation`）只防并发，不防崩溃。
- 建议修法: 都改成「写临时文件 → fsync → rename」，背景缓存额外校验能被 fitz 打开。对前端无影响。

### 8. 派生产物子进程没有超时，会永久占住只有 2 个名额的下载生成通道
- 等级: 中
- 确认程度: 存疑（需要一个会让 fitz/qpdf 卡死的 PDF；代码上没有任何保护）
- 场景:
  1. `DownloadGeneration::default()` 只有 2 个并发名额、128 个 key（`retainpdf-files/src/download_generation.rs:57-60`）。`JobDownloads::open` 把所有文件出口（包括普通的 translated.pdf 下载、页预览、封面）都放进它（`files/downloads/service.rs:10-25`；书库的 `open_document_file` 同理）。
  2. 页预览和封面用 `std::process::Command::status()` 起 python，没有超时（`preview.rs:~100,~150`）。Word 超时 600 秒，对照 PDF 120 秒，这两个有 `run_supervised`。
  3. 一个让 fitz 卡死的 PDF 打两次预览，两个名额被占满；之后所有文件请求排队，新 key 积到 128 后返回 429，只能重启恢复。HTTP 客户端断开不会取消阻塞线程。
- 位置: `retainpdf-files/src/derived_artifacts/preview.rs:render_book_image/render_pdf_page_preview`；`retainpdf-files/src/download_generation.rs`
- 现有防护为什么不够: 「admitted 的任务不因请求取消而取消」的设计让卡死的任务永久占名额。
- 建议修法: 预览/封面也走 `run_supervised`（带超时和 kill）。对前端无影响。

### 9. 派生产物新鲜度只比较 mtime，构建期间输入被替换会把旧内容标成新鲜
- 等级: 低
- 确认程度: 已确认（代码）；触发需要重渲染恰好落在对照 PDF/Word 构建的几十秒到十分钟窗口内
- 场景: `ensure_side_by_side_pdf` / `ensure_layout_docx` / `linearized_pdf_or_original` 读取 `translated.pdf` 开始构建；构建期间原地重渲染写完新 `translated.pdf`（mtime T2）；构建结束 rename 出的产物 mtime T3 > T2，被当作新鲜，内容却来自旧 PDF（`derived_artifacts.rs:cached_output_is_fresh`，`pdf.rs:21-25`）。另外条件是 `>=`，在 1 秒粒度的文件系统上同一秒内的重渲染也会误判。
- 位置: `retainpdf-files/src/derived_artifacts.rs:62-77`；`derived_artifacts/pdf.rs:20-26`
- 现有防护为什么不够: 没有在构建开始时记录输入 stamp 并在结束后比较。
- 建议修法: 构建前取输入 stamp，构建后再取，不一致就丢弃结果；或把输入 stamp 写进文件名。对前端无影响。

### 10. 删除文档时 `data/documents/<id>/` 不清理；有收藏的文档删除会 500 而不是文档里写的 409
- 等级: 低
- 确认程度: 目录遗留已确认；收藏分支存疑（当前路由里没有创建收藏的入口，只可能是旧数据或同步导入）
- 场景:
  1. `delete_document` 删 job 目录、下载 zip、上传目录（`documents.rs:150-185`），但 `documents/<document_id>/`（封面、缩略图、`pages/` 预览缓存、`merged/` 合并目录、`ai/`）没人删；全仓库没有对它的 `remove_dir_all`。合并目录是整本书的 PDF，占空间。
  2. `favorites.job_id` 是 `ON DELETE RESTRICT`（`v04_favorites_job_fk.sql`）。`delete_jobs`/`delete_document_cascade` 先删 job 行，遇到有收藏的 job 会触发外键错误，经 `From<rusqlite::Error>` 变成 500 internal，事务回滚什么都没删。`documents.rs:119` 和 `v04` 注释说的「应用层 409」在代码里不存在。
- 位置: `retainpdf-library/src/documents.rs:124-190`；`retainpdf-library/src/books.rs:35-100`；`database/retainpdf-db/src/db/schema/migrations/v04_favorites_job_fk.sql`
- 现有防护为什么不够: 没有测试覆盖「有收藏时删除」。
- 建议修法: 删除文档时一并删 `documents/<id>/`；收藏检查改成显式 409（或先删收藏）。对前端无影响（收藏分支仅把 500 改为 409）。

### 11. Word 导出读 `job_root/translated/`，复用别的任务译文的渲染任务可能找不到 manifest
- 等级: 低
- 确认程度: 存疑（没确认这类任务的 `translated/` 目录是否被创建/复制）
- 场景: retry-stage `create_new_job=true` 的渲染任务，`artifacts.translations_dir` 指向源任务目录（`translations/revision.rs:owned_job_root` 的注释和 409 `translations_owned_by_another_job` 都在说这点）。`ensure_layout_docx` 把 `job_root` 传给 Python，Python 用 `job_root/translated/translation-manifest.json`（`render/output/word/job_io.py:19-27`），不接受 `translations_dir` 参数。如果新任务目录里没有 `translated/`，导出报 500。`data`、`reports`、`reader` 这几个读取方都按 `translations_dir` 解析，只有 Word 例外。
- 位置: `retainpdf-files/src/derived_artifacts/word.rs`；`pipeline/.../render/output/word/job_io.py:19`
- 现有防护为什么不够: 没找到覆盖该场景的测试。
- 建议修法: 给 `layout-docx` 加 `--translations-dir` 参数，Rust 用 `translations_dir` 传入。对前端无影响。

## 查过、靠得住的

- 修订写回的原子性：页文件、checkpoint、修订日志都经 `_atomic_write_bytes`/`store.save`（tmp + fsync + rename + fsync 目录），快照用硬链接，原子替换新 inode 不影响旧快照；Python 异常路径的 `_rollback` 把页、checkpoint、日志、新建快照目录都还原。
- 两个 PATCH 并发：`CheckpointStore.acquire` 是非阻塞 `flock`，第二个直接得到 409 `checkpoint_locked`；`expected_generation` 提供乐观并发；同一块并发修改靠 `generation_mismatch`。Rust 侧 `job_running` 检查之后才启动的 worker，由 Python 文件锁挡住。
- 修订之后 DB 登记：`publish_translation_revisions` 幂等、单调，以 checkpoint 为准，登记失败不回滚文件，重发同一请求或打开实时译文会补登记；`prune_superseded_revision_snapshots` 只在所有页都已登记、没有 running attempt 时才删小于当前 generation 的目录。
- 渲染读译文：`load_translated_pages` 校验 checkpoint 已提交、page_hash 与文件一致，并在读完后再次比较 checkpoint/manifest 字节，不会读到半写状态。
- 译文页预览缓存：mtime 感知，并用 `.part.jpg` + `os.replace`（batch-1 的修复），有测试。
- 对照 PDF、Word、线性化、zip 都是「临时文件 → rename」；`all.zip` 与 markdown zip 每次请求重建，没有陈旧问题；Word 缓存键含 DPI 与导出器版本。
- `SummaryCache` 是请求级，失败也只缓存在本次请求里；`data/` 数据集缓存键是路径+大小+mtime，解析失败不缓存，读盘期间文件被替换最多多解析一次。
- 同一份产物的并发生成靠 `DownloadGeneration` 单飞，结果不保留（没有历史缓存）；取消请求不取消已受理的写入。
- 合并阅读目录按内容指纹命名且不可变，先在临时目录生成再整体 rename。
- 删除书/文档：先在一个 IMMEDIATE 事务里删完 DB 行（子表有 ON DELETE CASCADE），再删文件，最坏是孤儿文件而不是悬空索引；有测试覆盖「某一步失败回滚」。
- 备份：`VACUUM INTO` 得到一致快照，临时名 + rename，恢复前做完整性检查、版本检查、先存「恢复前」备份，恢复期间互斥并暂停同步。
