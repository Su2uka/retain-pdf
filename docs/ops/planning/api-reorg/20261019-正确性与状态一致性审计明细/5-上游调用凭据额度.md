# 上游调用、凭据与额度

范围：retainpdf-providers（model_executor / 凭据库）、OCR provider 派发日志（pipeline_dispatches）、OCR 歧义恢复、翻译请求 journal（Rust 读取 + Python 写入）、凭据 GC、页数额度、平台模型设置。读的是 wt-int 工作树，没改任何东西，没跑 cargo。

## 结论

写前日志（write-ahead）本身做得扎实：model_executor 的 claim 在单个 IMMEDIATE 事务里先落 `running` 再发请求；OCR 派发意图在发请求前落库；Python journal 的 dispatch 记录 fsync 之后才发请求，还有 torn-tail 截断和组提交；凭据库原子写 + 目录 fsync + flock/RwLock。这几处我没找到能丢记录的路径。

问题集中在"日志和使用它的闸门对不上"：最重的一个是默认的 book/translate 流程里 OCR 派发记录落在 `{id}-ocr` 子任务名下，而所有歧义闸门、诊断、恢复接口都按父任务 id 查，等于整套 OCR 歧义保护对默认流程不生效，重启后重试会无提示地重复提交 OCR（重复计费）。其次是进程内报错（超时等）不会把派发记录标成歧义；翻译自动续跑不看 journal；提交接口没有幂等。多用户（已冻结）的额度逻辑整体靠触发器，我只找到低级别隐患。Rust model_executor 是 env 开关（默认关）的 staged 路径，相关问题都标低。

## 问题

### 1. 默认 book/translate 流程的 OCR 派发记录挂在 `{id}-ocr` 子任务上，歧义闸门全按父任务 id 查，保护对它不生效
- 等级: 高（重复计费，且系统自己声称有保护）
- 确认程度: 已确认（静态追到底；"book 为默认 workflow"来自 library/translate.rs 注释和 UI 入口，未跑真实栈）
- 场景:
  1. 用户提交 book 任务（带 upload，无 artifact_job_id）。`run_job_with_ocr` 先把父任务置 Running，再 `create_ocr_child_job` 建 `{parent}-ocr`（translation_flow.rs:176 调 `execute_ocr_job` 传的是子任务）。
  2. OCR 在子任务里跑，`begin_ocr_dispatch` 用 `job.job_id`（= `{parent}-ocr`）取 attempt 并写 `pipeline_dispatches`（dispatch_journal.rs:27、mineru.rs:50/169、paddle.rs:57/137）。父任务在 OCR 阶段没有任何 pipeline attempt（attempt 只在 worker 启动时和 OCR dispatch 时取，父任务的 translate worker 还没起）。
  3. 此时 API/jobsd 重启（或崩溃）。startup_recovery 对父任务：`has_running_pipeline_attempt(parent)` 为假 → 直接判 Failed `worker_process_missing`（startup_recovery.rs:74/95）；子任务 `-ocr` 被 `list_resumable_pipeline_job_ids` 明确排除，`settle_orphaned_ocr_children` 把它收成 failed。派发记录停在 `intent`（提交瞬间）或 `receipted`（已拿到 provider 任务号，正在轮询）。
  4. 用户在详情页看到父任务失败，点"重试 OCR"（retry-stage stage=ocr）或"重跑"。`ambiguous_ocr_dispatch(db, 父任务id)`（stage_retry.rs:82、rerun.rs:77、ocr_ambiguity.rs:35/106）只查父任务 id 下的 `ocr-submit`，查不到 → 不拦。`resume_plan` 因为 OCR 没完成不给续跑 → 只能整体重新 `submit_job`，新子任务 `{newid}-ocr` 重新提交 OCR。
  5. 结果：provider 那边已有（可能已经解析完、已计费）的任务被丢弃，再付一次；`receipted` 的 task_id/batch_id 完全没被复用；`resolve-ocr-ambiguity` 对父任务返回 409 "job has no durable OCR dispatch to resolve"。诊断里 `failure_code` 虽然可能被文本分类成 `ocr_request_ambiguous`（job_failure.rs:96，来自子任务错误文本复制到父任务），`ocr_ambiguity` 字段为 None，用户没有可操作的恢复入口。
- 位置: translation_flow.rs:166-190；translation_flow_child.rs:75-95（子任务 id 写死 `{parent}-ocr`）；ocr_flow/dispatch_journal.rs:17-48；actions/ocr_ambiguity.rs:106-113；actions/stage_retry.rs:80-92；actions/rerun.rs:77；reports/failure.rs:15-21；runner/startup_recovery.rs:74-146；database/retainpdf-db/src/db/pipeline/queries.rs:57-80（排除 `-ocr`）。
- 现有防护为什么不够: 测试 `ambiguous_ocr_requires_explicit_resolution...`（api_tests/jobs_retry/retry_stage.rs:50-）把歧义派发记录直接 seed 在"源任务 id"下，掩盖了真实流程里记录在子任务名下这一点；没有任何代码把子任务的派发记录映射回父任务（grep `latest_pipeline_dispatch` 只有这几个按 job_id 直查的调用点）。
- 建议修法: `ambiguous_ocr_dispatch` / 诊断 / 恢复接口在源任务是复合任务时，先按 `artifacts.ocr_job_id`（或 `{id}-ocr`）解析出实际持有派发记录的 job，再查；恢复任务创建时的 CAS（`create_ocr_recovery_job_state`）也要对这个子任务 id 生效。另需决定 OCR 阶段崩溃时父任务是否该按子任务的 receipt 续跑，而不是判 Failed。前端：诊断里 `ocr_ambiguity` 会从 None 变成有值，是新增行为，不破坏旧字段。

### 2. 进程内的 OCR 提交报错（超时/断连）不会把派发记录标成 ambiguous，闸门只认 `ambiguous`，失败任务重试无提示重发
- 等级: 中
- 确认程度: 已确认
- 场景:
  1. OCR 任务（workflow=ocr，或复合任务的子任务）`begin_ocr_dispatch` 写 `intent` 后调用 `client.apply_upload_url(..).await?` / `create_extract_task` / paddle `submit_*`。请求已被 provider 收到，但响应读超时（reqwest 请求超时、连接被重置）。
  2. `?` 直接返回 Err → `execute_provider_transport` 错误 → `fail_ocr_transport`（ocr_flow/mod.rs:128）把任务标 Failed。全仓库没有任何生产代码调用 `mark_pipeline_dispatch_ambiguous`（只在 dispatches.rs 定义），所以派发记录一直是 `intent`。
  3. 用户重试：`ambiguous_ocr_dispatch` 过滤 `status == "ambiguous"`（ocr_ambiguity.rs:112），`intent` 不算 → 不拦、`build_ocr_ambiguity_view` 也只对 `ambiguous` 出视图（presentation/ocr_ambiguity.rs:5-8）。新任务直接再发一次，provider 侧可能已有一份在算/已计费。
  4. 只有"同一个 attempt 被原地续跑"才会在下次 `begin_pipeline_dispatch` 里把 `intent` 转成 ambiguous（dispatches.rs:56-76）；而失败任务不会被原地续跑（relaunch_in_place 只支持 render）。取消中途上传（paddle.rs"Watched::Canceled"注释写明"结果说不清"）同样留下 `intent`。
- 位置: ocr_flow/mineru.rs:50-75、169-199；ocr_flow/paddle.rs:57-100、137-160；ocr_flow/mod.rs:118-130；db/pipeline/dispatches.rs:56-76、163-195；actions/ocr_ambiguity.rs:106-113。
- 现有防护为什么不够: 设计假设"崩溃后同 attempt 续跑时才会遇到未确认意图"，没覆盖"进程活着但请求结果不明"这种更常见的情形；连接被拒/DNS 失败这类确定未送达的错误也没法和"可能已送达"区分，所以既不能安全自动重试，也没人把"可能已送达"的标出来。
- 建议修法: 在 submit 调用的错误路径按错误类型分流——连接/DNS/TLS 握手失败（确定未送达）把意图撤销或标 `failed`；其余（响应超时、断流、5xx）调 `mark_pipeline_dispatch_ambiguous`。取消路径同理。对前端无破坏（只是更多任务会出现 ocr_ambiguity）。

### 3. 翻译/精修的"重启后自动续跑"不看 journal，会无确认重发在途请求（和 OCR 的"自动重发被阻断"不一致）
- 等级: 中（重复计费，量级 ≤ 并发数个请求）
- 确认程度: 已确认（精修一支：确认没有 journal，续跑行为按同一机制推断）
- 场景:
  1. 翻译阶段 worker 在跑，N 个请求在途（journal 里有 N 条未配对 dispatch，已 fsync）。API/jobsd 重启。
  2. startup_recovery：任务有 running attempt → 置回 Queued 等自动续跑（startup_recovery.rs:95-103）→ `dispatch_workflow` 见 `running_pipeline_stage_key == "translate"` → `resume_translation_stage_from_durable_state`（lifecycle.rs:~104-120）。
  3. 新 worker 打开同一个 journal：`TranslationRequestJournal.__init__` 读出未配对 dispatch，只记进 `inherited_unresolved_dispatches` 摘要（request_journal.py:39-44），之后照常续跑，未提交 checkpoint 的单元被原样重新请求，`prior_ambiguous: true` 只写进 journal，没有任何阻断。
  4. 对比 OCR：同样场景下 `begin_pipeline_dispatch` 会直接 bail "automatic resubmit blocked"。翻译这边只有"手动 retry/rerun"才走 `requires_confirmation` 闸门（stage_retry.rs:99-118、rerun.rs:83-90）。
  5. 精修（render worker 里调模型，retry-stage stage=refine）连 journal 都没有（journal 只接在翻译聚合器 aggregator.py:399-420），同样机制下自动续跑会重发。
- 位置: translation/artifacts/request_journal.py:39-44、115-141；runner/lifecycle.rs（dispatch_workflow）；runner/startup_recovery.rs:74-103；jobs/actions/stage_retry.rs:99-118。
- 现有防护为什么不够: 闸门只挂在用户手动操作的 API 上；自动路径没有人问。
- 建议修法: 要么在自动续跑前读 journal、有活动歧义就不自动续（落成 Failed 等用户确认，和 OCR 一致），要么明确文档化"翻译自动续跑接受少量重复请求"。无前端影响。

### 4. 建任务 / 重试 / 文档翻译入口没有幂等键，也不拦同一文档的重复在途提交
- 等级: 中
- 确认程度: 已确认（没找到任何幂等或在途去重代码）
- 场景:
  1. 客户端提交 `POST /jobs`（或 `documents/:id/translate`、`retry-stage create_new_job=true`），响应在网络上丢了或用户双击。
  2. `submit_job` 每次都新生成 job id、各自 `persist_and_launch`（creation/submit.rs:93-150），没有 Idempotency-Key，也不检查"这本书已经有在途任务"（launcher.rs 只是把 active_job_id 指向最新的）。
  3. 两个任务并行跑两遍 OCR + 全文翻译，两份上游费用；其中一个成为"孤儿"仍占着执行槽，直到跑完。
- 位置: lifecycle/creation/submit.rs:93-150；library/src/translate.rs:18-70；actions/stage_retry.rs:159-175。
- 现有防护为什么不够: `reject_client_job_id` 禁止客户端自带 id，反而让客户端没法用 id 做幂等；重试按钮是否防抖只在前端（我没读前端）。
- 建议修法: 加可选 `Idempotency-Key` 头（新增字段，旧客户端不受影响），或对 retry-stage / document translate 在"同一源任务/文档已有 queued|running 的后继任务"时返回 409。

### 5. Python 模型客户端：非预期异常（如 `choices: []`）会漏掉 `record_request_end` 和 `release_request_slot`
- 等级: 中（请求槽泄漏可能让翻译无声卡死；还会留下一个假的未配对 dispatch）
- 确认程度: 已确认代码路径；"供应商真会返回 200 + `choices: []`"是推断（内容过滤类网关会这样）
- 场景:
  1. 非流式请求 200 返回，`data["choices"][0]["message"]["content"]`（client.py:462）遇到空 `choices` 抛 `IndexError`（或 `choices` 为 null 时 `TypeError`）。外层 `except` 只捕获 `(RequestException, ValueError, KeyError, JSONDecodeError, gaierror)`（client.py:483），这些异常不在内。
  2. 直接跳出循环：`release_request_slot` 没调（`_adaptive_inflight` 永久 +1），`record_request_end` 没调（journal 里 dispatch 永不配对，也不写 terminal）。
  3. 上层 `single_item_flow.py:67/216`、`sentence_level.py:150` 都是 `except Exception` 后继续降级，所以进程不会死；每泄漏一次，`acquire_request_slot`（aggregator.py:421-425，无超时的 while-wait）可用并发少一个；workers=1 时一次就永久卡死，较大并发时累积到上限后全体卡住。
  4. journal 侧：这次请求其实拿到了响应，却留下未配对 dispatch → 任务结束后 `requires_confirmation=true`，后续重试被要求 accept_duplicate_risk（假歧义）。
- 位置: translation/llm/providers/deepseek/client.py:404-425、455-470、483-505；artifacts/aggregator.py:421-441、548-575。
- 现有防护为什么不够: dispatch 前的 `except BaseException` 只守"dispatch 记录失败"，没守"响应后解析阶段的任意异常"。
- 建议修法: 把 `IndexError/TypeError/AttributeError` 并入捕获并归为 `invalid_response`，或用 `try/finally` 保证 slot 释放与 terminal 记录。无前端影响。

### 6. 翻译 journal 的歧义只被"相同 request_key 的后续终态"消解；降级重发（批→单条、换 thinking/temperature）用的是不同 body，旧 key 永远挂着
- 等级: 低（任务成功后诊断仍显示 ambiguous；每次后续重试都要再 accept 一次）
- 确认程度: 存疑（没逐条确认哪些降级路径会在批次超时后改发不同 body；"消解只认同 key"是已确认的，见 translation_request_recovery.rs:92-103 与 request_journal.py:93-110）
- 场景: 批量请求 K1 读超时（terminal=ambiguous）→ 上层降级成单条请求（不同 body → 不同 key）→ 全部成功、任务 Succeeded，但 K1 仍在 `active_ambiguous_request_keys`。`copy_request_journal_if_present` 又把 journal 带进重试任务（translation_checkpoint_resume.rs:105-116），歧义代代继承；`accepted_ambiguous_request_risk` 只被存进 request_payload，没有任何代码消费它（grep 只有写入点），所以接受一次不会清除。
- 位置: jobs/actions/translation_request_recovery.rs:92-114；translation/artifacts/request_journal.py:93-110、144-170。
- 现有防护为什么不够: 用户总能手动接受，所以不是死锁，只是状态长期偏保守；成功任务的 `resume_plan` 因 `translations_available` 先返回 Render，不受影响。
- 建议修法: 终态成功后按 stage/unit 而不是仅按 request_key 消解；或让 accept 动作往 journal 追加一条"resolved"记录。

### 7. Rust model_executor（env 开关，默认关）：`paused` 一旦置位永不清除；定义明确的"未发出"也消耗 unit 预算
- 等级: 低（staged 路径，`RETAIN_MODEL_EXECUTOR_ENABLED/WORKER_ENABLED` 不为 1 时根本进不来；submit.rs:182-187）
- 确认程度: 已确认（代码层面），影响限于开关打开后
- 场景:
  1. `ModelWorkerLease` 在每次 `execute_process_job_stage` 结束时 Drop → `close_model_worker_session`：无条件 `expires_at=0, paused=1`（model_requests.rs:279-290），连正常结束也置位。
  2. 同一 job id 之后若再起翻译 worker（自动续跑、同 attempt 重启），`create_model_session` 的 `ON CONFLICT DO UPDATE` 只更新 token_hash/expires_at，不动 `paused`（model_requests.rs:91-111）→ 所有新 operation 的 `reserve_model_operation` 返回 `Paused`，worker 报 "executor conflict or paused job"（rust_executor.py:88），只有已完成的 operation 能返回缓存回执。全仓库没有任何 `paused=0` 的写入。
  3. 另：API 在 `queued` 阶段重启，`recover_model_operations` 把它标 `cancelled executor_restarted_before_dispatch`（确定未发出），但 `unit` 的 primary 预算（`count != 0` 即 `UnitBudgetExceeded`）已被占用，同 unit 不可能再发，任务只能失败。
  4. 恢复入口也被刻意关死：`supported_retry_policies: ["block"]`、stage_retry/rerun 对 execution_connection 任务直接 409（translation_request_recovery.rs:51-60、rerun.rs:72-76）。
- 位置: database/retainpdf-db/src/db/model_requests.rs:91-111、135-185、279-300；runner/worker_process.rs:19-52；providers/model_executor/mod.rs:150-230。
- 现有防护为什么不够: 设计上就是"手动恢复未实现"；开关默认关，实际暴露面小。
- 建议修法: 正式放量前补"恢复"动作（清 paused、对 `cancelled before dispatch` 的 operation 放行重新预留），或把 Drop 里的 pause 限定为"有 running 操作时才 pause"。

### 8. 凭据：导入凭据先于使用锁创建，和任务删除 GC 有一个窄窗口；失败的提交会遗留已导入凭据
- 等级: 低
- 确认程度: 已确认（窗口），后果是误报错而非丢数据
- 场景:
  1. 提交 B 带内联 key K，`get_or_create_managed_credential` 复用了已有的 managed 凭据 C1（写锁，随即释放；submit.rs:`secure_job_credentials`）。
  2. 此时别处删除了最后一个引用 C1 的任务 A，`cleanup_deleted_job_credentials` → `delete_unreferenced_managed_credential` 拿写锁，`count_jobs_referencing_credential(C1)=0`（B 还没落库）→ 删掉 C1。
  3. B 随后 `acquire_job_credential_usage_lock` 再校验 → 凭据不存在 → 返回 400/404。用户重试即可。不会出现"任务已落库但凭据没了"（使用锁覆盖了 校验→落库）。
  4. 反向：`secure_job_credentials` 导入成功但后续校验/落库失败（或 `import_inline_refine_keys` 之后 `write_refine_override` 失败），已导入的 managed 凭据无人引用且没有周期性清理，明文 key 一直留在 vault。
- 位置: lifecycle/creation/ocr_credentials.rs:30-40、`acquire_job_credential_usage_lock`；providers/credentials/service.rs:`get_or_create_managed_credential`、`delete_unreferenced_managed_credential`；jobs/lifecycle/managed_credential_gc.rs。
- 现有防护为什么不够: GC 以"数据库里是否有任务引用"为准，创建与落库之间天然有空窗；清理是 best-effort 且仅在删任务时触发。
- 建议修法: 导入与使用锁合成一个临界区（先拿读锁再导入需要升级锁，可改为"先拿使用锁再导入，导入走已持有的文件锁"）；或加一个启动时的孤儿 managed 凭据清扫。无前端影响。

### 9. 多用户额度（已冻结）：预扣早于落库、恢复任务不计费等隐患
- 等级: 低（仅多用户模式；单机 owner=LOCAL_USER_ID 直接 `reserve_for_job -> false`）
- 确认程度: 已确认（代码层面）
- 要点:
  1. `persist_and_launch` 先 `reserve_for_job`（写 job_page_charges + 账本）再 `persist_job_with_resources`（submit.rs:190-196）。两步之间进程崩溃：留下指向不存在任务的 `reserved` 行，退款触发器挂在 jobs 表上，永远不会触发，页数丢失。`release_for_job` 失败也只记日志。
  2. OCR 歧义恢复路径 `persist_ocr_recovery` 不预扣（"不计费"），而源任务失败时已被触发器全额退款 → 恢复出的整条流水线（OCR+翻译+渲染）免费。
  3. 退款/确认触发器是 `AFTER UPDATE OF status_json`，只要 SET 列表含该列就触发（不要求值变化）；失败态任务被原地重渲染预扣后，若在 `save_job` 改成 queued 之前有别的写入把行以 failed 再写一遍，会立刻被退回，随后免费渲染。窗口很窄。
  4. `apply_platform_models_to_input`（submit_job）与 `apply_platform_models`（persist_and_launch）各解析一次平台设置，设置在两次之间改了的话，使用锁校验的凭据和最终落库的不是同一个。
- 位置: lifecycle/creation/submit.rs:93-150、186-200；accounts/src/page_quota/mod.rs:87-135；db/schema/migrations/v23_page_quota.sql；db/page_quota.rs:`reserve_job_pages`。

## 查过、靠得住的

- model_executor 写前：`claim_model_operation` 在 IMMEDIATE 事务里先把 `queued→running` 落库才发网络请求，且校验 `paused=0` 与 session 未过期；失败标 `cancelled dispatch_fenced`，不会永远 queued。`reserve_model_operation` 以 (job, operation_id) 幂等，内容 hash/unit/purpose 不同返回 Conflict；primary/repair 预算在同一事务内检查。
- model_executor 崩溃恢复：`ModelExecutor::new` 启动时 `recover_model_operations` 把 `running→ambiguous`（并暂停相关 job）、`queued→cancelled`；取消 running 操作变 ambiguous 并暂停；worker 停止时 `close_model_worker_session` 同样处理。ambiguous 终态不会被自动重发（Python 客户端对 ambiguous 直接抛 `AmbiguousModelRequest`，重试沿用同一 operation_id）。`finish_model_operation` 只更新 `queued/running`，终态不会被覆盖。
- 真正发请求的传输层 `.retry(never())`、不跟随重定向、只对 429 重试一次且预算内；响应体/密钥不进错误串。
- OCR 派发日志的 DB 层：`begin_pipeline_dispatch` 在 IMMEDIATE 事务里先查再插，身份（provider/operation/request_hash）变化会 bail；已有 `receipted` 才 Resume，裸 `intent` 一律转 ambiguous 并阻断；`create_ocr_recovery_job_state` 把"源派发 ambiguous→resolved（带 generation 和源任务 failed 校验）+建恢复任务+种子 attempt/dispatch+审计事件"放在同一事务，两个请求同时来只有一个成功（有测试覆盖，见 retry_stage.rs 与 db/pipeline/tests.rs）。
- Python journal：dispatch 记录写入 + `fsync` 后才返回（组提交，失败后整体 fail-closed）；打开时截断 torn tail 并 fsync；O_APPEND、0600；Rust 与 Python 对同一文件的解析规则一致，损坏的完整行 fail-closed 为 `corrupt`；journal 文件不存在时 `resolve_translation_request_journal` 返回 None，不会误报 corrupt。
- 凭据库：写入走临时文件 + `sync_all` + `rename` + 目录 `sync_all`，0600/O_NOFOLLOW；进程内 RwLock + 跨进程 flock；使用锁覆盖"存在性校验 → 任务落库"，submit_job 里 `_credential_guard` 活到 `persist_and_launch` 之后；运行期凭据靠"任务行里的 ref"被 `count_jobs_referencing_credential`（覆盖 translation/reviewer/ocr 三个 ref 字段）保护，不依赖使用锁；非 force 的用户删除也会被任务引用挡住。
