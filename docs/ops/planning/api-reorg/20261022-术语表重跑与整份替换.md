## 取舍

1. **内联条目单独存，不靠计数猜。** `glossary_inline_entries` 空的时候不写出来（`skip_serializing_if`），老任务、没有内联的新任务
   序列化结果都不变，`submissions.txt` 没动。读的时候问任务（`JobRecord::glossary_inline_entries_for_rerun`）：
   存了就用；没存而 `glossary_inline_entry_count == 0` 就是没有内联；没存而计数不是 0 只能是 2026-10-22 以前的任务，
   分不清快照里哪些是内联的，退回旧行为（整份快照当内联）。新代码写的计数总等于存下的条数，所以三种情况不会混。
2. **字段放在 `TranslationInput` 上**，契约 `create-job.v1` 跟着加（`contracts/` 和 `backend/contracts/` 两份、生成的 TS 和 `dist/`）。
   客户端发了也会被 `resolve_task_glossary_request` 覆盖成从 `glossary_entries` 规范化出来的那份，不会被拿来骗重跑。
3. **在哪儿换回、在哪儿查 409。** 换回放在两个复制源任务请求的地方（`build_rerun_request`、`build_retry_request`），在套用 overrides
   之前：重试的 overrides 给了 `glossary_entries` 以它为准。查「表还在不在」放在套用 overrides 之后、`submit_job` 之前
   （续跑、`retry-stage` 出新任务、`resolve-ocr-ambiguity` 绑定回执三处），而且只管**源任务那张表**：overrides 换成别的表、
   别的表不在，是请求写错了，照建任务的规矩 400。出新的渲染任务不用术语，快照原样带过去，不查。
   助手文件 `actions/rerun_glossary.rs` 只问任务（`translation_glossary_id()`、`glossary_inline_entries_for_rerun()`），
   不进 `KNOWN_REQUEST_PAYLOAD_WRITERS`。
4. **停用的表重跑也是 409（`glossary_disabled`）。** 用户只定了删表 409；停用的表建任务 400 是用户定的，重跑若照样走到解析就是
   400，但续跑的请求本身没错，是表的状态不允许，按 400/409 的分工给 409，和 `glossary_missing` 并列。
5. **这两个原因不进 `GET /jobs/:id/actions` 的 `disabled_code`。** 要知道就得在算操作清单时读术语表，代价和收益不成比例；
   文档写明「只在提交时才知道」。
6. **`updated_at` 精确到毫秒且单调。** `now_iso()` 只到秒，同一秒里连着保存两次 `updated_at` 不变，`expected_updated_at` 就分不出版本。
   术语表自己的时间戳改成毫秒，保存时不晚于上一版就取上一版加 1 毫秒。老表的值还是到秒，字符串排序在同一秒内会略有出入，无碍。
7. **`expected_updated_at` 不给时照旧后写覆盖**（只增不改）。给了时先和读到的比一次（快速 409），再在 `UPDATE … WHERE updated_at=?` 里比，
   读完到写之间被改也能拦住。
8. **`entries` 由可缺省变成必填。** 用户定「`name`、`entries` 仍必填」；以前 `entries` 有 `#[serde(default)]`，PUT 缺省字段保留原值以后，
   不给 `entries` 等于清空就说不通了。缺字段按通用规矩 422。前端、AI 都一直带着。
9. **去重键里正则也区分大小写。** 审计写的是「`exact` 区分、其余小写」，但正则小写化会改变它的意思，而 Python 编译正则不带 IGNORECASE；
   照翻译时的实际匹配，只有 `case_insensitive` 按小写比。代价：同一个词的 `exact` 和 `case_insensitive` 两条算两个键
   （内联的 `exact` 不再覆盖表里同词的 `case_insensitive`）——这种写法本身就自相矛盾，按「各留一条」处理并写进文档。
10. **Python 侧的键不改。** `retainpdf_translation/core/terms/glossary.py` 里的键 `(source.casefold(), target.casefold(), level, context)`
    是「同一次命中去重」，比 Rust 的键细（还带译文和类型），Rust 留下的两条到 Python 不会被并掉，没有必要对齐，翻译包没动。
11. **JSON 接口认别名、拒不认识的值。** 以前 JSON 和 CSV 共用宽松规则；现在 JSON（建表、保存、建任务的内联条目）对不认识的
    `level`/`match_mode` 400，空串仍是默认值，中英文别名照认（`case-insensitive`、`不翻译` 这类已有测试在用）。CSV 照旧宽松。
    顺带让别名表认 `preferred`、`exact` 的几个中文写法（以前落到默认值也是它们，结果不变）。
12. **正则只拒明显写错的。** 用 `regex-syntax` 解析，环视、反向引用（Python 有、Rust 没有）放过。
13. **CSV 默认列序不改**（用户定），前端改占位符，写进交接文档。

## 调用方核对

- 前端：`frontend/packages/api/src/glossaries.ts`（`fetchGlossaries` 不带参数；`updateGlossary`/`createGlossary` 发 `name`、`entries`，
  词条带 `source/target/level/match_mode/context/note`，`level`、`match_mode` 都是合法值；`parseGlossaryCsv` 发 `csv_text`；
  `exportGlossaryCsv` 读 `content-disposition`）；`features/ingest/domain/workflow/payload.ts` 建任务只发 `glossary_id` 和空的
  `glossary_entries`；`features/ingest` 里没有按 404 分支的代码（`git grep 404`）。`POST /glossaries/import` 全仓库没有调用方。
- AI：`agent_translation_runner.py` 的 `term-set` 经 `retainpdf-agent glossary get/list/create/update`，请求体原样转发；
  改成带 `expected_updated_at`，409 `glossary_changed` 重读重试一次；续跑、重试的 409 提示补两个新原因。
- CLI（`backend/cli`）、脚本：没有术语表调用。

## 没做的

- 契约 `glossaries.v1`（审计建议等接口定型后补）。
- 列表在库层只数条数、不读全量词条（量小，先不改）。
- 停用的表在下拉里还列着，要前端改调 `?enabled=true`（交接文档）。
