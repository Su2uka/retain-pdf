# 从契约生成前端请求函数

**状态：** 方案，待后端评估

**日期：** 2026-10-22

**范围：** `contracts/`、`frontend/packages/api`；后端只补契约里的端点表

## 1. 为什么要做

前后端现在的摩擦集中在“请求函数”这一层：

- `frontend/packages/api/src` 里有 95 个手写的导出请求函数。地址、方法、查询参数、请求体字段名都是手敲的，类型
  靠手写或者 `any`（2026-10-22 之前合集、搜索还返回 `Promise<any>`）。
- 后端改一个接口，要写交接（文件、旧写法、新写法），前端再照着改一遍。漏改了要到运行时才发现。
- 后端 2026-10-22 起对不认识的查询参数和请求体字段返回 400（`fix/library-paging-and-unknown-fields`）。
  前端拼错一个字段名，以前是被悄悄忽略，现在直接报错，所以更需要编译期就拦住。

类型这一半已经做了：`contracts/*.schema.json` 生成 `contracts/dist/*.d.ts`，前端从
`@retainpdf/contracts/<名字>` 引用（书库这一批 2026-10-22 刚换完）。缺的是另一半：**请求函数本身**。

## 2. 现有的底子

- **接口登记表：** 每个接口在 `crate::endpoints!` 表里一条，`backend/api/docs/routes.txt` 从表生成，
  158 个接口。
- **契约端点表：** 15 份契约里有 `endpoints` 数组，共 63 条。每条至少有 `method`、`path`，大多数有
  `query`、`input`、`output`（定义名），比如：

  ```json
  { "method": "GET", "path": "/api/v1/documents", "query": "ListDocumentsQuery", "output": "DocumentListView" }
  ```

  其中 `library-documents.v1` 的 17 条已经覆盖书、合集、搜索的全部接口。
- **生成器：** `contracts/scripts/generate-types.mjs` 已经从 schema 生成 TS 类型，`generate:check` 在测试里守着。
- **运行时：** `packages/api` 里有现成的 `apiFetch`、`buildApiHeaders`、`unwrapEnvelope`（拆 `{code, data}`）、
  `attachErrorDetails`（把 `reason`、`error_code` 挂到错误上）。

所以只差一步：让生成器在类型之外，再按端点表生成调用函数。

## 3. 方案

### 3.1 后端：把端点表补成“能生成代码”的样子

每条端点补齐以下字段（已有的不动）：

| 字段 | 说明 |
|---|---|
| `client_name` | 生成的函数名，例如 `listDocuments`、`patchDocument`。显式写，不从路径推，免得改路径时函数名跟着变 |
| `query` / `input` / `output` | 已有。没有请求体或查询参数就不写 |
| `response` | 返回方式：`json`（默认，`{code, data}` 信封）、`sse`、`binary`、`websocket`、`raw_json`（不带信封） |

再加一条后端测试：契约端点表里的每条 `method + path`，都必须在 `routes.txt` 里存在。反过来不强制，管理后台、
内部接口可以不进契约。这样契约里不会留下已经删掉的地址（今天删书架旧地址时，就是靠手工 grep 发现的）。

前端实际在调用、但契约里还没有的接口，由前端列一张清单交给后端，分批补进去（见第 5 节）。

### 3.2 前端：生成器

在 `contracts/scripts/` 加 `generate-client.mjs`，`npm run generate` 时一起跑，输出
`contracts/dist/<契约名>.client.ts`（或放进 `frontend/packages/api/src/generated/`，二选一，见第 6 节）。
每条 `response: json` 的端点生成一个函数：

```ts
// 生成，不要手改
export function listDocuments(
  apiPrefix: string,
  query?: ListDocumentsQuery,
  init?: RequestOptions,
): Promise<DocumentListView> {
  return request({ apiPrefix, method: "GET", path: "documents", query, init });
}

export function patchDocument(
  apiPrefix: string,
  params: { document_id: string },
  body: PatchDocumentInput,
  init?: RequestOptions,
): Promise<DocumentRecord> {
  return request({ apiPrefix, method: "PATCH", path: `documents/${enc(params.document_id)}`, body, init });
}
```

- 路径参数从 `:document_id` 这种占位里取，全部 `encodeURIComponent`。
- `query` 按 schema 编码：数组按后端约定用逗号连接（`job_ids=a,b`），`undefined` 和空串不发。
- 生成的只是传输层，用一个手写的小 `request()`：拼地址、带 `X-API-Key`、拆信封、出错时 `attachErrorDetails`。
  这样多用户模式的 Cookie、`AbortSignal` 等横切逻辑只在 `request()` 里写一次。
- `sse`、`binary`、`websocket` 第一期不生成，照旧手写（流式、下载、终端各有各的处理）。

### 3.3 前端：手写层变薄

现在的手写函数除了发请求，还做两件事：把错误翻成中文、给返回值补默认值。生成以后：

- 纯转发的函数直接删掉，调用方改用生成的函数；
- 有中文报错、兜底逻辑的，保留成薄包装，内部调用生成的函数。

再加一个棘轮测试：`packages/api/src` 里直接写 `buildApiEndpoint(` 的数量只减不增（现在 55 处），新接口只能走生成的函数。

## 4. 得到什么

- 后端改了接口，重新生成以后前端编译就报错，不用再靠交接文档逐条对。
- 字段名、查询参数名在编译期检查，碰不上新的“不认识的字段 400”。
- 交接文档只需要写行为变化（比如“现在返回 404”），不用再写调用方式。
- 前端 `packages/api` 预计能删掉一半以上的手写代码。

多用户相关的接口（管理后台、账号）已经冻结，放到最后，或者不做。

## 6. 待后端决定的问题

1. 字段名用 `client_name` 可以吗？还是复用已有的 `op`（目前只有 4 条在用）？
2. “契约端点必须在 `routes.txt` 里”这条检查，放在 `contracts/tests` 还是 rust_api 的测试里？
3. 生成的客户端放在 `contracts/dist`，还是 `frontend/packages/api/src/generated`？
   - 前者：后端改完契约跑一次 `npm run generate` 就能看到前端的编译结果；
   - 后者：契约包保持只有类型，生成器和运行时都归前端。
   - 我倾向后者，`request()` 依赖前端的运行时配置，不该进契约包。
4. 有没有返回不带 `{code, data}` 信封的 JSON 接口？需要在 `response` 里标出来。

## 7. 不做的事

- 不换框架。dsh 用 `typert` 从服务端装饰器生成客户端，前提是后端也是 Cordis 上的 Node 服务；我们的后端是
  Rust，照它的思路做，不搬它的代码。
- 不引入 OpenAPI 全家桶。现有契约加一个几百行的生成器就够了，不需要再维护一份 OpenAPI 文档。
