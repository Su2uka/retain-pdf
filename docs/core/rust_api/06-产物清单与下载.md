# 产物清单与下载

> 文件接口已统一到 `/jobs/{job_id}/files/…` 和 `/documents/{document_id}/files/…`；旧的 `/artifacts`、`/artifacts-manifest`、`/pdf` 等地址已于 2026-10-18 删除（返回 404），本文已改成新地址。新旧对照见 [下载总览](../../api/07-产物下载/01-下载总览.md)，全部接口见 [接口目录](../../api/00-接口目录.md)。

先看边界：

- `provider raw`
- `normalized`
- `published artifact`
- `download API`

这里这篇文档主要讲后两层：

- `published artifact`
- `download API`

前两层的 Rust 侧职责说明见：

- [10-Rust 侧 Artifact Boundary.md](./10-Rust%20%E4%BE%A7%20Artifact%20Boundary.md)

## 1. 为什么需要文件清单

任务目录是后端内部实现细节，后面可能会继续调整。

所以前端或外部调用方不应该依赖：

- `rendered/` 下面一定有什么
- `md/` 下面一定有什么
- `ocr/unpacked/` 一定不变

现在正式的对外真源是数据库里的稳定产物登记表，再通过文件清单 `/files` 暴露出来。

## 2. 主接口

`GET /api/v1/jobs/{job_id}/files`

原来的 `/artifacts-manifest`（含 OCR 子任务的 `/ocr/jobs/{job_id}/artifacts-manifest`）已删除，`/files` 返回的结构不一样。

## 3. 它返回什么

它按 `output`、`pages`、`internal` 三组列出这个任务的文件，每条条目有：

- `name`
- `url`
- `content_type`
- `ready`
- `on_demand`
- `size_bytes`
- `updated_at`
- `stage`

另有 `source`（原文 PDF，书的文件）、`attempt`、`pages.url_template`。字段细节见 [下载总览](../../api/07-产物下载/01-下载总览.md)。

前端真正该用的是：

- `name`
- `ready`
- `url`

详情接口里的 `artifacts` 适合快速判断按钮状态；完整机器读取以 `/files` 为准。

## 4. 常见 artifact_key

目前常见包括：

- `source_pdf`
  - 如果请求设置了 `ocr.page_ranges` 且走本地上传，这里指向的是任务内生成的子集 PDF
- `translated_pdf`
- `typst_source`
- `typst_render_pdf`
- `markdown_raw`
- `markdown_images_dir`
- `markdown_bundle_zip`
- `normalized_document_json`
- `normalization_report_json`
- `layout_json`
- `translation_manifest_json`
- `provider_bundle_zip`
- `provider_result_json`
- `pipeline_summary`
- `events_jsonl`
  - 对应任务运行期落盘的事件流导出，适合调试下载（`files/internal/events.jsonl`）

其中语义要分清：

- `provider_result_json` / `provider_bundle_zip`
  属于 `provider raw`
- `normalized_document_json` / `normalization_report_json`
  属于 `normalized`
- `markdown_raw` / `markdown_bundle_zip` / `translated_pdf`
  属于 `published artifact`

而 `/files/output/…`、`/files/internal/…` 这些接口属于 `download API`。`internal/` 下的文件名和 artifact_key 的对应表是 `JOB_INTERNAL_FILES`（`backend/packages/retainpdf-files/src/links.rs`）

对照 PDF 不要求前端本地合成，直接调用：

- `GET /api/v1/jobs/{job_id}/files/output/side-by-side.pdf`
- 返回 `application/pdf`
- 后端会读取源 PDF 和最终翻译 PDF，生成并缓存
  `jobs/{job_id}/artifacts/{job_id}-side-by-side.pdf`
- 每页左侧是原文，右侧是译文；如果两边页数不一致，输出页数取两者最大值，缺失的一侧留空
- 源 PDF 或译文 PDF 未 ready 时返回 `404`

## 5. 推荐读取方式

前端或脚本不要再根据目录结构猜文件位置，而应：

1. 先请求 `/files`
2. 找到目标文件的 `name`
3. 检查 `ready`
4. 使用 `url`

其中 `output/ocr.zip` 是最适合前端直接下载的 Markdown 包：

- 只包含 `markdown/full.md`
- 只包含 `markdown/images/**`
- 不包含原始 PDF
- 不包含翻译后 PDF
- 不包含 provider bundle
- 不包含其他调试 JSON

原来 `/artifacts/markdown_bundle_zip?include_job_dir=true` 那种带任务号目录的变体，随 `/artifacts/{artifact_key}` 一起删除了；
`files/output/ocr.zip` 的根目录固定是 `markdown/`。

如果你想下载任务的原始事件流，可以取：

- `files/internal/events.jsonl`（多用户下只给管理员）

它的语义是：

- 一个稳定调试产物
- 内容来自任务日志目录下的 `events.jsonl`
- 适合排错、导出、归档

但注意：

- 前端主界面的“事件流”tab 仍然应该优先读取 `progress/events` 接口
- 不建议前端把 `events.jsonl` 当成主展示接口真源

## 6. 和旧接口的关系

旧的 `/pdf`、`/markdown`、`/normalized-document`、`/artifacts*` 等接口已于 2026-10-18 删除，
统一换成 `/jobs/{job_id}/files/…`，新旧对照见 [下载总览](../../api/07-产物下载/01-下载总览.md)。

现在的关系是：

- `/files/output/…`、`/files/internal/…` 是稳定下载入口
- `/files` 是稳定发现入口
- 详情里的 `artifacts.pdf` / `artifacts.markdown` / `artifacts.bundle` 是推荐的页面状态字段
- 详情里的同级 `pdf_url` / `markdown_url` / `bundle_url` 等旧字段只是兼容别名（字段名没动，值已是新地址），不建议新代码继续依赖

但要注意一个边界：

- 这里的“稳定入口”指的是当前 API 里的稳定资源入口
- 不是指旧任务目录布局兼容

如果任务本身仍来自 `originPDF/jsonPDF/transPDF/typstPDF` 旧布局，或者 artifact 还存绝对路径，那么这些下载入口也会直接拒绝，必须重跑

## 7. 为什么这样做更稳

因为以后即使后端把文件从：

- `rendered/...`

改到：

- `outputs/render/...`

只要后端更新数据库登记逻辑，外部接口就不需要跟着改。

这正是这次重构的目的：把“目录结构”从公开契约里剥离出去。
