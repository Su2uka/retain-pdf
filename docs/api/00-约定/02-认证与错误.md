# 认证与错误

## 认证

除 `GET /health` 外，接口需要请求头：

```http
X-API-Key: your-api-key
```

认证失败通常返回 `401` 或 `403`。

## 凭据字段

任务请求里可能包含下游 provider 凭据，例如：

- `ocr.mineru_token`
- `ocr.paddle_token`
- `translation.api_key`
- command provider 的 `ocr.options.credential`

后端响应不会回显这些明文。前端只能通过类似 `*_configured` 的布尔字段判断是否已配置。

## 错误处理原则

- HTTP status 表示请求级错误，例如认证失败、参数非法、资源不存在。
- job 的 `status=failed` 表示任务运行失败。
- 任务失败原因优先读 `failure` 或 diagnostics 接口，不要从 `stage_detail` 反推。

常用状态：

- `400`: 请求本身写错了：字段不合法、组合不支持、请求体里有不认识的字段。和任务现在是什么状态无关，同样的请求换个状态还是 400。
- `401`: 缺少或错误的 API key。
- `404`: job 或 artifact 不存在。只有数据库里确实没有这条记录才是 404；有记录但读不出来（行解码失败、库被锁……）是 `500`，不会说成 "job not found"。
  任务在、原始文件或报告还没产出也是 `404`，但带 `error.details.reason = "not_ready"`，见下面的「还没产出」。
- `409`: 请求没问题，但任务或产物的当前状态不允许该操作（任务在跑、产物不在、请求结果不确定……）。任务操作的 409 都带 `error.details.reason`，见下面的「机器可读原因」。
- `500`: 后端内部错误。响应里不带原因，只带编号：`message` 是 `internal server error (ref <编号>)`，
  `error.details.error_id` 是同一个编号，凭它在后端日志里搜 `error_id=<编号>` 找完整原因。

## 400 和 409 的分工

2026-10-19 定下的规矩，所有接口照这个来：

- 请求本身写错了 = `400`。字段值不合法、组合不支持（例如 `create_new_job=false` 用在 `ocr`）、请求体里有不认识的字段（拼错的字段不会被悄悄忽略）。
- 请求没问题，是任务或产物现在的状态不允许 = `409`。同一个请求等状态变了可能就成功。
- 判断顺序：先看请求写没写对（400），再看状态（409）。在跑的任务收到写错的请求，得到的是 400，不是 409。

## 机器可读原因：`error.details.reason`

4xx 可以带一个稳定的 `reason`，客户端按它分支，不要解析 `message`（`message` 是给人看的，措辞会变）。
信封和没有 reason 的同状态码错误完全一样（同样的顶层 `code`、`error.code`、`message`），只是 `error.details` 里多一个字段：

```json
{
  "code": 40900,
  "message": "job is queued or running; cancel it before retrying a stage",
  "error": {
    "code": "CONFLICT",
    "http_status": 409,
    "details": { "reason": "job_active" }
  }
}
```

没有 reason 的错误 `details` 是 `{}`。`reason` 只增不改：客户端对不认识的值按「状态不允许，看 `message`」处理。

### 任务操作的 409 原因

适用于 `POST /jobs/{job_id}/actions/` 下的 `retry-stage`、`resume`（旧名 `rerun`）、`resolve-ocr-ambiguity`、`cancel`。

| `reason` | 什么时候 | 接口 |
|---|---|---|
| `job_active` | 任务在排队或运行，先取消再操作 | `retry-stage`（所有阶段，含原地重渲染、精修）、`resume`/`rerun`、`resolve-ocr-ambiguity` |
| `job_not_active` | 取消一个不在排队/运行的任务 | `cancel` |
| `artifacts_missing` | 这个阶段或续跑要用的产物、原始来源（upload_id / source_url）已经不在 | `retry-stage`、`resume`/`rerun` |
| `translations_not_owned` | 精修要写回任务自己的译文目录，但这个任务渲染的是别的任务的译文，请去精修源任务 | `retry-stage stage=refine` |
| `ambiguous_ocr_dispatch` | OCR 派发的结果不确定：先 `resolve-ocr-ambiguity` 绑定已有回执，或 OCR 重试时带 `ambiguous_request_policy=accept_duplicate_risk`。不能拿「从翻译阶段重试」处理 | `retry-stage`（ocr）、`resume`/`rerun` |
| `ambiguous_translation_request` | 翻译请求的结果不确定：`retry-stage` 选 translation 并带 `ambiguous_request_policy=accept_duplicate_risk`（通用续跑一律挡住） | `retry-stage`（translation）、`resume`/`rerun` |
| `request_journal_corrupt` | 翻译请求日志损坏，接受重复风险也修不好 | `retry-stage stage=translation`、`resume`/`rerun` |
| `model_executor_unsupported` | 任务绑定了 Rust 模型执行器，这条旧路径不支持（精修，或除渲染外的重试 / 续跑） | `retry-stage`、`resume`/`rerun` |
| `stale_resolution` | OCR 歧义处理的 `resolution_revision` 过期，或已被别的请求处理 | `resolve-ocr-ambiguity` |
| `no_ocr_dispatch` | 任务没有可处理的 OCR 歧义：既不是失败也不是已取消，或没有记录在案的派发 | `resolve-ocr-ambiguity` |
| `ocr_dispatch_unsupported` | 不确定的 OCR 派发属于不支持绑定收据的服务商/操作 | `resolve-ocr-ambiguity` |

同时命中多条时 `job_active` 最先判，其余的先后不保证。

`GET /jobs/{job_id}/actions` 的每个阶段的 `disabled_code`、`GET /jobs/{job_id}/actions/resume` 的 `reason_code`
是同一套值（文字说明仍在 `disabled_reason` / `reason`），可以不发请求就知道会得到哪个原因。

### 删除的 409 原因

`DELETE /library/books/{job_id}`、`DELETE /documents/{document_id}`。

| `reason` | 什么时候 | 接口 |
|---|---|---|
| `job_has_dependents` | 删除范围之外还有别的任务在用被删任务的产物（`source.artifact_job_id` 指向它，典型是重新排版的 render 任务）；先删依赖者，或带 `force=true` | `DELETE /library/books/{job_id}`（`DELETE /documents/{document_id}` 的依赖者在别的书里时也会触发） |

这两个接口里「任务在排队/运行」的 409 目前没有 `reason`；`force=true` 会先取消再删。

### 还没产出（404）

2026-10-19 定下的规矩（[规矩和删留](../../ops/planning/api-reorg/20261019-任务接口规矩和删留.md) 第 2 条），所有接口照这个来：

- **任务（或书）本身不存在**：普通 `404`，`error.details` 是 `{}`，提示 `job not found: …`。
- **原始文件和报告**：任务在、要的东西还没产出，返回 `404` + `error.details.reason = "not_ready"`，提示统一是 `<名字> not ready`
  （`<名字>` 是缺的那个文件或报告，如 `translated.pdf not ready`、`all.zip not ready`、`refine report not ready`）。
  等任务往下跑、这一步做完，同一个请求就能成功。
- **摘要类**（质量摘要、用量、失败诊断、各种列表、取数目录、阅读区块和元信息）：照旧 `200`，没有的部分给 `null`、空列表、`0`
  或 `available: false`，不报 404。
- 名字本身写错（没有这个文件名、这个数据集、这个条目、这一页）是普通 `404`，不带 `reason`：那不是"还没好"，是"没有"。

```json
{
  "code": 40400,
  "message": "all.zip not ready",
  "error": {
    "code": "NOT_FOUND",
    "http_status": 404,
    "details": { "reason": "not_ready" }
  }
}
```

客户端分「任务没了」和「还没好」只看 `reason`，不要解析 `message`。

| 接口 | 还没产出时 |
|---|---|
| `GET /jobs/{job_id}/files/output/{name}`、`files/pages/{page}.jpg`、`files/internal/{name}` | `404` + `not_ready`，`<名字>` 见 [下载总览](../07-产物下载/01-下载总览.md#通用约定)。`all.zip` 以前是 `409`，现在也是这个 |
| `GET /jobs/{job_id}/reader/markdown` | `404` + `not_ready`（`markdown not ready`） |
| `GET /jobs/{job_id}/reports/translation`、`translation-qa`、`layout-fit`、`refine` | `404` + `not_ready`（`translation report not ready` 等） |
| `GET /jobs/{job_id}/translations/{item_id}`、`…/revisions`，`PATCH …/translations/{item_id}`，`POST …/replay` | 还没有翻译清单：`404` + `not_ready`（`translation manifest not ready`）；清单在、条目不在是普通 `404` |
| `GET /jobs/{job_id}/translations` | `200`，空列表（以前是 `404`） |
| `GET /jobs/{job_id}/reports/quality`、`reports/quality/items` | `200`，各段 `null` / 空清单（任务还没有输出目录时以前是 `404`） |
| `GET /jobs/{job_id}/data`、`data/{dataset}` | `200`，`available: false`（任务还没有输出目录时以前是 `404`） |
| `GET /jobs/{job_id}/reports/usage`、`reports/failure`、`files`、`reader/regions`、`reader/metadata` | `200`，空值（没变） |

暂时不在这条规矩里的：

- 边翻边看 `GET /jobs/{job_id}/progress/layout` 还没就绪是 `409` + `error.code = "LIVE_TRANSLATION_LAYOUT_NOT_READY"`，
  `progress/pages/{page}` 还没提交是 `404` + `LIVE_TRANSLATION_PAGE_NOT_COMMITTED`。前端按这两个 `error.code` 决定要不要重试，保持不动。
- 书的原文 PDF 不在磁盘上（`/documents/{document_id}/files/…`、`/documents/{document_id}/reading`）是普通 `404`：原文随上传就有，不在就是丢了，不会"过一会儿产出"。
- AI 画板里点名的文件不在（`GET /jobs/{job_id}/ai/board/{name}`）是普通 `404`：名字是调用方给的。
