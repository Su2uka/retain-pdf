# 多设备同步

几台电脑通过一个「同步文件夹」交换书库，不需要任何一端跑服务。同步文件夹可以是：

- **网盘文件夹**：iCloud、坚果云、Dropbox 等网盘客户端同步的本机目录；
- **WebDAV**：群晖 / 威联通 NAS、Nextcloud、坚果云等。

格式与合并规则见 `backend/packages/retainpdf-data/src/sync.rs` 与 `sync/store.rs`。

设置存在后端的数据库里（跟着数据目录走），桌面版、网页版、Docker 都一样。开启后后端每隔
`RUST_API_SYNC_INTERVAL_SECS`（默认 60）秒同步一轮；改设置或调用「立即同步」时马上跑。

## 同步什么

- 同步：上传的原文、书（标题、阅读状态、标题建议等）、合集与合集成员、收藏与收藏截图、
  结束了的任务（成功、失败、取消；含 OCR 结果、译文与手改记录、成品 PDF、事件与进度）、
  术语表、AI 对话（含全部消息与分支）、AI 算完的计算与生成的图、AI 改文档的操作与产出的
  文档版本（出了结果的都同步，等人确认采用的也同步，可以在另一台设备上采用）。
- 不同步：还在排队或运行的任务、还没算完的 AI 计算、还没出结果的 AI 改文档（结束后再同步）；
  渲染中间文件与 Word 下载（各设备需要时重新生成）；AI 对话在本机接着哪个会话往下聊（另一台
  设备从对话记录重建）；凭据与 API Key、界面偏好。
- 新版本才有的内容种类，旧版本收到后先放进等待区（`pending` 里显示需要更新版本），升级后
  自动补上，不会丢。
- 收到的内容里记着的文件路径（上传的原文、任务产物清单、产物登记、AI 计算的产物、文档版本）必须落在本机数据目录里；
  有绝对路径、带 `..` 的，整条不收，算进 `rejected`，日志里记一条警告（2026-10-24 起）。正常的同步数据
  发出前都换成了相对数据目录的写法，不受影响；这一条防的是共享的 WebDAV 账号被别人写进一条指到本机任意文件的记录。

## `GET /api/v1/sync`

返回同步状态：

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "enabled": true,
    "transport": "folder",
    "webdav_url": null,
    "webdav_username": null,
    "webdav_has_password": false,
    "folder": "/Users/me/Library/Mobile Documents/com~apple~CloudDocs",
    "sync_root": "/Users/me/Library/Mobile Documents/com~apple~CloudDocs/RetainPDF-Sync",
    "device_id": "6ce4ea829f53da8e",
    "device_name": "书房的 Mac",
    "running": false,
    "interval_seconds": 60,
    "last_run": {
      "started_at": "2026-10-09T08:00:00Z",
      "finished_at": "2026-10-09T08:00:03Z",
      "ok": true,
      "error": null,
      "exported": 2,
      "applied": 5,
      "deleted": 0,
      "files_uploaded": 1,
      "files_downloaded": 9,
      "rejected": 0,
      "folder_changed": false,
      "device_renewed": false
    },
    "pending_total": 0,
    "pending": [],
    "peers": [{ "device_id": "fedcba9876543210", "name": "办公室的 Mac", "segments_read": 12 }]
  }
}
```

- `transport`：`folder`（网盘文件夹）或 `webdav`。
- `folder`：用户选的文件夹；`sync_root`：实际读写的位置。网盘文件夹时，所选文件夹里已经有
  同步数据（`format.json`）就直接用，否则在里面建 `RetainPDF-Sync`；WebDAV 时就是 `webdav_url`。
- `webdav_has_password`：WebDAV 密码只写不读，这里只告诉有没有保存过。
- `peers`：每轮同步结束时记下的其它设备（查状态不会去访问同步文件夹）。
- `pending`：还在等文件从网盘下载、或等相关的书和任务同步过来的改动（最多列 20 条），到了自动补上。
- `last_run.folder_changed`：换了同步文件夹，本机书库已全部重新放进去。
- `last_run.device_renewed`：数据目录是从别的电脑复制来的，这台电脑已换成新设备号加入。
- `last_maintenance`：最近一次整理同步文件夹（见下面「整理」），没整理过为 `null`：
  `{"at", "segments_compacted", "packs_retired", "packs_deleted", "bytes_freed", "bytes_repacked", "error"}`。
  `bytes_freed` 是删掉的包腾出的空间，`bytes_repacked` 是为了留住还在用的内容重新上传的大小。

## `PUT /api/v1/sync`

改设置，没给的字段不变，返回新的状态：

```json
{ "enabled": true, "transport": "folder", "folder": "/absolute/path", "device_name": "书房的 Mac" }
```

```json
{
  "transport": "webdav",
  "webdav_url": "http://100.122.161.7:5005/webdav/retainpdf",
  "webdav_username": "sync-user",
  "webdav_password": "……"
}
```

`webdav_url` 是同步文件夹本身（不存在会自动建，上级目录要存在）。`webdav_password` 给了就保存
（空串清除），不给保持原样；密码只存在本机数据库里，不进同步数据、不进数据库备份（2026-10-22 起，见
[数据库备份](../10-备份/01-数据库备份.md)），任何接口都不会返回它。

全部校验通过才写，写在一个事务里：校验失败（`400`）时什么都没改（2026-10-22 起；以前先写了同步方式、地址等，最后才查
「开启时目标齐不齐」，失败时已经改了一半）。「开启时必须已配好同步位置」按「请求里给的值叠在已保存的值上」算。
请求体里不认识的字段（比如拼错的 `webdav_pasword`）`400`，`message` 带字段名（2026-10-22 起；以前静默忽略、回 `200`）。
恢复备份期间改设置，要等恢复结束才生效。

`400` 的情况：请求体里有不认识的字段；开启时还没配好同步位置；`transport` 不是 `folder` / `webdav`；文件夹路径不是
绝对路径、不存在、不是文件夹、写不进去，或在 RetainPDF 数据目录里面、包含数据目录；WebDAV
地址不是 http(s)、缺主机名、把账号密码写进了地址；设备名超过 64 个字。传空串表示清除该项。

## `POST /api/v1/sync/test`

用请求里给的设置（没给的用已保存的，比如密码留空就用已保存的）试一次读、写、删，不保存设置、
不碰同步数据。连不上不算接口错误，结果在 `ok` / `error` 里：

```json
{ "code": 0, "message": "ok", "data": { "ok": true, "location": "http://100.122.161.7:5005/webdav/retainpdf", "latency_ms": 2658, "error": null } }
```

- 请求体和 `PUT` 一样，不认识的字段 `400`。
- WebDAV 用单独的客户端（2026-10-22 起）：每个请求（含连接）最多等 10 秒，没拿到回复不重试；一次测试通常 3 个请求
  （写、读、删；同步文件夹还没建时先建，多 2 个）。整体超过 60 秒也回 `ok: false`（`error` 是「测试连接超时」）。
  以前用的是正式同步的客户端（单个请求最长 30 分钟、失败重试 3 次、一次 5 个请求），地址写错要一分钟、连得上不回能挂两小时。
  正式同步的客户端不变。

## `POST /api/v1/sync/run`

立即同步一轮，等它跑完后返回状态（已经有一轮在跑就等它跑完再跑）。不跑的时候 `409`，带
`error.details.reason`（2026-10-22 起）：`sync_disabled`（同步没开启）、`sync_not_configured`（开着，但同步位置被清空了，
`message` 是「同步已开启，但还没有填写同步位置」；以前也说「同步没有开启」）。

请求中途断开时这一轮照样跑完，结果记在 `last_run`；跑完之前别的「立即同步」、后台定时那一轮、恢复备份都要等它
（2026-10-22 起；以前请求一断锁就放了，「同一时间只跑一轮」不成立）。

## 整理

同步文件夹里每台设备只追加自己的改动记录和文件包，不整理的话会越来越大，新加入的设备也要从头
读完全部历史。每台设备每轮同步成功后看一次（每天最多整理一次），只整理自己的目录：

- **改动记录**：自己的段攒到 64 段以上时，每样东西只留最后一条，抄进几段新的，删掉旧段。
  读得落后的设备、新加入的设备直接从新段读起（最晚十分钟内知道）。
- **文件包**：里面的内容都没人用了（删掉的书、重新渲染换掉的旧 PDF 等）就登记停用，**7 天后**
  删掉；大半没用的包，把还在用的内容重新打一个小包再停用旧的。停用期间别的设备不再往停用的包里
  引用，需要那份内容时自己重新上传一份。
- 第一次整理前把 `format.json` 升到格式 3；还没更新的旧版本程序会提示先更新，而不会读错。
- 群晖等 NAS 开着回收站时，删掉的包会先进 `#recycle`，空间要等回收站清空（可在共享文件夹设置里
  让回收站定期自动清空）。

## 速度

WebDAV 上每个请求都有一次往返。文件按段打包（每包约 32MB），首次同步一本书只要十几个请求，
没有变化的一轮只要三四个请求；耗时主要是传输。经 Tailscale 访问 NAS 时如果没有直连、走的是
中转（`tailscale status` 里显示 `relay`），带宽会小很多，能直连时快得多。
